## 我的笔记

在 Codex 的 Harness 里，沙箱是一条贯穿“配置 → 模型提示 → 工具调度 → 进程执行 → 失败处理”的链路。 bubblewrap、MXC 是这条链路最后调用的系统执行后端。

| 模式 | 普通命令的执行边界 | 需要额外权限时 |
|---|---|---|
| **Ask for approval** | 工作区沙箱 | 请求人工审批 |
| **Approve for me**（截图当前选中） | 同样的工作区沙箱 | 符合条件的请求交给自动审核 |
| **Full access** | 取消 Codex 本地执行沙箱限制 | 通常无需这类审批 |


针对 Codex 本地命令执行，可以这样理解：
- Ask for approval：启用沙箱，额外权限由你审批。 （工作区越界）
- Approve for me：启用同样的沙箱，额外权限交给自动审核。（危险行为审批，比如上传env文件）
- Full access：不启用 Codex 这层本地执行沙箱限制。



## harness中和沙箱有关的部分

| 阶段 | 真实 Hook／函数 | 与沙箱的关系 |
|---|---|---|
| **Session 初始化** | `Session::new()`、`SessionConfiguration` | 保存权限状态、环境选择、Windows 沙箱类型等。**这是内置初始化，不是 Hook。** |
| **Session Hook** | **`SessionStart`**；由 `run_pending_session_start_hooks()` 调度 | 运行已配置的启动 Hook。**本次核验的沙箱创建链不靠这个 Hook 实现。** |
| **Prompt 组装** | `PermissionsInstructions::from_permission_profile()` | 把权限说明提供给模型。**不是 Hook，也不创建隔离。** |
| **Tool 执行前 Hook** | **`PreToolUse`**；由 `run_pre_tool_use_hooks()` 调度 | 可阻止调用、更新输入、补充上下文。**它与内置沙箱执行逻辑是两个环节。** |
| **Tool 内部** | `ToolOrchestrator::run()` → `SandboxManager::transform()` → 进程启动 | 检查审批、选择后端、包装命令，并启动受限进程。**沙箱执行主要在这里落实，不是某个 Hook。** |
| **Tool 完成后 Hook** | **`PostToolUse`** | 处理工具结果；不能撤销已经发生的执行。 |


并没有在一开始的时候启动沙箱

而是bash工具内部，会转到类似于 sandbox bash

```bash
原本：bash -c "python demo.py"

包装：沙箱启动器 <权限规则> -- bash -c "python demo.py"
```

## 实例例子

项目目录：/repo
外部文件：/home/alice/outside.txt

普通bash
```bash
bash -c 'echo hello > /home/alice/outside.txt'
```

沙箱执行, 用 bwrap
```bash
bwrap \
  --unshare-user \
  --ro-bind / / \     
  --bind /repo /repo \
  -- bash -c 'echo hello > /home/alice/outside.txt'
```

几个参数含义
--unshare-user       创建用户命名空间，声明一下
--ro-bind / /        给沙箱挂载只读的文件系统视图
--bind /repo /repo   单独把项目目录开放为可写 

其实就是 
bwrap + 沙箱规则参数 + -- + 普通 Bash 及其参数

# Codex沙箱的生命周期

**用完销毁**

首先，每个bash都有个沙箱，一旦，沙箱执行结束了，这个沙箱就销毁

exec_command("命令 A")
  → 新沙箱 A → 新进程 A

exec_command("命令 B")
  → 新沙箱 B → 新进程 B

write_stdin(A 的 ID)
  → 继续操作进程 A，沿用它原来的隔离环境

但是 codex 可以复用
比如 exec_command("命令 A")，进程A还没结束
就 write_stdin(A 的 ID) 可以往里面塞新的命令

但是若write_stdin(A 的 ID)，A进程已经不存在了怎么办 ？

不会自动重建 A，也不会偷偷新开一个沙箱。 分两种情况：
- A 已退出，但记录还在：读取剩余输出，返回退出状态，清理记录。
- A 的记录也已经清理了：返回 UnknownProcessId，表示这个 ID 已经找不到了。
如果还想执行命令，就需要重新调用 exec_command，启动新的进程和沙箱。原进程里的内存状态不会恢复，已写入项目目录的文件仍然保留。

但是！这不是复用的逻辑！

这只是 A 在同步等待二次输入而已！

所以没有沙箱服用的逻辑！

## Codex 底层不同沙箱机制

### Windows 沙箱

Codex 原生 Windows 沙箱主要有两条路线：

- **MXC（Microsoft Execution Containers）**：通过原生进程容器执行文件、网络等隔离策略。
- **受限身份＋ACL**：进程携带受限 Token，Windows 结合 Token 中的 SID 和文件 ACL，判断是否允许读取、写入、删除等操作。

传统后端分为 `elevated` 和 `unelevated`：前者使用专用低权限账户，首次初始化需要管理员批准；后者从当前用户派生受限 Token，网络隔离较弱，不支持禁止读取路径。

### Linux 沙箱

Codex 使用 **Bubblewrap（命令名 `bwrap`）＋seccomp**：

- **namespace＋挂载**：组织进程、网络和文件系统视图，将目录设置为只读、可写或不可访问。
- **seccomp**：过滤系统调用。
- **no_new_privs**：阻止  ·通过执行 setuid 等程序获得额外权限，由 `bwrap` 自动设置。
- **cgroup**：可另行限制 CPU、内存等资源，不是每次使用 Bubblewrap 都自动配置。

这些机制约束执行进程，不需要复制项目或启动独立内核。WSL2 中使用 Linux 这套实现。

### worktree：工作副本隔离

Git worktree 为同一仓库提供多个工作目录，各自维护工作文件、索引和 HEAD，共享提交对象等数据。

Codex 在支持的环境中可向模型提供 **`create_worktree` 等工具**，由后端管理器调用 Git 创建；客户端或启动参数也能触发创建。

它用于分开不同任务的代码改动，**不提供文件访问、网络或进程权限边界**。不是每个 session 或普通 subagent 都自动创建 worktree。

### 权限审批与保存

权限检查主要位于 `exec_command` 的后端执行链中：

- **请求校验**：扩权参数是否合法、配置是否允许申请审批。
- **命令策略**：根据命令规则决定禁止、审批或执行。
- **实际访问检查**：命令启动后，由操作系统沙箱强制执行权限。

用户批准后，保存方式取决于范围：

| 批准范围 | 保存内容 |
|---|---|
| 仅本次 | 本次决定，不生成复用规则 |
| 本会话的命令批准 | 会话审批缓存 |
| 以后允许某命令前缀 | 持久化到 `.rules` |
| 本轮／本会话的路径权限 | 对应范围的资源授权 |

显式命令 `allow` 规则可能允许绕过沙箱；路径授权则可以保留沙箱，只扩大指定资源权限。

### exec_command 主流程

调用 exec_command
    |
校验扩权请求 ── 不合法 → 拒绝执行
    |
检查命令规则 ── 禁止 → 拒绝执行
    |
需要时等待审批 ── 拒绝 → 终止执行
    |
确定本次执行权限
    |
准备沙箱并执行命令
    |
返回结果给模型
