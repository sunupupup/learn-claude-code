## 何时触发

利用的是 after turn end (用户的一次query处理完毕)

一轮结束，直接发起预测

## 如何高效、省钱

保留主 Agent 的输入前缀，尽量复用它刚刚建立的 Prompt Cache（提示词缓存）。

1. 继承原配置、工具和历史，尽量保持前缀一致。预测模式的源码注释明确写着：maximize prompt-cache reuse。协议源码
https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L547-L554

2. 测试检查请求一致性：相同后续输入下，父会话与预测分支的 input、instructions、tools、model 等一致，prompt_cache_key 也一致。测试源码
https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/app-server/tests/suite/v2/thread_fork.rs#L2801-L2829

最大化利用缓存

但是缓存命中仍有成本。但目前 Codex 的“生成预测建议”不计入你的使用额度，也不消耗 credits。 这是官方明确说明的

https://learn.chatgpt.com/docs/features/composer-predictions


成本控制
会有个 0.5 的随机，一半的几率不预测
```js
// Math.random() 随机产生一个 0～1 之间的数
if (Math.random() >= 0.5) {
  return null; // 跳过，不调用模型
}

// 抽中了，才调用模型预测
```

## 如何判断有用

要考虑某些话，是否还值得展示给用户
避免用户看到没价值的内容

| 情况 | 合理的处理 |
|---|---|
| 对话已经结束，比如用户说“谢谢” | 可以不给建议，避免硬找话题 |
| 预测过程中，用户已经发送了新问题 | 旧预测作废，因为上下文变了 |
| 建议出现后，用户直接输入自己的内容 | 不干扰用户输入 |
| 用户没有接受建议 | 让它自然被忽略，不自动执行 |

Codex 已确认允许返回 {"suggestion": null}，也就是“这次不给建议”。但模型具体依据什么决定返回 null，还要看尚未取得的远端提示词。
