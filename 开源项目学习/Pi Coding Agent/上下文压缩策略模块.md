## 术语速查

- **Token 预算**：按模型处理文本的单位衡量可保留内容，不等于消息条数。
- **Cut point（切分点）**：区分生成摘要的较早历史与保留原文的近期历史的位置。
- **Compaction（上下文压缩）**：减少模型输入中的历史体积；策略与存储格式是不同问题。

## 第一小步：默认策略与切分依据

🟢 **源码已核验**（固定快照，2026-10-12）；没有运行 Pi 或调用模型。

默认策略是：**较早历史生成摘要，近期历史保留原文**。这是 Harness（模型外围执行程序）选择模型输入的逻辑。100 条消息不是切分依据，也不是触发阈值。

- `keepRecentTokens` 默认 `20000`，衡量近期原文的保留范围，可由配置覆盖。
- `findProjectedCutPoint` 从最新条目向前累加各消息的 `estimateTokens`；达到或超过预算时，选择当前位置或其后的第一个合法候选切分点。因此 20000 是选取目标，不是必定精确保留的 Token 数。
- `prepareCompaction` 记录 `firstKeptEntryId`（第一条保留记录的 ID），并收集更早内容用于摘要。真实输入先经会话投影（把保存的条目整理为当前有效消息），不是直接截取 JSONL 的前若干行。
- 若切在一轮对话中间，该轮前半段会作为 `turnPrefixMessages` 单独参与摘要，再合并；合法切分点与此边界后续展开。

教学例子（假设首次压缩，没有上下文编辑，每条消息估算为 1000 Token，且第 81 条是合法切分点）：

```text
倒着累计：100 → 99 → … → 81，累计达到 20000 Token
1–80：参与摘要
81–100：保留原文
压缩后的历史形态：摘要 + 第 81–100 条原文
```

若每条只有 500 Token，倒数 40 条才达到预算，相同前提下可能变为 1–60 参与摘要、61–100 保留原文。数字仅为简化示例，不是真实运行记录；消息类型、长度和合法边界都会影响结果。

直接源码摘录（未改写）：

```typescript
accumulatedTokens += messageTokens;
if (accumulatedTokens >= keepRecentTokens) {
    exceededBudget = true;
    cutIndex = cutPoints.find((candidate) => candidate >= i) ?? cutPoints[cutPoints.length - 1];
    break;
}
```

来源：[预算与候选切分选择：824–850](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/compaction/compaction.ts#L824-L850)、[摘要输入划分：920–934](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/compaction/compaction.ts#L920-L934)。本轮只确认默认划分；触发条件、估算算法、合法候选和摘要生成后续逐个学习。

## 第二小步：压缩与相关机制的发生时机

2026-10-12：用户将范围扩展为本包各处上下文压缩，先只讨论时机。以下是固定 Commit 的静态源码核验，没有运行验证，不把同仓库其他 Harness 的机制套入 Coding Agent。

### 会话摘要压缩的检查时机

| 时机 | 触发条件与用途 | 直接源码 |
| --- | --- | --- |
| 手动调用 | `/compact` 或 `AgentSession.compact()`；用户主动要求，不依赖自动阈值 | `agent-session.ts:2406` |
| 新用户 prompt 提交前 | 存在上一条 assistant 消息时调用 `_checkCompaction(lastAssistant, false)`，覆盖之前被取消回复等情况；新 prompt 此时尚未加入 | `agent-session.ts:1693–1697` |
| 下一次 assistant 回复前 | `prepareNextTurnWithContext` 调用 `_compactBeforeNextAssistantResponse`；包含同一任务中工具结果写入后、模型继续回复前 | `agent-session.ts:590–608, 690–700` |
| 一次 Agent 运行结束后 | `_handlePostAgentRun` 调用 `_checkCompaction`，根据阈值或溢出情况处理最后一次回复 | `agent-session.ts:1495–1525, 2599–2733` |

检查不等于必定执行。阈值是 `contextTokens > contextWindow - reserveTokens`，默认预留 `16384` Token，自动压缩受 `enabled` 开关控制。下一次回复前的检查不要求工具调用存在；工具批次若结束整个运行且没有排队消息要求继续，不走这个批次之后的下一次回复检查。

运行后检查的三个自动条件：① 超过阈值，摘要压缩但不重试已经完成的回复；② 上下文溢出错误或可恢复的输出长度截断，省略失败尝试、压缩并最多进行一次恢复重试；③ 回复成功结束，但用量超过配置的窗口，压缩并保留完成的回复，不重试。`length` 不是一律触发，需符合 `isRecoverableLength` 判断。

### 相关但不同的减量时机

- 切换会话树节点时：`navigateTree(..., { summarize: true })` 对离开分支的内容做分支摘要；不以窗口快满为条件，普通导航不必生成摘要。源码 `agent-session.ts:3581–3616, 3670–3690`。
- 工具产生结果时：内置工具限制返回大小。例如 `read` 保留头部、`bash` 保留尾部，通用默认上限是 2000 行或 50 KiB；这是截断，不调用模型生成历史摘要。源码 `tools/read.ts:156`、`tools/bash.ts:325`、`tools/truncate.ts:11–12`。
- 扩展介入时：可在工具结果、请求前的 `context`、边界事件等位置自定义缩减。存在扩展入口不代表默认执行了某种压缩策略；具体策略须继续读扩展实现。源码 `agent-session.ts:554–569`、`extensions/runner.ts:1186–1242`。

下一步可先追“每次模型回复前”的检查，因为它能说明同一用户任务内如何处理工具导致的上下文增长；方式与完整恢复链路尚未在本轮展开。

## 手动 /compact：触发入口与执行前检查

### getCompactionSettings 返回什么配置

固定版本静态核验：`settings-manager.ts:896–905` 返回三个最终字段：`enabled`（默认 true，自动压缩开关，不禁止手动压缩）、`reserveTokens`（默认 16384，自动阈值的窗口预留量，也参与摘要输出预算计算）、`keepRecentTokens`（默认 20000，近期原文保留目标，非固定条数或精确长度）。

`modelOverrides` 是配置文件中的按模型覆盖表，不是返回结果中的第四个字段。两个 Token 字段逐字段按“当前 provider/modelId 的覆盖值 → 普通 compaction 配置值 → 内置默认值”解析；模型参数用于选择覆盖项，不是此函数指定摘要模型。两个预算须为非负安全整数，否则抛错。手动压缩使用这些预算来准备范围和生成摘要，但不走自动阈值判断。

配置示意（教学例子，不是本机实测配置）：`{ "compaction": { "enabled": true, "reserveTokens": 16384, "keepRecentTokens": 20000 } }`。配置位置为 `~/.pi/agent/settings.json` 或项目 `.pi/settings.json`；全局与项目合并细节后续按需学习。

### prepareCompaction 之后的交接

固定版本源码已核验：prepareCompaction 返回的是准备对象，不是生成好的摘要。包含 messagesToSummarize、firstKeptEntryId，以及轮次前缀、旧摘要、文件操作等辅助信息。手动入口先检查结果是否存在，然后执行 session_before_compact 扩展钩子；扩展可取消或提供 compaction 结果。若无扩展结果，则调用 _runDefaultCompaction 进入默认摘要生成。生成完成后检查取消信号，再 appendCompaction 保存并刷新上下文；保存与生成细节后续单独追。源码 agent-session.ts:2429–2502、compaction.ts:948–957。

### 底层 compact 怎样生成压缩结果

固定快照静态源码已核验：`compaction/compaction.ts:987–1092` 的底层 compact 接收 preparation、模型和认证等参数，生成并返回 CompactionResult，本身不写 JSONL。当前优先学习非 split-turn 分支。

- 普通切分调用 generateSummaryWithUsage（1056–1075），把 messagesToSummarize 交给摘要模型；若 previousSummary 存在，则使用更新摘要的提示，融合旧摘要与此次历史。
- generateSummaryWithUsage（734–787）先 convertToLlm，再 serializeConversation 转成文本；用 conversation 标签包装，旧摘要另用 previous-summary 标签包装，追加摘要提示及 customInstructions。形成独立的摘要请求，历史成为一条 user 消息中的材料，使用摘要专用 system prompt，而非让模型继续原任务。
- 普通摘要 maxTokens 为 min(floor(0.8 * reserveTokens), 模型最大输出预算)，默认预留 16384 时算出 13107；这是输出上限而非保证摘要长度。若模型 maxTokens 非正，代码不以其限额约束。
- 若切在同一轮中间，compact 为较早历史和该轮前半段分别生成摘要，再拼接；前者为空时可只生成轮次前缀摘要。此分支后续再逐步学习。
- 摘要后 computeFileLists 得到已读/已改文件列表并追加到正文；结果返回 summary、firstKeptEntryId、tokensBefore、usage、details（readFiles、modifiedFiles）。边界 ID 沿用 preparation，不由摘要模型决定。
- 摘要响应经 getSummarizationFailure 检查；出现 toolCall 直接抛错；firstKeptEntryId 缺失也抛错。重试策略与取消清理后续单独追。外层 AgentSession 在结果返回后才负责 appendCompaction 和上下文刷新。

### 手动摘要完成后的持久化与事件

固定版本静态核验：agent-session.ts:2495–2559。生成结果后先检查取消，再 appendCompaction 追加会话记录，刷新 Agent 内存消息并估算压缩后 Token 数。随后发出 session_compact 扩展事件、清理手动压缩状态、发出 compaction_end 运行时事件并返回结果。

持久化记录字段（session-manager.ts:1260–1285）：type、id、parentId、timestamp、summary、firstKeptEntryId、tokensBefore，以及可选 details（默认已读/修改文件）、usage（摘要调用用量）、fromHook（扩展生成标记）、systemMessage（当时完整提示及工具状态）。原始历史不因本次追加而删除。启用持久化时由 _persist 追加 JSON 行到当前会话文件；不持久化模式只留内存。

estimatedTokensAfter 在外层返回结果及 compaction_end 的 result 中，不属于上述 CompactionEntry 默认保存字段；manual 原因也在事件里，未作为独立字段保存到该记录。压缩事件本身不等于持久化 trace，读取的默认路径未找到独立 trace/span 文件写入或遥测上报；扩展可监听事件自行实现。

失败或取消：compaction_end 带 result: undefined、aborted/errorMessage，另发 session_compact_failed 扩展事件，清理状态并重新抛错。不能笼统声称所有失败都没有记录：若保存前失败，尚未调用追加；若追加或后续步骤失败，_appendEntry 先改内存再落盘，代码未显示事务回滚，需要按失败位置判断。

### 摘要压缩的错误处理补充

固定快照静态核验，未运行故障测试。用户已观察 retryAssistantCall 与禁止摘要响应 toolCall。

- retryAssistantCall（ai/src/utils/retry.ts:176–241）仅对分类为可重试的 error 响应按预算退避重试；aborted 不重试；length 与含 toolCall 的非 error 响应不由此自动重试。produce 抛出的异常也不是在此函数统一 catch 并重试。
- getSummarizationFailure（compaction.ts:607–614）把最终 error 响应和 length（摘要不完整）判为失败；调用处抛错，不保存为成功摘要。
- 禁止摘要响应包含 toolCall（777–787）；轮次前缀摘要也执行相同检查（1129–1135）。没有执行这些工具调用。
- 取消 signal 传到请求和重试等待；外层在 appendCompaction 前再次检查 signal.aborted（agent-session.ts:2495–2497），避免将本次取消的生成结果作为正常压缩保存。扩展 cancel 也作为取消收尾。
- compact 返回前校验 firstKeptEntryId 存在（1082–1084）；执行前还有模型、预算、认证和可压缩范围检查。
- 外层 catch/finally 清理压缩控制器与空闲等待状态，发 compaction_end 与 session_compact_failed，重新抛错；界面按事件显示失败或取消。失败发生在写入之后时不等于撤销成功，_appendEntry 先更新内存再落盘，未见事务回滚。
- 已读默认生成路径未见摘要章节格式或语义完整性校验；运行成功不证明关键上下文没有丢失。

## 第三个时机：同一次运行中准备后续模型回复

### 默认四工具的额外机制地图

每次的结果都会进入到 message 
messages：
  工具结果：第 1～2000 行
  工具结果：第 2001～4000 行
  工具结果：第 4001～6000 行

这样看起来，这个对于主agent是一个很大的影响，影响大量context、经常触发compact

#### 1-2：read 工具读取图片的压缩

图片读取时候的压缩机制

在调用read工具的时候，如果发现是图片，会先进行压缩

| 项目 | 默认值 |
|---|---:|
| 最大宽度 | 2,000 像素 |
| 最大高度 | 2,000 像素 |
| 最大编码大小 | 约 4.5 MiB，按 **Base64 数据大小**计算 |

会按比例缩小，最大边小于2000

最红read出来的数据是base64格式的

```js
// Read image as binary.
const buffer = await ops.readFile(absolutePath);
const processed = await processImage(buffer, mimeType, {
	autoResizeImages,
	resizeOptions: ctx?.model?.inputLimits?.images?.resize ?? fallbackResizeOptions,
});
if (!processed.ok) {
	let textNote = `Read image file [${mimeType}]\n${processed.message}`;
	if (nonVisionImageNote) textNote += `\n${nonVisionImageNote}`;
	content = [{ type: "text", text: textNote }];
} else {
	let textNote = `Read image file [${processed.mimeType}]`;
	if (processed.hints.length > 0) textNote += `\n${processed.hints.join("\n")}`;
	if (nonVisionImageNote) textNote += `\n${nonVisionImageNote}`;
	content = [
		{ type: "text", text: textNote },  // 附在图片旁边的说明，让模型知道读取和处理的结果
		{ type: "image", data: processed.data, mimeType: processed.mimeType }
	];
}
```

读取图片二进制数据
  → 检查尺寸、预计的 Base64 大小
  → 都合适：原图片直接转 Base64
  → 超限：缩放或重新编码，直到符合限制，再返回 Base64

如果图片缩放失败，也就是 `!processed.ok`
这时候，就只有错误的 text content了，没有image的二进制数据

> 提问：这个 image 的二进制数据放在 content 里面，1M的图片二进制数据一般1.3M左右，岂不是上下文爆炸了 ？

> 回答：image content 部分的token是单独计算的，不会算成是普通文本的分词来计算，
视觉token的计算不像文本，文本的估算是 char/4 来计算的

视觉 Token = 向上取整(宽度 ÷ 28) × 向上取整(高度 ÷ 28)

一张1000*1000的图片，token数也就 1200多token而已，所以不用担心上下文爆炸的情况

**输入上下文占用 ≈ 文本 Token + 图片对应的视觉 Token**

### 机制3：分支摘要

触发时机： /tree 命令

返回历史节点或切换分支时，把刚才那条路线上的工作总结带过去。
他并不是因为上下文太长而触发的

加入原来的对话是 

> ① 用户：帮我优化查询
> ② 助手：可以加缓存，也可以优化 SQL
> ③ 用户：先试缓存
> ④ 助手：分析缓存方案……

后来你想试 SQL，就通过 /tree 返回 ② 助手回复的位置，再输入：

> ⑤ 用户：这次试 SQL 优化
> ⑥ 助手：分析 SQL 方案……

历史结构变成了：

① → ②
     ├─ ③ → ④：缓存路线
     └─ ⑤ → ⑥：SQL 路线

分支摘要的作用是：从缓存路线离开时，可把“已经发现缓存有什么问题”总结一下，带到 SQL 路线，避免重复研究。

### 机制4：全量摘要

全量摘要：把当前历史总结成摘要，不再保留压缩前的对话原文。

触发时机：依赖于插件的实现，pi本身不会直接全量压缩，
- 一般会在用户query处理结束之后，适合一次全量的总结
- 还有任务没结束，预算接近上限

和默认策略对比
```
默认压缩：
较早历史 → 摘要
近期历史 → 保留原文

全量摘要：
当前有效历史 → 摘要
此前对话原文 → 不再进入后续模型输入
```

他的压缩结果中 firstKeptEntryId=null ，在上下文重建的时候，不需要考虑之前的任何内容

> 问题：pi自己的上下文压缩和插件的这种全量压缩，怎么避免冲突啊？

可能的问题
1. 重复压缩：Pi 刚总结，插件又总结
2. 反复摘要丢信息：摘要再摘要，关键细节逐渐消失
3. 节省 Token 却增加总成本

**pi的解决办法**

1. **同一次压缩，可以由插件接管**

Pi 决定执行压缩
  → prepareCompaction() 准备材料
  → 检查有没有 session_before_compact 的扩展回调
  → 有就调用
  → 根据回调结果决定下一步

session_before_compact 的扩展回调，扩展返回的结果可能会有多个属性
如果返回了 compaction，那其实pi自己就不用压缩了

| 扩展返回什么 | Pi 怎么处理 |
|---|---|
| `cancel: true` | 取消本次压缩 |
| `compaction: {...}` | 使用扩展提供的结果，跳过默认摘要生成 |
| 没提供压缩结果，或根本没注册回调 | 调用 `_runDefaultCompaction()` |

**关键就是规定 hook 的返回结构，用字段表达插件这次的处理结果或意图，主流程据此决定下一步。**

2. **避免旧用量重复触发。**

触发

```js
		// Skip compaction checks if this assistant message is older than the latest
		// compaction boundary. This prevents a stale pre-compaction usage/error
		// from retriggering compaction on the first prompt after compaction.
		const compactionEntry = getLatestCompactionEntry(this.sessionManager.getBranch());
		const assistantIsFromBeforeCompaction =
			compactionEntry !== null && assistantMessage.timestamp <= new Date(compactionEntry.timestamp).getTime();
		if (assistantIsFromBeforeCompaction) {
			return false;
		}
```

假设压缩前

messages：
  ……大量历史
  用户：继续分析
  助手 A：分析结果……
          usage = 90,000

压缩后 

messages：
  摘要
  用户：继续分析
  助手 A：分析结果……
          usage = 90,000 ← A 的历史用量没有改写

所以压缩的时候，要额外检查下 jsonl 里面最新的那个 compact json的usage
