## 提示词保温

别让等待工具的时间，把已有缓存耗过期
先区分两种存储：
- 会话 JSONL：在你这边保存历史，供恢复使用。
- 提示缓存（prompt cache）：模型供应商保存已经处理过的请求前缀，用于降低后续重复处理的成本。
假设一个教学场景：某供应商的缓存有效期是 5 分钟，而工具需要运行 8 分钟。

第 0 分钟：模型读取大量上下文，产生工具调用
第 0～8 分钟：工具执行，暂时没有新的模型请求
第 8 分钟：工具完成，再次请求模型

此时原缓存可能已经过期，后续请求就可能需要重新支付较高的处理成本。
Pi 的保温方式是：缓存到期前，如果估算值得，就额外发送一次刷新请求。 源码复用之前的请求上下文，并把输出上限设为 maxTokens: 1；刷新产生的回答不进入对话上下文，只记录用量和费用。缓存保温源码

它不是无条件定时请求：
- 模型必须声明可用的缓存有效期。
- 默认 streaming：在 Agent 执行期间保温。
- 可选 idle：执行结束、等待用户期间也允许保温。
- 内置策略要求估算的预期节省至少达到 0.05 美元，才进行刷新。配置说明

所以它的本质是：花一笔较小的刷新费用，尝试避免下一次较大的缓存失效成本。 是否实际命中，仍取决于供应商。

## 会话中途更新指令和工具

把“规则什么时候变了”也记进历史

它还有缓存方面的意义：尽量保留前面的历史前缀，在后面追加变化，而不是每次都重写最前面的系统提示

对，你指出的就是关键：动态增减工具并不新鲜，也不是所有模型接口都支持“在历史中间追加工具定义”。Pi 有能力判断和转换兜底。

但是有些供应商不认这种数据，所以他还有个供应商适配层


| 层次 | 负责什么 |
|---|---|
| **Pi 内部会话记录** | 用 `toolsAdded` / `toolsRemoved` 保存工具变化 |
| **供应商适配层** | 判断接口支持什么，再转换成实际请求 |

针对于这种适配器中
Pi 的 Anthropic 和 OpenAI Responses 适配器，都实现了原生增量工具变更的路径
明确有俩函数 支持 tool_addition / tool_removal

确实明确只有Anthropic 和 OpenAI 的模型支持

```js
supportsMidConvoSystemMessages
supportsMidConvoToolChanges
```

其他不支持的

```
第一次请求：
tools = [read, bash]

中途增加 edit，删除 bash

第二次请求：
tools = [read, edit]
```
