## 术语速查

- 注册：让 Harness 知道工具及其实现；启用：选择当前可供模型调用的工具。
- Tool call（工具调用）：模型提出的工具名与参数；tool result（工具结果）：执行后返回的内容。
- Hook（钩子）：扩展介入某个处理阶段的回调入口；不等同于默认有审批机制。

## 第一步：工具在哪里注册，默认启用哪些？

2026-10-12；源码已核验，未运行验证。适用固定 Commit `d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31`、包版本 `0.87.1`。这里只研究启动时的工具集合，不展开调用审批。

场景：用户让 Pi 阅读一个文件并修改其中一行。模型需要知道可以使用 read 和 edit；Harness（模型外围执行与支撑程序）负责准备工具并把当前启用集合放进 Agent 状态，模型负责提出调用。

| 状态 | 含义 | 本轮例子 |
| --- | --- | --- |
| 已实现 | 源码存在工具定义和执行逻辑 | grep 有对应工厂函数 |
| 已注册 | 当前会话的工具注册表知道该工具 | 普通默认路径将内置工具包装后登记到 `_toolRegistry` |
| 已启用 | 工具进入当前 Agent 的 `state.tools` 集合 | 默认内置列表含 read，不含 grep |
| 某次调用获准 | 针对具体参数的调用通过执行前检查 | 不能仅凭 bash 已启用就断言某条命令已获准；后续追拦截路径 |

下面是原始源码摘录，仅增加中文解释注释（sdk.ts:258–265）：

```ts
// 未另行配置时使用的默认内置工具名称。
const defaultActiveToolNames: ToolName[] = ["read", "bash", "edit", "write"];
const configuredDefaultToolNames = settingsManager.getDefaultTools();
const allowedToolNames = options.tools ?? (options.noTools === "all" ? [] : undefined);
const excludedToolNames = options.excludeTools;
const excludedToolNameSet = excludedToolNames ? new Set(excludedToolNames) : undefined;
// 显式选择优先；否则考虑禁用、配置默认值，最后使用代码默认值，再排除指定工具。
const initialActiveToolNames = (
  options.tools ?? (options.noTools ? [] : (configuredDefaultToolNames ?? defaultActiveToolNames))
).filter((name) => !excludedToolNameSet?.has(name));
```

因此，无额外工具配置、禁用项或扩展时，默认启用 read（读文件）、bash（执行 shell 命令）、edit（修改文件）、write（写文件）。powershell、grep、find、ls 有内置实现，但不在这个默认启用列表中。`createCodingTools` 也返回默认四种工具，但当前会话构建实际走的是完整定义集合加名称选择，不能只看该辅助函数就当作完整注册链路。

### 本轮边界

- 默认四种指默认**内置**集合，不能据此断言所有会话总共只有四个工具：构造器以 `includeAllExtensionTools: true` 建运行环境（agent-session.ts:444–446），注册刷新会在没有显式 allowed 集合时加入扩展工具（3222–3225）。扩展的登记方式和重名规则留待后续。
- `allowedToolNames` 是工具名称过滤条件，不是某次文件访问或命令执行的审批结果。
- 固定源码能证明选择与登记逻辑；不能证明当前机器 shell 可用、命令成功或具体请求获得许可。
- 工具输出怎样控制长度与压缩关联，沿用[上下文压缩策略模块](上下文压缩策略模块.md)，这里不重复整理。
- 下一小步候选：选 read 一个工具，看它的描述和参数怎样定义；等待用户追问再推进。

## 管理模式概览：内置集合、动态调整与扩展注入

2026-10-12；固定版本源码已核验，未运行验证；用户理解待确认。

可以把当前模式理解为“统一注册表 + 当前启用集合 + 扩展注册入口”，均由 Harness 管理。

- 内置工具：有完整内置集合，默认启用 read、bash、edit、write；其他内置工具可以选择。详见上面的第一步。
- 动态调整启用集合：`setActiveToolsByName` 从已有注册表选出工具，更新 `agent.state.tools` 和 System Prompt；这不需要重新加载工具代码。
- 扩展注入：Extension（扩展，外部代码接入 Harness 的机制）调用 `pi.registerTool`，登记工具定义；会话刷新注册表时合入扩展工具。SDK 调用方也可通过 `customTools` 提供工具。
- 运行中新增：extensions/loader.ts:273–285 的 `registerTool` 登记后调用运行时 `refreshTools`，agent-session.ts:3085 将它绑定到 `_refreshToolRegistry`。因此不仅启动时能登记，也有运行中刷新路径；新工具能否进入集合仍受名称允许/排除条件影响。
- 重载扩展代码：`AgentSession.reload` 调用资源加载器 reload 后重建运行环境（agent-session.ts:3291–3304）。这与仅切换已注册工具的启用状态是不同操作。

证据入口：[扩展注册](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/extensions/loader.ts#L273-L285)、[刷新绑定](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/agent-session.ts#L3082-L3085)、[重载入口](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/agent-session.ts#L3291-L3304)。

“动态加载”需明确是哪一种：切换已有工具、扩展注册新工具、重新加载扩展代码，还是按模型需求搜索工具后加载。本轮核验支持前三种机制，没有核验最后一种自动搜索与按需加载能力；扩展接口也不能直接等同于原生 MCP 接入。

### Pi 的完整执行主线

内置定义 / 扩展 / SDK 自定义工具 → 注册表 → 当前启用集合 → 模型获得描述与参数结构 → 模型提出调用 → 按名称查找当前工具 → 参数准备与校验 → 调用前拦截 → 执行与进度回调 → 结果处理 → toolResult → 模型上下文与会话记录。

| --- | --- | --- |
| 注册、默认值与切换 | 复用前两节：八种内置定义，默认启用四种；动态登记和切换是不同操作 | core/tools/index.ts:182；core/sdk.ts:258；core/agent-session.ts:1282、3144 |

| 自定义与覆盖 | 扩展工具合入统一注册表；自定义同名工具可以覆盖内置。不同扩展同名时 runner 收集顺序中先遇到者保留；SDK customTools 后续合并可覆盖，不是所有重名都统一报错 | core/extensions/runner.ts:587–596；core/agent-session.ts:3152–3175、3206–3210 |

| 持久化审批与恢复 | 请求挂起等人工处理，状态写数据库，稍后恢复；[LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)配合持久 checkpointer；[持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)区分 RAM 与数据库存储 | 会话记录和内存 hook 已实现，本轮未找到通用工具任务状态机/持久审批恢复链路。对话保存不等于执行现场恢复 |
| 副作用幂等与未知结果核对 | 退款超时后按业务请求 ID 查询结果；幂等指同一业务请求重复提交不重复产生效果。[LangGraph 恢复注意事项](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent)说明恢复可能重跑节点，因此副作用应自行设计幂等 | 未找到通用业务幂等登记/核对层；toolCallId 用于调用关联，不能直接当作业务去重保证；外部框架持久化也不自动提供严格一次 |

其他工程设计观察项（不宣称某个产品已完整实现）：工具级并发上限、限流与成本预算；按只读/副作用类型制定重试策略；多用户凭证隔离；审计脱敏与耗时统计；工具契约版本与回归评测。这些都可在现有 hook/执行后端上构建，但必须另外核验。

### 术语与后续学习候选

- Schema（参数结构规则，工具契约层）：说明字段、类型与必填项；校验通过不等于参数有业务权限。
- Execution mode（执行模式，Runtime 层）：决定调用串行或并行；资源队列负责共享文件的互斥，二者不相同。
- Sandbox（沙箱，操作系统或虚拟化层）：限制运行程序可访问的资源；与请求是否获准不同。
- Checkpoint（检查点，工作流运行层）：持久化可恢复状态；与对话文本日志不同。
- 适合后续逐个追源码：工具定义如何同时服务模型和 UI → 参数校验与调用前 hook → 并行调度与文件队列 → 输出减量 → 权限/持久化对照。暂不自动启动新模块或实验。

## 注册与启用追问：谁决定名单，怎样动态改变？

2026-10-12；固定源码与同版本文档已核验，未运行。之前 read、grep 是教学示例，不是 Pi 自动选择结果。

- 启动选择：终端 `pi --tools read,grep` 显式选择；SDK `options.tools` 也可选择。SDK 优先显式 tools，否则考虑 noTools、settingsManager.getDefaultTools()，最后回落到 read/bash/edit/write；excludeTools 再排除。`--tools` 同时作为名称 allowlist，不只是初始菜单，未列工具不会进入当前注册表；以后 setActiveTools 不能取出未注册工具。
- 配置默认值：设置文件 `defaultTools: ["read", "grep"]` 指定初始内置集合；它不是所有扩展工具的允许名单，也不会因为修改文件立即更新运行中状态。设置读取发生在初始化/重载路径。
- 动态启用：扩展调用 `pi.setActiveTools(["read", "grep"])` 替换整个当前集合，不是追加；保留已有工具时组合 `pi.getActiveTools()` 返回的名称。名称必须已注册，未知名称被忽略。触发条件可由扩展事件、命令或工具执行逻辑决定，不是核心自动猜任务。
- 按需启用模式：同版本 docs/extensions.md:146–150 明确给出“先注册工具、保持可选项未启用、由 loader 工具调用 setActiveTools”的做法。模型可以调用扩展提供的加载工具间接触发切换；这是扩展实现的能力选择，不等于默认内置自动搜索工具库。
- 动态新增：`pi.registerTool` 注册新定义并刷新；官方 examples/extensions/dynamic-tools.ts 提供 session_start 注册 echo_session，以及扩展自定义命令 `/add-echo-tool <name>` 运行中注册工具的例子。该命令不是默认内置命令；需加载这个扩展。

## 我的笔记

我们先看 pi 有哪些工具管理相关的机制 

| 机制 | Pi 怎样做 | 值得注意什么 |
| --- | --- | --- |
| **内置工具与默认集合** | 提供八种内置工具，默认启用 `read、bash、edit、write` | 有实现、已注册、已启用是不同状态 |
| **动态切换工具** | 运行中修改启用名单，同时更新工具相关 System Prompt | 可以按任务提供不同工具集合 |
| **扩展注入与覆盖** | 扩展用 `registerTool` 加入工具；SDK 也能传入自定义工具 | 同名自定义工具可以覆盖内置工具；重名并非一律报错 |
| **统一工具定义** | 定义名称、描述、参数结构、执行函数，也能定义界面展示 | 同一个工具同时服务“模型调用”和“用户观看” |
| **执行后端替换** | 部分内置工具允许替换底层读写、命令执行函数 | 模型调用 `read`，底层可以被接到远程环境 |
| **参数准备与校验** | 先处理原始参数，再按 Schema 校验 | Schema 是字段、类型等结构规则；通过校验不等于业务合法 |
| **调用前拦截** | 扩展监听 `tool_call`，可以阻止执行 | 能用来实现业务限制或人工确认，但不是默认完整审批系统 |
| **调用后结果改写** | 扩展监听 `tool_result`，可以调整结果 | 可以控制最终交给模型的内容 |
| **并行与串行执行** | 默认允许并行；可全局指定串行，也可由工具声明串行要求 | 一批调用中有工具要求串行，该批就走串行路径 |
| **同文件修改队列** | `edit/write` 修改同一文件时排队，不同文件仍可并行 | 并行调度之外，还有资源级并发保护；只限本进程 |
| **错误、取消与超时** | 异常变成错误工具结果；传递取消信号；bash 支持可选超时 | 不能推断所有工具都有统一超时或安全重试 |
| **输出减量** | read/bash 等工具截断长输出；bash 截断时保存完整临时输出 | 自定义工具不会自动获得同等截断策略 |
| **执行事件与记录** | 有开始、进度、结束事件；最终消息进入会话记录 | 可以关联调用与结果，但事件接口不等于完整审计系统 |


我认为最值得学习的是这五个：
1. 工具契约与执行实现分开。 工具告诉模型“能做什么”，底层决定“在哪里、怎样做”。
2. 调用前、调用后都有扩展入口。 可以集中处理限制与结果加工。
3. 并行调度和文件队列分层。 提高速度，同时保护共享资源。
4. 模型输出被截断时拒绝执行调用。 Pi 检测到输出因长度限制结束，会让该批工具调用失败，避免执行不完整参数。
5. 工具结果同时用于上下文、展示和记录。 返回值不只是一个字符串，还包含调用关联、错误标记等信息。
