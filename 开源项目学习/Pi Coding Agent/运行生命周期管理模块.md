#### 结论

流式，影响的只是某一个content或者是tool的input,不会影响本身的完整，message对象 

流式被打断的正文，后续可以不带入messages

取消后留下的部分正文
  → 保存在 agent.state.messages 和 JSONL
  → stopReason = "aborted"
  → 下次构建模型请求时，跳过整条消息

但是有个问题

如果流式输出：一段正文 + A tool call + B tool call
在B流式的时候被打断，A已经执行了

这时候，按理来说需要保留A tool的call和result

但是在Pi 中不会出现这个问题

Pi 本身虽然请求 llm 还是流式的 

但是他执行tool call，会等待流式结束再执行，不会读完一个 tool call 就立即执行它。

整轮流式生成结束
  → 检查是否取消或出错
  → 正常结束后，进入工具执行

### 问题2：Pi正在执行一个工具，用户中断了，信号如何传递？最终留下啥结果？

在run bash的时候，因为是通过子进程执行bash命令
所以取消的时候，可以直接通过进程kill的方式来中断
并且在已有的输出内容后面加上 已收到的命令输出加上 Command aborted
并且额外多一个 isError: true 的标记

这边只能中断，不提供回滚的能力

这种中断的message后续还是会到日 llm call的 messages 

他算是一个合法的 toolResult 消息，只是标记为了 isError: true

就算前端那边中断了流式

Agent后端也不会立刻停止，还有很多事要做，比如状态的清理

```js
this._state.isStreaming = false;
this._state.streamingMessage = undefined;
this._state.pendingToolCalls = new Set<string>();
this.activeRun?.resolve();
this.activeRun = undefined;
```

如果此时用户又输入了内容，会先排队，不会启动新的运行
后台先完成取消和状态清理，确认空闲后，再把新消息作为新一轮处理。 在 Pi 会话层，对应的是 isStreaming 变成 false。

### 问题3：对话插入机制

新消息进入 steer 队列
  → 当前生成、工具执行继续
  → 当前助手这一轮结束
  → 取出排队消息，加入历史
  → 下一次 LLM 请求带上这条用户消息

所以 其实就是 在 loop 的中间，某一次 llm call tool、正文都结束之后，再插入一个 user message是吧

可以在hook中进行这个插入的流程，在 turn_end hook 中

本轮助手生成及工具执行完成
  → finishTurn 回调
  → turn_end 事件
  → getSteeringMessages() 读取队列
  → 下一轮将 user message 加入上下文
