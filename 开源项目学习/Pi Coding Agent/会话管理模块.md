## 第一小步：保存历史与恢复模型上下文

先建立这个心智模型：**Pi 保存会话记录，重启时读回记录，再构建当前要交给 Agent 的消息。** 这属于 Harness 的会话管理，不是模型自己记住了昨天的对话。

```text
对话产生条目
  → SessionManager 在内存登记，按持久化规则写入 .jsonl
  → Pi 退出
  → 重启并选择旧会话
  → 从文件加载条目、恢复索引
  → buildSessionContext() 构建当前消息
  → SDK 初始化 Agent 状态，后续进入模型调用
```

| 概念 | 保存/得到什么 | 解决什么问题 |
| --- | --- | --- |
| 会话持久化 | 磁盘中的历史条目 | 程序退出后还能找到历史。 |
| 会话恢复 | 已加载的会话与管理状态 | 选择并接着使用旧会话。 |
| 上下文重建 | 当前分支对应的消息等状态 | 决定下一轮使用哪段历史。 |
| 上下文压缩 | 摘要及保留消息等记录与策略 | 减少模型要处理的历史；后续单独学习。 |

简化示意（教学伪代码，不是 Pi 完整真实代码）：

```typescript
// 从磁盘条目恢复会话管理状态，并不直接调用模型。
const manager = openSavedSession(file);
// 保存的历史与当前模型消息不必一一对应，需要重建。
const context = manager.buildSessionContext();
// 把重建的历史接入 Agent；完整请求还有系统提示词、工具等。
const agent = createAgent({ messages: context.messages });
```

本轮只需理解“磁盘历史”和“当前上下文”有不同职责。为何文件里有分支、为什么压缩后不能简单把所有行塞进 `messages`，留到对应小问题再展开。

必要边界：会话恢复不等于恢复上次进程中所有东西，也不证明外部工具已执行的操作会自动回滚或安全重放；这部分尚未追踪。当前静态阅读不能证明断电不丢数据、并发写入安全或工具副作用恢复正确。

## 会话持久化：实际文件与数据结构

2026-10-12 补充，继续读取同一 Commit；以下是静态源码证据，未运行 Pi。用户已建立“一个 session 对应多条消息，可用 messages 表保存”的通用模型；本节核对 Pi 的具体实现，不将用户理解标为已掌握。

### 一个会话文件，包含头部与条目

默认持久化实现使用 JSONL 文件，没有在这里用数据库 messages 表。默认路径形如 `~/.pi/agent/sessions/--<编码后的工作目录>--/<时间戳>_<会话ID>.jsonl`。

第一行是 `SessionHeader`（会话元信息），后面是 `SessionEntry`（会话条目）。源码定义 `FileEntry = SessionHeader | SessionEntry`，说明文件的一行可以是这两类之一。后续条目不只包含消息，还有模型变更、压缩等记录。

下面是核心类型的原始字段摘录，只增加中文解释；省略其他条目类型，`AgentMessage` 的完整联合类型不在这里展开：

```typescript
export interface SessionHeader {
  type: "session";
  version?: number;       // 文件格式版本，当前快照为 3，不是包版本 0.87.1。
  id: string;             // 会话 ID。
  timestamp: string;
  cwd: string;            // 此会话所属的工作目录。
  parentSession?: string; // 可选的来源会话记录。
}

export interface SessionEntryBase {
  type: string;
  id: string;             // 当前条目的 ID，不是会话 ID。
  parentId: string | null;// 前驱/父条目 ID；没有父节点时为 null。
  timestamp: string;
}

export interface SessionMessageEntry extends SessionEntryBase {
  type: "message";        // 外层说明这是一条消息记录。
  message: AgentMessage;  // 内层包含 role、content 等实际消息字段。
}
```

来源：[session-manager.ts：41–67](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L41-L67)、[条目联合类型：182–197](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L182-L197)。

一个简化的用户消息条目（按真实字段构造的教学示意，不是运行产生的文件）：

```json
{"type":"message","id":"a1b2c3d4","parentId":null,"timestamp":"2026-10-12T02:00:00.000Z","message":{"role":"user","content":"帮我看看订单","timestamp":1791770400000}}
```

`parentId: null` 仅表示此示例是根条目；真实用户消息之前可能已有系统消息或设置条目。条目时间是 ISO 字符串，消息内时间是毫秒时间戳。

外层 `type` 与内层 `role` 不能混淆：`type: "message"` 的内层可以是 `user`、`assistant`、`toolResult`、`system` 等。助手的 `content` 是内容块数组，可能包含文字、思考或 `toolCall`；工具结果用 `toolCallId` 对应工具请求。来源：[types.ts：515–574](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/ai/src/types.ts#L515-L574)。

### 物理上逐行保存，逻辑上用父子关系连接

`id` / `parentId` 将条目连成树。普通聊天可以是一条链；回到旧节点继续时可以产生分支。会话头部的 `id` 标识会话，后续条目的 `id` 标识节点，`parentId` 指向条目而不是头部。

```text
A：用户问题
└─ B：助手回复
   ├─ C：原来继续的问题
   └─ D：从 B 重新继续的问题
```

这是关系示意，不是实际运行数据。树结构的用途留待会话恢复时继续学；当前只需知道它比“按序号排列消息”多保留了父子关系。

### 新消息怎样写入

`appendMessage(message)` 创建外层条目，将 `parentId` 设为当前 `leafId`，再调用 `_appendEntry(entry)`。后者依次：加入 `fileEntries` 数组、登记 `byId` Map、更新 `leafId`、调用 `_persist`。

内存的数组保留文件条目顺序，Map 按条目 ID 快速查找，`leafId` 表示当前继续的位置；它们不是额外的数据库表。字段来源：[session-manager.ts：987–998](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L987-L998)。

`_persist` 在持久化启用且有文件路径时工作。新会话仅有设置条目时暂不创建文件；第一次出现用户或助手消息后，把已有条目写出为 JSON 行；此后每次追加一行。普通追加路径使用 `appendFileSync(sessionFile, JSON.stringify(entry) + "\n")`。不要把它理解为从不重写文件：版本迁移等另有 `_rewriteFile` 路径。

来源：[session-manager.ts：1160–1213](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L1160-L1213)。

对应数据库类比：头部像 `sessions` 表的一行，后续记录更像带 `type`、`parent_id` 与 JSON 载荷的 `session_entries` 表；消息只是条目的一种。Pi 用文件归属表示这些条目属于哪个会话，没有在每条消息外层重复 `session_id`。

## System 消息：先组装，再比较，再记录变化

2026-10-12 固定版本源码核验：`AgentSession` 在 `message_end` 时明确将 system、user、assistant、toolResult 交给 `appendMessage` 保存，见 [agent-session.ts：925–943](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/agent-session.ts#L925-L943)。这些是实际写入路径，不仅是类型声明。

组装当前系统提示词与比较旧记录是两步。`buildSystemPromptSections(options)` 根据当前加载的配置、资源等构造期望的 sections；`getCurrentSystemMessage(messages)` 按顺序读取历史 system 消息，按名称应用 sections 更新，恢复之前声明的状态。恢复会话时，这些历史消息来自会话记录；正常运行时则已在内存中，不是每次比较都重读 JSONL。

`diffSystemPromptSections(previous, current)` 按 section 名称比较完整字符串：新增或变更的 section 保存新文本；当前已不存在的 section 保存 null；相同 section 不放进结果。完全相同时返回 undefined，不生成该次提示词 section 更新消息。它不是聊天摘要或用户消息比较，也不是按字符计算文本差异。

例如旧状态 `{preamble: "你是编程助手", rules: "使用中文"}`，当前状态 `{preamble: "你是编程助手", rules: "使用中文，不修改配置"}`，生成的更新仅含 `{rules: "使用中文，不修改配置"}`。后续按名称替换 rules，得到新的完整状态；这里是按真实行为构造的教学例子。

直接设计效果：在保留旧记录的前提下记录提示词状态变化，避免每次把所有未变的 sections 再记录一遍。这是该快照的实现选择，不能由此直接宣称供应商缓存命中或费用减少；请求最终怎样序列化要看适配器。

源码：[比较及返回更新消息](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/agent-session.ts#L1400-L1423)、[差异函数](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/system-prompt.ts#L199-L215)、[重放 system 记录](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/ai/src/utils/transcript.ts#L68-L95)。静态核验，未运行；用户理解待确认。

## Compaction：记录摘要与上下文保留边界

2026-10-12，仍以固定 Commit 的静态源码为准，未运行。用户提出“能替代某个范围的消息并参与 context 重建”，在普通线性历史中，这个主线理解成立；不因此标记为已掌握。

`CompactionEntry` 保存通用条目字段 type、id、parentId、timestamp，以及 summary（摘要）、firstKeptEntryId（保留起点）、tokensBefore（压缩前 Token 计数）。可选字段是 details、usage、fromHook、systemMessage；systemMessage 是压缩边界处的提示词与工具状态快照，不是模型生成的聊天摘要。来源：[类型定义](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L91-L104)、[实际追加](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L1261-L1286)。

普通线性示例：JSONL 已有 m1 至 m100，追加 compaction c1，parentId=m100，firstKeptEntryId=m81，summary=摘要文本。旧消息行不删除。之后还有新消息 m101、m102。

恢复上下文时，buildContextEntries 先取活动路径，再选择路径上的最新 compaction，构造“compaction + 从 firstKeptEntryId 到压缩点之前的保留条目 + 压缩点之后的新条目”。因此例子中旧 m1 至 m80 原文不再入选，由摘要承担相关信息；m81 至 m100 保留，再接 m101、m102。压缩前保留区间的 system 消息会被排除，相关状态由 compaction 的可选 systemMessage 快照提供；不要理解为不加区分地切整个文件。来源：[选择逻辑](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L476-L511)。

sessionEntryToContextMessages 将 compaction 转为内部 role=compactionSummary 的消息（如有 systemMessage 还一并返回）；convertToLlm 再将摘要转换为带固定前后说明的 user 消息。这不是直接把 role=compaction 或 role=compactionSummary 传给模型供应商。来源：[条目转换](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L461-L464)、[模型消息转换](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/messages.ts#L176-L183)。

关键边界：替代发生在构建模型上下文时，持久化文件里的旧原文仍在；摘要可能丢失细节，不等价于无损压缩。摘要如何生成以及保留起点如何确定留待下一小步。

## Branch summary：离开分支时保存摘要

2026-10-12：继续会话持久化，暂不展开完整恢复流程。固定源码中 branchWithSummary 在用户切换会话树位置并生成摘要时追加 type=branch_summary 条目。通用字段为 id、parentId、timestamp；主要内容为 fromId（离开时的旧叶节点 ID）与 summary（离开路线的摘要）。可选 details 保存附加信息，usage 保存摘要生成用量，fromHook 标明是否来自扩展。

教学场景：A→B→C→D 正在研究缓存，用户回到 B 改走 SQL，并选择携带旧路线摘要。新摘要记录的 parentId=B、fromId=D；JSONL 追加该记录，旧 A、B、C、D 不删。parentId 是摘要挂接的位置，fromId 是离开的旧位置，两者不同。后续新消息可以接在摘要之后。

该记录不是因为消息过长必然产生；切换分支也不保证一定生成摘要。来源：[字段定义](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L106-L116)、[实际追加函数](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/session-manager.ts#L1595-L1619)、[有摘要时才调用](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/agent-session.ts#L3726-L3737)。静态源码核验，未运行，用户理解待确认。

| custom | customType、可选 data | 扩展自己的持久化状态，不直接进入模型上下文。 |
| custom_message | customType、content、display、可选 details | 扩展注入的上下文消息；display 只控制界面显示，details 不送给模型。 |
| label | targetId、label | 给某个旧条目设置标签；撤销标签也追加记录，undefined 在 JSON 序列化后省略 label 字段。 |
| session_info | name | 当前实现记录会话名称；追加新记录而不是修改 session 头部。 |

以上记录也包含 id、parentId、timestamp；customType 标识扩展约定的数据类别，不是供应商 API 的 role。custom_message 的 content 可为字符串或文字/图片内容块数组，转换为模型消息时使用 user 角色。custom 与 custom_message 不可混淆。

## 恢复后接回 Agent：只看两个连接点

2026-10-13：用户选择跳过上下文合并、筛选和裁剪的实现细节，保留“完整 JSONL 读入内存，选出当前可用 messages”的主线理解。本轮仅跟踪恢复输出与新输入如何接回执行；固定版本静态核验，未运行。

1. sdk.ts 调用 sessionManager.buildSessionContext() 得到 existingSession，将 existingSession.messages 放进 new Agent({initialState:{messages:...}})。恢复历史因此成为新进程 Agent 的初始消息状态，不是单独打印出来的聊天记录。model、thinkingLevel 等也有恢复及回退处理，本轮不展开。
2. 用户提交新输入后，AgentSession._runAgentPrompt 调用 agent.prompt(messages)；Agent.prompt 将新输入规范化后进入 runPromptMessages。后者把新消息与 createContextSnapshot() 返回的当前消息/工具状态一起交给 runAgentLoop。新执行接着恢复后的历史进行，随后产生的新消息仍走已学习的事件保存路径。

简化流程：JSONL → 恢复得到的 messages → Agent 初始状态 → 新用户输入 → runAgentLoop → 模型/工具执行 → 新记录追加。这里的恢复不是恢复原进程调用栈或自动重跑全部旧工具；消息数组后续仍经过请求准备与供应商格式转换。

源码：[恢复输出](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/sdk.ts#L194-L195)、[Agent 初始消息](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/sdk.ts#L380-L388)、[新输入入口](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/coding-agent/src/core/agent-session.ts#L1471-L1475)、[交给循环与上下文快照](https://github.com/earendil-works/pi/blob/d6af72e1857cfb10b41d8ff8e69f0d72b4cf6d31/packages/agent/src/agent.ts#L432-L464)。

## 术语速查

- **Session（会话）**：Harness 管理的一段交互及相关记录，不等于模型内部记忆。
- **Persistence（持久化）**：将数据写入进程退出后仍存在的存储。
- **JSONL（JSON Lines）**：每行一个 JSON 对象的文件格式；文件格式本身不保证事务或断电安全。
- **Context（上下文）**：本轮供模型处理的输入信息；完整输入还包括系统提示词和工具等，不仅是会话消息。
- **Compaction（上下文压缩）**：减少历史输入体积的机制；具体如何选择与保存摘要待深入。

### 会话恢复

执行 pi --continue 后，Pi 怎么找到要恢复的那个 JSONL 文件？

顺序是：
找到会话文件 → 读取条目 → 恢复会话状态 → 组装当前上下文buildSessionContext

JSONL 全部读成内存里的记录，再选择、合并、裁剪或替换，整理成当前可用的 messages 数组，供下一次 LLM 调用使用。

这个恢复的是内存中的messages数据

还有一种恢复，是前端的完整对话列表！
这边其实还好，其实完全可以把所有 jsonl 给到前端，然后前端自行选择需要渲染啥 


> 问题：这个jsonl 啥都记，会不会内存爆炸啊！

这边有两个内存占用很大
1. messages 对象
2. jsonl数据读到内存

jsonl文件，可以一边读取一遍释放，可以定一个最大缓冲区
然后messages对象这玩意，就算最大，其实也就 1M token， 4M chars，大概 4MB 左右，还好

这边讨论的是session重建的情况，初次重建确实可能有点慢
但是如果是持续的对话，其实影响很小，基本上只有 messages 对象大小在变化，不涉及大量的jsonl数据读入

#### pi 从 jsonl 恢复数据

有三部分内存

| 部分 | Pi 的情况 |
| --- | --- |
| 文件读取缓冲 | 分块读取，可以复用、释放 |
| 完整历史条目对象 `fileEntries` | **解析后仍保留在内存，随对话持续增长** |
| 当前上下文 `messages` | 从历史中整理出来，压缩后可以变小 |

fileEntries 会把 jsonl 数据缓存在内存中 

Pi 当前采用全量历史驻留内存的方案；对规模适中的本地会话，这个取舍可以合理，但没有保证内存始终很小。

这就产生了问题，云端的agent怎么办 ？

会话相关内存 ≈ 同时驻留的会话数 × 单会话内存
假设一个会话占 20MB，这是示意数字：
- 100 个会话：约 2GB
- 1,000 个会话：约 20GB

这是个很实际的生产环境问题
