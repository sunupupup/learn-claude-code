# 现在的Agent现状

过去一年里，以 Coding Agent 为代表的单任务 Agent 已经证明，模型能够使用工具解决复杂问题，且越来越少需要人类持续监控和逐步干预

模型的多 Agent 协同能力也在提升，使跨会话的组织与调度变得可行。

随着人类在底层执行中的参与减少，人的角色正逐步上移到更高层的决策与验收。

模型能力的这一提升，也催生了新的应用形态。近期个人助手（Personal Agent）开始集中涌现，它们直接接入日常的消息、日程、邮件与工作平台，持续观察信息流并协助处理事务

持续在线、事件驱动的工作模式


Agent 的工作模式仍然以单一 Session 为基本单位，不同 Session 之间彼此独立。当用户并行推进多项工作时，必须手动切换并记住各个 Session 的上下文，而据我们观察
**一个人通常只能同时跟进 3 到 5 个活跃 Session**
在这种设计下
**单任务的上限取决于模型能力，多任务的上限取决于人的注意力**

针对于本地Agent + MCP + CLI 的形式
Agent的能力受限于 单会话同步阻塞、多任务上下文混乱、本地设备离线即停止等问题
还需要大量人工维护

要突破这些限制，需要打破 **Agent 与单次手动会话的绑定**，使其成为一个能跨会话保持上下文、同时推进多项复杂任务且互不干扰的连续实体。我们把这种 Agent 形态及其系统架构称为 Super-agent

# Super Agent 特性

1. 连续

用户可以在任何地方进行交互，只需要感觉“有这个Agent在”
用户在不同的地方提出不同的方案
Agent能够理解并且调整执行方向

2. 高效

响应迅速，能并行、高质量完成多个复杂任务
不用等待之前命令完成，直接能接受下一条指令

3. 主动

不需要用户下达指令，能主动观察环境事件并且主动推动值得处理的任务
不需要介入时，则保持安静

4. 持久

始终在线、直接接入用户真实的工作环境，并在长期运行中遇到异常时自动恢复。


补充：单个ReAct Loop方式的Agent肯定是不支持上述的特点
为了目标是 构建持续在线、并发响应环境事件的系统

# 2. 双层架构

要同时实现跨信道的连续交互与多任务的高效并发，系统在底层会话组织上面临连续性与吞吐量之间的根本权衡（Trade-off）。

两个情况
如果每个事件都给一个session，虽然上下文连续，但是受限于单个的执行的速度上限
如果每个事件都新建个session，吞吐并发最高，但是上下文过于独立，缺少全局上下文，强行打断各个session之间的关联性;重要的是，用户面对多session的响应会混乱

所以需要兼顾 吞吐量和连续性

”没什么是不能解决的，如果有的话，那就加一层“

加了一层 [Router](./asset/Router层.jpg)

IM                      Worker Session1
Github       Router     Worker Session2
邮件、日历               Worker Session3


用户只看到Router，拜托Session的负担
Router 层来承接所有的人类交互和全局协调, 共享上下文、路由、交互
Worker负责并发执行任务

接下来的问题就是：向用户如何暴露交互、任务管理方式
这两个独立产品问题


## 2.1 双层架构：Router层
负责承接所有入口的人类交互，所有任务的信息、决策都在这里

为了避免瓶颈，Router不会执行具体任务，只派发任务（可以理解为只有 dispatch task一个工具）


确实看起来有点像Agent Team
Agent Team比较倾向于领导详细规划、推理

但是Super-agent的Router只负责分发，不负责任务的拆解

所以Router这里的不会处理复杂的任务，只需要一些兼顾速度和效果的模型即可


还有个小瓶颈，如果事件密集涌入，这时候Router处理不过来
这边可以将消息进行合并，然后Router Session只做最轻量的分发

不过，还是会有问题，单个Router Session的并发上限，始终有限
若需要提高Router的吞吐，必然需要多Session

当规模进一步扩大、单个会话确实不足以承载时，Router 层内部也可以设计为多层过滤结构，或水平切分（Sharding）为多个会话。此时，Router 层的内部设计本质上是连续性与吞吐量的权衡。切分粒度越细，Router 层的并发吞吐量就越高，但分片之间的记忆与上下文连续性就会越低。在全局记忆问题被解决之前，这一权衡始终存在。


## 2.2 双层架构：Worker层

各个 Worker 彼此上下文隔离，挂载完整的执行工具，在独立上下文中专注完成单一任务。由于 Worker Session 直接决定任务结果与代码质量，通常需要配置能力最强的模型。

Worker的内容只向Router汇报，人不会直接收到
从而避免，大量session的混乱理解

Worker session agent，可以是很强大的agent


# 3. 事件驱动

群聊消息、邮件与日程提醒、代码审查评论、CI 运行结果等环境事件被称为 Trigger
需要大量的Trigger，不用人下令

通过监听并响应 Trigger，Agent 不必再像单 Session 模式下那样，等人类下达指令才被动执行一次。

事件一般会有下面这些问题

围绕一条环境事件从进入到处理的生命周期，下文将依次讨论四个递进的问题：
1. 如何通过程序与模型结合的两级策略过滤大量噪音（3.1 节）、
2. 如何通过订阅与直通机制将事件路由给 Worker（3.2 节）、
3. 如何利用 Inline & Spill 与链式召回向模型高密度地注入与按需召回上下文（3.3 节），
4. 如何利用投机执行根据环境信号在后台提前行动（3.4 节）。

## 3.1 事件过滤

环境事件流呈现出显著的“高噪音、低触发率”特征，绝大多数日常消息并不需要 Agent 介入

借鉴计算机系统中的 Fast Path / Slow Path 思想，大模型推理可以看作一条灵活但高成本的 Slow Path，而将已经明确且稳定的高频判断固化为确定性代码，则构成了低延迟、低成本的 Fast Path。

程序层策略 Fast Path: 针对事件来源、群组范围、用户、白名单等，直接过滤大量无关信息

语义层策略 Slow Path: LLM通过语义的方式来处理事件，比如对事件A保持静默（因为无需介入）、对事件B触发，发送给Router

这边是对Router接收到的事件进行过滤
