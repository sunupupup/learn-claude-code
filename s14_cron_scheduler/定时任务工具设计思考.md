# 定时任务工具设计思考

从 CC 的 Cron 工具设计中提取的通用原则，不局限于定时任务本身。

---

## 一、CRUD 精简为 CRD：用组合代替专用工具

CC 只暴露了三个 Cron 工具：`CronCreate`、`CronDelete`、`CronList`。没有 `CronUpdate`。

想改 cron 表达式？`CronDelete(old_id)` + `CronCreate(new_cron, ...)`。想改 prompt？同样。

### 为什么能这样做

CronJob 是一个简单的值对象，全部状态就五个字段（id, cron, prompt, recurring, durable），没有累积状态需要保留。Delete + Create 不会丢失任何有价值的信息。

### 三个好处

**1. 减少工具数量，降低模型选择成本**

每多一个工具，模型就多一个选择分支，token 消耗和误选概率都上升。能用组合实现的就不单独暴露。这是 CC 工具设计的一贯克制——原语足够了，就不加便利方法。

这里有一个权衡：省掉 Update 工具换来的是模型偶尔需要多输出一次 Delete + Create 的 token 和一次额外调用。CC 的判断是：工具数量的认知负担比偶尔多一次组合调用的代价更大。

**2. 避免 in-place 修改的并发问题**

调度线程每秒在读 `scheduled_jobs`。如果支持 Update，需要处理"调度线程正在用旧表达式 match，同时 Update 把表达式改了"的竞态。而 `_last_fired` 记录的是旧表达式的触发历史，新表达式的语义可能完全不同。

Delete + Create 天然避免这个问题：旧 job 消失，新 job 用新 ID，`_last_fired` 里没有旧记录，从零开始。

**3. 新 ID = 干净的审计链**

Delete + Create 产生新 ID，日志里能清楚看到"旧任务 `cron_001234` 被取消，新任务 `cron_005678` 被创建"。in-place Update 保持同一个 ID 但行为已经变了，对调试和追踪更不友好，也容易出现旧 ID + 新数据的残留歧义。

### 适用条件

当对象满足以下条件时，CRUD 可以精简为 CRD：

| 条件 | 说明 |
|------|------|
| 状态字段少，无累积状态 | 没有执行历史、统计计数等绑定在 ID 上的数据 |
| 创建成本低 | 生成 ID + 写一条记录，不涉及外部资源分配 |
| 无外部引用依赖 ID | 没有其他系统通过这个 ID 做关联 |

**反例**：如果 CronJob 的 ID 被 webhook、告警规则、审计报告等外部系统引用，Delete + Create 会断开所有关联。这时才真正需要 in-place Update。

### 更一般的表述

> 好的 API 提供最小完备的原语集（能组合出所有操作），只在高频场景才加便利方法。

## 二、三层门控：从编译到运行到本地

CC 的 Cron 工具受三层开关控制：

```
编译时: feature('AGENT_TRIGGERS')
  │ 关 → 代码不存在于构建产物
  │ 开 ↓
运行时: tengu_kairos_cron (GrowthBook)
  │ 关 → 代码存在但工具不暴露给模型
  │ 开 ↓
本地: CLAUDE_CODE_DISABLE_CRON 环境变量
  │ 设了 → 用户主动禁用
  │ 没设 ↓
工具注册给模型
```

三层各解决不同粒度的问题：

| 层级 | 解决什么 | 可逆性 |
|------|---------|--------|
| 编译时门控 | 这个能力在这个构建版本中**存不存在** | 需要重新构建 |
| 运行时标志 | 这个能力对这个用户/组织**开不开** | 秒级远程切换 |
| 环境变量 | 用户**自己想不想用** | 本地即时生效 |

这是工业级特性发布的标准模式：**build gate → remote flag → local override**。
