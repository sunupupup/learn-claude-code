# W-2026-036：AI 长任务工程（规划、进度、持续执行、恢复与完成证据）

- Status: ready
- Area: Agent / Harness / Planning / Task State / Continuation / Recovery / Verification
- Difficulty: D2 → D3
- Created: 2026-10-15
- Discovered From: 用户发现缺少完整的“AI 做长任务”学习模块，提出完成证据、记住做过哪些事、长时间规划与进度判断、Codex Goal 实现等问题
- Owner: personal
- Priority: high
- Learning Mode: 混合线（通用模型 → 固定版本源码 → 最小实验 → 失败恢复 → 设计取舍）

## Objective

理解一个 Agent 如何把跨多步骤、多轮对话、等待甚至进程重启的目标持续推进到可核验的结果。能回答“谁在继续执行、依据什么决定下一步、状态保存在哪里、如何恢复、谁允许宣告完成”，并用一个安全的小实验串联完整流程。

**这是长任务的端到端学习主线。** 已有完成验证、记忆、压缩、调度和权限专题提供局部机制，本任务学习它们如何共同支撑持续执行，不复制各专题的完整教程。完整指覆盖常见问题链路；低频分布式难题作为选学，不以穷尽所有情况为完成条件。

**当前学习安排（2026-10-15）：先逐块学习下面第 1–7 块通用知识，再按需要做最小实验；Codex Goal 的具体实现仅保留独立入口，暂缓，不阻塞本主线完成。Typed Evals 先作为执行检查的候选资料留存，不自动启动项目学习。**

## 用户原始问题

- AI 说办成了，证据呢？
- AI 之前怎么记得做过了哪些事？
- AI 怎么规划长时间运行的任务？怎么知道完成了哪些？
- Codex 的 goal 命令怎么实现的？
- 还有哪些问题属于这一整块能力？

## Core Learning Model

```text
用户目标、成功标准、权限与预算
  → 拆分步骤、依赖与阶段验收点
  → 读取可信进度和已有证据，选择下一步
  → 模型决策 → 工具/后台任务执行
  → 记录结果、产物、业务操作标识和状态变化
  → 等待事件 / 请求批准 / 验证 / 调整计划
  → 在允许的时机继续；中断后核对并恢复
  → 对照成功标准验收
  → 完成，或明确报告失败、阻塞、部分完成、结果未知、预算耗尽
```

上述是通用观察框架，**不代表任何产品已经完整实现这些能力**。教学状态图与 Demo 也不能自动视为 Codex 的实现。

## Work

### 1. 什么叫长任务，什么才叫完成

- 区分：一次模型调用很慢、一个工具执行很久、跨轮推进一个目标、跨进程/跨天恢复、按时间重复运行。
- 从“整理 20 份本地资料，生成有来源的汇总并校验”这一贯穿场景定义范围、产物与可检查的成功标准。
- 区分模型自述、工具返回成功、进程退出、子任务完成、业务目标完成和最终验收。
- 回答证据来自哪里、由谁检查、检查的范围是什么；引用已有完成验证专题深入学习验证器。

### 2. 目标如何变成可执行且可调整的计划

- 区分 Goal（最终目标）、Plan（执行路径）、Task（可跟踪步骤）、Run/Attempt（一次执行尝试）。
- 学习步骤粒度、前置依赖、阶段验收、动态发现新工作，以及什么时候重新规划。
- 比较边做边决定、先规划再执行、固定流程三种常用方式，说明适用条件，不把某一种设成唯一正确模式。
- 计划需要明确已完成、待做、失败和被替代的步骤；改计划不能悄悄丢掉用户约束或把失败步骤算作成功。

### 3. AI 如何知道之前做过哪些事

- 区分模型当前上下文、会话历史、压缩摘要、用户长期记忆、任务状态、操作记录和外部系统真实状态。
- 观察数据写入、查询、恢复和注入模型输入的时机；说明模型不是在每次调用中自动拥有全部历史。
- 明确完成记录由谁写、存在哪里、哪些是事实、哪些只是模型判断；日志、摘要和任务板各承担什么职责。
- 学习恢复时的最小状态：目标与约束、计划版本、步骤状态、证据引用、待处理事件、已发生操作及未知结果。
- 讨论记录过时、状态与产物冲突、摘要漏信息时以什么为准，如何回到原始证据核对。

### 4. 谁让任务持续运行，谁决定下一步

- Harness（模型外围负责工具、状态与控制流程的程序）和模型分别决定什么？
- 追踪一轮结束后的继续条件：读取目标 → 检查状态/预算/用户输入 → 发起下一轮或停止。
- 区分进程仍在运行、模型正在推理、工具正在执行、任务正在等待、已停止但可恢复。
- 学习轮内工具循环、跨轮继续、后台结果回收、外部事件唤醒；对比轮询与事件驱动。
- 定时唤醒用于等待/监测，不能自动替代进度保存、恢复和结果验证；记录进度也不能单独保证有人继续执行。

### 5. 如何在有限上下文中保持方向

- 学习长任务上下文如何组织：稳定目标与约束、当前步骤、相关历史、结构化进度、证据与产物引用。
- 理解摘要和上下文压缩如何辅助继续执行，以及为什么摘要不应作为唯一完成依据。
- 保留操作标识、待批准事项和未知结果，避免压缩后重复执行或遗忘边界。
- 接续已有 Context/Compaction 专题，只验证这些机制在长任务中的交界。

### 6. 中断、重启、失败后如何接着做

- Checkpoint（恢复检查点，属于执行层）保存继续任务需要的状态；不等于只保存聊天消息。
- 区分重试一次工具、从检查点恢复、重放事件、从头重做；了解 Durable Execution（持久执行）的常见思路。
- 覆盖“工具已成功，但结果未写入任务记录”窗口：先按操作标识查结果，不能盲目重复有副作用的动作。
- 区分用户取消意图、进程中断、外部操作已停止；恢复时核对仍在运行的后台工作。
- 用单执行者建立主线，再简要认识重复唤醒、并发认领和过期执行者写回的风险。

### 7. 如何判断有进展，以及什么时候应停

- 根据有效产物、阶段验收、解决的问题判断进展，不以 Token 数、调用次数或运行时长冒充完成度。
- 学习时间/Token/费用/重试预算、无进展检测、阻塞报告、等待用户和人工接管。
- 区分暂停、取消、失败、阻塞、预算耗尽、部分完成、结果未知和已验证完成；明确各自允许怎样继续。
- 控制重复尝试与权限扩张，给用户提供可核对的进度、证据、遗留项与停止入口。

### 9. 串联一个最小长任务实验

- 先无付费模型地演示持久状态和恢复，再按授权与学习需要接真实模型；两种结果分别标注。
- 输入固定的 20 份本地小资料；目标是逐份处理、保存来源引用、生成汇总并通过约定校验。
- 演示创建目标、拆步骤、记录进度、选择下一步、生成产物、最终验证；状态展示能区分运行中、等待和停止。
- 逐项注入下面的失败，保留命令、真实输出、前后状态、产物与恢复证据。
- 可再选一个窄对照：检查点框架或持久工作流；最多一个主项目加一个窄对照，不同时泛读全部候选。

## 候选项目：Typed Evals（先留存，未启动）

- 项目：[TrustifAI/typed_evals](https://github.com/TrustifAI/typed_evals)，Python 的 LLM / RAG / Agent 评测工具；身份与能力描述来自维护者 [PyPI 0.2.1 资料](https://pypi.org/project/typed-evals/0.2.1/)及[官方 README](https://raw.githubusercontent.com/TrustifAI/typed_evals/main/README.md)，2026-10-15 已读取。
- 与当前问题的关联：`agent` 预设接收用户任务、最终回复、实际执行记录（trace）和预期结果，评估任务完成及回复是否符合工具结果；例如工具报错，AI 却说操作成功。
- 文档还描述调用前的工具策略检查；执行后评测与执行前检查是不同环节，后续按需区分。
- 后续观察问题：执行记录由谁采集？哪些事实交给确定性校验，哪些交给评判模型？记录不完整、结果未知或评判失败时如何处理？
- 边界：评测结论依赖输入证据及评判模型；不能据此保证真实业务完成。顺序、效率和恢复质量也不自动由默认 `agent` 预设覆盖。
- 当前状态：仅资料留存，未读实现源码、固定 Commit、安装、调用模型或运行评测；不预建项目目录。需要学习时再按 Prompt 7 初始化项目与模块。

## Planned Experiments（未实施、未验证）

| 场景 | 要观察的问题 | 预期验收方向 |
| --- | --- | --- |
| 模型/执行器声称完成，但漏处理一份资料 | 完成状态是否依赖实际证据 | 校验拒绝完成，并列出缺项 |
| 处理中途退出并重启 | 状态是否能恢复并选择下一步 | 已确认步骤不重复，未完成步骤继续 |
| 产物已生成，进度写入前崩溃 | 如何处理结果未知窗口 | 按稳定标识核对产物再修复记录 |
| 压缩历史后继续执行 | 目标、约束、进度和证据是否仍可获得 | 不丢掉缺项、不把摘要自述当验收 |
| 等待事件期间暂停/取消，随后旧结果到达 | 迟到结果是否错误触发继续 | 按当前控制状态处理并保留记录 |
| 重复失败或预算达到上限 | 无进展和资源限制是否真能止损 | 停止原因准确，不宣告完成 |

每次只做能回答当前小问题的一个实验。表中是本任务 Demo 的验收方向，不是 Codex 的已验证行为。

## Success Criteria

必学主线完成时，学习者能够：

1. 用自己的话解释“模型说完成、步骤状态完成、真实结果完成、验收通过”的差别。
2. 对一个典型长任务给出成功标准、合理步骤、依赖、可信进度来源与下一步选择依据。
3. 说明模型上下文与持久任务状态如何配合，以及是谁在什么时候启动下一轮。
4. 面对中断、历史压缩、未知结果、等待用户和预算耗尽，判断继续、核对、暂停或停止。
5. 区分通用长任务机制、教学实验和项目实际行为；Codex Goal 与 Typed Evals 的具体实现留待后续独立学习，不作为主线验收条件。
6. 重复运行主流程与上述失败实验，能从状态、产物和证据判断结果；模拟调度与真实模型运行分开记录。
7. 各模块笔记与总览串联完整流程，记录实际掌握状态、必学未完成项和选学内容。

**选学扩展**：多执行者的 lease/fencing（租约与隔离过期执行者）、分布式事件重放、工作流版本迁移、跨机器容灾、多 Agent 长任务协作、复杂补偿、长期计划质量评测。遇到相应需求再深入，不阻塞单执行者主线。
