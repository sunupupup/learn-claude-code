## 后续基础协议学习清单

当前先不要求掌握协议报文和全部 MCP 能力，等进入实操前再按下面顺序补齐：

1. **角色边界**：Host、MCP Client、MCP Server、模型和下游业务系统分别负责什么；模型 Tool Calling 与 MCP 请求如何衔接。
2. **协议骨架**：JSON-RPC 请求、响应、错误、通知；初始化、版本协商、能力声明和连接关闭。
3. **核心方法**：`tools/list`、`tools/call` 的请求与返回；工具名称、描述、输入 Schema、结果和错误的边界。
4. **三类能力**：Tools（可调用动作）、Resources（可读取数据）、Prompts（可复用提示模板）；它们分别如何进入 Host 和模型上下文。
5. **传输方式**：stdio、本地子进程和远程 HTTP/Streamable HTTP；通信位置与信任边界的关系。
6. **动态发现与上下文**：工具列表变化通知、按需发现、分页、结果大小和上下文预算；理解“统一接入”不等于“全部内容自动塞给模型”。
7. **基础 Demo 到真实服务**：将 s19 的 `MCPClient.register()` / `call_tool()` 映射到真实 `tools/list` / `tools/call`，明确 mock 隐藏了哪些进程、通信和错误处理。
8. **能力模型深入**：分别学习 Tools、Resources、Prompts 的定义、发现、读取/调用、结果进入模型上下文的方式，以及它们与普通 Tool Calling、Skill 和 RAG 的边界。
9. **库与 SDK 选择**：对照官方协议、客户端 SDK、服务端 SDK/框架和测试工具；固定语言与版本后，核对 API、Transport、认证、错误、生命周期和升级策略，不把某个 SDK 的便捷封装当成协议本身。

### 必须单独掌握的生命周期与状态模型

有状态和无状态不是“HTTP 长连接与短连接”的简单同义词，而是 MCP 协议如何保存跨请求状态、如何识别一次交互、如何进行能力发现和路由的架构选择。实操前必须对照固定协议版本学习：

- 2025-11-25 及更早生命周期：initialize、notifications/initialized、能力协商和逻辑会话；理解协议会话状态与 TCP/HTTP 连接复用的区别。
- 2026-07-28 无状态核心：每个请求自描述，initialize/initialized 和 Mcp-Session-Id 的变化，server/discover、请求级元数据、负载均衡和缓存提示。
- 应用状态仍可能存在：即使 MCP 传输层无状态，长任务、幂等键、授权上下文、业务句柄和执行进度也可能由 Server 或下游系统持久化。
- 设计时要画出连接/会话状态机，说明重连、路由、缓存失效、取消、超时、恢复和多实例部署的行为。

这些内容是后续真实 MCP 实操的前置学习，不是当前章节必须一次学完的范围。当前学习阶段只保留问题清单，不预先实现协议客户端或服务端。

## 推荐学习顺序

1. 确定真实使用者、任务、数据来源，以及现有工具为何不能充分解决问题。
2. 区分 Host（宿主应用）、Client（协议客户端）、Server（能力提供方）与模型工具调用；核验官方协议和所选 SDK 的版本。
3. 定义最小工具输入、输出、错误与权限边界；候选场景是查询本仓库学习笔记、章节与 Work Pool，但尚未选定。
4. 完成真实连接、初始化、工具发现、一次实际调用与结果返回；传输方式及语言待启动时选择。
5. 验证非法参数、越权访问、断连、超时、结果过长；若包含写操作，再验证重试幂等性与审计。
6. 在实际客户端中完成一项有用任务，并对照 s19 mock 说明新增了哪些工程责任。
7. 按下表完成生产差距分析，选定量化验收目标，逐项实现适用能力、注入故障并收集证据；最后演练发布、回滚和恢复。

## 责任边界与关键认知

- Tool Calling 是模型提出工具名称和参数、宿主执行并返回结果的机制，不限定本地或远程实现。
- MCP 统一宿主与能力提供方的发现和调用契约；业务 API 适配仍需实现，服务器也可以部署在本机。
- 把工具移到 MCP Server 不会自动减少模型看到的 Schema 或结果；上下文治理要另外设计和验证。
- 为每项保证标明 Host/Client、MCP Server、下游业务系统及部署平台分别负责什么；不能假设服务端能单独保证宿主正确审批或模型正确选择工具。
- MCP Resources、Prompts 等能力与 Tools 做边界对照；按需求选用，不为覆盖名词而全部实现。

## Expected Output / Success Criteria

- 一个可重复启动、具有清晰配置说明的 MCP 服务及客户端接入示例。
- 至少一个返回真实数据、解决明确问题的工具，不能仅返回固定演示字符串。
- 从发现工具到结果回到宿主的调用链说明，标清模型与程序分别负责什么。
- 正常路径及适用失败场景的验证记录，注明已验证范围和遗留问题。
- 能解释 MCP 统一接入契约与底层业务 API 实现的区别，以及工具声明与实际权限执行的区别。
- 一份完整生产验收矩阵：所有维度有评估结论，适用维度有实现与验证证据，不适用维度有理由和复审条件。
- 一份架构与信任边界图，以及关联日志、权限拒绝、故障恢复、负载和回滚的实际记录。
- 一份运行/部署/升级/故障排查手册和已知限制清单；按场景确定的 SLO 与安全验收门槛通过后，才能声明达到约定生产使用要求。
- 如阶段性只完成连通性，应明确标记为阶段成果，不以 Demo 完成作为本 Work Pool 完成。

## Boundaries / 待确认

- 业务场景、使用客户端、语言、SDK、部署位置、传输和认证方式均未选定。
- 协议报文、Tools/Resources/Prompts 的具体结构、传输和客户端选择暂缓到实操前学习；当前以 s19 基础 Demo 的工具发现和调用链为主。
- 有状态/无状态生命周期及其协议版本差异已经列为前置学习项；当前 Context7 实测使用的是 2025-11-25，不能直接代表最新协议行为。
- 本轮新增的能力模型和 SDK 学习先不展开；启动时先选一个主语言和一套官方/维护方 SDK，使用最小可运行实验验证，再做生产级扩展。
- 优先讨论最小只读场景；是否需要写入由实际需求决定。
- 公网部署、多租户、OAuth、高可用等全部纳入评估；按使用场景决定实现深度并记录依据，不将生产考量缩减为最小 Demo。
- 当前不安装依赖、不启动服务、不修改教学代码、不预写完整章节笔记。
- 主参考采用官方协议与所选官方 SDK 源码；真实产品行为必须另行核验。
