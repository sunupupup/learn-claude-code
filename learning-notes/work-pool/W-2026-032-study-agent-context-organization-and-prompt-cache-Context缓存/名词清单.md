# 名词清单：Agent Context 组织与缓存命中

这份清单按知识块提供查词入口。名词解释是学习地图，不表示已经掌握；每个模块学完后再更新状态。

## A. Context 与 Agent Harness

| 术语 | 初学者解释、层次与相邻概念边界 |
| --- | --- |
| Context（上下文） | 一次模型调用能看到的指令、消息、工具定义和资料，属于 Agent Harness 到模型输入之间的数据。它比 System Prompt 广，也不是模型长期保存的 Memory。 |
| Harness（Agent 外围执行程序） | 组织模型循环、上下文、工具和权限的应用层程序。它决定“这轮把什么交给模型”；Provider/Runtime 决定“如何处理模型输入”。 |
| Context assembly（上下文组装） | 从多个来源读取、过滤、排序并序列化成模型请求的过程；与模型内部的推理计算不同。 |
| Stable/dynamic content（稳定/动态内容） | 稳定内容在相邻请求中保持相同，如基础指令；动态内容随用户、任务或状态改变。分类必须看具体 Run 和权限范围，不能只看文本模板是否相同。 |
| Serialization（序列化） | 将消息、角色、工具等变为 Provider 请求格式的过程。肉眼相似的聊天内容，序列化后的字段和顺序也可能不同。 |
| Tool Schema（工具模式/定义） | 工具名称、描述和参数结构，属于模型请求输入的一部分；它不仅是“工具代码”，变化也可能影响 Provider 缓存前缀。 |
| Chat Template（聊天模板） | 将结构化的 role/content/messages/tools 等数据排布成特定模型接受的对话格式，属于 Tokenizer/模型适配层；不同模型格式不同，不能按 SDK 参数排列推断。 |
| Token ID（Token 编号） | Tokenizer 词表中每个 Token 对应的整数编号；模型推理处理的是编号序列。可见的 `<|...|>` 拼写用于阅读格式，不保证任意同名字符串在任意模型中都是特殊 Token。 |
| API Request Object（API 请求对象） | Harness/SDK 按 Provider 约定发送的结构化字段；例如 `system`、`tools` 和 `messages`。它是网络 API 层数据，不等同于模型内部输入 Token。 |

## B. 三类相邻缓存

| 术语 | 初学者解释、层次与相邻概念边界 |
| --- | --- |
| Prompt/Prefix Cache（提示词/前缀缓存） | Provider 或推理服务可能重用相同请求前缀已算出的中间状态，减少重复处理；通常按精确前缀和 Provider 规则判断，不是语义相似搜索。 |
| KV Cache（Key-Value Cache，键值缓存） | Transformer 推理中保存历史 Token 的 Key/Value 张量，属于模型 Runtime。它不是 Agent 的跨会话记忆；服务端 Prompt Cache 可能复用类似计算，但两个词的生命周期和计量不可直接等同。 |
| 应用层 Prompt 组装缓存 | Harness 在本地保存已组装 Prompt，Context 未变时避免重新拼接。缓存的是应用数据，不是 Provider 已复用模型计算的证据。 |
| Response Cache（响应缓存） | 应用按请求键保存旧模型答案并直接复用输出。它复用的是响应结果，可能改变功能语义，和仅减少模型输入计算的 Prompt Cache 不同。 |
| Memory（记忆） | Agent 在多个回合/任务间保留的事实或经验，属于应用状态/知识层；缓存是访问或计算的优化，不能当作长期记忆。 |

## C. 命中与指标

| 术语 | 初学者解释、层次与相邻概念边界 |
| --- | --- |
| Prefix（前缀） | 请求开头一段按顺序排列的输入 Token。若中间部分改变，后续内容是否还能复用由 Provider 缓存规则决定；不能把“内容大致相同”当成“前缀相同”。 |
| Cache breakpoint（缓存断点） | 某些 API 中标记缓存前缀截止位置的字段或标记，属于 Provider 请求配置；不等同于 Agent 自己的 Context 分段。 |
| Cache read / hit（缓存读取/命中） | Provider 报告本次输入中复用的缓存 Token 或状态。必须结合总输入与字段定义理解，不代表整条请求都缓存。 |
| Cache write / creation（缓存写入/创建） | Provider 为后续复用建立缓存时报告的 Token；可能有额外成本或生命周期限制，不能与 cache read 合并统计。 |
| Uncached input（未缓存输入） | 本次正常处理但未从缓存读取的输入 Token。通常每轮新内容都要处理，它不自动表示缓存系统故障。 |
| Cache hit rate（缓存命中率） | 一种汇总比例；常见口径是 cached input tokens / total input tokens，但必须检查 Provider 与产品采用的实际分子、分母和时间窗口。一次 hit/miss 不足以代表系统整体比例。 |
| TTFT（Time To First Token，首 Token 时间） | 从请求开始到模型返回首个输出 Token 的时间。缓存可能缩短输入处理，但排队、网络和 Provider 调度也会影响它。 |
| TTL（Time To Live，存活时间） | 缓存可复用的时间窗口；超时可能需要重新写缓存。TTL 是 Provider/缓存策略，不是 Agent Session 自动持续时间。 |
| Keepalive（保活请求） | 定期发请求以避免缓存因空闲过期；可能产生请求成本、占用速率额度或改变测量负载，需要计算是否划算。 |

## D. 证据类型

| 标签 | 含义 |
| --- | --- |
| `documented` | 官方文档描述的行为或配置，不证明当前项目运行时一定执行成功。 |
| `source-verified` | 固定 Commit 的实际源码调用链支持的结论；仍不自动证明 Provider 已命中。 |
| `observed-runtime` | 固定输入、版本、Provider 和配置下实际返回的日志/Usage/延迟。 |
| `production-proven` | 生产工作负载中具有代表性的数据；还需说明样本、分母和运行条件。 |
