# 缓存命中的前缀与新增后缀

## 学习问题

如果第二轮请求保留原有前缀，只在末尾追加一条工具结果，DeepSeek 会把哪部分算作缓存命中？为什么？

学习者回答：

> “原有前缀 都算是 缓存吧”

## 校准后的理解

🔴 **已验证理解**：如果新请求开头的旧前缀与 DeepSeek 已持久化的缓存前缀完全匹配，那么这段旧前缀可以计为缓存命中；末尾新追加的工具结果不属于这段旧缓存，通常要作为未命中的新输入处理。

这里的“可以”有条件：请求前缀必须与服务端已有缓存匹配，而且缓存已写入；DeepSeek 文档将缓存描述为 best-effort，不保证每次都命中。因此，“原有前缀都算缓存”方向正确，但不能只凭它曾经出现在上一轮请求里，就断言整段一定命中。

```text
第一轮：固定指令 + 工具定义 + 已有对话历史
                                  ↓ 服务端可能保存可复用前缀
第二轮：固定指令 + 工具定义 + 已有对话历史 + 新工具结果
         └────────────── 可能命中的旧前缀 ──────────────┘└ 新增后缀
```

服务端返回的 `prompt_cache_hit_tokens`（缓存命中的输入 Token 数）与 `prompt_cache_miss_tokens`（未命中的输入 Token 数）可以用来核对实际结果。它们是 API 用量统计，不是模型回答是否重复，也不是应用本地是否复用了 Prompt 字符串。

## 术语速查

| 术语 | 含义与所在层 | 本例中的位置 |
| --- | --- | --- |
| Prefix Cache / 前缀缓存 | Provider（模型服务）尝试复用此前相同输入前缀的计算状态。 | 旧请求开头与新请求开头逐 token 相同的部分可能命中。 |
| 持久化（persisted） | 服务端已经把可复用缓存单元保存好，后续请求才有机会读到。 | “上一轮发过”不等于“这一刻一定已有可读缓存”。 |
| Tool Result / 工具结果 | Harness 执行工具后加入会话上下文的新消息。 | 新追加的结果属于后缀，不能假设它已经在旧前缀缓存里。 |
| Usage / 用量统计 | Provider 返回的 Token 计数等请求元数据。 | 看 hit/miss token 字段验证实际命中范围。 |

容易混淆的一点：缓存命中复用的是模型服务侧对输入前缀的计算，不是把上一轮答案直接拿来当这一轮答案。模型仍会根据新增的工具结果继续生成。

## 边界与证据

- 🟢 **已验证（文档）**：DeepSeek 官方中文指南给出多轮对话示例，第二次请求在首轮消息后追加 Assistant 和 User 消息，并说明可通过 hit/miss Token 查看缓存状态。
- 🟢 **已验证（文档）**：DeepSeek 响应字段定义 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`；`prompt_tokens` 由两者相加。
- 🟡 **依实现而定**：Agent 如何序列化工具调用与结果、缓存单元边界如何落在这段序列化内容中，要继续沿项目请求构造和 Provider 文档核查。

## 对后续学习的连接

这个例子说明，Agent 的上下文要按消息顺序序列化成一次请求；新增工具结果如果只追加在尾部，较早的稳定前缀就有机会复用。下一步阅读 CodeWhale（原 DeepSeek-TUI）时，沿“固定 system/tool 前缀 → 追加历史 → 工具结果 → Provider Usage”追踪源码，确认项目做了什么、又有哪些结论只能由运行指标验证。
