# LLM 网关概念

## 为什么聊到这个

我们从 Agent 如何组织 system prompt、tools 和 messages 来学习缓存时，聊到应用怎样把请求交给不同模型厂商。由此引出了“模型适配器”和“LLM 网关”这些容易混用的说法。

## 用处

LLM 网关处在 Agent 应用和模型厂商之间，是实际请求链路中的基础设施。它不只是一个转发地址：它决定请求送给哪个模型、用哪套厂商凭证、失败后怎么办，并把调用结果和用量带回应用。没有网关时，这些工作通常散落在每个应用里；接入模型越多，重复配置和排查工作就越多。

一次调用可以理解为：

```text
Agent 组织 system prompt、tools、messages
  → 应用选择一个模型名并提交请求
  → 网关查模型映射和策略，选择厂商与凭证
  → 网关转换或适配厂商 API，发送请求
  → 厂商返回结果
  → 网关整理响应、记录用量并返回应用
```

网关通常承担这些具体工作：

- **统一接入**：让应用用相近的请求格式访问不同厂商，处理各家 API 的请求、响应、流式输出和错误格式差异。这样应用不必为每家模型都写一套连接代码。
- **模型路由**：把应用使用的模型名映射到具体厂商和模型；根据配置选择模型，也可在请求失败、超时或限流时重试或切换备用模型。
- **凭证与访问控制**：集中保存厂商 API 密钥，给内部应用发放自己的调用密钥，并按应用或用户设置访问范围、额度和速率限制。应用不必直接持有所有厂商密钥。
- **用量与成本记录**：记录请求、模型、令牌用量、延迟和错误，按应用或用户统计费用，帮助定位“谁在调用、花了多少、哪里失败”。
- **统一策略**：在一个位置配置日志、内容检查、缓存或其他调用策略，使多个应用采用相同规则。具体功能取决于网关产品和部署配置。

它对 Agent 开发的价值是把“怎么连模型、怎么管模型调用”从 Agent 业务流程里抽出来。Agent 仍负责决定 system prompt、tools 和 messages；网关一般负责传输、选路和调用治理。两层通过请求内容相连，但职责不同。

这也和本章的缓存主题直接相关：网关可能影响请求是否持续发往同一模型、是否走到支持相同缓存机制的厂商，以及是否改写会影响请求前缀的内容。若路由在不同厂商或模型间切换，或中间层改变了提示词、工具定义或消息结构，应用侧保持不变的内容也未必能在目标模型处形成相同的缓存前缀。具体会不会改写、缓存由哪一层提供，要检查网关配置和目标厂商的实现；网关本身不保证高缓存命中率。

“模型适配器”常指应用代码或 SDK 内的请求转换层；“网关”通常是单独部署的服务。两者相关，但所在位置不同。

## 实际例子

- **New API**：主要作为独立的模型 API 网关，配置渠道来接入不同模型服务。
- **LiteLLM**：既提供应用内 SDK，也提供可独立部署的 Proxy 网关。
