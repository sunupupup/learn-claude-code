## 本组统一看法

缓存分析不能只看基础 system prompt。应逐项追踪 Skill 索引/正文、Memory 快照/检索结果、tool schema、工具结果分别进入哪一层、何时刷新，以及更新是否改写了已有前缀。

- **Skill 被发现**不等于 Skill 正文已进入模型请求；有的产品常驻短目录、触发后才读取全文，有的会将激活内容直接渲染进 Prompt。
- **Memory 被保存**不等于 Memory 每轮都注入；它可能会话开始时读成快照，也可能每轮检索，或由工具按需返回。
- 只要内容进入 Prompt、tools 或 messages，就可能影响请求前缀；但是否实际命中仍由 Provider 规则和运行时指标确认。
- Skill/MCP 能改变模型可见的 tools 时，也要检查 tool schema 是否重建；Prompt 中的工具说明不等同于 tool schema 或执行权限。

## 证据边界

各页区分官方文档说明、源码确认与工程推论。当前目录记录的是应用侧组装设计和待追调用链；没有把任何产品的缓存命中率当成已验证结论。正式源码学习时应固定版本与 commit。

## 为什么学习这些开源项目

我们学习这些项目，是为了弄清成熟 Agent 的 Harness 怎样在每次模型调用前组织上下文，并从源码中找到可复用的设计方法。重点不是比较谁的缓存命中率最高，也不是先钻进各家模型的 Token 化细节。

学习每个项目时，持续回答这些问题：

1. **System prompt 怎么建设？** 它由哪些固定部分和动态部分组成？由哪些函数或配置生成？项目指令（如 `AGENTS.md`）何时加载、更新后何时生效？
2. **Tools 怎么组织？** 工具说明和实际 tool schema 分别放在哪里？工具如何注册、筛选、动态增删？这些变化是否会改变模型请求？
3. **Skill 放在哪里、怎样进入上下文？** Agent 是常驻一个简短索引，还是直接注入 Skill 正文？何时发现、激活和读取？
4. **Memory 放在哪里、怎样进入上下文？** Memory 如何保存、检索和更新？是固定注入 system prompt、每轮生成快照，还是通过工具按需取回？
5. **这些动态内容怎样影响缓存前缀？** 文件、Skill、Memory 或工具发生变化时，Harness 怎样更新会话上下文？再继续追具体模型适配器如何将其转换成请求，并用运行时指标验证缓存效果。

最终目标是从 Codex、Pi、Hermes、OpenClaw、CodeWhale 和 OpenHands 的实现中，整理出一套自己设计 Agent 上下文的检查框架：哪些内容适合稳定常驻，哪些适合按需加载，动态更新放在哪里，以及怎样在上下文新鲜度、指令优先级和缓存复用之间做取舍。
