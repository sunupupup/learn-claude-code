# Tokenizer：词表、合并规则与括号实验

本笔记承接 [LLM Runtime 学习笔记](./LEARNING_NOTES.md)，对应 [Tokenizer Demo](./experiments/tokenizer-basic/tokenizer_demo.py) 和 [实验说明](./experiments/tokenizer-basic/README.md)。

## 1. 本次实验在观察什么

Tokenizer（分词器 / 文本编解码器）负责把文本转换成 Token ID 序列，也能把 ID 序列解码为文本。Token 是分词器使用的文本表示单位，不一定是一个字符或一个完整单词。

```text
文本 → 按规则切分、合并 → Token → 按词表映射 → Token ID
Token ID → 查回对应表示 → 由解码器还原文本
```

本实验使用 `deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B` 的配套 Tokenizer，不加载模型权重、不执行输入的代码，不需要 GPU。编码时设置 `add_special_tokens=False`。

🟢 用户实际输出：

```text
原文：print("hi")
Token：['print', '("', 'hi', '")']
Token ID：[1350, 445, 6023, 899]
字符区间：[(0, 5), (5, 7), (7, 9), (9, 11)]
解码结果：print("hi")
往返一致：True
```

字符区间使用原文中的 `[start, end)`：从 0 计数，包含开始位置，不包含结束位置。例如 `ABC` 的 `(1, 3)` 对应 `BC`。一个 Token 可以覆盖多个字符。内部 Token 字符串可能是字节级可打印表示，解码不能简单理解为直接拼接屏幕上显示的字符串。

## 2. 词表和合并规则是两份不同的数据

🟢 本次读取本机缓存的 Tokenizer 配置，确认模型类型是 BPE，并且具有 `vocab` 与 `merges` 字段。

| 数据 | 含义 | 解决的问题 |
| --- | --- | --- |
| `vocab`：词表 | Token 表示与 Token ID 的映射 | 这个 Token 的编号是什么？ |
| `merges`：有序合并规则列表 | 哪两个相邻片段可以合并，以及规则先后顺序 | 哪两个片段先合并？ |

Demo 打印的 `len(tokenizer) = 151665` 表示当前 Tokenizer 的条目总数（包含额外添加的 Token），不代表有 151665 个单词，也不代表本次输入需要这么多 Token。

实际相关条目：

| 相邻片段的合并规则 | 在 `merges` 中的索引（rank） | 合并结果的 Token ID |
| --- | ---: | ---: |
| `(` + `(` → `((` | 932 | 1188 |
| `((` + `(` → `(((` | 6380 | 6636 |
| `((` + `((` → `((((` | 66588 | 66844 |

Rank（规则排名）就是规则列表中从 0 开始的位置。程序规定数值越小越优先，因此列表顺序本身就表达了优先级，不需要再有第三张“优先级表”。表中的箭头展示合并结果；配置中的规则可以只保存两个输入片段，结果由二者连接得到。

这三个条目恰好满足 `Token ID = rank + 256`，但不要把 ID 当作通用的优先级指标：基础 Token、特殊 Token、额外添加的 Token 不一定对应合并规则。Token ID 为 1 也不表示出现概率最大。

## 3. 用户的五个括号例子

用户的理解：

> 先是 1 1 1 1 1，相邻合并后变成 2 2 1；因为 2 2 合并的优先级低于 2 1，所以得到 2 3。

🟢 对本次例子，这个理解正确。下面数字表示片段包含几个左括号，不是 Token ID。

```text
开始：              1 | 1 | 1 | 1 | 1
先用 1 + 1 规则：   2 | 2 | 1
```

此时有两个候选：

- 左边 `2 + 2 → 4`，rank 为 66588。
- 右边 `2 + 1 → 3`，rank 为 6380。

因为 `6380 < 66588`，先合并右边，得到：

```text
2 | 3
(( | (((
```

用户实际输出：

```text
原文：'((((('
Token：['((', '(((']
Token ID：[1188, 6636]
字符区间：[(0, 2), (2, 5)]
往返一致：True
```

概念上，每一步是在当前相邻候选中选择 rank 最小的规则；同一规则在多个位置可用时，本例先处理左边位置。不要理解为从左到右扫描一次就结束，也不是每一步优先取最长片段。这里展示的是依据实际规则重建的推演，不是内部执行日志。

## 4. 为什么六个括号连前缀都不一样

```text
开始：              1 | 1 | 1 | 1 | 1 | 1
先用 1 + 1 规则：   2 | 2 | 2
接着用 2 + 2：      4 | 2
对应：           (((( | ((
```

这次没有剩余的单括号，所以没有 `2 + 1` 候选，左边的 `2 + 2` 可以先合并。

用户实际输出：

```text
原文：'(((((('
Token：['((((', '((']
Token ID：[66844, 1188]
字符区间：[(0, 4), (4, 6)]
往返一致：True
```

🟢 已检查预切分结果：五个和六个括号分别作为一个完整片段进入后续处理。因此，本例差异可以由上面的 BPE 合并规则解释。

两次都是独立编码完整输入。末尾新增字符改变了中间候选组合，进而改变最终边界。因此原文前缀相同，不保证 Token 序列前缀相同；字符增加，也不保证 Token 数增加。

## 5. 最后一个问题：优先级怎么得来的？

用户确认中的理解：

> 优先级和训练时的统计数据有关，还和合并过程有关。

🟢 这个理解正确。简单说：**统计决定这一轮先合并谁；这一轮的合并又改变下一轮统计的片段；把逐轮选出的规则依次保存，就得到了合并优先级。**

```text
统计当前相邻片段的次数
        ↓
选出本轮要合并的片段对，记下一条规则
        ↓
执行合并，片段发生变化
        ↓
更新统计，进入下一轮
```

### 完整教学例子：一边合并训练语料，一边生成规则表

以下全部是假设的教学数据，不是 DeepSeek 分词器的真实训练记录。假设整个训练语料只有三种文本，从单字符片段开始，各条文本独立处理，不跨文本边界统计。

| 训练文本 | 出现次数 | 初始片段 |
| --- | ---: | --- |
| `ABC` | 5 | `A ｜ B ｜ C` |
| `ABX` | 3 | `A ｜ B ｜ X` |
| `YBC` | 2 | `Y ｜ B ｜ C` |

#### 第 1 轮：统计所有相邻片段对，再选一种

| 训练文本 | 对统计的贡献 |
| --- | --- |
| `ABC` × 5 | `A+B` 加 5 次，`B+C` 加 5 次 |
| `ABX` × 3 | `A+B` 加 3 次，`B+X` 加 3 次 |
| `YBC` × 2 | `Y+B` 加 2 次，`B+C` 加 2 次 |

汇总整个训练语料：

| 相邻片段对 | 总次数 |
| --- | ---: |
| `A+B` | **8** |
| `B+C` | 7 |
| `B+X` | 3 |
| `Y+B` | 2 |

**`BC` 也统计了，没有优先统计前缀。** 本轮选中 `A+B`，因为它出现次数最多，而不是因为它在左边。

把 `A+B → AB` 追加到规则表，分配序号 `rank = 0`。然后在训练语料当前的片段序列中执行这条规则：

```text
合并前                     合并后
A | B | C  × 5             AB | C     × 5
A | B | X  × 3             AB | X     × 3
Y | B | C  × 2             Y | B | C  × 2
```

本轮只选一种组合，但这条规则可以在语料的多处执行。`A | B | C` 中的同一个 `B` 不能既归入 `AB` 又归入 `BC`；本轮选择 `AB` 后，这一处变成 `AB | C`。其他地方的 `B+C` 并没有被永久排除，例如 `Y | B | C` 中仍然存在。

#### 第 2 轮：根据新的片段边界更新统计

| 当前相邻片段对 | 总次数 | 来源 |
| --- | ---: | --- |
| `AB+C` | **5** | `AB ｜ C` × 5 |
| `AB+X` | 3 | `AB ｜ X` × 3 |
| `Y+B` | 2 | `Y ｜ B ｜ C` × 2 |
| `B+C` | **2** | `Y ｜ B ｜ C` × 2 |

**为什么 `B+C` 从 7 次变成 2 次？** 原来的 5 条 `ABC` 已经表示成 `AB | C`。这里 `AB` 是一个完整片段，`B` 不再单独参与相邻片段配对，所以这 5 处现在贡献的是 `AB+C`；只有 `Y | B | C` 的 2 处继续贡献 `B+C`。

**训练文本本身没变，变的是它被表示成了哪些片段。统计的是当前相邻片段对，不是始终统计原文中的两字符子串。**

本轮 `AB+C` 的 5 次最多，因此追加规则 `AB+C → ABC`，分配 `rank = 1`，并执行合并：

```text
ABC          × 5
AB | X       × 3
Y | B | C    × 2
```

#### 第 3 轮：继续选择、记录和合并

| 当前相邻片段对 | 总次数 |
| --- | ---: |
| `AB+X` | **3** |
| `Y+B` | 2 |
| `B+C` | 2 |

`ABC` 已经是一个片段，不再贡献内部的相邻片段对。本轮选中 `AB+X`，追加规则 `AB+X → ABX`，分配 `rank = 2`，执行后得到：

```text
ABC          × 5
ABX          × 3
Y | B | C    × 2
```

教学示例在此停止；真实训练会按词表大小等停止条件继续。

#### 结果：统计决定选择，自增序号保存顺序

| 训练轮次 | 选中时的次数（解释依据） | 保存的规则 | 自增序号 rank |
| --- | ---: | --- | ---: |
| 第 1 轮 | 8 | `A+B → AB` | 0 |
| 第 2 轮 | 5 | `AB+C → ABC` | 1 |
| 第 3 轮 | 3 | `AB+X → ABX` | 2 |

次数列用于解释本例的选择，不表示发布后的 `merges` 必须保存次数。规则依次追加，序号为 `0、1、2……`。**编码时，序号越小，优先级越高。**

用户最终确认的理解：

> 序号就相当于优先级；这个序号是在合并过程中，不断合并、形成新组合、再合并得来的。

🟢 对。展开就是：**统计当前组合 → 选中一种组合 → 记录规则并分配自增序号 → 执行合并 → 形成新的相邻组合 → 更新统计 → 再选、再合并。**

这里“变成自增序号”表示把选择顺序记录下来，不是把次数换算为序号。此前反复纠正“次数不等于序号”忽略了用户本来就在表达这一点。

### 训练和使用的边界

保存下来的 rank 是这段训练过程形成的规则顺序；运行 Demo 时直接使用它，不重新训练，也不重新计算训练频数。

**在标准 BPE（Byte Pair Encoding，字节对编码）训练中，逐轮选择合并规则，并把选择顺序保存下来；这个顺序就是编码时的优先级。**

简化训练过程：

1. 把训练文本表示成初始单位；字节级 BPE 从字节的表示出发，本例的 ASCII 括号可直接按一个单位理解。
2. 统计当前所有相邻片段对的出现次数。
3. 选择出现次数最多的可合并片段对，加入规则列表。
4. 在训练文本的当前表示中执行合并，更新相邻组合及统计。
5. 重复以上过程，直到满足词表大小等停止条件。

如果次数相同，训练实现需要用确定的方式选择顺序；这里没有核验该 Tokenizer 原始训练过程的平局处理方式。

```text
训练时：当前统计次数 → 选择下一条合并规则 → 保存到有序列表
使用时：读取固定列表 → 当前可用规则中，rank 小的先合并
```

所以“统计次数决定训练时怎么选”这个直觉有道理，但 rank 不是次数压缩后的数字，也不是概率；它记录的是逐轮形成的规则顺序。每轮合并都会改变统计对象，不能当成一次统计后给所有最终 Token 排序。

也没有“先学完所有双字符，再学所有三字符”的长度分层。形成 `AB + CD → ABCD` 前需要先有 `AB` 与 `CD`，但不需要先形成所有其他双字符 Token。

🟡 上面解释的是标准 BPE 训练原理。本次核验了发布后的配置、规则与输出，没有原始训练语料、频数和训练日志，不能断言括号组合在原始语料里具体出现多少次。

## 6. 当前结论与后续边界

- 词表解决编号映射；合并规则解决相邻片段如何逐步组合。
- 编码时比较合并 rank，不重新统计输入中的概率或训练频数。
- 模型预测下一个 Token 的概率属于模型计算，和 Token ID、合并 rank 是不同概念。
- 后续再单独观察 `add_special_tokens=False/True`；本笔记不展开 Chat Template 或 Self-Attention。
