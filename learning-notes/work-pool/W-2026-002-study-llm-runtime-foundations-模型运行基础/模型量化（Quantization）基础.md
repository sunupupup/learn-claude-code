# 模型量化（Quantization）基础

## 先记住：权重量化影响什么

**权重量化：用更少的 bit 保存同一模型的权重参数。** 正常使用支持对应量化格式的推理框架时：

| 影响对象 | 最关心的结论 |
|---|---|
| 权重文件（checkpoint 中的 tensor 数据） | 文件更小，磁盘占用、下载和传输量减少。 |
| 权重显存 | 权重加载到 GPU 后占用更少显存；模型参数个数没有变。 |
| 权重读取量与推理速度 | **同样一批权重，位数越低，要从显存搬到计算单元的数据越少。读取权重是瓶颈时，更容易加速。** |
| 输出效果 | 数值变成近似值，可能影响回答质量；具体损失取决于模型、任务和量化方案，没有统一的位数—准确率对应表。 |

**显存容量管「装多少」，显存带宽管「每秒搬多少」，算力管「算多快」。** 权重量化不会提高显存带宽，而是减少需要搬的数据：读取耗时 ≈ 读取数据量 ÷ 实际可用带宽。整体推理还有计算和缓存读取等耗时，因此 16bit → 4bit 不代表整体快四倍。

**KV Cache 是推理算出的 K、V 缓存，也占显存，但有自己单独的量化。**「4bit 模型」通常指权重；完全可以是 **4bit 权重 + 16bit KV Cache**。只量化权重不会自动缩小缓存。

同一模型的权重从 16bit → 8bit，**权重数值本身的文件大小和显存占用减半**，另有量化辅助数据开销；总运行显存还包含 KV Cache、中间计算等，不能直接说总显存减半。

## 量化是什么

模型的权重（weight）本质上就是一堆数字（浮点数）。
量化就是：**用更少的 bit 来存储这些数字**，从而减少显存占用、加快推理速度，代价是精度有一定损失。

类比：
- 原始模型像一张用高清相机拍的照片（每个像素 32bit 色深）
- 量化后的模型像把照片压缩成 JPEG（色彩精度降低，但文件小很多，肉眼看差别不大）

## 学习确认：量化到底量化什么？

我的理解：**量化的参数，应该是神经网络矩阵里的参数，比如 Wq、Wk、Wv。**

🟢 对于「权重量化」，这个理解正确。`Wq、Wk、Wv` 是注意力层中训练得到的**权重矩阵（weight matrices）**。采用输入在左的记法，数据流可以写成：

```text
输入表示 X × Wq → Q（Query，查询）
输入表示 X × Wk → K（Key，键）
输入表示 X × Wv → V（Value，值）
```

量化 `Wq`，就是把矩阵中的权重数值改用较低位数的编码表示。**矩阵的逻辑行数、列数通常不变，变化的是元素的数值表示**；实际存储还可能包含缩放因子等辅助数据。

权重量化不限于这三个矩阵，还可能涉及注意力输出矩阵 `Wo`、前馈网络（FFN，Feed-Forward Network）的权重等。哪些矩阵量化、哪些保留高精度，取决于具体方案。

### 术语速查：权重、激活值与 KV Cache

以下都是模型推理计算层的概念，但量化对象不同：

| 量化对象 | 是什么 | 是否随输入变化 |
|---|---|---|
| 权重（Weight），如 `Wq、Wk、Wv` | 训练得到的模型参数 | 通常在推理时固定 |
| 激活值（Activation），如 `X、Q、K、V` | 处理输入时产生的中间数值 | 是 |
| KV Cache（键值缓存） | 为后续生成保留的历史 K、V 结果 | 随处理和生成的 token 更新 |

**量化 `Wk、Wv` 与量化 KV Cache 是两件事**：前者压缩计算用的参数，后者压缩已经算出并缓存起来的结果。权重使用低位数表示，不意味着算出的激活值或缓存也自动采用相同位数。

因此，看到「模型 4bit」时，需要确认它指哪些权重，以及激活值、KV Cache 分别采用什么格式，不能理解成所有数值都是 4bit。

与前面聊天中的信息量讨论对齐：如果用「n 维向量的可能状态数」解释**权重量化**，这个向量应理解为一组权重数值；编码器输出向量属于中间表示，不能直接把它的状态数换算成权重量化后的模型准确率。

## 常见的数字格式

### 浮点格式（Floating Point）

浮点数的存储结构：`符号位 + 指数位 + 尾数位`

```
FP32 的一个数字长这样（32 bit）：
┌───┬──────────┬───────────────────────┐
│ 1 │ 8 位指数  │     23 位尾数          │
└───┴──────────┴───────────────────────┘
 符号   决定数量级    决定小数精度

FP16 的一个数字长这样（16 bit）：
┌───┬──────┬────────────┐
│ 1 │ 5 位  │  10 位尾数  │
└───┴──────┴────────────┘
 符号  指数    有效数字 ~3位（FP32 是 ~7位）
```

- **符号位**（1 bit）：正数还是负数
- **指数位**：决定数字的"数量级"，类似科学计数法的 10^n 部分。指数位越多，能表示的范围越大（比如能表示非常大或非常小的数）
- **尾数位**：决定小数精度，类似科学计数法的有效数字部分。尾数位越多，小数越精确

具体对比：

| 格式 | 总 bit | 符号 | 指数 | 尾数 | 精度感受 |
|------|--------|------|------|------|---------|
| FP32 | 32 | 1 | 8 | 23 | 小数点后 ~7 位有效数字 |
| BF16 | 16 | 1 | 8 | 7 | 范围和 FP32 一样大，但精度低（~2-3 位有效数字） |
| FP16 | 16 | 1 | 5 | 10 | 精度比 BF16 好一点，但范围小（容易溢出） |

**注意：指数位从 8 → 5 不是"少了一点"，而是范围暴跌。** 因为指数位本身就代表"2 的几次方"，少 1 bit 范围就砍一半的幂次：

| 格式 | 指数位 | 能表示的数量级范围 | 最大值约 |
|------|--------|-------------------|---------|
| FP32 | 8 位 | 10^(-38) ~ 10^(38) | ~3.4 × 10^38 |
| FP16 | 5 位 | 10^(-5) ~ 10^(5) | ~65504 |

FP16 最大只能表示到约 65504，再大就溢出变成 inf（无穷大）。范围从 ±10^38 缩到 ±10^5，差了 33 个数量级。

这就是 **BF16 被发明出来的原因**：训练大模型时梯度可能突然变得很大或很小，数值范围比小数精度更重要。BF16 保留了 FP32 的 8 位指数（范围不缩），只砍尾数（精度差一点），所以训练时常用 BF16 而不是 FP16。

### 整数格式（Integer Quantization）

整数量化的思路完全不同：不再用浮点表示，而是把一组权重的取值范围**均匀切成 N 档**。

```
假设一组权重的范围是 [-1.0, 1.0]：

INT8（8 bit = 256 档）：
-1.0 ────|────|────|────|────|──── 1.0
     每档间距 ≈ 0.0078（还算细）

INT4（4 bit = 16 档）：
-1.0 ──|──|──|──|──|──|── 1.0
     每档间距 ≈ 0.133（很粗）
```

原本 0.12 和 0.13 这两个不同的权重：
- 在 INT8 里可能分别映射到第 143 档和第 144 档 → 还能区分
- 在 INT4 里可能都映射到第 8 档 → 区别被抹平了

这就是量化精度损失的来源：**不是小数位不够，而是可选的"刻度"太少，不同的值被迫归到同一档**。

## 量化的显存收益

以 Llama 3 70B（700 亿参数）为例：

| 格式 | 每个参数占用 | 模型总大小 | 所需显存 |
|------|------------|-----------|---------|
| FP32 | 4 字节 | ~280 GB | 至少 280 GB |
| FP16 / BF16 | 2 字节 | ~140 GB | 至少 140 GB |
| INT8 | 1 字节 | ~70 GB | 至少 70 GB |
| INT4 | 0.5 字节 | ~35 GB | 至少 35 GB |

INT4 量化后，70B 模型的权重理论占用可能下降到约 35 GB，但实际部署还要给量化元数据、KV Cache、中间激活和推理框架预留空间，不能仅凭权重大小断定一张显卡一定能跑。

## 量化对推理效果的影响

位宽越低，可表示的数值档位越少，量化误差的风险通常越大。但不存在通用的“FP16 99.5 分、INT4 95 分”或“某个位宽一定可感知”的结论。

同样是 4 bit，不同模型、量化算法、校准数据、任务和硬件内核都可能得到不同结果。因此选择量化版本时，需要把高精度版本作为基线，实际比较：

- 模型质量：困惑度（Perplexity）、任务评测和人工样例；
- 资源：权重大小、峰值显存和可支持的上下文长度；
- 性能：首 Token 延迟、生成速度和吞吐量。

“小模型一定比大模型更怕量化”也不是固定规律，只能作为需要实验验证的假设。

训练通常比纯推理更依赖数值稳定性，因为还要保存和计算梯度、优化器状态等；现代训练会结合 BF16、FP32 累积或混合精度。具体选择取决于硬件、训练方法和模型，不能简化成训练一律使用某一种精度。

## 量化发生在什么阶段

两种主要路线：

### PTQ —— 训练后量化（Post-Training Quantization）

```
训练（FP32/BF16）→ 保存原始权重 → 量化工具压缩 → 部署推理
                                    ↑
                            这一步做量化
```

先正常训练完模型，然后用量化工具把权重从高精度压缩到低精度。模型架构不变，只是数字的存储格式变了。

这是目前最常用的方式。优点是简单 —— 拿到别人训好的模型就能直接量化；缺点是模型从来没见过量化后的"粗糙版自己"，如果量化太狠可能效果掉得多。

### QAT —— 量化感知训练（Quantization-Aware Training）

```
训练时就模拟量化误差 → 模型学会适应低精度 → 保存 → 部署
```

训练过程中就告诉模型"你以后要被量化"，让模型提前学会在低精度下也能正常工作。相当于戴着沙袋跑步训练，比赛时脱了沙袋反而跑得更稳。

QAT 让模型在训练或微调时适应量化误差，在某些模型和位宽上能比 PTQ 保留更多质量，但并不保证总是更好，而且训练成本更高。

### 实际选择

| | PTQ | QAT |
|---|---|---|
| 成本 | 不重新训练；耗时取决于模型、算法和校准过程 | 需要训练或微调，成本通常更高 |
| 效果 | 取决于模型、位宽、算法和校准数据 | 某些场景下可提高低位宽鲁棒性，仍需评测 |
| 适用场景 | 对已训练模型做部署压缩 | 有训练能力，且 PTQ 结果不能满足目标 |

## 不是所有层都一样量化

模型的不同张量可能对量化误差有不同敏感度，但不能给 Embedding、Attention、FFN、LM Head 排一个适用于所有模型的固定顺序。量化工具会按方法选择分组方式、缩放参数或混合精度；哪些张量保留较高精度，应以具体格式说明和评测结果为准。

例如 llama.cpp 的 K-quant 中，`Q4_K_S` 与 `Q4_K_M` 会采用不同的量化组合；`M` 版本通常稍大，并为部分张量使用更高精度。标签含义应以所用 llama.cpp 版本的说明为准。

## 常见量化方案

| 名词 | 全称 | 核心思路 | 常见场景 |
|------|------|---------|---------|
| GGUF | 一种模型文件/容器格式，不是量化算法 | 可保存模型张量和元数据，也可装载多种量化类型 | llama.cpp 生态、本地推理 |
| GPTQ | GPT Quantization | 使用校准数据和二阶近似降低权重量化误差的训练后量化方法 | GPU 推理 |
| AWQ | Activation-aware Weight Quantization | 观察哪些权重对激活值影响大，重要的权重保留更高精度 | vLLM 等 GPU 推理框架 |
| bitsandbytes | - | HuggingFace 集成的量化库，使用简单 | 用 transformers 库加载模型时 |
| EXL2 | ExLlamaV2 format | 逐层自适应精度，可以指定目标 bpw（bits per weight） | ExLlamaV2 推理框架 |

### GGUF 文件名怎么读

```
llama-3-70b-Q4_K_M.gguf
│          │ │ │ │
│          │ │ │ └── M = 这一 K-quant 变体的标签
│          │ │ └──── K = K-quant 类型
│          │ └────── 4 = 主要权重量化到约 4 bit 档位
│          └──────── Q = Quantized
└─────────────────── 模型名和参数量
```

GGUF 文件还可能出现 `Q2_K`、`Q3_K_M`、`Q4_K_S`、`Q4_K_M`、`Q5_K_M`、`Q6_K`、`Q8_0` 等标签。通常更高位宽会带来更大的文件和更低的量化误差风险，但实际 bpw（bits per weight，每个权重平均占多少 bit）、文件大小、速度与模型质量取决于模型结构和量化实现，不能只凭标签给出通用分数。

## 实际部署怎么选

```
先确定推理框架、硬件、模型和目标上下文长度
│
├─ BF16 / FP16 能满足容量和性能目标
│   └─ 先作为质量基线
│
├─ 权重或 KV Cache 放不下
│   └─ 选择框架和硬件支持的 8 bit / 4 bit 候选版本
│
└─ 对候选版本做同一组评测
    └─ 同时比较质量、峰值显存、上下文长度、延迟和吞吐量
```

部署时应把“较大模型 + 激进量化”和“较小模型 + 较高精度”都当作候选方案，用目标任务实测；不能只根据参数量和位宽断定哪一个效果更好。

## 一句话总结

量化通过更低精度表示权重或激活来减少存储和显存，并可能在硬件与推理内核支持时提高速度；它同时引入近似误差。最终方案必须结合模型、框架、硬件和目标任务评测，不能从位宽直接推出固定的质量损失。

参考：[Hugging Face Transformers：Quantization overview](https://huggingface.co/docs/transformers/en/quantization/overview)、[llama.cpp：quantize 工具说明](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md)。
