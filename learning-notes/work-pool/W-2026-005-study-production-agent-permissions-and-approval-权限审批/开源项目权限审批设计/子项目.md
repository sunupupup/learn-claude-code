# 开源项目权限审批设计：候选、比较与学习路径

> 本文是选型和阅读导航，不表示已经部署或完成源码分析。官方仓库/维护者资料已于 **2026-09-26** 做初筛。GitHub 仓库元数据中的默认分支推送时间、latest release tag/date 和 SPDX license 都已只读核验；开始源码学习前仍要固定 tag/commit，并复核该版本实际 LICENSE、依赖和对应版本文档。

## 比较矩阵

| 分类 / 项目 | 主要解决层 | 本章值得观察的机制 | 开源/商业边界 | 初学难度与推荐顺序 |
| --- | --- | --- | --- | --- |
| Agent 框架：OpenAI Agents SDK | Harness / 单次或多 Agent Run | Tool approval interruption、RunState 序列化、批准后恢复 | Python/TS SDK 源码开源；平台 API/托管能力按各自条款另看 | 低中；**主项目首选 1** |
| Agent 框架：LangGraph | Harness / 有状态图 Runtime | interrupt、checkpointer、恢复时节点重跑 | LangGraph 库开源；LangGraph Platform/托管服务是独立产品层 | 中；对照 2 |
| Agent 框架：PydanticAI | Harness / Python Agent SDK | deferred tool、ApprovalRequired、客户端历史信任边界 | MIT SDK 开源；托管服务或附加产品另核条款 | 低中；对照 3 |
| 工作流：Temporal | 分布式 Workflow Runtime | 等待人类信号、持久历史、计时器和失败恢复 | Temporal Server/SDK 开源；Temporal Cloud 商业托管 | 中高；理解长审批再读 |
| 策略引擎：OPA | Policy Decision Point | Rego、输入上下文、服务如何调用 PDP 并落实决定 | OPA 核心开源；厂商托管控制面/企业服务分开核 | 中；策略路线 A |
| 策略语言/引擎：Cedar | 应用内/服务端授权 PDP | principal/action/resource/context、schema 校验、策略测试/分析 | Cedar SDK、语言与文档开源；托管授权服务另核 | 中；策略路线 B、适合和 OPA 窄对照 |
| 关系授权：OpenFGA | Authorization Service / ReBAC | authorization model、tuples、Check API、模型测试 | Apache-2.0 开源授权引擎；官方云托管服务另属服务产品 | 中；关系授权首选 |
| 关系授权：SpiceDB | Authorization Service / ReBAC | schema、关系图、权限检查与一致性边界 | Apache-2.0 开源；Authzed Cloud/企业服务属商业托管 | 中高；作为 OpenFGA 对照 |
| 身份服务：Keycloak | Identity Provider / OAuth2、OIDC、用户会话 | 登录身份与服务端 token；Authorization Services 的 PDP/PEP/PAP/PIP | Keycloak Server Apache-2.0；Red Hat 产品支持/发行另核 | 中；解释认证与授权分界 |
| 工作负载身份：SPIRE | Runtime/Infra 身份证明与凭证签发 | workload attestation、SVID、短期身份和轮换 | CNCF 开源 SPIRE/SPIFFE，Apache-2.0；托管能力独立 | 高；建立 Agent/service 身份时读 |
| 隔离 Runtime：gVisor | OS / 执行器隔离 | 用户态应用内核、runsc、host syscall 与文件代理边界 | Apache-2.0 为主（个别文件有其他声明）；Google Cloud 托管产品另核 | 高；接 W-030，授权并不替代沙箱 |
| 隔离 Runtime：Kata Containers | OS / microVM 容器 Runtime | OCI/CRI 到 VM、guest kernel、运行时取舍 | 开源 Apache-2.0；云托管形态另核 | 高；和 gVisor 比较边界 |

## 为什么覆盖这些路线

审批框架负责“如何暂停并继续 Agent 工作流”；策略引擎负责“规则如何判断”；关系授权服务负责“用户和资源之间有什么权限关系”；Keycloak/SPIRE 提供不同类型的身份；Temporal 解决长时间等待和崩溃恢复；gVisor/Kata 把授权后的执行限定在操作系统隔离边界内。这些是能组合的系统层，不是同一类产品的高低档。

12 个候选按不同职责选取，每类只留有代表性的 1–3 个，避免把框架名、授权库和沙箱当作互相替代品。OpenFGA 与 SpiceDB、OPA 与 Cedar、gVisor 与 Kata 是窄对照组。

## 推荐主项目与窄对照

- **默认主项目：OpenAI Agents SDK Python**。初学者容易看到“工具调用 → interruption → 保持服务端 RunState → reviewer 决定 → 恢复”；Context7 可访问官方 human-in-the-loop 指南。必须同时读文档的信任边界部分：RunState 序列化状态包含待处理工具参数/审批，不能从不可信客户端直接反序列化。
- **窄对照建议：Cedar**。将审批流程与 `principal/action/resource/context` 的策略决定分开，回答“人批准了，工具还需要什么授权检查？”
- 若重点是多小时审批/重启恢复，把 Temporal 作为一个后续窄对照；若重点是与 W-030 沙箱结合，选择 gVisor 或 Kata 其中之一，不同时搭两个复杂环境。
- 有明确关系型资源树需求时，再选 OpenFGA 或 SpiceDB 中一个。Keycloak 解决登录/令牌身份，不能替代 Agent 每个副作用点的最终授权检查。

## 初学者学习路线

1. 先回看 s15 与本章图谱，手动画出 Tool Call、Policy、Approval、Executor 的边界；
2. 阅读 OpenAI Agents SDK 的 Human-in-the-loop guide 和一个 server-side approval example，确定 `RunState` 如何保存、批准和恢复；先只做文档/静态源码阅读；
3. 用一个“读取非敏感记录 / 删除生产记录”的小案例填写主体、动作、资源、条件，并将策略结果分成 `allow / ask / deny`；
4. 读 Cedar 教程中的授权请求及策略语法，比较“策略判定”和“用户审批”如何组合；
5. 按兴趣只选一个专项：OpenFGA（资源关系）、SPIRE（工作负载身份）、Temporal（长审批恢复）、gVisor/Kata（执行隔离）；
6. 用户明确要运行后，才设计本地、假数据、无真实外部写入的可复现实验和一个失败对照。
