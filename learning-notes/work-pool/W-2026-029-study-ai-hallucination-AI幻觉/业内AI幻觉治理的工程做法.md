# 业内 AI 幻觉治理的工程做法

核验日期：2026-09-20。承接用户“业内有啥解决办法么”的追问；通过 Exa 查阅官方公开资料，并通过 Context7 核对 Bedrock 文档。证据为厂商文档，不是本仓库实测，也不用于推断全行业采用比例。

## 主要结论

公开产品已经将“提供资料、生成、核验与处理失败”中的部分环节做成服务。用户提出的“附依据 + 二次分析”对应其中的依据核验环节；完整系统还需要资料治理、确定性计算、信息不足时的处理，以及评测。

**Grounding（让输出有证据依据，应用层）**是把回答约束在提供的资料上；**Groundedness checking（依据一致性检查，应用校验层）**是检查已经生成的结论是否被资料支持。两者都不自动证明资料本身符合现实。

## 已有产品能力

| 实例 | 公开能力 | 适用范围与局限 |
| --- | --- | --- |
| Microsoft Azure AI Content Safety | Groundedness detection 检查输出与来源是否一致；提供检测模式，纠正能力在所查概念页标为 preview | 面向文本问答、总结等来源约束任务；纠正依据仍是输入资料，不能把错误来源自动变正确 |
| Google Cloud Check grounding | 接收候选答案和参考事实，返回整体支持分数及断言对应的来源；可返回断言级结果 | 检查给定事实是否完整支持断言；分数不是现实真值的保证，阈值需业务评测 |
| Amazon Bedrock Contextual grounding checks | 检查来源支持程度和回答相关性，可按阈值过滤 | 官方当前明确支持总结、改写和问答，并说明不支持 conversational QA/chatbot 用例；不能将该能力直接等同于任意多轮聊天保障 |
| Amazon Bedrock Automated Reasoning checks | 把自然语言内容对照已定义政策，以形式逻辑给出验证反馈 | 适用于可明确表达的规则；自然语言到逻辑的转换仍依赖模型，政策完整性和正确性需核验；返回验证反馈不等于应用已完成拦截或修复 |

上述是能力实例，不构成产品选型建议；语言、区域、配额、成本和上线状态应在实施时重新核验。

## 工程上怎样组合

1. **获取可信证据**：知识问答用内部或外部检索；实时状态用业务接口。维护版本、适用范围、访问权限和来源。
2. **按证据生成**：关键事实对应具体片段，事实与推测分开；资料缺失时允许澄清或保留结论。
3. **分工核验**：语义交给依据一致性检查器；金额、资格、库存、执行状态等尽可能用数据库、规则、计算程序或实际产物核验。
4. **处理不通过**：补充检索、删除无依据部分、重新生成后复查、说明不足或转人工；限定次数，不无限重试。
5. **评测和监控**：分别评测检索、生成和核验器。比较错误率、漏检、误报、回答覆盖率、误拒答率与延迟成本；记录必要证据，避免无边界保存敏感内容。

这是基于公开能力归纳的应用设计，不是所有厂商产品内部流程的断言。后训练承认未知的方向另见[研究笔记](教AI拒答、纠错与减少迎合的研究.md)，不能假设所有应用团队都会训练模型。

## 一个企业报销案例（教学构造）

问题：用户能报销多少？

系统先取得当前有效制度及用户有权访问的订单和资格信息，再由规则或程序计算上限；模型负责解释，解释中的关键结论关联条款与结果。最后检查是否误写数字、遗漏条件。

若缺少城市、日期或票据金额，应说明缺什么；若制度版本冲突，应先解决冲突。仅仅“引用了制度文档”不能替代这些步骤。

## 不应承诺的事

- RAG、第二个模型或引用检测不能保证消除全部幻觉。
- 形式化验证证明的是在给定规则、输入与正确转换前提下的关系，不是开放世界所有事实。
- 核验失败或服务超时不能当作通过；修正后的文本也应按要求重新核验。
- 降低随机性或保证 JSON 格式，不等于保证语义和事实正确。
