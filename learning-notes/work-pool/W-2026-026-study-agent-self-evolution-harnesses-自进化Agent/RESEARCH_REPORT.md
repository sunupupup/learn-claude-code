## 1. 先抓住核心：系统的哪部分在改变

这组研究中的共同问题是：**系统能否把执行反馈转化成可保留的变化，让后续任务做得更好？** 变化可以发生在模型之外，也可以发生在模型参数之内。

用一个工作模型理解：一次 Agent 行为由“模型参数 + 本次上下文 + 工具和控制程序 + 环境”共同决定。即使模型参数固定，改变后面三项也会改变结果。[Reflexion](https://arxiv.org/html/2303.11366)、[DGM](https://arxiv.org/html/2505.22954v3) 分别展示了记忆与代码层面的尝试；[SEAL](https://arxiv.org/abs/2506.10943) 则涉及权重更新。

因此先问四件事：**改什么、依据什么改、谁判定变好、变化怎样保留？** “反思了”“写入记忆了”“生成了一个新技能”只描述某个动作，不能单独证明质量提升。

| 情况 | 改变对象和层次 | 是否更新模型参数 | 怎样判定其含义 |
| --- | --- | --- | --- |
| 本次回答重新检查 | 当前输出/上下文，推理过程 | 通常不更新 | 是当前任务修正，不自动构成跨任务学习 |
| 保存与召回经验 | 外部记忆，应用数据层 | 不需要 | 有跨任务信息积累，仍需验证相关性与效果 |
| 优化 Prompt / Skill | 提示词、技能或策略，应用层 | 不需要 | 形成可复用行为变化，需在新任务上测试 |
| 修改 Harness | 控制循环、工具、工作流、上下文管理，执行层 | 不需要 | 运行程序变化，需测试兼容、行为和回滚 |
| 后训练 | 权重或适配参数，模型层 | 更新 | 数据与奖励影响模型本身，需训练和评测管线 |
| 模型与 Harness 协同 | 上述多个对象 | 视阶段而定 | 必须固定变量，拆开各部分贡献 |

这是一套阅读分类，不是必然逐级升级的行业标准。在线/离线、人工/自动、单候选/群体搜索也是独立维度：每天离线优化一次 Skill，同样可以构成改进流程。

## 2. 术语速查

| 术语 | 中文含义、层次与例子 | 相邻概念边界 |
| --- | --- | --- |
| Harness | Agent 外围执行与控制程序，执行层；如控制工具调用、保存状态、检查完成 | 与 LLM 模型参数分开；Runtime 更强调实际运行与生命周期 |
| Trajectory / Trace | 执行轨迹/追踪记录，观测层；包含可见动作、工具结果、产物、错误与耗时 | 不要求取得模型隐藏思维链，也不是把聊天全文永久保存 |
| Reflection | 反思，候选生成过程；分析某一步失败的可能原因 | 是假设来源，不是正确性证明 |
| Credit Assignment | 贡献/责任归因，学习与诊断层；定位失败来自检索还是工具参数 | 最终失败不代表最后一步就是根因 |
| Mutation / Candidate | 变异/候选，优化层；生成一份不同的 Prompt 或代码补丁 | 候选还不是已上线版本 |
| Evaluation / Eval | 评测，验证层；用任务集和判定规则测效果 | 单元测试只覆盖它声明的性质，不能代替业务评测 |
| Gate / Promotion | 门禁/晋级，发布层；允许通过检查的候选成为新版本 | 模型建议与程序授权分开 |
| Pareto frontier | 帕累托前沿，搜索层；保留在不同任务上各有优势的候选 | 不只保留平均分最高的一份，仍需最终选型规则 |
| SFT / RL | 监督微调 / 强化学习，模型训练层；分别从示例或奖励学习 | 自然语言“反思反馈”不意味着执行了梯度训练 |
| Holdout / Generalization | 留出数据 / 泛化，评测层；未参与修改的新任务及其效果 | 反复看着同一测试集调参，就不再是独立最终测试 |

## 3. 主线一：从经验中学习，模型权重不变

### 3.1 Reflexion：把失败反馈写成下次可读的经验

🟢 论文把过程拆为行动者、评估者和反思组件。执行后接收反馈，把反思文字存入情景记忆，再交给后续尝试。它明确以语言反馈而非权重更新实现适应；记忆容量有界，反馈既可来自环境，也可来自模型或启发式规则。[原始论文](https://arxiv.org/html/2303.11366)

🟡 实现映射：记录失败步骤及证据 → 生成“在何种条件下，应改用何种做法”的经验 → 下次相关任务召回。经验最好同时带来源、适用范围和反例，避免把偶然失败写成全局禁令。

边界：后一次重试成功，不足以证明在完全不同的新任务上学会了通用方法。原论文也没有提供“反思必定正确”的保证。

### 3.2 Voyager：经验变成可执行技能库

🟢 Voyager 在 Minecraft 中结合自动课程、可执行代码技能库与迭代提示。环境反馈、执行错误和验证结果帮助修改程序；完成任务的程序被保存，并按描述进行检索复用。底层模型通过黑盒调用使用，不要求参数微调。[论文 v2](https://arxiv.org/html/2305.16291v2)

🟡 学习价值：理解“记住我做过什么”与“保存下次可以调用的做法”的区别。可以迁移的是“技能提出—验证—入库—检索—组合”思路，不能直接把 Minecraft 中的指标当作办公 Agent 的收益。

### 3.3 ACE：把经验维护为结构化策略手册

🟢 ACE（Agentic Context Engineering，上下文策略演化）将生成、反思、整理分开。经验以条目表示，含标识和帮助/有害计数，通过增量修改与确定性合并更新上下文，并进行去重整理。其动机之一是避免每轮整篇重写导致细节被压缩丢失。[论文 v3](https://arxiv.org/html/2510.04618v3)

🟡 实现映射：对经验做新增、修订、停用，而不是让 LLM 每次重写整本手册。条目增多之后仍需处理召回、冲突、预算和过期。论文提出的详细上下文策略有适用场景，不等于所有任务都应使用更长提示词。

## 4. 主线二：把策略改进做成显式搜索

### 4.1 GEPA：反思负责提议，评测负责筛选

🟢 GEPA 将执行轨迹中的自然语言反馈用于提出提示词修改，并在候选之间进行搜索，保留不同任务上有优势的候选，尝试合并互补经验。[论文](https://arxiv.org/html/2507.19457)

直观过程：

```text
固定基线与开发任务
  → 执行并保留错误反馈
  → 从候选池选一个父版本
  → 根据轨迹提出局部修改
  → 小批任务初筛，再做验证集评测
  → 更新候选池
  → 预算耗尽后选择候选
  → 用未参与搜索的测试集作最终检查
```

🟢 当前官方库还提供可对文本化产物执行优化的接口，范围可包括代码和配置；因此“GEPA 只能改提示词”也不准确。必须区分原论文的主要实验、独立 GEPA 库、DSPy 的具体集成路径。[官方快速入门](https://gepa-ai.github.io/gepa/guides/quickstart/)

🟡 工程上要准备四种东西：明确可修改的产物、能执行候选的适配器、返回分数及诊断反馈的评测器、数据划分与预算。API 帮助组织搜索，不能替你定义业务正确性。所谓“语义梯度”是文字指导修改的比喻，不是对提示词字符串做数值反向传播。

## 5. 主线三：修改执行程序与 Harness

### 5.1 Darwin Gödel Machine（DGM）

🟢 DGM 在固定基础模型下修改 Coding Agent 自身代码，用编码任务评估新版本，维护多版本档案并继续搜索。保留暂时非最优的候选，是为了探索可能成为后续改进基础的路径。它采用经验评测，并未提供理论 Gödel Machine 所要求的收益形式证明，也未在该研究中训练新的基础模型。[论文 v3](https://arxiv.org/html/2505.22954v3)

🟡 实现映射：从档案选父版本 → 独立目录生成代码补丁 → 隔离执行 → 测试与任务评测 → 记录谱系、结果和成本 → 决定哪些候选继续探索、哪些允许发布。**保留作研究候选**与**批准投入使用**应分开。

论文的编码基准结果属于具体模型、搜索预算与评测划分下的结果，不证明无限改进；也不能把训练搜索期间反复使用的任务当作完全独立的新任务。

### 5.2 Self-Harness（2026-06）

🟢 核心流程是失败模式挖掘、针对性 Harness 修改、回归测试后接受。本次可确认的 arXiv v1 在 Terminal-Bench-2.0 上报告三个模型的留出任务提升。[v1 摘要](https://arxiv.org/abs/2606.09498v1)

**版本差异：**搜索中的 PDF 摘录出现扩大到多个基准的描述，而摘要页及所读 HTML 对应较窄实验。本报告采用明确的 v1 描述，不拼接不同快照的指标。

### 5.3 HarnessEvolve（2026-09）

🟢 论文将执行、评估、优化和门禁分离；用提供正确答案后生成并验证的参考轨迹，辅助比较失败路径与定位错误；候选还需经过数据泄漏/上下文膨胀检查，以及当前批次和此前批次的性能检查，最后在验证集选择版本。[论文 v1](https://arxiv.org/html/2609.00829v1)

🟡 值得借鉴的是“失败归因 + 历史能力回归 + 独立版本选择”。但参考轨迹依赖可信答案和轨迹验证，开放式任务未必具备这些条件；多个 LLM 角色也不自动形成权限隔离。其有效性仍是论文场景内的作者报告。

### 5.4 HarnessDev（2026-09）：对自进化能力的反向检验

🟢 该基准把“创建可运行 Harness”和“进一步演化 Harness”分开评测。作者观察到部分改进不稳定，向留出任务和其他执行模型迁移有限；生成的 Harness 在部分领域仍落后于成熟人工参考实现。[论文 v1](https://arxiv.org/html/2609.01437v1)

这与前面报告提升的论文不必矛盾：初始基线、任务域、执行模型、可改范围、反馈与预算不同。不能据单篇正面或负面结果宣布整个方向“已解决”或“无效”。

### 5.5 JIT-Agent（2026-08，9 月有修订）

🟢 它研究训练一个专门生成 Harness 的模型，根据当前任务组合记忆、规划、行动和能力模块，而非始终复用一套提前调好的执行结构。[论文](https://arxiv.org/html/2608.25593)、[版本记录](https://arxiv.org/abs/2608.25593)

🟡 可把它理解为“学习如何配置执行系统”的方向。生成 Harness 的模型训练与被包裹执行的任务模型是两个角色；不能由此推断每次用户交互都在训练任务模型。本轮只读机制，未审计代码或复现指标。

## 6. 主线四：真的更新模型参数

🟢 MIT 的 SEAL（Self-Adapting Language Models）让模型生成用于微调的数据或更新指令，再以更新后模型的下游效果训练这种生成能力。因此它与纯记忆、提示词优化有本质区别：有实际参数更新。[论文](https://arxiv.org/abs/2506.10943)

🟢 Agent Lightning 研究将 Agent 执行与训练解耦，把交互轨迹接入训练；2026 年后续工作进一步讨论让实际 Harness 参与强化学习的挑战。[初始论文](https://arxiv.org/abs/2508.03680)、[2026 后续论文](https://arxiv.org/html/2608.17528)

🟡 对应用开发者，这意味着另一套工程成本：准备高质量轨迹和奖励、使用可训练模型、保存训练版本、处理推理部署和能力回归。调用闭源模型 API 并保存记忆，并不会自动获得这种权重更新能力。

注意同名缩写：2026 年还有名为 SEAL 的 Agent—环境协同研究，与上面的 MIT 工作不是同一篇。本报告中的 SEAL 限指 Self-Adapting Language Models。

🟡 学习顺序应由机制决定：先理解外部经验与候选评测，再看程序自修改。DeepSeek/Cordis 适合作为“怎样承载可变能力”的基础设施对照，FrontierAgent/Apodex 适合作为执行—训练关系对照，不再仅靠两者覆盖全部主题。

## 8. 实现方案：推荐先理解受控的离线 Skill 优化

以下是**教学设计建议，未实现、未验证**。目标是理解一套最小端到端机制，而非直接部署自治产品。

### 8.1 示例任务与基线

场景：一个只读的项目排障助手，读取固定日志与文档，输出诊断结论和证据。先比较固定规则、固定 Prompt 和固定 Agent；如果规则已能稳定解决问题，就没有必要用自进化替代。

允许变化的对象只是一份诊断 Skill。模型、工具、权限、数据和预算先固定，避免无法判断收益来自哪里。

### 8.2 两个循环与可信边界

```text
任务执行循环：
用户任务 → 加载已发布版本 → 执行/读工具 → 检查结果 → 输出及反馈
                                  │
                           保存必要的执行证据
                                  ↓
离线改进循环：
失败聚类 → 候选规则/Skill → 隔离评测 → 接受/拒绝 → 新版本登记
                                               │
                                        下一次任务加载
```

🟡 执行者、候选生成器与评测器首先是职责，不必实现成多个长期运行的 Agent。可以先用普通函数、脚本及少量模型调用串起流程。规则执行、预算、文件权限和发布状态由代码控制。

### 8.3 需要保存的数据

| 对象 | 建议字段 | 为什么需要 |
| --- | --- | --- |
| 经验记录 | 任务类型、可见动作、结果、错误证据、模型/Skill 版本 | 分清模型判断错、工具坏或输入缺失 |
| 候选 | 父版本、补丁、变化范围、原因、适用条件、内容哈希 | 能追踪变化并确认评测的是哪份产物 |
| 评测 | 数据集版本、候选哈希、各类分数、错误、延迟、Token 与费用 | 避免仅报告一个总分 |
| 发布记录 | 生效版本、上个版本、启用时间、拒绝原因、回滚事件 | 能解释线上任务用了什么，也能恢复 |

日志默认脱敏；用户偏好与通用技能应分开作用域。错误文本只能作为诊断数据，不获得修改权限策略的权力。

### 8.4 候选从提出到上线

1. 分析开发任务中的失败，提出有边界的修改。
2. 检查修改仅涉及允许的文件和字段，拒绝绕过检查、硬编码答案或扩大权限的补丁。
3. 在干净执行器中加载**最终要保存的产物**，而非只测试优化器内存中的对象。
4. 在验证任务中比较基线和候选，包含既往成功用例、边界任务和攻击性输入。
5. 成功率、严重错误、成本和延迟分别达标后再登记候选。效果不确定时保留旧版。
6. 发布前做独立最终测试；若根据结果继续调参，应承认该测试已成为开发信息，并补充新测试。
7. 初期通过人工审查启用，任务运行时固定版本；发现回归后恢复旧版。

状态可表达为：`proposed → evaluated → accepted/rejected → released → rolled_back`。评测超时是 `inconclusive`（证据不足），不算通过；并发发布须检查父版本仍为当前版，避免覆盖另一候选的改进。

### 8.5 最小实验及反例

计划用几十条人工检查过的案例把流程跑通，按任务族划分开发、验证和最终测试数据；此规模只适合演示，不足以证明生产统计显著性。

- 基线：固定诊断 Skill。
- 候选 A：遇到某类依赖错误时，先核对版本和日志证据，再给原因。
- 候选 B：遇到错误就一律归因于网络。
- 对照：相同模型、输入、工具和执行预算下分别运行；包含非网络故障与无法确定原因的案例。
- 验收：A 是否在留出案例真正改善，B 是否因其他任务退化而被拒绝；保存拒绝原因。
- 额外故障：评测器超时、候选文件丢失、加载版本不一致、恢复旧版。确认这些情况不会被报告为进化成功。

### 8.6 整个生命周期的范围

本轮均未实现。后续最小实验应明确覆盖业务指标、模型输出、控制流与停止条件、只读工具、证据来源、上下文预算、经验作用域、评测、日志、安全、可靠性与成本、版本恢复及用户结果说明。暂不引入在线多租户服务、复杂向量库、多 Agent 编排和权重训练，因为它们不是验证这个闭环的必要条件；凭据与实际模型预算在实验开始时确认。

## 9. 如何防止“看起来进化了”

| 容易误判的情况 | 建议检查 |
| --- | --- |
| 模型说“我总结了经验” | 后续任务是否实际加载经验，结果是否改善 |
| 优化器中分数提高 | 导出并重新加载同一产物后是否仍提高 |
| 针对一批题不断涨分 | 对未参与优化的任务族是否有效 |
| 平均分上涨 | 是否牺牲重要任务、安全边界或尾部延迟 |
| 多跑了很多轮之后成功 | 固定总预算后是否仍优于简单重试基线 |
| Agent 自己打分认为更好 | 对照可执行检查或人工标注，测试评分偏差 |
| 新版本效果变差 | 能否定位到具体修改，切回完整旧版本 |
| 没训练权重所以不会遗忘 | 提示词、记忆与工具变化同样可能破坏旧能力 |

早期研究发现，无外部反馈的内在自我纠错在其测试条件下可能无效甚至退化；不能把它泛化为所有新模型都无法纠错，但它提示我们别把反思本身当作可靠评测。[原论文 v2](https://arxiv.org/html/2310.01798v2)

推荐分别记录：任务成功率、严重错误率、旧任务回归、可追踪的证据覆盖、工具违规、执行费用与延迟、离线优化总成本。重复实验与按任务族留出有助于发现随机波动、样例泄漏及相关样本导致的虚假收益。

## 11. 证据限制与后续核验

- 原论文支持“作者提出什么、报告什么结果”，不等于本轮复现或独立生产验证。
- Hermes 两个文件固定到提交；其他动态仓库文档只标读取日期，不声称完成固定版本源码审计。
- Self-Harness 检索快照存在版本差异，采用 v1 范围；GEPA 的库功能与原始论文范围分开说明。
- 未完整验证各项目安装条件、许可证传递、性能预算与 Windows 兼容性，因此本报告不提供即装即用的推荐。
- 本轮未衡量社交热度，也没有“覆盖所有项目”的保证；选取的是能解释不同机制与局限的代表样本。
- 原任务卡中的微信文章不是本轮技术结论的证据，未读取或转述其正文。

## 反思

1. **调查与决策的不确定性：**最初任务卡主要围绕可组合 Harness 与模型协同，容易把“能改”当作“会变好”。本轮加入独立评测研究与源码反例，但各路线在用户具体任务上的收益仍未知；真正选型前应固定版本、重新加载最终产物，并进行同预算对照。
2. **值得补足的考量与学习目标：**重点不仅是“怎样自动写 Skill”，还包括“评测的是不是最终上线那份东西、有没有看过测试答案、旧能力有没有退化”。先掌握数据划分、版本与证据关联，再实现一个能明确拒绝坏候选的最小闭环。
