# DeepSeek 插件化与 RSI 的关系

## 用户的直观理解

“感觉会是一种 RSI 的基础框架了啊，除了模型没法进化，他的这种插件形式，所有内容都能去优化了。”

🟢 **常见场景下成立的理解：**插件化把模型之外的许多能力变成可替换、可组合的组件，扩大了自动改进可以作用的范围，因此可以作为构建 RSI 的基础设施。

这里“适合作为 RSI 基础设施”是工程判断；并不是说已验证 DeepSeek Harness 具有持续提升改进能力的完整闭环。

## 2026-09-23 文档核验

- [官方介绍](https://www.deepseek.com/harness/en/)将模型接入、工具、技能、会话、沙箱、存储、循环、调度与 UI 列为插件化能力；Creator 模式提供运行时检查与插件实验。
- [Extensions 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/extensions/README.md)描述面向 Agent 的运行时检查、动态包定义、运行及撤回能力。
- 通过 Context7 查询 `/deepseek-ai/deepseek-harness`，取得[扩展子系统文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/extensions.zh.md)与[生命周期文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-tutorial/02-lifecycle-and-effects.md)：动态插件有版本与运行身份，组件卸载需要清理受管理的注册和资源。
- 本轮为官方文档核验，未固定源码提交、未运行插件，也未验证所有能力都可在运行中无条件替换。官方介绍仍标记为 developer preview。

## 三个层次

| 层次 | 回答的问题 | 与 RSI 的关系 |
| --- | --- | --- |
| 可修改性 | 系统有哪些组件能被检查、替换和重新组合？ | 插件化提供修改入口与生命周期基础 |
| 自动改进 | 谁从反馈提出候选，谁评测、选择并发布？ | 需要在基础设施之上组织改进流程 |
| 递归改进 | 改进后的能力是否参与并帮助后续自我改进？ | 建立 RSI 式反馈关系，实际增益仍需证据 |

**插件化扩大改进空间，但不保证所有组件都能任意修改，也不保证修改后一定更好。**尤其权限、评测标准与发布控制，应保留候选不能随意放宽的边界。

## 一个沿用 Memory 场景的假设例子

下面是教学设计，不是对 DeepSeek 默认功能的描述：

1. Memory 插件 v1 把“今天回答简短点”误存为长期偏好。
2. 改进流程收集用户纠正和提取结果，提出 Memory 插件 v2，增加时间范围判定。
3. 独立评测检查临时要求、长期偏好和否定表达，确认没有通过少存所有信息来虚假减少误存。
4. 候选通过后，新任务使用 v2；保留旧版本供回退。
5. 如果改进后的记忆机制还用于保存系统自身的失败经验，并帮助后续优化器提出更有效的修改，就进一步形成递归改进关系。

插件框架解决的是插件如何承载和运行；上面收集什么反馈、采用什么标准、何时晋级，需要具体实现。用户偏好与系统改进经验仍应分开存放和授权。

## 模型不需要被排除在外，但接入与训练不同

- 模型插件可以替换模型服务、调整接入与路由；这不等于更新模型权重。
- 改进系统也可以在另行具备数据、训练权限与资源时接入训练流程，再切换到新权重；本轮未验证 DeepSeek Harness 默认提供这种训练闭环。
- 因此更准确的说法是：**插件化可以直接支撑模型外围的改进；模型参数改进还需要额外训练体系。**

## 从模型调用到模型训练：完整例子（2026-09-23 补充）

### 保留用户的进一步理解

“他只要把需要训练的模型传上去，用 API 的形式训练，然后最后再把模型在云上暴露 API 或者本地自己 host 就行了啊。”

🟢 **已确认的架构理解：**可以将外部训练与部署能力封装为工具，由 Agent 编排；训练后的候选模型再通过模型接入插件进入系统。这让模型参数改进也有机会进入整个自我改进流程，而不要求 Harness 自己实现训练算法。

两个常见前提：平台已有底模时，通常提交底模标识、训练数据和配置，不必上传整个模型；自带模型权重需要平台支持且具备相应使用权限。训练完成只代表产出了候选，效果仍需评测。

### 为什么插件化能提供 RSI 基础设施

**它把系统的能力拆成有接口、可组合的组件，让“观察问题、提出修改、试验候选、采用新版”有地方接入。**下表区分已查到的框架能力与需要自行构建的改进流程，不能把设计例子当成默认产品功能。

| 环节 | 可借助的框架能力 | 还需要具体实现什么 |
| --- | --- | --- |
| 执行任务 | 模型接入、工具、技能、Agent Loop | 任务目标、允许执行的动作、完成标准 |
| 收集经验 | 会话事件记录、存储、可扩展工具 | 关联用户反馈与真实结果，筛选并脱敏训练样本 |
| 分析问题 | 模型调用与自定义流程 | 诊断失败原因，判断应改 Prompt、工具还是参数 |
| 提出候选 | 插件扩展及动态包能力 | 生成修改，保存父版本、差异、理由和适用范围 |
| 执行训练 | 工具可以封装外部服务调用 | 对接训练平台，提交任务、查询状态、取消与限制预算 |
| 评测候选 | 可复用执行能力与记录机制 | 独立数据、业务正确性判断、旧能力回归和成本对照 |
| 部署模型 | 外部部署工具与模型接入能力 | 启动推理服务，检查就绪状态和接口兼容性 |
| 发布与回滚 | 插件组合、配置与版本管理的接入点 | 新任务切换、旧任务版本固定、保存可恢复的旧模型和配置 |
| 递归延续 | 新模型与新插件可以继续组成执行系统 | 让改进后的能力参与下一轮改进，验证改进效率是否增强 |

### 一条完整技术链路

```text
当前 Agent：模型 M0 + 插件组合 H0
    ↓ 执行任务
任务记录、工具结果、用户纠正
    ↓ 筛选、去重、脱敏，划分开发与评测数据
诊断：是否确实需要训练，而非修工具或改上下文？
    ↓ 需要训练时
训练工具提交：底模标识 / 可支持的权重 + 数据 + 配置
    ↓ 返回训练任务编号，后续查询进度
候选模型 M1（或适配参数）
    ↓ 在测试环境加载，对照 M0 评测
未通过：保留 M0，记录拒绝原因
通过：云端部署或本地托管推理服务
    ↓ 检查接口、工具调用能力与服务状态
模型接入插件切换到 M1，供新任务使用
    ↓
若 M1 同时参与后续诊断、数据生成或方案改进
    ↓
观察“改进后的能力 → 下一轮自我改进”的反馈关系
```

这是一条待实现的教学方案，没有调用训练或部署 API，也未测得能力收益。模型训练不是每轮必经步骤；能通过数据修正、提示词或工具改动解决的问题，不必直接训练。

### 必须区分的三个接口职责

| 接口职责 | 输入与输出 | 它不代表什么 |
| --- | --- | --- |
| 推理调用（Inference） | 输入消息与工具定义，返回文本或工具调用请求 | 不会因为调用次数变多就自动更新模型权重 |
| 训练任务（Training Job） | 输入数据与训练配置，返回任务编号，完成后产生模型或适配参数 | 不代表自动部署，也不代表候选优于旧模型 |
| 部署服务（Model Serving） | 加载模型版本并暴露可调用地址 | 不保证不同模型的消息格式、工具调用行为完全兼容 |

**模型接入插件负责“用哪个模型、怎么调用”；训练工具负责“请求外部平台产生新模型”；部署工具负责“让新模型成为可调用服务”。**它们可以协作，但不是同一个接口，也不一定由同一家平台提供。

### 异步任务、版本与回滚怎样考虑

- 训练往往耗时较长，提交后保存任务编号，由后续调度查询完成状态；网络超时先查询是否已创建任务，避免重复提交产生费用。
- 平台可能提供基础健康与训练指标；最终是否满足业务需求，仍需自己的候选评测。比较时固定 Harness 等条件，避免无法判断提升来自模型还是外围变化。
- 发布记录应关联模型版本、Prompt/Skill/插件配置及评测结果。正在运行的任务默认固定旧版本，新任务再采用新版。
- 旧模型和对应配置要保持可恢复；仅记录一个旧 URL 不够，如果服务已经关闭，仍需能重新部署。
- 训练数据、访问凭据、预算和发布权限由外部约束控制。不能让候选通过修改评分规则或取消预算限制来宣称改进。

### 什么时候称为 RSI

**如果 M1 只用于提高客服等业务任务效果，是自动模型改进；如果 M1 或改进后的插件也参与后续自我改进，就建立了 RSI 式递归关系。**是否真正提高“产生有效改进”的能力，需要另做对照；接上了循环不等于无限变强。

## 术语与后续入口

- **Plugin（插件；执行层）：**按宿主约定提供能力的可组合组件；可插拔不代表可以无条件实时替换。
- **Lifecycle（生命周期；运行时）：**组件从加载、运行到卸载的过程；卸载清理程序资源不自动撤销外部业务操作。
- **Endpoint（服务端点；模型接口层）：**接收推理请求的服务地址；换地址或模型标识是切换服务，不等于训练。
- **Training Job（训练任务；训练平台层）：**一次异步训练工作，通常用任务编号跟踪状态与产物。
- **Model Serving / Hosting（模型服务 / 托管；部署层）：**把模型加载到计算资源上，对外提供推理能力；可在云端或本地运行。
