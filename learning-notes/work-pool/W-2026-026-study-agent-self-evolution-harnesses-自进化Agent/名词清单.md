# 自进化 Agent 与 RSI：名词清单

这份清单按知识块查词，不要求一次背完，也不代表已经掌握。基于本主题已有调研与讨论整理；具体项目的版本、API 和默认行为仍需在使用时重新核验。

详细机制与来源见 [调研报告](RESEARCH_REPORT.md)，个人理解与例子见 [我的笔记](我的笔记.md)。本文件负责术语解释，不替代详细笔记或完整知识图谱。

## 先看知识分块

1. **改进对象：**Memory、Prompt、Skill、Tool、Harness、模型参数分别是什么。
2. **反馈与诊断：**怎样从用户纠正、工具结果和任务评测中发现问题。
3. **产生变化：**怎样提出候选、搜索方案、积累策略。
4. **验证与发布：**怎样判断改好了、何时生效、如何回滚。
5. **RSI：**改进后的能力怎样参与下一轮自我改进。
6. **研究名称与选学：**把论文名字放回对应机制，不按名字背框架。

主线是：**执行任务 → 收集反馈 → 提出候选变化 → 评测 → 接受或拒绝 → 后续任务使用。** RSI 进一步关注改进能力自身是否进入这个反馈循环。

## 一、改进对象：究竟在改什么（主线）

| 术语 | 初学者解释与边界 |
| --- | --- |
| Agent（智能体；应用层） | 由模型参与决策、借助工具推进任务的系统。模型是其中一部分，不等于整个 Agent。 |
| LLM（Large Language Model，大语言模型；模型层） | 根据输入生成输出的模型。外部保存了新记忆，不表示它的参数已经训练更新。 |
| Self-improvement（自我改进；系统层） | 系统针对自身能力提出和采用改进，例如修正自己的任务策略。是否真的改善效果，要看证据。 |
| Self-evolution（自进化；研究与产品用语） | 常用于描述根据经验持续调整系统的过程，但范围没有统一口径。看到这个词先问改什么、怎样验证、怎样保留。 |
| Prompt（提示词；模型输入层） | 给模型的任务说明、规则或示例，例如“先查订单再判断退货条件”。指导模型不等于程序已经强制执行规则。 |
| Context（上下文；模型输入层） | 本次调用中模型能看到的信息，包括提示词、历史、工具结果和召回的记忆。它不只是一段系统提示词。 |
| Memory（记忆；应用数据层） | 跨步骤或任务保留并按需使用的信息，例如用户偏好、环境事实和经验。保存不代表下次一定被正确召回。 |
| User Preference（用户偏好；个人记忆） | 用户希望系统怎样服务自己，例如“先给结论”。“今天简短点”与“以后都简短点”的时间范围不同。 |
| Episodic Memory（情景记忆；经验层） | 保存过去发生的具体经历，例如某次任务如何失败。它不自动等于适用于所有任务的规则。 |
| Procedural Memory（程序性记忆；策略层） | 保存“怎样做事”的方法；这里的“程序性”也可以是文字步骤，不一定是代码。Skill 可以承载这类记忆。 |
| Skill（技能；应用能力层） | 可复用的做事方法与资源，可能包含说明、参考资料和脚本。不能把所有 Skill 都当成纯 Prompt。 |
| Tool（工具；执行层） | 实际执行操作的函数或服务，例如读取文件、查询订单。工具描述指导模型选择，工具实现负责真正执行。 |
| Harness（执行控制框架；执行层） | 包围模型、管理上下文、工具、循环和约束的程序。修改 Harness 可以改变系统如何行动，而不改模型参数。 |
| Runtime（运行时；执行基础设施层） | 管理程序实际运行、进程、状态与生命周期的机制。与 Harness 职责相邻，产品中常组合在一起。 |
| Agent Loop（Agent 循环；控制层） | 模型观察信息、提出动作、程序执行工具、再反馈结果的循环。一次任务里的循环不等于跨任务自进化。 |
| Model Weights（模型权重；模型层） | 模型计算所使用的数值参数。修改外部文件与通过训练修改权重是不同事情。 |

## 二、反馈与诊断：怎样发现问题（主线）

| 术语 | 初学者解释与边界 |
| --- | --- |
| Feedback（反馈；改进输入） | 来自用户、工具、环境或评测的信息。用户表达新偏好是新信息，不一定意味着原系统有错误。 |
| Explicit Feedback（显式反馈） | 用户直接说“这次查错了”“只限今天”。含义通常比猜测用户是否满意更明确，但仍需理解上下文。 |
| Implicit Feedback（隐式反馈） | 从反复重试、取消或重写等行为推测问题。只能作为线索，例如取消不一定意味着结果错误。 |
| Trajectory（执行轨迹；观测层） | 一次任务中可见的观察、动作和结果序列，用来分析在哪一步出问题。并不要求获得模型隐藏的思维链。 |
| Trace（追踪记录；观测层） | 把模型调用、工具执行等操作关联起来的记录。可用于还原轨迹，也常包含耗时和错误等工程信息。 |
| Reflection（反思；诊断与候选生成） | 让模型分析成功或失败原因，提出下次如何改变。反思结果是一种判断，不能代替验证。 |
| Credit Assignment（贡献或责任归因；诊断层） | 判断哪些步骤导致成功或失败。例如最终回答错，根因可能是前面检索了错误资料。 |
| Failure Pattern（失败模式；诊断层） | 多个案例共同出现的问题，例如反复把临时要求存成长期偏好。比只针对某一次失败写补丁更适合提炼通用策略。 |

## 三、产生变化：谁来改、怎么改（主线）

| 术语 | 初学者解释与边界 |
| --- | --- |
| Optimizer（优化器；改进流程层） | 组织提出、执行、评测和选择候选的组件。可以是脚本或 Agent，不一定是独立外部服务。 |
| Candidate（候选版本；搜索层） | 一份等待检查的新提示词、技能或代码版本。“生成了候选”不等于已经采用。 |
| Mutation（变异；搜索操作） | 对已有候选做修改，例如增加一个检查步骤。这里可以是模型提出的针对性修改，不必是随机字符变化。 |
| Prompt Optimization（提示词优化；策略层） | 根据任务效果修改并选择更好的提示词。区别于只保存一条事实，它通常需要比较候选效果。 |
| Playbook（策略手册；上下文层） | 组织可复用步骤、经验和注意事项的内容，例如不同错误的排查办法。它需要维护冲突和过期条目。 |
| Delta Update（增量更新；内容维护） | 只新增、修改或删除相关条目，不每次重写整份手册。可降低无关内容被意外丢失的风险。 |
| Self-modification（自修改；变更行为） | 系统修改自身的指令或程序。描述的是“发生了修改”，不保证修改后更好。 |
| Harness Evolution（执行框架演化；执行层） | 根据反馈改变工具、上下文管理或控制逻辑，并评估新版本。与只修复用户项目中的业务代码不同。 |
| Online / Offline Adaptation（在线 / 离线适应；运行安排） | 在线是在服务或交互过程中吸收反馈，离线是在独立阶段集中改进。离线改进同样可以自动化。 |

## 四、验证与发布：怎样证明有效、怎样生效（主线）

| 术语 | 初学者解释与边界 |
| --- | --- |
| Baseline（基线；对照层） | 修改之前或一个简单方案的表现。没有基线就难以判断新增复杂度是否有收益。 |
| Eval（Evaluation，评测；验证层） | 使用任务和判定标准检查效果，例如能否正确提取长期偏好。不同于模型自己说“我进步了”。 |
| Evaluator / Judge（评测器 / 评审者；验证层） | 给结果做判断的程序、模型或人。模型评审也可能偏差，需要与可信检查或人工样本对照。 |
| Train / Development Set（训练 / 开发集；优化数据） | 用于发现问题和生成修改的数据。在 Prompt 优化里称作 trainset，也不意味着训练了模型权重。 |
| Validation Set（验证集；候选选择） | 用于比较候选并选择版本的数据。参与了版本选择，就不能再当完全独立的最终证据。 |
| Held-out Test Set（留出测试集；最终验证） | 不参与修改与候选选择、用于最终检查的任务。反复根据它的结果调整方案，会削弱其独立性。 |
| Generalization（泛化；能力表现） | 改进能应用到没有用于优化的新任务。只记住几条测试答案不代表学会方法。 |
| Regression（回归或能力退化；质量层） | 新版修好一个问题，却破坏原来正常的功能。回归测试用来发现这种变化。 |
| Overfitting / Data Leakage（过拟合 / 数据泄漏；评测风险） | 前者是过度适配已见样例，后者是本应隔离的答案或测试信息进入优化过程。两者都可能让分数看起来比真实能力更好。 |
| Gate / Promotion（门禁 / 晋级；发布层） | 按预设条件决定候选能否进入下一阶段或成为可用版本。通过一项测试不等于满足全部发布条件。 |
| Artifact（产物；交付层） | 实际保存、加载和发布的文件或模型版本。必须确认评测对象与最终使用对象一致。 |
| PR（Pull Request，合并请求；Git 协作层） | 提交修改供审查、测试和合并的载体。自动提交 PR 只表示提出变更，不证明已经改进。 |
| Version Pinning（版本固定；执行层） | 让一次任务明确使用某个 Prompt、Skill 或程序版本。避免任务前半段和后半段悄悄使用不同规则。 |
| Hot Reload（热重载；运行时） | 不重启整个进程而重新加载部分内容的机制。修改磁盘文件不会自动使已经加载的内容更新。 |
| Rollback（回滚；恢复层） | 恢复之前的可用版本。回滚程序不自动撤销它已经发出的邮件、付款等外部操作。 |
| Sandbox（沙箱；执行隔离层） | 限制候选代码可访问的文件、网络和资源。隔离有助于控制影响，但不证明候选业务逻辑正确。 |

## 五、RSI：学习方法也进入改进范围（当前扩展）

| 术语 | 初学者解释与边界 |
| --- | --- |
| RSI（Recursive Self-Improvement，递归自我改进；系统层） | 改进后的系统能力又参与后续自我改进，形成反馈循环。这里采用学习用工作解释，不把某一种实现视为统一定义。 |
| Improvement Mechanism（改进机制；优化层） | 系统发现问题、生成修改、评测并采用修改的方法。它本身可以包含提示词、工具或程序。 |
| Meta-level Improvement（元层改进；学习方法层） | 改进“怎样学习或优化”的方法。例如不只是新增用户习惯，而是改进提取习惯的提示词。 |
| Recursive Continuation（递归延续；改进循环） | 新版本获得的能力被用于产生后续版本。与始终由完全不变的改进者维护另一个系统相比，反馈关系不同。 |
| Improvement Capability（改进能力；评测对象） | 在给定预算下，产生有效改进的能力。任务分数提高与改进能力提高，应分别找证据。 |
| Fixed Evaluation Boundary（固定评测边界；治理层） | 保留不由候选随意改写的外部标准，防止通过放宽评分“证明进步”。RSI 不要求每个组件都能修改自己。 |

**用我们讨论过的 Memory 例子区分：**保存“我喜欢先看结论”是更新记忆；自动改进“怎样提取习惯”的提示词，是改进学习方法；改进后的方法继续支持后续自我改进，才进一步建立递归关系。这是概念例子，不是已运行的实验，也不意味着无限加速。

## 六、研究名称：知道它研究哪一块即可

以下为已有调研中的机制定位，具体证据、版本与限制见 [调研报告](RESEARCH_REPORT.md)，本次未做产品能力查新。

| 名称 | 对应知识块与简短解释 |
| --- | --- |
| Reflexion | 反馈与记忆：把任务反馈转换为反思文字，供后续尝试使用；不要求更新模型权重。 |
| Voyager | 技能积累：将完成任务的代码保存到技能库，之后检索和组合；研究场景为 Minecraft。 |
| GEPA（Genetic-Pareto） | 候选搜索：借助轨迹反馈提出修改，比较并选择候选；原论文重点研究提示词优化。 |
| ACE（Agentic Context Engineering，Agent 上下文工程） | 策略维护：通过生成、反思与整理，增量维护结构化策略手册。 |
| DGM（Darwin Gödel Machine，达尔文哥德尔机） | 程序自修改：修改编码 Agent 自身代码，评估候选并维护版本档案；论文实验中基础模型固定。 |
| Self-Harness | 执行框架改进：挖掘失败模式，提出针对性变更，并通过回归测试筛选。 |
| HarnessDev | 改进能力评测：研究模型能否创建、继续改进可运行的 Harness，以及收益能否迁移。 |
| SEAL（Self-Adapting Language Models，自适应语言模型） | 参数学习：生成微调数据或更新指令，并实际更新权重；此处特指该论文，避免与同名研究混淆。 |

## 七、选学词汇：深入搜索或训练时再看

| 术语 | 初学者解释与边界 |
| --- | --- |
| Pareto Frontier（帕累托前沿；多目标搜索） | 保留各有优势、不能简单判定全面更差的候选。例如一个更准确，另一个更便宜。 |
| Candidate Archive（候选档案；搜索层） | 保存历史版本、结果和父子关系，便于从不同路线继续探索。进入档案不等于允许上线。 |
| Ablation（消融实验；验证方法） | 去掉某个机制再做对照，检查提升是否确实与它有关。比把所有改动一起加入更容易判断贡献。 |
| Reward Hacking（奖励钻空子；优化风险） | 系统提高评分，却没有达到真正目标，例如绕过检查而不是解决任务。需要检查评分与目标是否一致。 |
| SFT（Supervised Fine-Tuning，监督微调；模型层） | 用输入和目标输出示例训练模型参数。与把示例放进 Prompt 的上下文学习不同。 |
| RL（Reinforcement Learning，强化学习；学习方法） | 利用交互和奖励优化策略。在模型后训练中通常涉及参数更新；文字反思本身不等于执行了这类训练。 |
| LoRA（Low-Rank Adaptation，低秩适配；参数训练） | 学习较小的附加参数以适配模型，减少需训练的参数量。依然需要训练数据和效果验证。 |
| Model–Harness Co-evolution（模型与执行框架协同演化；系统层） | 模型和执行机制相互适配、共同改进。需要拆开各自贡献，不把所有收益归给一个组件。 |

## 反思

1. **定义边界：**自进化与 RSI 存在不同研究口径；本清单服务于常见机制理解，不把工作解释当成严格统一标准。
2. **学习建议：**先能用一个例子指出“改了什么、凭什么采用、何时生效”，再学习搜索算法或参数训练；读过词表不等于掌握。
