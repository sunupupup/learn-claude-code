# 我的笔记

聊沙箱之前，应该先聊沙箱到底明确有哪些能力

而不是讨论 某个项目提到了自己具有沙箱能力，钻研他是否真是一个沙箱

定义：
沙箱（Sandbox）是一个受控的程序执行环境，通过限制程序能访问的资源、能执行的操作，把它的运行影响约束在预先规定的边界内。

通用链路：

Agent 需要执行动作
       ↓
后端把任务放进受限环境
       ↓
环境运行代码、命令或浏览器
       ↓
后端读取结果并检查

## 场景描述

1. coding Agent 改代码、跑测试
  问题：错删文件、读外部文件、启动非法进程
  沙箱：限制访问的文件范围、限制进程

2. 分析用户上传的文档
  问题：文件格式异常
  沙箱：放独立环境、分配独立资源

3. 运行Agent生成的脚本
  问题：脚本死循环、占满内存、删除文件
  沙箱：设置资源上限、超时、限制资源

4. Agent使用浏览器自动化
  问题：网页内容误导、Agent误点
  隔离浏览器进程、文件、会话数据

5. Agent并行多任务
  问题：共用同目录
  沙箱：不同任务创建不同执行环境、减少干扰

6. 临时安装依赖项
  问题：安装脚本比较危险、额外访问网络
  沙箱：将依赖项限制在临时环境，完成后清理




## 沙箱的能力


| 维度 | 主要解决什么 |
|---|---|
| **文件系统隔离** | 能看到哪些文件；修改原件还是副本；哪些目录只读 |
| **进程隔离** | 能否看到、控制其他进程；子进程是否受同样约束 |
| **身份与权限隔离** | 以哪个用户运行；能否提权；能使用哪些凭证 |
| **用户／任务之间的隔离** | 不同用户、项目、任务的数据和运行状态是否会串 |
| **网络限制** | 能访问哪些地址、端口；是否允许联网 |
| **资源配额与调度** | CPU、内存、磁盘、进程数、运行时间如何限制和分配 |
| **生命周期与回收** | 如何停止整个任务、清理进程和临时资源、保留产物 |

## 沙箱的形式有哪些

宏观的层面，任何有一种东西进行了隔离，都算是沙箱

| 形式 | 怎样理解 |
|---|---|
| 云函数／边缘函数 | 平台提供执行环境，具体隔离和限制取决于平台 |
| Docker 容器 | 可配置文件、进程、网络和资源边界；镜像只是环境模板 |
| 普通子进程 | 天生有独立地址空间，但通常仍共享用户权限、文件和网络访问能力 |


不过大多数情况下，还是在讨论 云端沙箱和本地docker类容器沙箱

普通子进程也能限制各种东西
```bash
node --permission --allow-net app.js
```
运行时层面的权限限制


## 场景1：代码执行

1. pi的sandbox插件，本机的 sandbox sdk，实现基本的代码隔离
2. pi的Gondolin插件，使用独立内核的虚拟化技术，来实现代码隔离
3. docker容器执行
```bash
# 启动容器
docker run -d --name session-123 python:3.12-slim sleep infinity
# 把主机文件复制到容器
docker cp analyze.py session-123:/tmp/analyze.py
# 在已有容器里启动 Python 执行
docker exec session-123 python /tmp/analyze.py
```

4. 远程代码执行

E2B沙箱，很有名的一个沙箱产品，同时也衍生出了一套标准
底层依然可能是 Docker 容器或微型虚拟机。

使用场景
- 本地 Agent：通常优先使用本机环境执行，并按需配合本地沙箱。本机缺少依赖、系统环境、算力，或需要任务持续运行时，可以转向远程执行环境；远程环境可以自建，也可以购买服务。
- 云端 Agent：执行用户提供或模型生成的不可信代码时，通常需要为任务提供隔离环境，避免影响主服务和其他用户。这个环境可以是同一物理机上的容器／虚拟机，也可以是另一台机器或第三方沙箱服务。

本机 Agent
  → 通过网络 API 创建远程沙箱
  → 上传代码和输入文件
  → 请求执行命令
  → 获取输出、退出码和生成文件
  → 结束后释放沙箱

```js
sandbox = RemoteSandbox.create()
sandbox.upload("analyze.py")
result = sandbox.exec("python analyze.py")
sandbox.download("result.csv")
sandbox.close()
```

远程沙箱可以提前准备好很多模版

| 方式 | 实际做什么 |
|---|---|
| **预装模板** | 提前装好 Python、Node.js、各种库，创建沙箱时传模板名称 |
| **通过 SDK 定义镜像** | 传入系统包、Python 包等要求，服务端构建并缓存环境 |
| **运行时安装** | 沙箱已经启动，再执行 `pip install`、`npm install` |


## 场景2：多任务

两个任务同时改同一个项目。
比如你让 Agent 同时做：
- 任务 A：升级项目依赖。
- 任务 B：修复登录功能。

如果它们共用一个目录：

还可能出现：双方修改同一个文件、覆盖临时文件，或者启动服务时抢占同一个端口。
**这里的隔离目标，是让任务各自拥有工作状态，减少相互干扰。**可以分几层处理：

| 隔离对象 | 常见做法 |
|---|---|
| 项目文件 | 每个任务使用独立目录、项目副本或 Git worktree |
| 依赖与临时文件 | 每个任务使用独立依赖目录、缓存或临时目录 |
| 进程与服务 | 为任务安排独立进程、端口，或使用容器／虚拟机 |

开worktree的形式，一般都需要用到sub-agent去完成了

主 Agent 分配任务
  ├─ Subagent A → Worktree A → 升级依赖、测试
  └─ Subagent B → Worktree B → 修复登录、测试
完成后 → 主 Agent 审查、合并结果

具体可以看 [pi子任务沙箱](../../../开源项目学习/Pi%20Coding%20Agent/worktree沙箱.md)

## 场景3：浏览器

具体场景
`子 Agent A 用账号甲测试购物网站，子 Agent B 用账号乙测试同一个网站。`

这时，光分开标签页不够，需要分开登录状态。

浏览器自动化里常用 Browser Context（浏览器上下文）：可以把它理解成同一浏览器进程中的两份独立浏览环境。

一个浏览器进程
  ├─ Context A：自己的 Cookie、网站存储 → 登录账号甲
  └─ Context B：自己的 Cookie、网站存储 → 登录账号乙

不过倒是可以用隐私浏览器

但是，不过，Chrome 里连续打开两个隐私窗口，它们仍属于同一段隐私会话，并不是每个窗口都获得独立 Cookie

普通窗口 + 隐私窗口：可以分开登录态

同一 Chrome 中两个隐私窗口：不能据此认为各自独立

自动化创建两个独立 Context：可以分开登录态

所以，一旦Agent关心 **真实独立会话** 那就需要沙箱启动浏览器了
