# 开源项目沙箱设计：子项目与学习路线

## 为什么研究这些项目

用户先问“是否通过 SDK 发送数据、具体怎么执行、环境里有什么”，随后关注阿里云 FC，再提出结合源码学习。这里用可读开源实现回答这些问题；不把 FC 的 E2B 兼容接口推断成 FC 内部实现。

2026-09-26：按学习 Prompt 初始化专题；这是推荐阶段，没有自动选定开读、克隆、安装、运行容器或调用付费服务。已有其他章节及暂存区改动保持原样。

## 按系统层次分类

| 层次 | 要回答什么 | 项目 |
| --- | --- | --- |
| Agent 应用接入层 | Agent 会话和工具怎样使用执行环境 | [OpenHands SDK](OpenHands%20SDK.md) |
| 沙箱平台与内部执行服务 | SDK 如何创建环境、发送命令、读写文件、回收资源 | [OpenSandbox](OpenSandbox.md)、[E2B Runtime](E2B%20Runtime.md) |
| 环境与工具组合 | 浏览器、Shell、文件等怎样协作 | [AIO Sandbox](AIO%20Sandbox.md) |
| 底层隔离 | 程序与宿主之间的边界如何实现 | [gVisor](gVisor.md)、[Firecracker](Firecracker.md) |

控制面（Control Plane）负责环境创建、状态和回收；数据面（Data Plane）处理运行中的命令、文件和服务流量；沙箱内守护进程（Daemon）是持续接收执行请求的服务。它们与真正提供进程/内核/虚拟机边界的隔离层不同。

## 推荐顺序与取舍

1. **主项目：OpenSandbox。** SDK、协议、管理服务、Docker 后端和 execd 均有可观察入口，适合建立完整链路。先限定 Docker 单机路径，不展开 Kubernetes。
2. **最多一个窄对照：E2B Runtime 的 envd。** 对比同一种命令与文件请求如何处理，连接此前 E2B/FC 讨论；整套 E2B 云平台不在第一轮范围内。
3. 后续若想研究 Agent 如何接入，再选择 OpenHands SDK；若想直观看工具组合，可选择 AIO 的小体验。它们是替代的下一步，不要求全部学习。
4. 只有追问“为什么真能隔离”时，再在 gVisor 与 Firecracker 中选择一个深入；两者不是必然逐级升级路线。

推荐依据是与当前问题的贴合度、服务端源码可见性、能否缩小到单条链路与实验前置成本；不是按 Star 排名或生产选型结论。

## 第一轮建议只研究什么

从“上传一个输入文件并运行脚本”切入，观察两条路径：

- 生命周期：SDK 创建请求 → 管理服务 → 后端创建资源 → 就绪 → 返回标识/地址 → 到期或主动清理。
- 执行：SDK 解析/获取执行地址 → 沙箱内执行服务 → 子进程/文件系统 → 输出、错误、退出与产物。

最后加入一个命令超时对照，检查进程状态与资源回收。网络策略作为下一知识块，不同时深入所有机制。以上为学习假设框架，正式源码阅读时按真实实现校准。

## 选定项目后的证据与验收

- 固定分支/Commit、版本、许可证和读取日期；浅克隆到仓库外独立目录，位置到开读时确定。
- 找真实入口，沿调用追踪参数、状态变化、副作用和结果，记录路径、行号和 Commit。
- 先用固定脚本验证，不依赖大模型；记录正常执行和一个失败对照，及清理证据。
- 能用自己的话区分“SDK 对象”“运行实例”“解释器上下文”“持久化产物”，并说明一个失败场景。
- 当前各项目均为文档/目录筛选证据，不能标成源码调用链已验证或用户已掌握。

## 筛选中发现的关键边界

- OpenSandbox 当前规范仓库为 opensandbox-group/OpenSandbox；旧 alibaba 地址仍可能出现在文档及模块名中。
- E2B 旧 infra 仓库重定向到 runtime，当前存在单机 Embed 评估路径，不能继续引用过时的“只能云上自建”描述。
- AIO 当前公开仓库主要能直接检查 SDK、示例和网站；docker 目录仅占位，完整镜像服务端源码位置待核验，因此不作为完整内部实现主课。
- 六个候选均核对了官方仓库 README 与 GitHub 元数据，未归档；推送日期只说明仓库活动，不证明成熟度、安全性或支持承诺。
