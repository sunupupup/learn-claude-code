# 虚拟机的两大分类

- VM虚拟机，有自己的操作系统内核
- Docker容器：共享Linux内核、称为“容器”

# 内核的作用

程序相关干的事，很多都要内核帮忙

| 程序想做的事 | 内核负责的事 |
|---|---|
| 读取文件 | 检查权限、访问文件系统 |
| 创建进程 | 创建和管理进程 |
| 申请内存 | 管理内存分配与映射 |
| 发起网络连接 | 处理网络协议和连接 |

程序向内核提出这些请求的入口，叫 系统调用（System Call）。

两类环境最关键的区别就是：程序的系统调用，交给谁处理？


| 路线 | 做法 | 典型例子 |
|---|---|---|
| **硬件级虚拟化** | 提供虚拟硬件，各自运行操作系统内核 | 普通虚拟机、微虚拟机 |
| **操作系统级虚拟化** | 共享内核，由内核隔离各组进程和资源 | Docker 容器 |


# vCPU

一个完整的 CPU 应该是啥样的 ？

首先CPU有自己完整的一份运行状态
真实CPU在执行的时候
- 当前执行到那条指令
- 寄存器有哪些数据
- 当前使用什么内存映射

vCPU（Virtual CPU，虚拟 CPU） 就有自己的一套这样的状态。虚拟化系统负责保存、恢复和管理它。

所以，创建两个 vCPU，并不需要制造两颗实体 CPU，而是创建两个可以被分别调度执行的虚拟处理器。


但是真正的计算还是真实的CPU

```
创建虚拟机
    ↓
创建 vCPU，并设置初始状态
    ↓
准备虚拟机内存，把 Linux 内核装进去
    ↓
让真实 CPU 开始执行这个 vCPU
```

一个物理 CPU 核心也可以轮流执行多个 vCPU：暂停一个，保存状态，再恢复另一个。分配了几个 vCPU，通常不意味着永久独占几个物理核心。

# VM虚拟机 VS Docker

VM 要额外运行自己的内核，Docker 容器复用已经运行的内核。


容器主要就是在已有内核上，给进程配置一套文件系统、资源限制和隔离规则，然后启动进程。没有再启动一台机器。

但是 VM 配置虚拟 CPU、内存、设备，需要准备一台完整的内核体系


AWS《容器与虚拟机有什么区别》 https://aws.amazon.com/compare/the-difference-between-containers-and-virtual-machines/

重点看 Software development speed（软件开发速度） 和 Scalability（扩展能力） 两节。它明确指出：
- VM 涉及整套系统环境，构建、重新生成和验证的工作较多。
- 容器更适合频繁构建、测试、发布新功能。
- 容器占用的存储通常更小，更容易增加运行实例。


主要就在于 构建速度和效率是吧 

减少很多重复构建、环境准备的问题

基础镜像和依赖没变，就可以复用；换一台机器或重建环境，也能沿用同一套配置。


VM虚拟机的启动：QEMU/Firecracker等虚拟机软件 + 虚拟硬盘镜像
Docker虚拟机启动：Docker Engine + 容器镜像

# VM虚拟机 VS Docker、MXC

Docker、MXC 
普通 Linux Docker 容器和 MXC 的 Windows 进程隔离模式，都属于共享内核的隔离。前者共享容器所在的 Linux 内核，后者共享本机 Windows 内核。

但是都是共享内核的，容易发生越界的问题
沙箱逃逸（sandbox escape），在 Docker 场景里也叫 容器逃逸（container escape）。意思是程序突破了原本给它划定的隔离边界，访问到了本应隔离的宿主资源或其他环境。
共享内核意味着，沙箱内的代码可以通过系统调用接触宿主内核
还有一个相关词叫 提权（privilege escalation），指拿到了比原来更高的权限。两者可以同时发生，但描述的是不同的事：提权看拿到了什么权限，逃逸看跨过了哪道边界。

！！！
提权和沙箱逃逸都是普通 Docker 容器和 MXC 进程隔离模式可能面临的安全问题。具体风险取决于隔离机制、补丁状态和开放的权限。
！！！

为了防止这种危险操作，这时候一般只能 VM 出马了
如果要求陌生代码使用独立内核、和宿主之间再隔一道虚拟化边界，就得选 VM 级隔离


如果仅仅是 限制本机 Agent 读写哪些文件、能不能联网
这种一般比较方便
1. windows上使用 ACL 或者 MXC ProcessContainer
2. linux上使用Bubblewrap


如果要控制一个失控任务把宿主机的CPU和内存资源耗光，就用docker容器的方式，能通过cgroup来控制
1. linux上使用docker (namespace + cgroup)


# 微虚拟机 和 普通虚拟机

tryboxi 自己定义了一个 微虚拟机 的概念

「Ubuntu 24.04 microVM」是 tryboxi 对它创建的环境的描述

它基于 Ubuntu 24.04 定制的一份磁盘镜像，删减了很多不必要的

他搞了个热池 + 快照

microVM（微虚拟机）是通用概念。tryboxi 用「Ubuntu 24.04 microVM」描述它给每个沙箱创建的环境。每台 VM 有自己的 Linux 内核，磁盘镜像基于 Ubuntu 24.04 的基础镜像定制，选装开发工具，精简开机时运行的服务。

- **黄金快照（Golden Snapshot）**把一台已经完成初始化的基础 VM 状态保存下来。下次创建沙箱时，可以从这份状态恢复出一台新的独立 VM，省掉重复开机和初始化。快照会占用磁盘空间。
- **热池（Warm Pool）**把恢复这一步也提前做了。tryboxi 先从黄金快照恢复出几台 VM，再暂停它们等待任务。Agent 来了，取出一台规格匹配的 VM，恢复运行，再按任务配置网络、同步项目。待命的 VM 会占用一部分本机资源。

**创建顺序是「热池取用 → 当场从快照恢复 → 从零启动」。** 池里有合适的机器就直接取，没有再走下一步。作者报告的 **20–50 ms** 对应从热池创建沙箱。

快照也可以保存**某个任务做到一半的状态**，方便晚点继续，或者用 `fork` 从同一状态开出副本，试不同方案。
