# Sandbox 演变过程

核心目的：
1. 保护外部
2. 隔离内部


沙箱的一些目的：
1. 限制指定目录：防止误操作其他文件
2. 限制敏感数据：让执行环境看不到敏感数据，比如密钥
3. 禁止联网：防止脚本把数据发给外部网络
4. 防止资源耗尽：限制CPU、内存、执行时间等
5. 防止不同任务互相干扰：不同任务有分离的文件系统

学习主线：最基础的执行方式 → 遇到问题 → 扩展方案 → 对照成熟项目。
这里按问题组织学习顺序，不代表技术历史，也不要求每个项目走完所有阶段。

# 1. worktree隔离机制, 无容器机制

为每个 Agent 任务分配一个 worktree，再由 Harness 把工具操作约束在对应工作区里。

这种能做基本的workspace路径的文件访问限制，只是最基本的

只能限制那种很明显的 bash 、 write 、read 等工具，里面有明显的 path 

但是没法限制 bash 脚本 或者 复杂的脚本执行

read / write / edit 等文件工具：Harness 能在执行前检查目标路径，限制访问范围。
Bash 或脚本：内部可以自行读写文件、启动子进程，这些操作不经过上述工具检查，因此这层限制管不住。

# 2. 用户权限限制，无容器机制

专用低权限用户 + 文件权限

这边补足了上面的worktree隔离的缺点
这一步让 Bash，以及它启动的脚本，都受到操作系统文件权限的限制了。

平时用 developer 用户开发
另外创建一个专门运行 Agent 任务的用户 agent-runner

```bash
# 以 agent-runner 身份启动 Bash，并在里面查看当前身份
sudo -u agent-runner -- bash -c 'whoami'
```

```
Harness
   ↓ 以 agent-runner 身份启动
Bash
   ↓
Python 脚本
   ↓ 尝试打开私人文件
操作系统检查权限
   ↓
拒绝：Permission denied
```

# 临时总结：纯文件访问限制，通过上面的1、2的 ACL + worktree workspace 机制，完全能实现

# 3. 网络限制，无容器机制

还是刚才的专用用户，可以单独设置系统防火墙

以 Linux 为例，可以根据发起网络通信的用户身份来匹配流量。比如 nftables 支持按网络套接字所属用户的 UID（用户编号）匹配

比如 `禁止 agent-runner 直接发送 IPv4 / IPv6 网络流量`

1. 获取用户uid 
```bash
# 查询系统用户的编号，供防火墙规则匹配
agent_uid=$(id -u agent-runner)
echo "$agent_uid"
```

2. 添加限制

省略吧。。。这边有点复杂看不懂，反正就是 在一个 nft里面创建这个uid的规则

nft: Netfilter Table  网络过滤规则表

```bash
sudo nft create table inet agent_net_demo
```

所以，文件限制、网络限制，都能通过基本的用户权限限制，来解决这个问题

# 4. docker

主要是 namespace + cgroup

namespace：（命名空间）负责把进程使用的系统环境分开。
cgroup： 负责资源计量、限额和分配


namespace 和 之前权限控制的区别
- namespace：有自己独立的一套的网络、挂载、进程
- 权限控制：同一个系统中，限制用户能做什么

## 网络 Network namespace

每个容器内部都有自己的网络 Network namespace
多个服务可以在自己的容器内部使用相同的端口

## 文件 Mount namespace

Mount namespace 挂在命名空间 + 容器根文件系统配置

容器有自己的一套目录树

容器 A 看到的 /
├─ /bin
├─ /usr
└─ /workspace    → 挂载任务 A 的文件

## 进程 PID namespace

之前的低权限，不一定会隐藏宿主机的其他进程

通过PID namespace，让容器有自己的进程编号和可见范围

# 补充：Docker 的问题

## 共享内核的问题：突破隔离限制

普通的Linux容器，虽然拥有自己的文件系统视图、网络、进程环节
但是底层还是公用宿主机内核


所以Docker容器这里的独立，仅仅是环境的独立，底层并没有独立


共享内核
容器 A 的程序 ─┐
              ├─→ 同一个宿主机内核
容器 B 的程序 ─┘


容器里面的读文件、创建进程、使用网络，都需通过操作系统来调用，会进入宿主机内核

如果程序能够利用某个可触达的内核漏洞，就能突破限制，影响宿主机和其他容器
称之为容器逃逸(container escape)
容器的运行时的漏洞，也可能造成逃逸
https://docs.docker.com/engine/security/
`这就是运行恶意或完全不可信代码时，共享内核方案需要重点考虑的边界。`

## 配置：主动放开了访问限制

假如宿主机项目目录以可写方式挂载进容器：

宿主机项目目录 ←→ 容器 /workspace

这样容器中的脚本删除 /workspace 中的文件，就会影响到宿主机
这不是逃逸，这个是配置了能力


## 资源：资源抢占

让然共享物理CPU、内存等资源
Docker默认没有设置 CPU 和 内存资源的使用上限
比如要配置 cgroup

## 总结
| 剩余问题 | 下一步解决方向 |
|---|---|
| 授予了过多访问能力 | 收紧挂载、权限和网络策略 |
| 资源消耗影响其他任务 | 配置资源限额 |
| 不可信代码直接接触共享内核 | 减少可用系统调用，或进一步考虑 VM／MicroVM 等隔离方案 |

# gVisor

针对普通容器里，应用直接调用宿主机内核、可能利用内核漏洞影响宿主机的问题。

gVisor 让应用的系统调用先由自己的应用内核处理，减少应用能直接触达的宿主机内核功能，从而降低攻击面。

可以简单理解为，用一层 “内核外壳” 包住了应用，实现独立的进程管理、文件系统、网络等内核功能

应用：我要读文件、创建进程、连接网络
                 ↓
gVisor：接住请求，按自己的内核逻辑处理
                 ↓ 必要时
通过受限接口使用宿主机资源

gVisor 使用 Linux 的 `seccomp` 机制。它允许为执行线程安装规则：遇到某类系统调用时，允许、拒绝，或者触发拦截。

# VM、MicroVM

## VM

VM有自己的内核，称之为客户机内核

内核一般负责这些事

```
| 内核里的功能 | 在 VM 里负责什么 |
|---|---|
| 进程调度 | 决定 Bash、Python 等进程什么时候使用虚拟 CPU |
| 内存管理 | 给各个程序分配内存，隔开它们的地址空间 |
| 文件系统 | 管理文件和目录，处理读写与权限检查 |
| 网络协议栈 | 处理 TCP/IP，让应用通过虚拟网卡通信 |
| 设备驱动 | 驱动虚拟磁盘、虚拟网卡等设备 |
| 系统调用与权限 | 接收程序发出的请求，检查它能不能执行这些操作 |
```

这就是 VM 在隔离上多出来的一层。即使脚本利用漏洞控制了客户机内核，它首先控制的是这台 VM

vm ，就算是提权了，最终也是 vm 内部的 完全体 root

影响不到宿主机是吧

但是，并非用了VM就肯定安全了，VM也有逃逸，攻破虚拟化层
2025 年，VMware 公告披露 CVE-2025-22224：已经拿到客户机管理员权限的攻击者，可以利用受影响版本的漏洞，在宿主机侧负责运行该 VM 的进程中执行代码。厂商报告有证据表明漏洞曾在真实环境中被利用，并发布了补丁

但是这种就不是我们业务代码、或者我们配置的问题了，这是VMware虚拟化软件的我呢提


## VM 逃逸的一个例子

CVE-2025-22224 是 VMware 虚拟化软件的实现漏洞。 VMware 在处理来自虚拟机的通信数据时发生越界写入。修复要更新宿主机上的 VMware 组件  

VMware 给这条通道起的名字是 VMCI（Virtual Machine Communication Interface，虚拟机通信接口）：客户机里的程序通过它发请求，宿主机上对应这台虚拟机的 VMX 进程来解析并处理。VMX 是宿主机上的普通用户态进程，负责模拟这台虚拟机的设备。

官方公告 VMSA-2025-0004 把 CVE-2025-22224 标成 VMCI 堆溢出：根因是 TOCTOU（Time-of-check Time-of-use，检查时刻和使用时刻不一致），结果是 越界写入（out-of-bounds write，写到分配好的那块内存外面）。

通俗讲，宿主机做了两步不该拆开的事：

检查：看客户机给的长度、指针是否落在合法缓冲区内。
使用：按刚才看到的长度去写。

这两步之间，客户机还能改同一份数据。
检查时看起来合法，真正写入时长度或目标已经变了

解决办法：将原来直接利用的那块内存，先拷贝一份出来，后续不直接读取危险内存的数据


## MicroVM

前提：Agent 可能只执行几秒钟的脚本，为什么还要启动一整套虚拟机环境？

比如执行 "python a.py"
脚本几秒就结束了，如果每次都启动完整的系统、许多后台服务的虚拟机，会有很大的开销
- 等待启动：虚拟硬件初始化、内核启动、系统服务启动
- 占用资源：虚拟机内部的软件、其他服务都占用很多内存和CPU

以 Firecracker 这个具体实现为例，它精简了虚拟设备，只提供少量必要设备，并简化内核加载过程。因此可以降低启动时间和虚拟化自身的内存开销。

```
普通通用 VM：
虚拟 CPU + 内存 + 丰富的虚拟设备
          ↓
客户机内核 + 系统服务 + 你的程序

MicroVM：
虚拟 CPU + 内存 + 少量必要的虚拟设备
          ↓
客户机内核 + 精简的运行环境 + 你的程序
```


普通 VM 可以提供独立内核，但启动时需要初始化客户机系统、虚拟设备和服务，运行时也要占用相应内存。`频繁创建、执行、销毁短任务时，这些开销就值得优化。`

`MicroVM（微型虚拟机）沿用 VM 的独立内核和虚拟化隔离，同时精简虚拟设备与运行环境，让它更适合这类任务。`

### KVM

| 方案 | 底层用什么 |
|---|---|
| Firecracker | 使用 Linux 的 KVM |
| QEMU + KVM（Linux 上常见的组合） | 使用 Linux 的 KVM |
| VMware Workstation 的 Linux 版本 | 使用 VMware 自己的实现，包括 `vmmon` 内核模块 |
| VMware ESXi | 自己的虚拟化系统，直接安装在物理服务器上 |

但是最底层，用的机制都是一样的 

- Intel 的 VT-x
- AMD 的 AMD-V

Firecracker                     VMware 的虚拟化产品
     ↓                                  ↓
Linux KVM                       VMware 自己的虚拟化实现
     ↓                                  ↓
Intel VT-x / AMD-V               Intel VT-x / AMD-V
                 CPU 硬件提供


有趣的事，VMware 先做出自己的虚拟化产品，后来才出现 KVM，并被纳入 Linux 内核。
| 时间 | 发生了什么 |
|---|---|
| 1998 年 | VMware 公司成立 |
| 1999 年 | 发布 VMware Workstation 1.0，已经能运行虚拟机 |
| 2006 年 | KVM 项目公开 |
| 2007 年 | KVM 随 Linux 2.6.20 正式发布，成为内核的一部分 |

### Firecracker

同类型的产品还有 Firecracker 、 QEMU 、 crosvm 

从“负责创建和运行虚拟机”这个层面看，Firecracker 和 VMware 的虚拟化产品是同一类东西。


创建MicroVM的流程

1. 准备文件
- Linux内核文件：虚拟机的内核 
- 磁盘镜像rootfs：装好bash、Python、ssh服务

2. Linux宿主机启动Firecraker

```bash
firecraker --api-sock /tmp/vm1.socket
```

启动一个 Firecracker 进程，并提供一个管理接口

3. 调用管理API，配置并开机

```
CPU 数量、内存大小
        ↓
内核文件、磁盘镜像
        ↓
网络接口
        ↓
发送 InstanceStart，启动客户机
```


4. 客户机启动后，通过SSH发送命令

假设网络、登录密钥都ok，虚拟机IP 是 172.16.0.2，里面也准备好了脚本：

```bash
scp -i vm1.key ./a.py root@172.16.0.2:/workspace/a.py

ssh -i vm1.key root@172.16.0.2 'python3 /workspace/a.py'
```
py文件可以通过 scp 协议放拷贝进去

这条命令会让 虚拟机内部启动 Python，输出返回当前终端。

```
Harness
  ├─ 调用 Firecracker API → 配置、启动虚拟机
  └─ 调用 SSH             → 在虚拟机内执行命令，拿回结果
```


## MicroVM的优势

### 精简虚拟机环境，减少启动时间

MicroVM 的核心是：保留独立内核和硬件虚拟化边界，同时把运行一个任务所需的虚拟机开销压低。

它精简了什么？

主要是两个地方：
- 虚拟化软件侧：减少虚拟设备、兼容功能，简化启动流程。
- 客户机侧：配合精简镜像，只启动运行任务需要的程序和服务。

启动的时候，就是一个精简的虚拟机环境，设备和功能较少，相关代码、状态和初始化工作也减少

这就天生带来三个优势
1. 启动时少做事：需要创建、初始化的设备更少
2. 运行时少占用资源：需要维护的设备状态和相关处理逻辑更少
3. 安全上减少攻击面：客户机能触达的虚拟设备代码更少了


### MicroVM性能对比

| 方案 | 启动耗时 |
|---|---:|
| QEMU 通用机器配置：`q35` + SeaBIOS | **约 1,280 毫秒** |
| QEMU 精简机器配置：`microvm` | **约 180 毫秒** |
| Firecracker | **约 125 毫秒** |

### 预热

提前把 VM 和执行器启动好，留在那里等任务

### 快照

还是解决这个问题：每次任务来的时候，是否能尽量少等 ？

把已经准备好的 VM 状态保存下来；任务来了，从保存的位置恢复

快照保存的是整台 VM 在某个时刻的运行状态，所以这个进程也一起保存了。


记住这三点：
- VM 里的程序状态，最终落在内存、虚拟 CPU 和设备状态里。
- Firecracker 配合 KVM，把这些状态保存下来。
- 恢复这些状态，就可以接着运行，省去重新开机和初始化。

说实话这么理解起来，很困难，不好理解，我们直接来看相关的命令

具体的命令 见 [快照命令](./firecracker命令.md)

一般来说，快照准备的都是 内核运行时 + 业务相关的磁盘文件
如果，业务相关的服务启动很慢
那这个快照，还可以把业务程序的运行时也准备好

例如 AWS Lambda 的 SnapStart，就是先加载函数代码、启动运行时、执行初始化，再保存 Firecracker 快照，避免每次创建环境都重复初始化


# 补充：沙箱逃逸

原因可能有俩
1. 当前内核版本有漏洞，没有及时补丁更新 
   CVE-2022-0185。它是 Linux 内核漏洞，研究人员实际用它完成了容器逃逸。
2. 容器运行时（如 runc）有漏洞
3. 容器权限控制不当，需要收紧

执行 docker run
    ↓
Docker Engine：接收请求，安排镜像、网络和运行配置
    ↓
containerd：管理容器的创建、启动、停止等生命周期
    ↓
runc：按配置建立隔离环境，启动容器内的进程
    ↓
Linux 内核：实际执行隔离和资源限制


如果当前内核版本存在漏洞，python脚本利用了这个漏洞，那就会影响到宿主机


首先，容器里面的用户，看启动方式，默认是 root 用户启动了进程
那么容器中，也是root用户

为啥已经是root了，还要提权 ？
这是因为这个root用户身份，不代表完整的宿主机管理能力，受到namespace的限制
此时 容器内受限的root -> 升级为宿主机的root

## 例子：内存越界写入
写到不该写的位置，覆盖了别的数据”这个方向。但这里叫内存越界写入

1. 容器里的程序向内核提交特意构造的参数。
2. 内核检查参数时有漏洞，导致数据写出了原本分配的内存范围。
3. 攻击者进一步利用这种内存破坏，让内核执行本来不允许的操作。
4. 最终改变进程的权限或隔离状态，获得访问宿主机的能力。

！！权限也是需要用数据表示的！！

比如一个Python程序在运行，内核需要记住：

| 内核记录的信息 | 用来判断什么 |
|---|---|
| 这个进程的用户编号 | 它属于普通用户还是 root |
| 它拥有哪些特殊权限 | 能不能执行某些系统管理操作 |
| 它属于哪些 namespace | 它使用哪套文件系统、网络和进程环境 |

Linux把其中的 用户身份、权限 等信息 全部放在 **credentials进程凭证** 结构里面
内核给每个进程保存了一个身份证和权限档案

正常情况下，程序不可能修改自己的档案
-> Python：我要打开这个文件 
-> 内核：查看这个进程的身份、权限，以及文件权限 
-> 允许，或者拒绝

假如在写数据的时候，长度检查出错，写入越界了

[接收参数的区域] [其他内核数据]
        写超了 ─────→ 被覆盖

一旦发生这种事，就完全可以把进程的权限提高

### 关于进程的身份证

实际要看三部分：身份、权限、所在环境。

```yaml
进程：Python

身份：
  用户编号：0（root）

权限：
  只具备容器配置允许的部分系统管理能力

所在环境：
  文件系统：容器 A 的目录树
  进程环境：容器 A 的进程空间
  网络环境：容器 A 的网络空间
```


假设攻击最终获得了宿主机管理能力，前后可以这样对照：


| 信息 | 逃逸前 | 一种成功攻击后的可能状态 |
|---|---|---|
| 用户编号 | 已经是 `0` | 仍然是 `0` |
| 系统管理能力 | 受到裁剪 | 获得原本被禁止的能力 |
| 文件系统访问范围 | 容器自己的目录树 | 获得访问宿主机目录树的途径 |
| 其他隔离限制 | 按容器配置生效 | 攻击所需的限制被突破或绕过 |

这边只要能修改 "所在环境" 的那个内容，其实容器内的root就被提权了



# 补充知识：SSH 这套通信机制
ssh、`scp`、`sftp` 这些工具都使用 SSH 提供的安全连接和身份认证机制，分别用于远程登录／执行命令、复制文件、交互式文件传输。

| 工具 | 用途 | 示例 |
|---|---|---|
| `ssh` | 登录远端，或者执行命令 | `ssh user@机器地址` |
| `scp` | 在本机和远端之间复制文件 | `scp a.py user@机器地址:/tmp/a.py` |
| `sftp` | 交互式上传、下载、浏览远端文件 | `sftp user@机器地址` |

# 补充知识：vsock  

Firecracker，刚才说除了 SSH，还可以用 vsock

vsock 是一种专门让宿主机和虚拟机通信的通道，不需要配置 IP 地址和普通网络。

Firecracker搞的一个宿主机、客户机的通信机制，能够更快捷

| | SSH 方案 | vsock 方案 |
|---|---|---|
| 怎么找到对方 | IP 地址 + 端口 | 虚拟机标识 CID + 端口 |
| 虚拟机里谁接收 | SSH 服务 `sshd` | 我们部署的接收程序 |
| 能做什么 | 已提供执行命令、传文件等功能 | 提供数据通道，具体功能由程序实现 |


宿主机 Harness
    ↓ 通过 vsock 发送：执行 python a.py
虚拟机里的任务执行器
    ↓ 启动 Python
收集输出
    ↓ 通过 vsock 返回
宿主机 Harness


# 补充知识：vsock 对比 ssh

vsock 对沙箱平台最有吸引力的一点，是“任务控制可以独立于客户机网络”。

| 方面 | SSH + sshd | vsock + 自定义任务执行器 |
|---|---|---|
| 接入成本 | 较低，现成工具齐全 | 较高，需要开发或复用执行器 |
| 网络配置 | 通常需要 IP、网络连通 | 不需要配置 IP 网络 |
| 执行命令、传文件 | 已有 `ssh`、`scp`、`sftp` | 需要执行器提供这些功能 |
| 身份认证、加密 | SSH 已提供 | vsock 本身不提供同等功能，需要按场景设计 |
| 人工调试 | 很方便，直接登录进去 | 需要调试工具，或额外保留 SSH |
| 定制任务管理 | 可以实现，但要另外封装 | 可以直接设计任务 ID、取消、超时、输出流等接口 |

# 补充知识：seccomp

Linux 的 seccomp 机制。它允许为执行线程安装规则：遇到某类系统调用时，允许、拒绝，或者触发拦截

seccomp 是 Linux 内核提供的“系统调用过滤机制”：限制一个进程能向内核请求哪些功能。

名字来自 Secure Computing（安全计算）。它是构建沙箱的一块基础能力，本身不是完整沙箱。


应用访问操作系统功能的时候，要发出系统调用，并且检查 seccomp 规则
比如

| 系统调用 | 请求的功能 |
|---|---|
| `read`、`write` | 读写数据 |
| `openat` | 打开文件 |
| `socket`、`connect` | 创建网络连接相关资源、连接对端 |
| `mount` | 挂载文件系统 |
| `ptrace` | 调试、检查其他进程 |


应用发出系统调用
       ↓
宿主机内核检查 seccomp 规则
       ├─ 允许 → 继续执行，并接受其他权限检查
       ├─ 拒绝 → 返回错误，或终止进程
       └─ 拦截 → 触发信号等机制，交给指定处理路径

## seccomp 限制一个进程 

```bash
firejail --noprofile --seccomp.drop=mkdir,mkdirat --seccomp-error-action=EPERM node -e 'require("fs").mkdirSync("/tmp/seccomp-test-" + process.pid)'
```

firejail 是一个小工具，里面可以帮忙安装 seccomp 规则

类似于这样的模型
```
一个很小的启动程序
    ① 调用内核接口，安装 seccomp 规则
    ② exec 启动 node a.js
```

如果不用 firejail， 也能自己写c脚本，调用内核的api

```c
int main() // 程序从这里开始执行。
{
    // prctl：设置当前进程的属性。
    // PR_SET_NO_NEW_PRIVS：禁止后续执行程序获得新特权。
    // 1：开启；后面三个 0：本次操作不用的参数。
    prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);

    // PR_SET_SECCOMP：设置当前进程的 seccomp。
    // SECCOMP_MODE_FILTER：使用自定义过滤规则。
    // filter：提前定义的规则，此处省略定义；&filter：规则所在的内存地址。
    prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &filter);

    // execlp：把当前程序替换成另一个程序，PID 和 seccomp 规则保留。
    // 第一个 "node"：在 PATH 中寻找 Node 程序。
    // 第二个 "node"：传给新程序的 argv[0]，通常是程序名称。
    // "a.js"：脚本参数；(char *)NULL：表示参数列表结束。
    execlp("node", "node", "a.js", (char *)NULL);
}
```
