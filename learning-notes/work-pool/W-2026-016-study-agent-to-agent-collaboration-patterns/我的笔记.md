# 我的笔记

ReAct 和 plan-execute 模式的差别

核心区别是：计划有没有成为程序驱动执行的依据。

ReAct：程序执行模型当前选出的动作。
```
while True:
    action = model(goal, history)  # 模型根据反馈决定下一步
    if action.is_final:
        break
    result = execute_tool(action)
    history.append((action, result))
```

程序关心的是：“模型这次要调用哪个工具？”

显式的 Plan-and-Execute：程序先拿到计划，再把计划中的步骤交给执行器。

plan = planner(goal)  # 先得到步骤列表

while plan:
    step = plan[0]                 # 程序从计划中取出当前步骤
    result = executor(step)        # 执行器负责完成该步骤
    plan = update_plan(plan, result)  # 根据结果推进或调整剩余计划

不过执行器内部本身，完全可以是一个 ReAct

# 其他理解

很多工具型 Agent 的基础循环，可以理解成 ReAct 风格，最基础的一个 loop

然后有些Agent产品，会有一个 Plan Mode  ， 比如 codex 的 /plan 开启 plan mode
这个和 plan-execute 模式不一样

codex中的plan mode，是注入了一个完整的prompt
https://github.com/openai/codex/blob/5c5308fc9a9ee789049d646ef11e5400384b9c6f/codex-rs/collaboration-mode-templates/templates/plan.md

plan-execute 是会有个 明确 的 造出 结构化 plan 对象的一个过程

在这次核对的源码版本中，Codex Plan Mode 通过模式配置注入规划指令，配合用户澄清、计划文本解析和确认交接。底层继续使用原有 Agent 循环；公开终端客户端确认执行后，切回 Default 并发送执行计划的请求。它没有把计划文本解析成步骤数组逐项派发。

# 选型

我的理解：
······
如果是那种，都一步看一步，没有特别明确的步骤需求的时候，一般loop就行 ， 比如说实现xxx功能， 得先读源码、改xx文件代码 等等， 需求进来的时候，步骤、调用tool是不明确的
但是如果是哪种
数据分析 Agent  ，必然要在给定的tool里面，都执行一遍拿到相关数据，才能做后续分析
那这个就需要提前规划
我说的，比较简单，但是应该也算是理解到位了一点点吧
···

问了，AI，确实
边探索边决定下一步，用普通 Agent Loop 很自然。已经能满足绝大多数情况

但是关于 plan-execute， 我上面描述的场景，有点接近于 workflow 了

而 Plan-and-Execute 更典型的是：
用户要求分析销售下降原因，但具体查哪些数据、分几步分析，需要规划器根据目标和数据情况生成计划，再由程序推进。

总结下
| 情况 | 自然的起点 |
|---|---|
| 读到结果才知道下一步做什么 | **ReAct 风格 Loop** |
| 必须做哪些步骤已经固定 | **确定性 Workflow** |
| 步骤尚未固定，但适合先拆成一组子任务，再管理执行 | **Plan-and-Execute** |
