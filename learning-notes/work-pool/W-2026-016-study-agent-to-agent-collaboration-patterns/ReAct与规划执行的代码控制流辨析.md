## 问题来源与原始理解

2026-09-20，用户从面试问题“ReAct 和 Skill 有什么区别”进入架构讨论，继续追问：

> 表现在代码层，有什么不同？什么样的东西决定了那种模式？Prompt？

> Plan 会添加专门用于计划、执行、执行步骤等的关键 Prompt；ReAct 基本上只需要确保一个完整的 Loop 执行就行，无需额外的提示词内容。第 20 章应该就是纯 ReAct 的流程吧。

🟡 部分正确：抓住了通用反馈循环与规划阶段的差异，但“ReAct 无需提示词”和“s20 整体是纯 ReAct”需要校准。已给出解释，尚未通过用户独立复述或实验确认掌握。

## 校准后的结论

**ReAct（Reasoning + Acting，推理与行动交替）关注依据反馈决定行动；Plan-and-Execute（规划后执行）关注将规划与执行分成职责或阶段。** 两者可以组合，不是必然互斥。

在本次比较的典型显式实现中：

| 观察点 | ReAct 风格工具循环 | 显式 Planner-Executor |
| --- | --- | --- |
| 本轮输入 | 总目标、历史与工具结果 | 规划阶段收总目标；执行阶段收当前步骤和必要结果 |
| 模型输出 | 工具动作或最终回答 | Planner 输出计划；Executor 输出当前步骤结果 |
| 控制位置 | 程序执行模型选择的工具并反馈 | 编排代码读取计划，派发当前步骤，推进或重规划 |
| 状态 | 历史、工具结果；也可以有 Todo | 计划、步骤进度、执行结果和重规划依据 |

关键不是 Prompt 是否出现“plan”，也不是变量名是否叫 `plan`，而是**计划是否真的参与调度**。这是一种实用的代码阅读判断法，不是所有研究和框架对 Plan-and-Execute 的唯一严格定义。提示驱动的规划执行也存在，不能一概排除。

调用关系示意（不是已运行程序）：

```text
ReAct 风格：model(goal, history) → action → tool result → model(...)
显式规划执行：planner(goal) → plan → 取 step → executor(step) → 更新 plan
组合：executor(step) 内部运行 ReAct 风格循环
```

Prompt 负责说明职责，状态保存计划与结果，控制流负责阶段衔接。现代工具调用模型不一定需要专门写出“使用 ReAct”，但仍依赖任务指令、工具描述和反馈；原始论文的提示方法不能简化成“只要 while 就是 ReAct”。

Skill 此处指以 `SKILL.md` 为入口的任务方法与资源包，属于上下文/能力组织；Tool 是可调用操作接口。它们可以被不同控制流使用。面试官若使用另一种 Skill 定义，应先确认。

## 边界、失败与下一步

- 模型返回结果不等于步骤成功；后续需明确什么证据才能推进计划。
- 错误计划可能持续误导执行；反馈循环也可能无进展，均需要预算和终止条件。
- 先规划不要求两个不同模型，多 Agent 也不是规划执行的必要条件。
- 目前没有速度、成本或质量对照实验，不推断哪种模式普遍更好。
