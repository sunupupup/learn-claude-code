# ReAct、固定工作流与规划执行的场景选择

[总览](我的笔记.md) · [控制流辨析](ReAct与规划执行的代码控制流辨析.md)

## 我的原始理解

> 如果是走一步看一步，没有特别明确的步骤需求，一般 Loop 就行。比如实现某功能，得先读源码，才知道改哪些文件、调用什么工具。

> 数据分析 Agent 必然要在给定的 Tool 里面都执行一遍，拿到相关数据才能分析，那就需要提前规划。

## 校准与状态（2026-09-20）

🟢 第一部分在常见场景成立：依据观察决定下一动作，适合 ReAct 风格循环。探索后也可以切入显式规划，不必把同一个任务永久归为一种模式。

🟡 第二部分需要校准：“所有工具必须执行一遍”意味着程序已经知道必需步骤，更自然的起点是确定性 Workflow（固定工作流），不一定需要模型规划。没有依赖的查询还可以并行。用户已收到解释；三种模式的完整场景判断尚未独立复述验收。

| 流程特征 | 自然的起点 | 例子 |
| --- | --- | --- |
| 下一步依赖刚获得的观察，难以提前列清 | ReAct 风格循环 | 读日志、追调用链，逐步定位未知故障 |
| 必须执行的步骤和分支已经明确 | 确定性 Workflow | 固定查询订单、商品和退款接口，收齐后分析 |
| 步骤需根据目标动态生成，但能拆成可验收子任务 | 显式 Plan-and-Execute | 根据目标和数据情况规划分析步骤，执行后按发现调整剩余计划 |

**按任务的控制方式分类，不按“数据分析”“代码开发”这样的业务名称分类。** 数据分析可以用三种方式；代码迁移也可以先生成计划，再按依赖执行。

## 与前面代码结论的衔接

本次比较的显式 Planner-Executor 通常先生成结构化计划，再由编排程序读取、派发、检查和推进。只输出 JSON Todo、不让计划参与执行控制，还不足以证明采用这种结构。

“计划是否成为程序驱动执行的依据”是这两种典型代码实现的观察点，不是所有论文和框架同名模式的统一定义。执行器内部可以继续采用 ReAct。

## 选择前的三个问题

1. 步骤是否需要依据用户目标动态生成？若完全固定，先考虑普通工作流。
2. 是否能拆成边界明确、有输入输出和完成证据的子任务？
3. 是否需要程序管理步骤依赖、进度和重规划？

后两项价值明显时，显式规划通常更值得考虑；不是因为任务长就一定要引入 Planner。

## 失败边界与后续学习

错误计划会误导后续执行；ReAct 也可能无进展循环。两者都需要预算、停止条件和结果验收。尤其要先明确“每一步凭什么判定成功”，避免模型自行勾选 Todo 被当作真实完成。
