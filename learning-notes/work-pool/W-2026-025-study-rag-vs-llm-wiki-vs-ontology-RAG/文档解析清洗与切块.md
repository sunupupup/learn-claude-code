# 文档解析、清洗与切块

## 我的问题

- Demo 级别和生产级别的文档切分，有什么不同？
- 除了按 size，Markdown 也会按一级、二级标题切分吧？
- 切块前还需要哪些清洗操作？
- 完整技术链路是什么？各环节碰到什么问题，通过什么解决？

## 完整技术链路

```text
原始文档
  → 解析：识别标题、正文、列表、表格、代码
  → 清洗：去掉噪声，保留有效内容和结构
  → 切块：先按章节，再处理过长或过短的片段
  → 补上下文：标题路径、表头、来源位置
  → 检查：内容完整、长度合规、来源可追溯
  → 向量化 → 入库
```

**重点：先识别内容结构，再决定在哪里切；size 用来限制长度。**

## 1. 解析：解决“程序不知道哪些是标题、表格和代码”

**实现：用对应格式的解析器，把文档转成有类型的内容块。**

| 文件 | 解析方式 | 要保留什么 |
| --- | --- | --- |
| Markdown | 识别标题层级、段落、列表、代码围栏、表格 | 章节关系、代码边界、表头 |
| HTML 网页 | 识别页面结构，提取正文区域 | 正文标题、列表、有效链接 |
| 普通 PDF | 提取文字并恢复版面阅读顺序 | 页码、段落、表格关系 |
| 扫描 PDF / 图片 | OCR（从图片识别文字），再分析版面 | 文字、位置，以及需要复核的识别结果 |

**易错点：不能见到 `#` 就当标题，代码块里也可能有 `#`。**

技术例子：Unstructured 的解析步骤输出标题、正文、列表项等元素，后续再对元素进行清洗和切块。

## 2. 清洗：解决“噪声也被拿去向量化”

**实现：按内容类型应用清洗规则，保留原件，避免删错后无法恢复。**

| 问题 | 处理办法 | 不能误删什么 |
| --- | --- | --- |
| 换行和编码不统一 | 统一换行，明确编码；乱码文件报告异常 | 不能静默丢掉无法解码的文字 |
| 网页导航、广告、重复页眉 | 提取正文，过滤确认无用的模板内容 | 版本号、生效日期可能需要保留 |
| 正文出现排版断行、多余空白 | 在正文范围内合并无意义断行和空白 | 代码缩进、列表层级、表格结构 |
| 重复文档 | 检测重复内容，同时保留来源和版本关系 | 金额或日期不同的制度不能直接合并 |
| OCR 把金额识别错 | 标记可疑结果并复核 | 不能凭猜测修改数字、单位、否定词 |

**重点：清洗是去噪声，不是删掉所有符号、空格和换行。**

例如：把“境外不适用”删掉，会直接改变住宿报销制度的含义。

## 3. 切块：解决“按长度切断一句话，或者把不同主题混在一起”

**实现：先按标题组织章节，再在章节内部按长度细分。**

```text
识别 #、##、### 的层级
  → 保存每段正文的标题路径
  → 小节长度合适：整节保留
  → 小节过长：按段落拆，再按句子拆
  → 小节过短：只在主题和章节关系合适时合并
  → 仍然超长：采用明确的兜底拆分规则，不能静默截断
```

### 例子：按标题切分后，片段应该长什么样？

原文：

```markdown
# 员工手册
## 差旅报销
### 住宿
国内住宿上限为每晚 420 元。
境外住宿不适用上述标准。
### 交通
高铁可报销二等座。
```

期望的住宿片段：

```text
标题路径：员工手册 > 差旅报销 > 住宿
正文：国内住宿上限为每晚 420 元。
      境外住宿不适用上述标准。
来源：员工手册.md + 原文位置 + 文档版本
```

**重点：金额和适用条件尽量一起保留；标题路径帮助片段脱离全文后仍能被理解。**

父标题下、子标题前的总则也要保存，不能只提取最底层小节。若条件在其他章节，标题路径不能自动补回条件，需要保留引用关系，后续取回相关上下文。

### 表格、代码、列表不能一律按字符切

| 内容 | 问题 | 处理办法 |
| --- | --- | --- |
| 长表格 | 切完只剩数字，不知道列名和单位 | 按行拆分时保留表名、重复表头，关联单位与脚注 |
| 代码 | 切在函数中间，含义不完整 | 尽量保留代码块；超长源码可用语法分析器按函数等结构拆 |
| 操作列表 | 步骤被拆散，顺序或前提丢失 | 尽量保留完整步骤组及其前置条件 |

### size 和 overlap 分别解决什么？

- **size（块长度）：**限制每块多长；生产中还应按实际模型的 Token 单位检查。字符数不等于 Token 数。
- **overlap（重叠）：**让被拆开的连续片段重复少量内容，缓解边界信息丢失；完整章节之间不必机械重复。

**重点：标题 + 前缀 + 正文的总长度都要计算，不能只检查正文。**

## 4. 检查：解决“切出了很多块，但内容已经坏了”

**实现：保存片段与原文的对应关系，做内容检查，再用固定问题比较检索结果。**

| 检查项 | 具体看什么 |
| --- | --- |
| 内容完整 | 总则、金额、单位、“不适用”、表格脚注有没有丢 |
| 长度合规 | 完整输入有没有超过向量模型的长度限制 |
| 来源正确 | 每块能否定位到原件的正确位置与版本 |
| 检索可用 | “境外住宿也是 420 元吗？”能否找到例外条件 |

对比两种切块方法时，固定文档、向量模型、问题和检索参数，只改变切块规则。

**重点：入库成功不等于检索效果好。**

## Demo 与生产处理的核心差别

| 当前 Demo | 生产处理需要补齐的能力 |
| --- | --- |
| 空行分段，超长按字符切 | 识别结构，处理长短块和特殊内容 |
| 统一换行、去首尾空白 | 按内容清洗，保留原件和处理规则版本 |
| 补一个文档标题 | 保存标题路径、表头、条件和原文定位 |
| 检查数量、能否写入 | 检查事实是否完整，实际问题能否找到证据 |

**生产不一定要用更复杂的算法；简单规则通过真实资料验证，也可以使用。语义切分不是必选项。**

# 记录到向量数据的一条数据有哪些内容

把标题路径与正文拼接后向量化，是常见做法。
比如原文：

员工手册
休假
年假
入职满一年后，每年可享受五天年假。

可以整理成：
标题路径：员工手册 > 休假 > 年假
正文：入职满一年后，每年可享受五天年假。

这是补充原文的上下文，并没有新的事实补充

同时，这个入库的时候，还需要有很多metedata一起留存
因为其实，是硬编码解析出来的，具有一定意义，可以存下来

heading_path：["员工手册", "休假", "年假"]
body："需要提前三天申请。"

所以这条数据入库之后

有这么多的内容

```
id：片段的唯一编号

vector：[0.12, -0.08, ...]
        ↑ 模型对“标题路径 + 正文”向量化的结果

payload：随片段保存的内容和元数据
  text："员工手册 > 休假 > 年假\n需要提前三天申请。"
  heading_path：["员工手册", "休假", "年假"]
  source："员工手册.md"
  chunk_number：3
```

# 除了 md， 其他的文档切割方式
大多数情况：
常规 Markdown 文档，按标题组织、超长再拆、补上标题路径，通常就够用了。

然后其他类型的文档切割方式：

| 文档类型 | 先解决什么问题 → 实现办法 | 常见切块方式 |
|---|---|---|
| **Word** | 识别章节 → 读取标题样式、段落、列表和表格 | 类似 MD，按标题组织，超长再拆 |
| **HTML 网页** | 页面混有导航、广告 → 提取正文区域，保留标题和段落 | 按标题、段落切 |
| **文字型 PDF** | 文字位置不等于阅读顺序 → 提取文字，结合版面恢复段落、标题和表格 | 按恢复出的章节、段落切，保留页码 |
| **扫描 PDF / 图片** | 内容是图像 → OCR（光学字符识别，把图片变成文字）配合版面分析 | 识别出正文、表格后再切 |
| **PPT** | 内容按幻灯片组织 → 提取每页标题、文本和表格 | 通常以一页为起点，超长再拆 |
| **Excel / CSV** | 每行依赖列名 → 读取表头和数据行 | 按行或若干行成块，每块带上表头 |
| **TXT** | 没有明确标题结构 → 利用空行、换行和句子边界 | 按段落组合，超长再拆 |


# 关于**数据清洗**，
这个其实是比较轻量、简单的工程
一个常见的处理是统一格式，不同的文件换行符 \r 、 \r\n 不同， 可以全部通用一起来
还有个事可能会带有 特殊的编码标记，比如 BOM 编码标记，需要删除

数据清洗，对于空格并不是舞男删除，需要保留有意义的空白，比如 代码缩进、列表缩进 这个有意义

# 关于**chunk大小、推荐大小、如何决定chunk大小、如何eval**
疑惑是否有成熟的直接利用的chunk大小？

已经有成熟的选型和评估方法：先用一个常见大小起步，再通过 eval（评估）比较切块效果。

可以从 512 tokens 起步，再对比 256、512、1024 三档。 这里的三档是建议的实验配置，不是强制标准；微软的切块指南也把 512 tokens 作为起点。https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents
微软官方建议，可以是 512 token


eval的方法，也简单

评估集：20～30 个真实问题，每题标出原文中的必要证据

方案 A：标题切分 + 256 tokens 上限
方案 B：标题切分 + 512 tokens 上限
方案 C：标题切分 + 1024 tokens 上限

保持相同：文档、向量模型、检索方式
分别检查：每题检索出的前 5 个片段

然后看几个指标重点看三个问题：
- 找全了吗？ 回答所需的证据有没有被检索出来。
- 杂不杂？   找到的内容里，有多少无关信息。
- 成本多大？ 检索结果总共占多少 tokens，耗时多少。


前两类评价有成熟指标，例如 **Context Recall（上下文召回）**和 Context Precision（上下文精确性），Ragas 等评估工具提供了相应实现。初学时先人工检查，也能开展这个实验。Ragas 指标文档


所以我总结下啊
有两种chunk的满足绝大多数的chunk带大小依据
1. 业务数据相关：比如我的数据全是excel，一行就100字不到，那就可以 按行切割，或者 100字切割
2. 模型相关：有些模型（上面谷歌的那个） 有自己的 max token限制，同时他有推荐的自己token大小切割建议

# 小问题：chunk太大、太小，分别有啥问题

除了 模型 token 上限 的问题

核心：太大容易杂，太小容易散。

太大的话
1. 多类别信息混杂，导致每次query的时候，可能 某些 信息就不突出了，可以当成是 计算相似度的时候，注意力不集中
2. 浪费检索的时间
3. token 太多，带了太多无关的内容给模型

太小的话
1. 语义被切割很散，一句话都不完整了


# 关于**切割方式， 除了chunk固定大小，还有啥方式**
https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents#common-chunking-techniques

也是参考这个文档

还有个比较常见的是：语义切割

不同的块，之间，在哪语义改变了，就在那切割

一个例子

"年假需要提前三天申请。申请后由直属主管审批。公司提供工作日午餐补贴。补贴随当月工资发放。"

前两句都是 年假 相关，后两句是 餐补 相关， 所以在间切割

没有必要按照chunk size，他们是一个整体了，浪费信息

这种按照语义，一般有两种方式
1. 切成散的小句子，然后向量化，自己计算相似度，然后自己聚合小句子，成为一个完整的向量数据库内容
2. 给LLM分析  “按话题连续性分组，只返回段落编号范围，不改写原文。”  就让他直接切分、内容分组

# 名词补充：召回

召回其实就是检索，但是我们上面的检索，单纯指的是 “向量检索”
还有其他检索方式：
1. metadata 关键字段检索， 比如 常见的 文档名、文档权限
2. 关键词 检索， 在 正文 内容 ，必须要有关键词 出现
3. 向量相似度检索

懂了懂了！

对，正是 ES（Elasticsearch）擅长的检索方式，完全可以用它实现 RAG 的关键词召回。 这里容易被名字绕进去：
- **text 类型：**用于正文全文检索，会分析、分词；常搭配 match 查询。 这边就以来数据库本身的分词器了，比如中文分词器cjk
- **keyword 类型：**把整个字段值当成一个整体；常搭配 term 做精确匹配，比如文件名、状态、标签。
所以，“在一段正文中搜索年假”，一般用 text；“只查文件名恰好是员工手册.md”，用 keyword

完全就是类似于 es 里面的检索方式

召回就是按某种条件或相关性，把候选数据查出来。完全可以借用你对 ES 的理解。
常见能力包括：
- **向量相似度搜索：**查含义接近的内容。
- **全文检索：**在正文、标题里匹配词。
- **精确匹配：**限定文件名、分类、用户 ID 等。
- **范围过滤：**限定日期区间、价格区间等。

了解，完全可以类比es啊
我说夸张点啊
所谓的召回，就是查数据，但是有各种方式
向量相似度，这是向量数据库独有的查询方式
然后还具有其他各种常用的查询方式，可以类比es，关键词检索、关键词精确匹配、甚至还有 比如 时间范围搜索 ？ 肯定是有这种能力的，只是可能某些向量数据库没搞是吧

# 名词补充：重排序

原因：向量相似度判断的是整体含义接不接近，最接近的内容不一定最能回答问题。

核心处理逻辑 就是 二次处理向量数据库出来的score -> 重新打分 -> 得到新的 re-rank score
对向量数据库召回的候选片段，结合用户问题重新评估相关性，得到新的 Rerank Score，再按新分数排序。

重排序（Reranking），就是把已经查出来的候选片段，再按“谁更能回答当前问题”重新排一次。
你可以类比 ES：第一轮查询拿到候选结果，第二轮用更细的相关性判断重新打分。
问题：不是已经按向量相似度排过了吗？
对，但向量相似度判断的是整体含义接不接近，最接近的内容不一定最能回答问题。

向量数据库出来的时候已经自带了 score
但是，这也只是 程序化的， 相似度 匹配

所以还可以经过一个 Rerank 的处理，这边需要依赖外部的模型了

有很多专门用于重排序的模型：
- BAAI/bge-reranker-base
  基于 XLM-RoBERTa，属于编码器路线：一起读取问题和片段，再输出相关性分数。通常称为“专门的重排序模型”，而不是聊天大模型。官方模型说明
- BAAI/bge-reranker-v2-gemma
  基于 Gemma 大语言模型，经过训练用于重排序。它就是 LLM-based Reranker（基于大语言模型的重排序模型），官方也明确使用这个分类。官方说明

# 额外扩展，不细看

结合我们已经聊过的内容，常见 RAG 可以先用这条链路串起来：
文档解析、清洗
→ 切块（Chunking）
→ 向量化（Embedding）
→ 建立索引（Indexing）

用户问题
→ 查询改写（可选）
→ 召回（Retrieval）
→ 重排序（Reranking，可选）
→ 上下文组装
→ 生成回答，并附引用

除了召回和重排序，还有哪些关键的词

| 技术名词 | 具体在做什么 | 小例子 |
|---|---|---|
| **索引（Index）** | 提前建立便于搜索的数据结构 | 向量索引用于相似度搜索；倒排索引用于关键词搜索 |
| **查询改写（Query Rewriting）** | 把用户问题变成更适合检索的表达 | 结合上文，将“那怎么申请？”改成“年假如何申请？” |
| **混合检索（Hybrid Search）** | 同时使用关键词与向量检索 | 关键词匹配产品型号，向量匹配问题含义 |
| **结果融合（Fusion）** | 合并多路检索结果，并整合排名 | 关键词查到一批、向量查到一批，合并去重；常见算法叫 RRF |
| **上下文组装（Context Assembly）** | 选择、排列检索片段，放进模型输入 | 保留相关正文、标题、来源，控制总长度 |
| **上下文压缩（Contextual Compression）** | 从候选资料中提取与问题相关的部分 | 从整段福利说明中提取年假规定 |
| **引用与溯源（Citation / Provenance）** | 让答案能对应回原文证据 | 回答后附“员工手册，第 3 节” |
| **忠实性（Faithfulness）** | 评估回答是否得到提供的证据支持 | 原文只说“五天”，回答不能自行增加“可累计三年” |
