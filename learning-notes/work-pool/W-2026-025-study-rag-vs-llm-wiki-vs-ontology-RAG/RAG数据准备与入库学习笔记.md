# RAG 数据准备与入库

用户的问题：入库前除了文档向量化，还有切割规则、入库参数等；把这一阶段单独展开，看看完整一些是什么样子。

这部分通常叫 **数据摄取流程（Ingestion Pipeline）**：把原始资料加工成后续可以检索的记录。在向量 RAG 中，也常把这部分称为索引构建。这里的“索引构建流程”比数据库内部的向量索引算法范围更大。

当前状态：🟢 已完成本地切块预览；真实模型服务与检索质量尚未验证；用户掌握情况待实操确认。

## 先看数据怎么变化

```text
原始文档
  → 读取、解析：获得正文与结构
  → 清洗：去掉无关噪声，保留事实和条件
  → 切块：把长文拆成若干 chunk（片段）
  → 补上下文和来源：标题、文件名、片段编号等
  → Embedding（向量化）：模型把每个片段编码成一组数字
  → 入库：保存向量 + 原文 + 来源信息
  → 检查：有没有漏文、错配、旧数据残留
```

一条入库记录可以理解成：`编号 + 向量 + 原文 + 元数据`。**元数据（Metadata）**是描述原文的信息，例如文件名、章节和版本；Qdrant 把这类附带字段放在 `payload` 中。

后续才是：问题向量化 → 检索 → 把取回的原文交给聊天模型。`top_k`（最多取几条）和检索分数 `threshold`（过滤门槛）属于后续检索阶段，不放进入库实验。

## 数据准备阶段有哪些要点

下面是知识地图，不要求第一次全部实现。先看“切块、来源、向量化、写入”四项。

| 环节 | 要决定什么 | 做不好会怎样 | 本实验做了什么 |
| --- | --- | --- | --- |
| 选资料 | 哪些资料有效、最新、允许进入知识库 | 把过期或无权限资料当答案 | 只读三份虚构 Markdown |
| 解析 | 如何读取标题、正文、表格、代码、扫描件 | 表格列错位；PDF 阅读顺序错乱 | 只识别首行一级标题；不支持 PDF/OCR |
| 清洗 | 去除哪些页眉、乱码、重复内容 | 把“不适用”、金额单位等重要内容删掉 | 统一换行、去掉首尾空白 |
| 切块 | 按什么边界切、多长、重复多少 | 条件与结论分离；一块混进多个主题 | 按段落后限长，或正文固定长度切 |
| 补上下文 | 是否给片段加文档标题、章节路径 | 单独看“上限 420 元”不知道指什么 | 可给每块加文档标题 |
| 保存来源 | 文件名、页码、章节、版本、权限等 | 无法引用、追查或过滤 | 保存文件名、标题、编号、原文哈希 |
| 向量化 | 模型、输入长度、文档编码规则 | 截断关键内容；语义匹配差 | 可配置模型和文档前缀，核对返回顺序 |
| 建集合 | 向量维度、距离计算方式 | 维度不兼容，或打分方式不适配 | 从输出取维度；使用余弦距离配置 |
| 批量写入 | 模型请求批量、数据库写入批量 | 请求超限、内存过大、部分失败 | 两个独立批量参数 |
| 更新与删除 | 重复导入、旧片段、模型变更怎么处理 | 新旧制度同时被检索出来 | 每轮用新集合，暂不做增量同步 |
| 检查与评测 | 内容完整性、记录数、典型问题能否找到答案 | 入库成功但根本找不到所需事实 | 预览原文、检查数量；检索评测后续做 |

**哈希（Hash）**是根据内容计算的摘要，本实验用它标记原文版本。它不自动完成重复文档清理或旧片段删除。

## 切块：先理解三件事

解析、清洗与切块的具体问题和技术实现见 [文档解析、清洗与切块](文档解析清洗与切块.md)。

### 1. 切分边界

| 方式 | 做法 | 取舍 |
| --- | --- | --- |
| 固定长度 | 每隔一定长度切一刀 | 简单，但可能切断句子、表格或条件 |
| 按段落/标题 | 优先保留原有结构 | 更容易保留完整含义，但有些段落仍然太长 |
| 递归切分 | 大段放不下，再尝试句子等更小边界 | 能兼顾长度和边界，需要明确分隔规则 |
| 语义切分 | 依据语义变化寻找边界 | 有额外计算和参数，也需要评测效果 |

实验中的 `paragraph` 只是“空行分段 + 超长时固定切”，不是完整 Markdown 解析器，也不是语义切分器。

### 2. chunk_size：一块多长

本实验 `chunk_size = 80` 指 **正文的 Python 字符数**，为了观察而故意设小，不是生产推荐值。

模型的输入限制通常按 **Token（模型处理文本的单位）**计算；字符数不等于 Token 数。加上的标题和前缀也会占模型输入长度，因此“正文没超过 80 字符”不等于“完整模型输入已经通过长度检查”。

块太小可能丢上下文；块太大可能把多个主题混在一起，增加检索和生成时的噪声。不存在所有资料通用的最佳长度。

### 3. chunk_overlap：相邻块重复多少

`chunk_overlap = 20` 表示同一段被拆成连续几块时，后一块从前一块结束前 20 个字符处开始。

重复能缓解边界信息丢失，但会增加编码成本、存储和重复检索。它也不能保证跨块的复杂条件一定完整。本实验不在不同段落之间添加重叠。

## 向量化、距离算法、向量库不是一回事

- **Embedding 模型**：负责把文字变成数字，影响“意思有没有表达好”。普通 RAG 导入通常调用已经训练好的模型，不是在这里重新训练模型。
- **距离/相似度计算**：负责比较两组数字，例如 Cosine（余弦相似度相关的度量）。需要遵循模型推荐配置，本实验固定使用 Qdrant 的 `COSINE`。
- **向量索引算法**：负责大量向量中怎样高效查找，例如 HNSW。它与文字如何被编码是不同层次。
- **向量数据库**：保存和查询向量、原文和其他字段；这里使用 Qdrant。本地实验不能代替服务端性能测试。

文档和问题的向量必须处于**兼容的向量空间**。一般使用同一检索模型规定的文档与查询编码方式；不能因为两个模型维度一样就随意混用。

有的模型区分文档和问题：例如 multilingual-e5 的模型卡要求文档使用 `passage: `、查询使用 `query: `。另一些服务通过专用参数区分输入类型。因此 `document_prefix` 默认留空，按实际模型文档配置，不能给所有模型一律加前缀。

更换模型、维度或文档编码规则后，通常需要重新编码文档，并让查询端同步使用匹配的配置。本实验保存配置记录，但没有自动处理服务商在同名模型下的版本变动。

## 实验代码：只展开入库这一段

代码：[ingest_demo.py](experiments/rag-basic/ingest_demo.py)。保留原来的 [rag.py](experiments/rag-basic/rag.py)，两个实验的数据目录独立；`rag.py` 不会自动检索这个新实验的集合。

主要参数都在代码顶部：

| 参数 | 默认值 | 用途 |
| --- | --- | --- |
| `preview_only` | `True` | 只展示切块并写预览 JSON；改为 False 才向量化入库 |
| `chunk_mode` | `"paragraph"` | 按段落后限长；`"fixed"` 则直接切整个正文 |
| `chunk_size` | `80` | 每块正文字符数上限 |
| `chunk_overlap` | `20` | 同一段连续块的重复字符数，必须小于块长度 |
| `include_title` | `True` | 给每块补文档标题 |
| `document_prefix` | `""` | 按模型要求添加的文档编码前缀 |
| `embedding_batch_size` | `4` | 一次模型请求发几个片段；仍需考虑服务的总 Token 限制 |
| `write_batch_size` | `4` | 一次数据库写入几条记录 |
| `base_url`、`embedding_model` | 待填写 | 向量模型的服务地址和名称 |
| `collection` | `"prepared_documents_v1"` | 数据集合名；每轮实际导入换新名字 |
| `documents_dir`、`output_dir` | 代码旁的目录 | 原始资料和实验输出位置 |

**维度（Dimension）**是每条向量有几个数字，不是每块有几个字。本实验根据实际向量输出确定维度，再创建集合。

第一次只执行下面一步，在 `experiments/rag-basic` 目录运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 ingest_demo.py
```

预期：打印每块正文和来源，生成 `.rag-data-preparation/chunks-preview.json`，不调用模型。2026-09-19 本地实际结果：办公时间 2 块、差旅制度 3 块、设备借用 2 块，共 **7 块**。

先观察差旅制度：一块末尾是“住宿标”，下一块包含“住宿标准”。这说明当前切分器严格按长度切，并不理解句子。**记录数正确只是程序检查通过，不等于资料加工得好。**

用户实操记录：待运行，待观察并复述。

下一轮可只把 `chunk_size` 改成 `160` 再预览，比较数量和内容；每次只改一个参数，便于知道差异从哪来。

真正入库时，再填写模型地址、模型名及本地 `.env` 的 `RAG_API_KEY`，把 `preview_only` 改为 `False`。这一步会把片段发送到所配置的服务，可能计费。本轮没有调用真实模型。

代码先收集向量，再按批写入本地 Qdrant，最后核对记录数并保存集合配置 JSON。返回结果按 `index` 对齐输入，避免“原文 A 配上向量 B”。若集合名已经存在，会在调用模型前停止，要求换新名字。

## 详细到哪里为止

这个实验仍然是教学版：把向量全部收集在内存中，不适合直接导入海量资料；没有失败续传、自动重试、PDF 解析、Token 精确计数或自动评测。

生产环境还有几个容易遗漏的点，后续逐个学：

- **更新和删除**：`upsert` 是同 ID 更新、无 ID 新增；它不会自动删除旧文档拆出来的多余片段。哈希和 ID 也不等于完整同步机制。本实验用新集合避开混杂问题。
- **权限**：入库保存权限信息还不够，检索时也必须执行相应过滤。
- **失败与发布**：批次失败可能留下部分数据；完成验证再切换到新集合，可以减少用户读到半成品的机会。本实验尚未实现自动切换。
- **规模和成本**：记录 Token、耗时、请求失败及费用；大规模才进一步评估 HNSW、量化、磁盘存储等配置。
- **质量验收**：准备几个确实有答案的问题以及没有答案的问题，检查能否找到正确原文。入库只是为这一步提供材料。
