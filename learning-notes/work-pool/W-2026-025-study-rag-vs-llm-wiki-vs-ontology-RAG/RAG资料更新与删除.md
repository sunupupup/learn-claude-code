# RAG 资料更新与删除

## 我的问题

> 文档和向量保存在库里，修改、删除文档后，旧片段是否还会被查到？

- 改了原文件，向量库会自动更新吗？
- 一份文档原来切成 3 块，修改后只有 2 块，剩下的旧块怎么办？
- 删除原文件，怎样找到并删除它对应的全部片段？
- 更新到一半失败，会不会同时查到新旧版本？

## 完整技术链路

```text
发现文档新增、修改或删除
  → 用文档 ID 找到库中的对应记录
  → 新增/修改：重新处理内容，生成需要更新的向量
  → 写入新片段，清理或停用旧片段
  → 删除：清理或停用这份文档的全部片段
  → 验证查询只返回当前有效资料
```

**重点：原文件与向量库是两份数据；没有同步逻辑，修改原文件不会自动修改库里的记录。**

## 第一个 Demo：为什么旧块会残留？

先用这个预期例子观察数据变化，实际代码与输出在新对话逐步补充。

```text
第一次导入：
文档 A → A-1、A-2、A-3

修改后只有两块，只覆盖前两个 ID：
文档 A → A-1（新）、A-2（新）

库里可能变成：
A-1（新）、A-2（新）、A-3（旧，尚未删除）
```

**问题：更新现有 ID，不等于同步整份文档。**

**解决方向：保存文档与片段的对应关系，找出这次不再存在的旧片段并清理。** 如果每次生成新 ID 而只新增，可能连旧版的全部片段都留下。

## 需要哪些字段？

| 字段 | 用途 |
| --- | --- |
| `doc_id` | 稳定标识一份文档，用来找到它的全部片段 |
| `chunk_id` | 标识一条片段，用来更新或删除具体记录 |
| `source` | 原文件或来源位置 |
| `version` / `content_hash` | 区分内容版本、帮助判断是否发生变化 |

**重点：文件位置、文档身份、内容版本是不同概念。** 内容改了，文档身份通常仍然相同；哈希变化只能帮助发现变化，不会自动执行同步。

## 按 Demo 一步步学

| 顺序 | 操作 | 看什么结果 |
| --- | --- | --- |
| 1 | 导入一份三块的文档 | 打印文档 ID、片段 ID、正文 |
| 2 | 改成两块，只写新内容 | 观察旧块是否残留 |
| 3 | 增加旧片段清理 | 验证只剩新内容，其他文档未受影响 |
| 4 | 删除这份文档 | 验证它的全部片段不再被查到 |
| 5 | 模拟更新中途失败 | 再讨论先删后写的空窗，以及版本切换办法 |

先用隔离的本地实验库观察记录变化。若使用模拟向量，要明确它只能验证同步逻辑，不能证明真实语义检索质量。

**每次只加一个机制：问题 → 小段代码 → 实际输出 → 修改后的对照。**

# 连接器的概念

企业 RAG 可以统一接入、统一检索，但原文仍由各自的业务系统管理。

企业网盘里的 PDF ──┐
内部 Wiki 页面 ────┼→ 同步程序 → 解析、切块、向量化 → 检索库
业务数据库的记录 ──┘

这里负责读取不同来源、发现变化的模块，叫连接器（Connector），属于数据接入层。例如 Azure AI Search 支持多个数据来源通过不同索引器写入同一个搜索索引。官方说明 https://learn.microsoft.com/uk-ua/azure/search/search-indexer-overview

当然这种文档管理方式只是一种方式， 不是RAG的必要条件


可以把它理解成“连接多个文档池”。 稍微校准一下：通常是 RAG 平台提供一组连接器，不同连接器负责对接不同来源，而不是一个万能连接器。
“文档池”是你的直观叫法，对应到系统里，可能是知识空间、网盘目录、对象存储桶、OSS，或者业务系统里的知识文章。
每个团队维护自己的资料，是一种合理的分工，但不要求每个团队单独部署一套系统。

三个层次来看：

| 层次 | 负责什么 | 例子 |
|---|---|---|
| 团队 | 内容正确性、更新、谁能看 | 人事维护员工制度 |
| 文档平台 | 保存原文、编辑、版本和权限 | Wiki、企业网盘 |
| RAG 平台 | 接入、同步、切块、建立索引和检索 | 通过连接器读取人事资料 |
