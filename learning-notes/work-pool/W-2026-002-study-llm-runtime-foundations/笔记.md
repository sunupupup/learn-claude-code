# LLM Runtime 基础笔记

> 当前状态：已经建立 Tokenizer、Checkpoint、LoRA 和推理程序的初步关系。下一阶段从“推理程序怎样加载并运行模型”继续学习。

## 一、Tokenizer：文本与 Token ID 的转换器

### 1.1 我的原始理解（保留）

- BPE 的训练过程会统计经常一起出现的字或片段，并将它们合并成 Token。
- 每个字都可以作为一个 Token，但这样会让一句话的 Token 序列变长。
- BPE 有两个重要内容：词表和合并规则。
- Tokenizer 编码一般可以理解为“切分 + 映射”。
- 模型的 Tokenizer 与神经网络需要严格匹配。

### 1.2 校准后的结论

Tokenizer（分词器）位于模型神经网络外部，负责：

```text
编码：文本 → Token → Token ID
解码：Token ID → Token → 文本
```

Tokenizer 是完整模型系统的配套组件，但通常不属于神经网络本体。它和模型权重必须兼容，因为模型训练时已经固定了每个 Token ID 的用途。

例如，训练时如果 ID `123` 表示“猫”，输入端的 Embedding 和输出端的 LM Head 都会按这个含义学习。随意换成一个让 ID `123` 表示“汽车”的 Tokenizer，即使程序能运行，语义也会错位。

### 1.3 Token 不等于词

原来的理解是“更常见的是一个词对应一个 Token”。更准确的表述是：

> 现代 LLM 常用子词或字节级切分；一个 Token 可能是完整词、词的一部分、单字、标点、带空格的片段，甚至是不完整的字节片段。

全部按字符切分是可行的，但会产生更长的序列：

- 相同上下文窗口能容纳的文字更少；
- 模型需要处理更多位置，计算量和内存开销通常更高；
- 自回归输出需要更多生成步骤；
- 模型需要从更细碎的单位中学习组合规律。

全部按完整词切分也有问题：词表会非常大，新词、人名、代码变量和拼写变化难以覆盖。因此子词方法在“词表大小”和“序列长度”之间做折中。

### 1.4 BPE：训练与编码是两个阶段

BPE（Byte Pair Encoding，字节对编码）的核心产物包括：

- **Vocabulary（词表）**：有哪些 Token，以及每个 Token 对应的 ID；
- **Merge Rules（合并规则）**：哪些相邻片段可以合并，以及合并的优先顺序。

#### 训练 Tokenizer

```text
准备训练文本
→ 标准化和预切分
→ 从基础符号开始
→ 统计当前最常出现的相邻片段对
→ 合并该片段对并加入词表
→ 重新统计并继续合并
→ 达到目标词表大小等停止条件
```

“智 + 能 → 智能”“人工 + 智能 → 人工智能”可以作为教学示例，但这里只能说明算法思路，不能当作某个真实模型的分词结果。真实 BPE 还可能从字节开始，而不一定从完整汉字开始。

[词表与合并规则示意图](./dict.png)

#### 使用 Tokenizer 编码

日常编码不会重新扫描大量训练数据，也通常不会产生新规则。它只是对新文本应用已经训练好的配置：

```text
我 喜 欢 人 工 智 能
→ 按已有切分与合并规则处理
→ 假设得到：我 / 喜欢 / 人工智能
→ 查词表
→ 假设得到：[1, 19, 32]
```

上面的 Token 和 ID 都是教学假设。真实结果必须指定模型和 Tokenizer 后实际运行验证。编码时还要遵守合并规则的优先级，并不只是从词表中随意寻找最长词。

#### 模型生成与解码

原先把“大模型计算”和“Tokenizer 解码”写在了同一个步骤里，应拆成：

```text
输入文本
→ Tokenizer 编码
→ 输入 Token ID：[1, 19, 32]
→ 神经网络计算下一个 Token 的候选分数
→ 采样器选择下一个 Token ID：假设为 [4]
→ Tokenizer 解码生成的 ID
→ 假设得到文字：“是的”
```

Tokenizer 的解码本身不需要模型参与。模型负责产生 Token ID，Tokenizer 负责把 ID 还原成文字。

### 1.5 算法、工具与厂商不要混为一类

- BPE、Unigram、WordPiece 是 Tokenization 算法或模型；
- SentencePiece 是一种 Tokenizer 工具，支持包括 BPE、Unigram 在内的方案；
- OpenAI、Anthropic、Google 是模型或产品提供者。

不能简单记成“Google 使用 Unigram，OpenAI 和 Anthropic 使用 BPE”。应对具体模型和版本核验其 Tokenizer 文件与官方说明。

### 1.6 当前必须掌握

1. Token 数不能只按字符数、词数或语义整体判断。
2. Token ID 只是词表编号，不表示语义大小或概率。
3. 训练 Tokenizer 是建立词表和规则；编码是应用已有规则。
4. Tokenizer 必须与模型权重和特殊 Token 配置匹配。
5. Chat 模型还需要匹配 Chat Template，将 system、user、assistant、tool 等消息转换为模型期望的 Token 序列。

## 二、从训练产物到运行中的模型

### 2.1 一个文本模型的主要产物

```text
训练数据
→ 训练 Tokenizer（或采用已有 Tokenizer）
→ 将文本编码为 Token ID
→ 训练神经网络预测后续 Token
→ 保存训练产物
```

常见产物包括：

| 产物 | 作用 |
| --- | --- |
| 模型配置 | 描述网络结构，例如层数、隐藏维度和注意力头数 |
| 模型权重 | 神经网络训练得到的大量参数 |
| Tokenizer | 词表、切分规则、特殊 Token 等 |
| Chat Template | 把聊天消息序列化成模型训练时使用的格式 |
| 评估信息 | 记录能力、适用范围和已知限制 |

### 2.2 Checkpoint

Checkpoint（检查点）原本表示训练过程中的一次存档。完整训练 Checkpoint 可能包含：

- 模型权重；
- 优化器状态；
- 学习率调度状态；
- 当前训练步数；
- 随机数状态等恢复信息。

实际使用中，人们也常把“只用于推理的模型权重文件”称为 Checkpoint。因此看到 Checkpoint 时，需要继续确认它保存了哪些内容，不能仅凭名称判断能否完整恢复训练。

`.safetensors` 是保存张量数据的一种文件格式，不等于 Checkpoint 这个概念：

- 基础模型 Checkpoint 可以使用 `.safetensors`；
- LoRA 也可以使用 `.safetensors`；
- 大模型权重还可能拆成多个 `.safetensors` 分片。

### 2.3 LoRA

LoRA（Low-Rank Adaptation，低秩适配）可以先理解为对基础模型权重的一组较小调整：

```text
基础模型权重（必需）
        +
LoRA 调整参数（可选）
        ↓
应用调整后的运行模型
```

LoRA 通常不能脱离兼容的基础模型独立工作。基础模型不加载 LoRA 也能推理；LoRA 还可能提前合并进基础模型权重，此时运行时不需要再单独加载。

## 三、这些是不是一个 LLM API 应该有的内容？

更准确地说，它们是 **LLM API 背后的模型服务所依赖的组件**。API 是应用看到的调用接口，不是这些文件本身。

```text
客户端 / Agent
→ LLM API：接收请求、鉴权、限流、返回流式结果
→ Chat Template：把消息整理成模型输入格式
→ Tokenizer：文本转换为 Token ID
→ 推理程序：调度并执行神经网络计算
→ 模型配置 + Checkpoint 权重 + 可选 LoRA
→ Logits 与采样：选择后续 Token ID
→ Tokenizer 解码
→ LLM API 返回文字或 Tool Call
```

必须区分：

| 层次 | 负责什么 |
| --- | --- |
| API 层 | 请求协议、认证、限流、流式传输和错误响应 |
| 推理 Runtime 层 | 模型加载、请求调度、Prefill、Decode、KV Cache、采样 |
| 模型层 | 根据权重执行神经网络计算并产生 Logits |
| Tokenizer 层 | 文本、Token 和 Token ID 之间转换 |
| Agent / Harness 层 | 组装上下文、校验 Tool Call、执行工具、保存业务状态 |

LoRA 是可选模型资产；Checkpoint、Tokenizer 和模型配置通常是运行文本模型所必需的。一个具体服务可能把多个步骤打包在同一个进程中，也可能拆成不同服务。

## 四、推理程序（Inference Runtime / Inference Engine）

### 4.1 当前理解

推理程序负责加载模型结构、配置和 Checkpoint 权重，并使用这些权重完成实际计算。Checkpoint 只是磁盘上的数据，不会自行运行。

```text
模型结构和配置
       +
Checkpoint 权重
       +
匹配的 Tokenizer / Chat Template
       ↓
推理程序加载到内存或显存
       ↓
接收请求并执行模型计算
       ↓
生成 Token ID 并返回结果
```

### 4.2 推理程序通常负责什么

1. **模型加载**：读取配置和权重，检查模型结构、参数名称、数据类型是否匹配。
2. **设备管理**：决定权重与计算放在 CPU、GPU，还是跨多张 GPU。
3. **请求预处理**：应用 Chat Template 和 Tokenizer，得到实际输入序列。
4. **请求调度**：对单个或多个请求排队、批处理，并管理并发。
5. **执行推理**：完成 Prefill 和逐 Token Decode。
6. **缓存与内存管理**：管理 KV Cache、显存块、模型权重和临时张量。
7. **生成控制**：处理 temperature、top-p、停止条件和结构化输出等规则。
8. **结果输出**：解码 Token，并通过流式响应或普通响应返回。
9. **运行观测**：暴露延迟、吞吐、Token 数、显存和错误等指标。

并非每个推理程序都独自实现以上所有能力。有些把 API Server 集成在内部，有些只提供计算库，需要外部服务补齐 API、鉴权和监控。

### 4.3 常见推理程序的定位

| 工具 | 适用场景 | 当前学习定位 |
| --- | --- | --- |
| Hugging Face Transformers | Python 研究、观察模型输入输出和生成过程 | 适合本任务做机制实验 |
| Ollama | Windows/macOS/Linux 上快速运行本地模型 | 适合第一次完整跑通 |
| llama.cpp | CPU、边缘设备、量化模型和本地服务 | 适合观察 GGUF 与本地推理 |
| vLLM | GPU 在线服务、高吞吐和多用户并发 | 生产候选之一 |
| SGLang | 低延迟、高吞吐、前缀复用和分布式服务 | 生产对照候选 |
| TensorRT-LLM | NVIDIA GPU 深度优化 | 对特定硬件做性能对照 |

不能直接说“大部分生产模型都使用 vLLM”。更准确的结论是：vLLM 是当前开源 LLM GPU 在线服务的主流候选之一，真实选型需要使用目标模型、硬件和请求负载比较首 Token 延迟、逐 Token 延迟、吞吐、显存、并发和功能兼容性。

### 4.4 推理程序学习路线

本章按下面顺序继续，不一次展开全部内容：

1. **加载阶段**：权重从磁盘进入内存/显存时发生什么；配置为什么必须匹配。
2. **一次请求**：Chat Messages 怎样经过模板和 Tokenizer 进入模型。
3. **Prefill 与 Decode**：为什么首 Token 和后续 Token 的计算特征不同。
4. **KV Cache**：缓存的对象是什么，为什么会消耗显存。
5. **调度与批处理**：vLLM 等引擎为什么比简单的逐请求执行吞吐更高。
6. **服务化边界**：推理引擎、API Server、Gateway、Agent Runtime 分别负责什么。
7. **生产验证**：TTFT、TPOT、吞吐、并发、显存、错误和恢复如何测量。

### 4.5 下一小节：加载阶段

下一轮只解决一个问题：

> 推理程序启动一个模型时，模型配置、Tokenizer 和权重分别加载到哪里，它们在运行中承担什么职责？

当前不要求安装 vLLM、下载大模型或占用 GPU。先建立加载链路，再决定使用 Ollama、llama.cpp 或 Transformers 做最小观察实验。

## 五、当前心智模型

```text
Tokenizer：文字和 Token ID 之间转换
Checkpoint：保存训练得到的模型权重，或更完整的训练状态
模型配置：规定神经网络怎样组织和计算
推理程序：加载模型资产、管理资源并执行计算
LoRA：可选的权重调整
LLM API：把模型服务能力通过网络接口提供给客户端
Agent Runtime：在模型之外管理上下文、工具、权限和业务状态
```

## 六、暂不深入注意力公式时，应该先补什么

自注意力涉及向量、矩阵和 Q/K/V，第一次接触时理论密度较高，可以先放下。为了理解“一个 LLM API 请求到底怎样跑完”，先掌握下面这条可观察的运行链路：

```text
messages
  → Chat Template 拼成模型规定的文本格式
  → Tokenizer 编码为 Token ID
  → Embedding 把每个 Token ID 查成向量
  → 模型计算下一位置的 Logits
  → 采样器选择一个 Token ID
  → 把新 Token 追加到序列并继续 Decode
  → Tokenizer 解码为文字
```

### 6.1 Chat Template：聊天消息怎样进入文本模型

API 中的 `system`、`user`、`assistant` 是结构化消息，但基础模型真正接收的是一串 Token ID。Chat Template（聊天模板）负责把角色、内容和特殊标记按模型训练时的格式串起来。

因此，同一组 messages 使用错误模板时，程序可能仍能运行，但模型可能分不清角色、不能正确停止，或输出质量下降。Chat Template 和 Tokenizer 一样，都是模型必须匹配的配套资产。

### 6.2 Embedding：Token ID 进入神经网络的第一步

Token ID 只是词表中的整数编号，本身没有“数字越接近，语义越接近”的含义。Embedding（词嵌入）通过权重表查询，把每个 Token ID 变成长度为 `d_model` 的向量，神经网络随后处理这些向量。

```text
Token ID 123
    ↓ 查询 Embedding 权重表的第 123 行
[0.12, -0.87, 0.33, ...]
```

这也解释了为什么 Tokenizer 不能随意替换：ID 的含义一旦错位，就会查到错误的 Embedding 行。

### 6.3 Logits 和采样：模型不是直接吐出一句话

模型每轮会为词表中的每个候选 Token 产生一个分数，这组原始分数叫 Logits。推理程序把分数转换成概率分布，再按生成策略选择下一个 Token。

| 概念 | 直观含义 | 所属层次 |
| --- | --- | --- |
| Logits | 模型对各候选 Token 给出的原始分数 | 模型输出 |
| Greedy | 每次选分数最高的 Token | 推理程序的生成策略 |
| Temperature | 调整概率分布的尖锐或平缓程度 | 采样参数 |
| Top-p | 只在累计概率达到阈值的一组候选中采样 | 采样参数 |
| EOS Token | 表示生成结束的特殊 Token | Tokenizer / 模型约定 |

模型通过“预测一个 Token → 追加到输入 → 再预测一个 Token”反复生成。生成 100 个 Token，大致需要重复 100 次选择与追加；第一个 Token 的 Logits 通常来自 Prefill 末尾，此后的 Token 才进入逐步 Decode，因此不同资料对第一步的阶段归类可能略有不同。

### 6.4 Prefill、Decode 和 KV Cache

- **Prefill（预填充）**：在逻辑上处理请求中已有的全部输入 Token，建立上下文表示；引擎可以一次处理，也可以分块处理。输入越长，这一阶段通常越重。
- **Decode（解码生成）**：每轮生成一个新 Token。它会反复执行，因此单步速度直接影响用户看到文字持续输出的速度。
- **KV Cache（键值缓存）**：保存已处理 Token 在各层注意力计算中的 Key/Value，避免每生成一个新 Token 都从头计算整个历史。它会随并发数和上下文长度增长并占用显存。

这里暂时只掌握用途，不要求推导注意力公式。等后续回到 Self-Attention 时，再解释 KV Cache 为什么保存 K/V，而不保存全部历史计算。

### 6.5 显存不只有模型权重

部署时至少要区分：

```text
总运行显存
≈ 模型权重
+ KV Cache
+ 中间激活和临时计算空间
+ 推理框架、CUDA Graph、通信等额外开销
```

因此，“权重文件能放进显卡”只是必要条件之一。并发、上下文长度、量化方式、批处理和推理框架都会改变真实显存需求。

### 6.6 建议学习顺序

1. 用一个真实 Tokenizer 观察四段文本的 Token ID 和数量。
2. 把一组 `system/user/assistant` 消息展开成 Chat Template 后的文本。
3. 用 3～5 个虚构 Logit 手算 Greedy、Temperature 和 Top-p 的选择直觉。
4. 观察一次请求的 Prefill 和逐 Token Decode 日志或指标。
5. 改变输入长度与并发数，观察 KV Cache 和显存变化。
6. 最后再回到 Self-Attention，用一个 3 Token、2 维向量的小例子理解 Q/K/V。

这条顺序先建立“看得见的输入输出”，再补模型内部公式，避免一次塞入过多线性代数。
