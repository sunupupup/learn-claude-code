# Ontology：定义概念、关系与含义

**Ontology（本体）：明确有哪些概念、概念之间有什么关系，以及这些关系表示什么。**

## 我的问题

- 概念定义和具体事实分别长什么样？如何用代码表示和查询？
- 哪些结论能通过规则推导，哪些需要明确的数据验证？
- 它如何与 LLM、RAG 配合？

## 完整技术链路

```text
业务问题 → 定义概念与关系 → 录入具体事实
  → 查询关系 / 按明确规则推导 → 返回结果及依据
定义或事实变化 → 更新数据与规则 → 重新检查结果
```

**重点：定义“员工属于部门”和记录“张三属于研发部”是两件事；本体本身不等于聊天模型，也不自动保证事实真实。**

Ontology  本体论 ， 本体论是对“存在”这一概念的哲学研究
“存在”涵盖了所有的现实事物以及其中的每一个实体。

https://learn.microsoft.com/en-us/fabric/iq/ontology/overview  微软的定义

该本体模型（属于 Fabric IQ 预览版的一部分）以数字化方式呈现了企业的词汇表和语义结构，从而实现了跨不同领域和 OneLake 数据源的统一语义表达。该模型将企业中的各种概念定义为不同的实体类型（如“客户”）、属性（如客户的姓名和电子邮件地址）以及关系（如“客户下订单”），同时明确了这些概念的约束条件。在定义好本体模型后，需将各种实体类型的定义与实际数据关联起来，这样下游工具才能使用相同的语言进行数据处理。人类和人工智能都可以利用这种语言来进行跨领域的推理和决策。

他的关键点，在于从业务对象出发建模

| 要定义的内容 | 示例 |
|---|---|
| **实体类型**：有什么东西 | 客户、订单、商品 |
| **属性**：这些东西有什么特征 | 客户姓名、订单金额 |
| **关系**：它们怎样关联 | 客户下订单、订单包含商品 |
| **规则或约束**：这些表达有什么要求 | 金额使用什么单位、订单与客户如何对应 |


# Ontology 和 GraphRAG 的关系

你可以这样记：
- Ontology：规定知识怎么表达、含义是什么。
- GraphRAG：利用图中的知识辅助回答。
- Ontology + 图谱 + RAG：一种可行的 GraphRAG 实现方式。

在 GraphRAG 方案里，Ontology 可以作为一个可选的建模组件，指导图数据的构建：
- 定义有哪些实体类型，例如员工、部门、项目。
- 定义有哪些关系，以及关系的含义。
- 让不同来源的数据按统一定义组织起来。

# Ontology 的图有啥优势

信息更丰富的图
一些核心概念
- 实体类型：客户、订单
- 实体实例：
- 资产、属性：客户的姓名、电子邮件地址
- 关系：客户 创建 订单

感觉说实话， ontology 就是一个对主体进行精细化建模的图模型

用 Ontology 指导构图，主要优势是：把构图标准明确下来，方便不同数据来源、程序和团队共同遵守。
但先说清楚：**如果普通图模型已经定义得很完善，这些优势可能已经具备，引入 Ontology 不一定带来额外收益**。

| 优势 | 具体例子 |
|---|---|
| **构图口径统一** | 从不同文档抽取“员工所属部门”时，统一使用 `任职于`，减少各自创造关系名称 |
| **跨系统整合更有依据** | 人事系统的“职员”和项目系统的“成员”，可以按定义映射到共同的“员工”概念；具体身份仍需匹配 |
| **定义可复用** | 构图、查询、数据检查使用同一套模型，减少规则散落在不同程序里 |
| **支持形式化推理** | 定义“正式员工是员工的一种”，配合推理工具，查询员工时可包含只被标注为正式员工的对象 |

# 图的更新

上游数据源中的任何更新内容（比如新增的记录），都需要手动刷新后才能在本体项中显示出来。更多信息请参阅“刷新图模型”相关说明。
