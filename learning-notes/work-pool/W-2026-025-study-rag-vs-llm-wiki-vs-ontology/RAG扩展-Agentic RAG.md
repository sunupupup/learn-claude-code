# RAG 扩展：Agentic RAG

## 面对什么问题？

> 第一次只查到“订单服务依赖订单数据库”，还没有负责人。谁来决定继续查“订单数据库”？

**改变：把检索变成工具，让模型根据已返回的证据决定下一步。** 这改变的是检索控制流程，不要求换一种数据库。

## 完整技术链路

```text
用户问题 → 模型决定查什么 → 程序执行检索工具
                 ↑                 ↓
                 └──── 返回证据 ────┘
证据足够 → 模型回答；证据不足 → 补查或说明不知道
达到轮数上限 → 程序强制停止
```

**重点：模型提出动作，程序执行动作，再把结果交回模型。** 固定执行两次查询，本身不等于 Agentic RAG。[微软官方架构说明](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-agentic)

| 参数 | 用途 |
| --- | --- |
| `use_real_model = False` | 默认模拟决策，不联网；True 才由真实模型选择工具 |
| `question` | 用户问题；模拟模式只支持代码里的默认问题 |
| `max_turns = 4` | 最多进行几轮决策，包括最后回答的那轮 |
| `base_url`、`model` | 真实模式的服务地址与支持工具调用的模型名 |

默认模拟流程：

```text
第 1 轮：search("订单服务") → D1
第 2 轮：search("订单数据库") → D1、D2
第 3 轮：停止，展示取回的证据
```

**模拟模式的决策是写死的，只用于观察工具循环，不代表模型有自主检索能力。** 它每次真的执行本地检索，但不生成新的自然语言结论。

先看 `search()` 的输入输出，再看循环中 `messages` 如何增加；工具返回消息通过 `tool_call_id` 对应模型发起的那次调用。

## 改一个条件看区别

- 把 `max_turns` 改为 1：查过一次就强制停止，不假装已经完成回答。
- 清空 `documents`：返回没有证据，观察模拟流程停止。
- 接真实模型：比较模型是否真的补查、选择的词是否能命中，而不是要求每次轨迹与模拟完全相同。

## 接真实模型时

填写 `base_url`、`model`，由环境变量提供 `RAG_API_KEY`，把 `use_real_model` 改为 `True`。代码不自动读取其他实验的 `.env`；不要把密钥写入代码或笔记。

真实模式使用已有环境中的 `openai` SDK（依赖版本范围见 [requirements.txt](experiments/rag-basic/requirements.txt)），服务需兼容 Chat Completions 的工具调用协议。该模式会发送问题和检索内容，可能计费；本轮不调用。

**模型可能选错关键词、过早回答或一直补查。轮数上限只能限制循环，不能保证答案正确。** 本例每轮只接受一个合法 `search` 调用，遇到未知工具、错误参数或多个调用会停止报错；引用与答案忠实性尚未自动验证。

工具调用实现已参考 [OpenAI 官方说明](https://developers.openai.com/api/docs/guides/function-calling)及 Context7 的 SDK 文档。资料核对：2026-09-20。

## 和 GraphRAG 的关系

**GraphRAG 关注怎样组织、查找关系证据；Agentic RAG 关注谁决定查什么、查几次。** Agent 可以调用图检索工具，两者可以组合。

# 我的笔记

Agentic RAG 在普通 RAG 中加入了“根据检索结果，决定下一步行动”的循环。

解决的是：第一次查到的资料可能不足以回答问题，而下一步查什么，要看第一次查到了什么。

| 流程 | 怎么做 |
|---|---|
| 普通 RAG | 用户问题 → 检索资料 → 把资料交给模型 → 回答 |
| Agentic RAG | 用户问题 → 决定查什么 → 检索资料 → **判断是否足够，不足就调整查询、继续检索** → 回答 |

那我感觉，这个和 graph rag可以结合呀

毕竟 graph 可以得到更多的一些上下文

结合上下文 能查出来更多的内容

那可不可以理解为

Agentic RAG ≈ Agent + RAG检索工具 + 根据证据继续检索或停止的指令prompt。

其实没啥太高深的内容 Agentic RAG

这个就是 和 agent 绑定很深的 rag

其实 rag 是完全可以脱离 agent 的一个 workflow 中间的数据来源而已
