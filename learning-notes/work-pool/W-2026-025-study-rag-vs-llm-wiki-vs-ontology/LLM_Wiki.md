# LLM Wiki：整理、使用、维护知识页

**核心：用 LLM 将资料整理成可保存、有来源的 Wiki 知识页，后续查询和更新这些页面。**

## 我的问题

- 原始资料怎样变成 Wiki 页面？模型具体做什么？
- 问题来了，怎样找到页面并回答？与已学的 RAG 有什么区别？
- 来源修改、删除或互相矛盾时，知识页怎么处理？

## 完整技术链路

```text
原始资料 → LLM 整理 → 保存知识页及来源
用户问题 → 查找知识页与必要原文 → 生成有依据的回答
来源变化 → 找到受影响页面 → 修订并检查引用
```

**重点：知识页是加工结果，可能出错；保留原文和引用。Wiki 也可以被 RAG 检索，两者可以组合。**

# 我的笔记

与传统 RAG 系统不同（后者需要针对每个查询重新获取知识），wiki系统只需将知识整理一次，之后即可保持知识的最新性。其中的交叉引用早已被建立起来，矛盾之处也已被标记出来。综合处理的结果反映了所有被纳入系统中的知识。

其实总感觉，这就是一种 Memory 机制

| LLM Wiki 的动作 | 对应的记忆机制 |
|---|---|
| 阅读资料，整理成知识页并保存 | **写入记忆** |
| 根据问题查找页面，放入上下文 | **召回记忆** |
| 来源变化后修订、合并或删除内容 | **更新、纠正或遗忘记忆** |

检索方式可能有多种：
| 查找方式 | 具体做法 |
|---|---|
| 读目录选页 | 模型看页面标题、简介，选择要读的文件 |
| 关键词搜索 | 搜索 `PAY-401`，找到出现它的页面 |
| RAG 检索 | 给 Wiki 建索引，检索相关片段再交给模型 |

所以，这种方式，除了某些关键词的匹配，其实很大程度都是在依赖LLM 理解wiki 、找到相关内容

对，在“让 Agent 读目录、选页面、继续查资料”的 LLM Wiki 实现里，你的理解是正确的：很大程度依赖 LLM 理解内容，并决定下一步读什么。 🟢

# LLM Wiki 解决的问题、原文链接

https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

这是 k 神的笔记， 核心是 "利用大语言模型构建个人知识库的方案"， 面相的是 "个人知识库"

痛点：以前的检索方案，要么是RAG检索，要么是 给几份文档，全部扔给LLM去理解然后出结果；**相当于每次都是从头开始理解、检索、出结果，没有任何持续的知识累积下来**

LLM 不会在每次查询时都直接从原始文档中获取信息，而是逐步构建并维护一个结构化的“维基”数据库——也就是由多个 Markdown 文件构成的、相互关联的信息集合。

当有新信息被添加进来时，LLM 不会只是将其索引起来以备日后查询使用。
它会先读取这些新信息，提取其中的关键内容，然后将其整合到现有的“维基”数据库中：更新相关页面的内容、修正主题摘要、记录新数据与旧信息的矛盾之处，从而不断完善整个知识体系。
这些知识只需被整理一次，之后就会保持最新状态，无需在每次查询时都重新处理。

这就是关键区别：维基是一种持续更新、不断完善的知识体系。

wiki的特点: 持续更新、完善的知识体系，各种交叉引用，各种矛盾之处 (有矛盾，是因为，知识本身就是冲突的，有时候，没有一个标准的答案)

| 展示形式 | 实际可能生成的内容 |
|---|---|
