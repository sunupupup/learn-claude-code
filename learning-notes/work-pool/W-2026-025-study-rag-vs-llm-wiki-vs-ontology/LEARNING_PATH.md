# 章节知识地图：从 RAG 主链路到知识管理的扩展方案

**这份文件是本章的 base：以主链路为骨架，罗列概念、扩展分支和彼此关系。看到一个方案，就能知道它面对什么问题、改变哪里、接下来读什么。**

## 总览：主链路与扩展分支

```text
准备数据：解析、清洗 → 切块 → 表示与索引
使用数据：问题 → 检索 → 整理证据 → 生成回答
维护数据：发现变更 → 更新或删除 → 检查旧资料是否失效
    │
    ├─ 找不准：关键词、向量、混合检索、重排序
    ├─ 切碎丢上下文：标题补充、父子片段、Contextual Retrieval、Late Chunking
    ├─ 一次查不够：查询改写、拆题、Agentic RAG
    ├─ 看不到跨文档关系或全局：知识图谱、GraphRAG、RAPTOR
    ├─ 综合结果需要保存复用：LLM Wiki
    ├─ 概念和关系需要统一含义：Ontology
    └─ 检查效果与维护代价：评测、引用、版本、权限、成本
```

**分支表示问题与方案的关联，不表示后一种必然替代前一种。**

## 概念导航：遇到什么问题，改变什么？

| 面对的问题 | 改变哪个环节、怎么改 | 相关概念或方案 | 深入入口 |
| --- | --- | --- | --- |
| 模型没有最新或内部资料 | 回答前查资料，将证据放入上下文 | RAG（检索增强生成） | 单元 0–1；[RAG 入口](RAG.md) |
| 文档混乱、太长，无法直接检索 | 解析结构、清洗、切块，保存标题与来源 | Parsing、Chunking、Metadata | 单元 1、3；[解析清洗与切块](文档解析清洗与切块.md) |
| 不同说法难以匹配 | 把文档与问题编码为兼容向量，再搜索 | Embedding、向量空间、向量索引 | 单元 1 |
| 语义相近却漏掉型号或错误码 | 增加关键词检索，并融合多路排名 | BM25、Hybrid Search、RRF | 单元 2 |
| 候选找到了，但次序不好 | 对问题与候选重新判断相关性 | Reranking（重排序） | 单元 2 |
| 片段离开全文后缺上下文 | 补来源上下文，或改变编码与切块顺序 | Contextual Retrieval、Late Chunking | 单元 3 |
| 问法含糊、复杂问题一次查不够 | 改写、拆题、补查，设置停止条件 | Query Rewriting、HyDE、Agentic RAG、Self-RAG、CRAG | 单元 4；这些方案机制不同，逐个辨析 |
| 局部片段难以表达跨文档联系或全局主题 | 增加关系结构或层次摘要 | Knowledge Graph、GraphRAG、RAPTOR、LightRAG | 单元 5 |
| 每次都重复跨资料整理 | 把整理结果保存成可维护、可引用的知识页 | LLM Wiki；OpenWiki 是具体工具 | 单元 6；[LLM Wiki 入口](LLM_Wiki.md) |
| 同名异物、概念和关系含义不一致 | 明确定义类型、关系与语义；另行选择数据校验机制 | Ontology、OWL；SHACL 用于图数据约束验证 | 单元 7；[Ontology 入口](Ontology.md) |
| 资料少，或者答案来自实时结构化数据 | 比较直接放上下文、查 SQL/API 等路径 | Long Context、SQL/API；Fine-tuning 则改变模型参数 | 单元 8 |
| 原文变了，旧答案还在 | 同步新旧片段，处理删除与派生内容失效 | 更新、版本、来源追溯 | 单元 9；[资料更新与删除](RAG资料更新与删除.md) |
| 能回答，但不知道是否可靠 | 检查证据覆盖、回答忠实性、无答案表现和成本 | Eval、Citation、Faithfulness、权限 | 单元 9 |

## 这些概念怎样连起来？

- **组成关系**：切块、Embedding、索引、检索、上下文组装可以组成一条向量 RAG 链路。
- **改进关系**：混合检索扩展候选来源，重排序调整候选次序；两者解决的问题不同。
- **组合关系**：LLM Wiki 组织知识页，RAG 可以检索这些页面；Ontology 可以为知识图谱提供概念与关系定义，图也可以参与检索。
- **实现关系**：LLM Wiki 是知识维护模式，OpenWiki 是具体工具，不能直接当作同一个概念。
- **取舍关系**：长上下文、检索、SQL/API 和微调改变的环节不同，按问题选择或组合。

**地图负责广度，子笔记与 Demo 负责深度。** 后续发现新概念，在相应分支补“问题 → 改变 → 方案 → 关联 → 学习入口”；实际代码、输出和深入讨论放进子文件，再链接回来。

## 一、先校准学习地图

这不是 RAG → GraphRAG → Wiki → Ontology 的替代史。下面按学习依赖和问题分类排序，不宣称它们在历史上依次因前一方案失败而出现。

| 对象 | 所属层次 | 关注的问题 |
| --- | --- | --- |
| RAG（Retrieval-Augmented Generation，检索增强生成） | 应用的知识访问与生成链路 | 如何用外部检索结果辅助回答？ |
| Hybrid Search / Reranking（混合检索 / 重排） | 检索组件 | 如何找到、排好相关证据？ |
| Contextual Retrieval / Late Chunking | 索引与文本表示 | 如何减少切分导致的上下文丢失？ |
| RAPTOR | 层次化索引 | 如何同时检索细节和跨段落摘要？ |
| GraphRAG | 图辅助检索与生成 | 如何利用实体关系、社区摘要等组织证据？ |
| Agentic RAG | 控制流程 | 如何按需要拆题、选源、补查并停止？ |
| LLM Wiki | 知识维护模式 | 如何保存和更新跨资料整理出的知识页？ |
| OpenWiki | 具体工具 | 如何由 Agent 生成和维护代码或个人知识 Wiki？ |
| Ontology（本体） / Knowledge Graph（知识图谱） | 语义建模 / 知识表示 | 概念关系是什么意思，以及有哪些具体实体关系？ |
| Long Context（长上下文） / Fine-tuning（微调） | 模型输入 / 模型参数适配 | 更多资料直接输入、检索资料、改变参数，各适合什么问题？ |

以上是课程分类，不是行业热度排名。本轮没有收集可比较的生产采用率，不能断言哪四个最流行。词频、GitHub stars、论文数量和生产价值也不是同一指标。

## 二、学习方式与贯穿样本

每节拆成若干小轮：一个问题 → 主读材料指定片段 → 用户复述 → 对照资料 → 一个反例或小实验 → 确认后写笔记。每轮只引入少量术语，不要求一次读完一篇长论文。

建议持续使用同一组研发资料：服务说明、负责人名单、依赖关系、故障记录，以及有版本日期的变更通知。先手工准备少量资料和预期证据，再逐步做实验，不同时部署多个平台。

问题集从基础阶段开始维护：

- 精确查找：“错误码 PAY-401 的处理办法是什么？”
- 语义改写：“支付偶尔卡住怎么排查？”
- 跨文档关联：“这次数据库升级影响哪些服务与负责人？”
- 全局总结：“这些事故反复出现的共性是什么？”
- 时效/无答案/权限：“旧负责人是谁、现负责人是谁、资料没有说怎么办、当前身份能否看？”

每个方法都记录正确证据、答案、引用、无答案行为、成本、延迟和更新成本。新增方法先与最简单基线比较；暂未运行的数字保持空缺，不用论文成绩代替本地结果。

## 三、主线：十个学习单元

### 0. 为什么需要外部知识？RAG 到底解决了什么？

- 前置：模型参数是训练得到的数值；上下文是当前调用输入。暂不要求掌握 Transformer 数学。
- 问题：训练后新出现的事实、内部资料、来源追溯，以及知识更新，不能只靠模型原有参数解决。
- 主读：[RAG 原论文，2020](https://arxiv.org/abs/2005.11401)，先读摘要、Introduction、Figure 1。
- 对照：[Meta 原作者博客](https://ai.meta.com/blog/retrieval-augmented-generation-streamlining-the-creation-of-intelligent-natural-language-processing-models/)，看外部知识如何替换。
- 必须校准：2020 年论文包含检索器与生成器联合学习；今天广义的“检索 → 放入上下文 → 生成”应用不一定训练任何模型。RAG 也不等于向量数据库，更不是所有幻觉的解决器。
- 验收：用新报销制度的例子，比较直接问模型、附上原文、检索后回答、微调四种做法；指出知识何时进入模型。

### 1. 最小 RAG 是怎样工作的？先建立基线和评测问题

- 主链路：资料摄取 → 解析与切分 → 索引；问题 → 检索 → 组装上下文 → 生成 → 校验引用。
- 学习词汇：Chunk（文本片段）、Embedding（用于检索的文本向量）、Top-k（排名前 k 个候选）、Metadata（来源/日期/权限等元数据）。区分文本检索 Embedding 与模型内部 Token Embedding。
- 主读：[本仓库 RAG Demo](../../../projects/rag-agent-demo/README.md)，先看主链路与 matched / answerable 的区别；后续按需读 ingest.py、vector_store.py、agent.py。
- 对照：[Ragas 原论文](https://arxiv.org/abs/2309.15217)，只看为何应分开评价检索、证据忠实度和答案质量。
- 风险：找到“相似片段”不代表有答案；引用 ID 合法不代表引用支持结论。LLM 自动评分需要人工校准。
- 验收：手工追踪一个成功问题和一个“内容相似但无答案”的问题；冻结最小问题集。

### 2. 找不准：关键词、向量、混合检索与重排

- 问题：关键词可能漏掉不同说法；向量相似可能漏掉错误码、型号等精确信息；候选顺序可能不合适。
- 主读：[Azure Hybrid Search 官方概念文档](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)，理解 BM25（词项相关性排序）、向量检索与结果融合。
- 对照：[Anthropic Contextual Retrieval 博客](https://www.anthropic.com/news/contextual-retrieval)的 RAG primer 与 reranking 部分。
- 先掌握：召回是找到候选，重排是重新排序候选；重排无法找回根本没被召回的材料。RRF（Reciprocal Rank Fusion，倒数排名融合）是组合多个排序的方法，先理解用途、不急着推公式。
- 代价：多路索引、额外打分和延迟；不能只调大 Top-k。
- 验收：用错误码问题与语义改写问题做对照，解释混合检索为什么可能互补。

### 3. 切碎后丢了含义：怎样保留上下文？

- 问题：“该公司增长 3%”离开标题与前文后，缺少公司、年份等限定。
- 先学简单方法：保留标题/元数据、按段落结构切分、命中小段后补读邻近或父级内容。
- 主读：[Anthropic Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)的 context conundrum 和方案部分：为片段添加解释性上下文再索引。
- 对照：[Jina Late Chunking 原论文](https://arxiv.org/abs/2409.04701)与[作者仓库](https://github.com/jina-ai/late-chunking)：先让较长文本参与编码，再按片段聚合向量。
- 边界：这两种机制不同；后者需要合适的编码/池化接口，不能把任意黑盒 Embedding API 当作直接支持。前者生成的解释可能出错，必须保留原文。
- 验收：同一段指代不明文本，说明两种方法各在哪一步改变信息表示。论文收益只在其数据与模型条件下成立。

### 4. 问法不合适、查一次不够：改写、拆题与检索控制

- 问题：用户语言和资料语言不同；复杂问题需要多个来源；首次证据不足。
- 主读：[Agentic RAG 官方架构说明](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-agentic)，关注把检索作为工具、拆题、补查和退出。
- 对照一：[HyDE](https://arxiv.org/abs/2212.10496)，即 Hypothetical Document Embeddings（假设文档嵌入），理解“生成假设文档辅助查找真实资料”。假设文本不能当证据。
- 对照二（选读）：[Self-RAG](https://arxiv.org/abs/2310.11511)与[CRAG](https://arxiv.org/abs/2401.15884)。前者原论文训练反思 Token，不等于随便加一句“反思一下”；后者评估检索质量并触发纠正动作。
- 代价：更多模型调用、错误拆题、循环、外部搜索边界；必须设置预算、终止和无答案策略。
- 验收：画一条“第一次没找到 → 补查 → 有据回答或停止”的可观察流程；暂不实现完整框架。

### 5. 找到局部仍看不到全局：层次索引、知识图谱与 GraphRAG

- 问题：回答一个具体事实，与总结整个资料集、追踪跨文档关系，是不同任务。
- 前置小节：实体、关系、路径、知识图谱；社区指图中联系紧密的实体群，不是聊天群。
- 主读：[Microsoft GraphRAG 原论文](https://arxiv.org/abs/2404.16130)的动机与方法图；[官方查询总览](https://microsoft.github.io/graphrag/query/overview/)的 Local / Global。
- 对照：[RAPTOR](https://arxiv.org/abs/2401.18059)，Recursive Abstractive Processing for Tree-Organized Retrieval，递归摘要构成树状检索；它展示“多粒度摘要”不必采用相同图方案。
- 选读：[LightRAG](https://arxiv.org/abs/2410.05779)，比较图与向量结合、双层检索和增量更新思路，不因名称轻巧就假设全面更优。Microsoft DRIFT 作为后续查询扩展选读。
- 代价：实体抽取/合并错误、摘要丢失、建索引与更新成本。图能组织证据，不自动证明事实。
- 验收：给局部事实题、跨关系题、全局总结题各选一种检索路径，解释差异；不能把 GraphRAG 仅定义为图遍历或事实校验。

### 6. 每次重复整理资料：LLM Wiki 与 OpenWiki

- 问题：反复跨资料综合，结果只留在聊天里；如何让知识页可保存、复用、修订和溯源？
- 主读：[Karpathy LLM Wiki 原始 Gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，创建于 2026-04-04；理解原始资料、派生 Wiki、维护约定，以及摄取/查询/检查。
- 对照：[LangChain OpenWiki 官方概览](https://docs.langchain.com/oss/openwiki/overview)及[仓库](https://github.com/langchain-ai/openwiki)。已核实它是维护代码/个人知识 Markdown Wiki 的具体工具；用户最初说的 OpenWiki 很可能指它，但尚未确认。
- 窄对照（选读）：[microsoft/llmwiki](https://github.com/microsoft/llmwiki)，另一种具体实现，不与 LangChain OpenWiki 混用。
- 边界：Wiki 内容仍可被检索；RAG 系统可以检索已整理知识，也可以配合写入流程。不能推导“RAG 结构性不能积累知识”。Gist 是作者提出的模式，不是通用性能证明。
- 代价：摘要错误被持久化、引用断裂、源文件变更后派生页面过时、并发编辑冲突、权限跨来源传播。
- 验收：手工把三篇小资料整理成一页带引用的知识页，再修改一份来源，列出需失效或重审的内容。实际安装、自动维护和付费调用另行进入实验步骤。

### 7. 术语和关系混乱：Ontology、知识图谱与业务操作层

- 问题：同一个客户/服务有多个名称，关系含义不统一；仅有一张图不代表语义一致。
- 主读：[W3C OWL 2 Overview](https://www.w3.org/TR/owl2-overview/)，先读 Introduction 与 Ontologies。OWL 是 Web Ontology Language（Web 本体语言），用于形式化描述概念与关系。
- 对照：[Palantir Ontology 官方概览](https://www.palantir.com/docs/foundry/ontology/overview/)，区分通用本体与包含对象、关系、动作、函数和安全机制的产品层。
- 选读：[SHACL](https://www.w3.org/TR/shacl/)，Shapes Constraint Language（形状约束语言），用于对 RDF 图做条件验证。不要把 OWL 的语义推理等同数据库必填字段校验。
- 代价：领域建模、实体对齐、规则维护、迁移和业务责任。类型合法与事实真实是两回事。
- 验收：用“员工—部门—项目”分别写出类型、具体事实、数据检查和业务动作；指出它们并不都由 Ontology 一词自动实现。

### 8. 长上下文、微调、SQL/API：什么时候可以不用复杂检索？

- 问题：少量资料直接输入是否更简单？精确库存为什么还要从描述文档里猜？
- 主读：[RAG or Long-Context LLMs?](https://arxiv.org/abs/2407.16833)，比较实验设置、预算和任务差异。
- 对照：[Lost in the Middle](https://arxiv.org/abs/2307.03172)，只将其作为特定受测模型中观察到的位置敏感性，以及可复用的实验方法，不当作所有当前模型的固定结论。
- 关联：微调修改参数，检索提供外部证据，两者可以结合；SQL/API 是获取结构化权威数据的途径，可以成为 Agent/RAG 系统的工具。
- 代价与边界：长上下文的输入预算和证据利用；微调的训练/更新与评测成本；SQL/API 的授权和结果解释。后续若进入具体微调方法，再单独补原始资料，不在本单元展开训练工程。
- 验收：对少量文档问答、大量频繁更新资料、实时库存、固定格式抽取四个场景提出最小基线；不给任一方法设无条件胜出规则。

### 9. 最后用证据选方案：评测、更新、权限与成本

- 汇总前面的问题集，分别比较检索覆盖、上下文相关性、答案正确性、证据支持、无答案处理、延迟和总成本。
- 主读：[Ragas 原论文](https://arxiv.org/abs/2309.15217)的评价维度；[本仓库 RAG Demo](../../../projects/rag-agent-demo/README.md)的授权、引用与 Eval 边界。
- 加入反例：资料过期、同名实体、没有答案、跨权限资料、索引未更新、Wiki 派生结论失效。
- 先做人工标注小集；自动评估只辅助，不能把一个分数当作系统正确性的证明。
- 验收产物：问题—证据—失败环节—候选改进—新增成本—验证结果表；只对真正实验过的方案写运行结论。

## 五、怎样对比官方文档与博客

每篇只填一张阅读卡：

1. 原问题与基线是什么？作者针对的是所有 RAG，还是简单向量 Top-k 基线？
2. 改了哪个环节：摄取、表示、检索、排序、上下文、生成、控制流，还是持久知识维护？
3. 证据类型：规范定义、官方实现描述、论文实验、作者经验，还是宣传判断？
4. 使用了什么数据、模型、版本、指标与预算？是否公平对照？
5. 提升之外，新增多少构建、查询、更新、权限和故障恢复成本？
6. 哪种反例可能让结论不成立？怎样用自己的小问题集验证？

原论文用于理解问题与受控实验，官方文档用于理解具体行为，原作者/工程团队博客用于直觉与取舍。官方身份也不能让营销判断自动成为普适事实；二手博客用于提出问题，再追溯原始证据。本路线以一手资料为主。

## 六、调研证据、修订与限制

- Exa 检索 4 个主题方向（起源与检索基础、改进分支、长上下文对照、Wiki/本体），随后追加 OpenWiki、Agentic Retrieval、Late Chunking 三次定向检索；共返回 35 条结果，含重复条目，并非 35 篇独立精读。
- 通过 Exa 抓取上述所引用的一手页面，主要审阅摘要、引言、方法说明和概览；尚未逐篇复核全部实验表，也没有复现实验。
- Context7 已解析并查询 `/microsoft/graphrag` 与 `/langchain-ai/openwiki`。结果属于文档/代码索引证据，不等于固定 Commit 的完整源码审计。
- OpenWiki 的 Exa 搜索快照、抓取的 README 和 Context7 索引存在更新差异（例如 OKF 版本与新增集成能力）；此路线仅采用它们一致的工具定位。实操前必须固定 Commit、许可证、版本和读取日期，不依据搜索快照执行安装步骤。
- 原卡“Karpathy 2025 年提出”由原始 Gist 创建日期校正为“本轮核验的原文创建于 2026-04-04”；这不证明类似思想此前不存在。
- 原卡“Wiki 50k–100k token 固定上限”“RAG 规模几乎无限”“RAG 不能积累知识”“GraphRAG 自动验证事实”“所有企业必须使用本体”等不进入本路线的事实前提。
- 热度未做量化统计；本路线是根据机制覆盖、前置依赖和学习收益做出的教学选择，不是市场采用率排名。

## 七、第一节阅读任务

现在只读 RAG 论文的 Abstract 和 Introduction，再看 Meta 原作者博客中外部知识替换的例子。暂不读公式，不安装框架。

用户用自己的话回答后，校准“模型参数 / 外部知识 / 当前上下文”的区别，并记录已确认结论，再进入单元 1。

## 反思

1. 未确认或需要再验证：论文性能与产品能力有版本边界；OpenWiki 身份是高匹配候选但用户尚未确认，正式源码学习时重新固定版本。当前调研不能证明任何方案在本仓库数据上最好。
2. 学习中应补的视角：除了新方法名称，还要掌握信息检索、实验基线、来源时效和派生知识失效。学习目标是能诊断失败并做公平对比，而不只是复述架构名词。
