# 有状态 MCP 与 Notion 编辑状态学习笔记

记录日期：2026-10-08。来源为本次学习对话与当轮已读取的官方资料。本文保存讨论，不代表完成整个专题，也不代表真实 Notion MCP 已实现这些设计。

## 从什么问题引出

最初的问题是：“MCP 似乎一直无状态，现在是否有新技术让它变得有状态？”

调研后需要区分：**旧版 MCP 已有协议会话；新版协议核心转向无状态；业务系统仍然可以保存跨请求状态。** 这不是单一的“无状态升级成有状态”路线。

业务上的动机很直接：查一次天气可以独立完成，但打开浏览器、登录、搜索和加入购物车，需要持续操作同一个环境。聊天里记着“登录成功”，不能替代浏览器里真实的 Cookie 和页面。

## 术语速查与状态分层

| 术语 | 中文解释、所属层次与边界 |
| --- | --- |
| State / Status | State 是系统保留的状态信息；Status 通常只是其中“处理中、完成”等阶段字段。 |
| Harness | 模型外侧负责上下文、工具调度与流程控制的程序；可以独立于聊天文本保存结构化状态。 |
| MCP Session | 协议会话；旧版中用于关联逻辑交互，不等于聊天记忆，也不等于一条 TCP 连接。 |
| Handle | 句柄，即对象引用编号，例如 page_id、edit_id；编号用来定位对象，不自动授予访问权限。 |
| Application State | 应用状态，如购物车、编辑操作记录；可以位于 Server 后端或下游业务系统。 |
| Task State | 任务状态，如执行中、等待输入、完成及结果；不等于完整 Agent 对话。 |
| Persistence | 持久化；状态在进程重启后仍能保留，不自动意味着工作会恢复执行。 |
| Idempotency | 幂等；同一操作重试不重复产生业务效果。基于记录的幂等需要保存操作信息，但并非所有幂等都靠去重表。 |

## 技术调研：各自改变了什么

以下是本次对话已核验的官方文档结论（documented），不是固定提交源码验证或运行实验。版本差异须在实际接入时再次核对客户端与 SDK。

### Streamable HTTP 与旧版会话

Streamable HTTP 是传输机制。2025-11-25 规范允许 Server 在初始化时分配 Mcp-Session-Id，后续请求携带该编号来关联会话。服务端可以保存会话相关信息。

SSE（Server-Sent Events，服务端推送事件）负责传输消息；长连接或流式输出本身不等于持久化存储。

来源：[2025-11-25 传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。

### 无状态核心与显式句柄

2026-07-28 规范移除协议级初始化握手与 Mcp-Session-Id，强调请求自描述。需要跨调用保留的业务对象用显式编号关联，例如创建购物车后返回 cart_id，后续修改携带 cart_id。

**无状态协议不禁止服务端查数据库；它避免依赖之前那条连接隐含建立的协议上下文。** 编号是对象名字，服务端仍需逐次校验访问权限。

来源：[版本公告](https://blog.modelcontextprotocol.io/posts/2026-07-28/)、[Stateful Tools 设计说明](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)。

### Durable Objects：有状态运行环境

Cloudflare Durable Objects 提供有固定身份、能处理请求并关联持久存储的对象。历史 McpAgent 方案将客户端会话与 Durable Object 关联，从而保存跨请求状态。

这里的状态来自运行环境和存储，MCP 负责调用接口。普通服务配合数据库也可以管理应用状态。当前 McpAgent 文档将其标为 legacy，不能把历史方案当作所有新 MCP 服务的默认选择。

来源：[Cloudflare 早期方案介绍](https://blog.cloudflare.com/remote-model-context-protocol-servers-mcp/)、[McpAgent 文档](https://developers.cloudflare.com/agents/model-context-protocol/apis/agent-api/)。

### Tasks：长时间运行的任务

Tasks 在 2025-11-25 作为实验能力出现，2026-07-28 移入独立扩展。通过 taskId 查询、更新或取消任务，可表达工作执行中、等待输入及结束状态，保存结果或错误信息。

任务交互契约不等于完整工作流引擎：落盘、进程崩溃后恢复、外部副作用核对仍需具体实现。

来源：[旧版 Tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)、[Tasks 扩展](https://tasks.extensions.modelcontextprotocol.io/seps/2663-tasks-extension)。

### MRTR：多轮往返请求

MRTR（Multi Round-Trip Requests）支持服务端返回“需要输入”，客户端获取答案后带回答案继续请求。它让无状态核心支持多轮交互，不等于自动持久化聊天历史，也不强制使用 Durable Objects。

来源：[MRTR 规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)。

## 批注：理解成立的部分与校准

**🟢 已验证（常见场景，依据用户复述与机制对照）：程序保存并传递工具返回的 ID，确实可以管理跨调用状态，减少模型记忆和填写参数的负担。**

“依赖上下文、依赖模型”需要按保存方式区分：

| 方式 | 还依赖模型做什么 |
| --- | --- |
| ID 只留在聊天或工具结果里 | 从历史中找到、选择并正确填写 ID |
| Harness 结构化保存，再写入提示词 | 少了从旧历史找 ID 的负担，仍需模型选对并填写 |
| Harness 结构化保存，并由程序绑定参数 | 不需要模型记忆或抄写 ID，但通常仍依赖模型理解操作意图 |

因此，**Harness 独立保存结构化数据并传参，本身已经是在做确定性状态管理**；不必等到 MCP Server 保存才叫状态。

“硬编码”更准确地说是“确定性的程序规则”：动态保存 Page ID，并把何时切换、何时校验、何时允许写入的规则写进程序，而不是把 P123 写死。

程序能准确执行规则，但不能自动保证模型理解的目标正确。例如“切换到另一篇笔记”仍可能被理解错。并行编辑时应按用户、会话或编辑任务关联目标，避免一个全局 active_page_id 互相覆盖。

## Notion 场景：什么服务端状态真正有价值

以下是设计示例，不是现有 Notion 产品或 MCP 实现事实。

用户目标：“读一下这篇学习笔记，把讨论内容补进去，保留原来的结构。”

| 状态 | 保存内容 | 价值 |
| --- | --- | --- |
| 编辑基线 | 读取时的内容、Block ID、可用的版本标记或内容摘要 | 发现编辑期间页面被其他人修改，减少基于过期内容覆盖 |
| 待应用修改 | 明确的新增、替换、删除操作及预览 | 确认与执行针对同一份修改，避免重新生成后内容漂移 |
| 执行记录 | 每步执行结果、新建 Block ID、错误和未知结果 | 部分成功后能定位进度，不把整次工作盲目重做 |
| 去重记录 | 操作编号、参数摘要、执行结果 | 同一次操作重试时可返回原结果，减少重复追加 |

编辑操作单可以概念性地表示为：

```text
edit_id = E456
目标页面 = P123
编辑基线 = 读取时的相关内容摘要
待应用修改 = 明确的追加内容
执行状态 = 待执行 / 执行中 / 已成功 / 已失败 / 结果未知
执行结果 = 新增的 Block ID 等
```

这些是应用自行设计的字段和阶段，不是 MCP Tasks 标准字段的复制。

职责划分：Harness 关联 edit_id、组织意图和交互；Server 或其后端管理操作记录和执行校验；Notion 是实际页面内容的主要来源。各方不必复制完整状态。

生产边界：未核验 Notion 当前原生幂等或条件写入能力。若只是先读取比较、再发起写入，中间仍可能有并发修改，不能宣称具有原子事务保证。该边界留作后续实现时核验，不打断当前主线。

# 幂等也是种状态

**在 MCP Server 加幂等判断，并跨请求保存操作编号与执行结果，就是服务端应用状态的一种。** 它保存的是“这件事有没有执行过、执行结果是什么”，不是聊天记忆，也不是协议会话。

## 用 Notion 追加笔记举例

```text
第一次请求：把一段学习总结追加到页面 P123，operation_id = OP123
→ MCP Server 调用 Notion
→ Notion 写入成功，新增块 B456
→ MCP Server 保存 OP123 → 已成功，结果 B456
→ 返回响应途中网络超时，Harness 没收到结果

重试：仍使用 operation_id = OP123
→ MCP Server 查询 OP123 的执行记录
→ 发现已经成功，返回 B456
→ 不再追加一次
```

**正是第一次请求留下的记录，改变了第二次请求的处理方式，所以这份记录就是状态。** 即使放在外部数据库，也属于 Server 管理的应用状态。MCP 协议无状态与这种做法完全兼容。

同一次重试必须复用同一个操作编号；新的用户追加意图应使用新的编号。服务端还应校验同一编号是否对应相同目标和内容，避免把两项不同操作误当成一次。编号需绑定调用者及业务范围，不能跨用户复用结果；拿到编号也不等于获得页面访问权。

## 这份状态能保证什么，尚不能保证什么

- 已有成功记录时，可以识别重试并复用结果。
- 并发收到相同操作编号时，需要原子地登记或领取操作，避免两个请求同时发现“没有记录”而重复执行；只有查询判断还不够。
- 如果 Notion 已写入，但 Server 还未保存成功记录就崩溃，结果仍可能未知；需要核对远端结果或依赖下游支持的幂等机制。不能直接把未知当失败重试。
- 记录若只在内存中，重启后可能丢失；记录到期清理后，旧请求的去重保障也会变化。

这里尚无实验或真实 Notion 接口验证，不能声称实现了跨系统“恰好一次”执行。

## 一个必要的小边界

**准确说法是“基于执行记录实现的幂等引入了状态”，而不是“所有幂等都必须有去重表”。** 将字段设为固定值，在限定语义下可能天然幂等；本例的追加操作会重复产生新内容，所以跨请求的执行记录特别有价值。
