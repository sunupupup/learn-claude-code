这是一个专门做决策的模型

一开始，LLM为了支持结构化输出输出，有了两种技术
- Tool Calling
- Structured outputs  

但是这部分的决策，速度很慢、成本高
每个决策都需要再次调用相应的模型

Jev 登场了。Jev 是 TypeSafe AI 公司最新推出的模型。据该公司称，在分类任务上，Jev 的推理速度比同类大语言模型快 200 倍，成本则低 400 倍。

Jev 其实并非传统的大型语言模型，它并不负责生成文本。TypeSafe AI 团队将其称为“System One 模型”。

比如这是一个 问题的示例
```
{
  "model": "jev-latest",
  "state": "Hi, I've been trying to connect my Stripe account for 3 days and it keeps failing. I'm losing sales. Please help ASAP.",
  "questions": {
    "is_urgent": {
      "type": "noul",
      "instructions": "The message conveys urgency or time-sensitivity"
    }
  }
}
```

单纯判断问题是否紧急

```
{
  "is_urgent": {
    "type": "noul",
    "noul": 0.999
  }
}
```

支持三种问题
1. Choice：从一组中选择
2. Score：比如 关于一个问题的紧急程度，进行打分
3. Noul：返回 question 是否为真的概率


现在的一个场景：浏览器Agent

对于某些浏览器自动化的场景，现在通过 Jev 能很快指导下一步点击的内容

# Laya

https://huggingface.co/convaiinnovations/laya

又来个 laya

这是一种支持多种语言、非自回归式的决策模型。只要输入相应的状态数据（文本、电子邮件、工单或 JSON 格式的数据）以及问题，该模型就能以数学上精确计算出的概率来给出答案。
开源的决策模型，基于其他模型强化学习

## 和 Jev 的关键区别（2026-09-23）

- **共同点**：主打分类、选择、评分等结构化决策，追求速度、成本和准确率的平衡。
- **Jev 像买决策服务**：闭源 API，省部署维护；**Laya 像拿到决策模型**：Apache 2.0 开放权重，可本地部署和微调，但硬件、运维和调优仍有成本。
- **不能直接说 Laya 更强**：宣传中的部分高分来自专门微调版；Jev 对比数据来自第三方，样本和提示不同。本地 GPU 推理耗时也不能直接与远程 API 全程耗时比较。
- **概率不等于保证正确**：上文“数学上精确计算出的概率”不代表现实准确率有保证。概率校准指“报 90% 把握的一批判断，实际是否约 90% 正确”；Laya 官方承认存在过度自信，需要用业务数据检验。
- **选择方向**：想省维护，先评估 Jev；需要数据留本地、针对固定任务训练，考虑 Laya。中文要关注 Laya 多语言版，根目录版本主要面向英语。

以上为官方资料对比，未做本地实测。来源：[Laya 模型卡](https://huggingface.co/convaiinnovations/laya)、[评测与限制](https://github.com/NandhaKishorM/laya/blob/main/BENCHMARKS.md)、[Jev 官方介绍](https://typesafe.ai/blog/introducing-system-one-models-and-jev)。

# 延伸讨论重点（2026-09-23）

以下是讨论总结与概念校准，未进行训练或业务实测。

## 全能模型与专用模型

- 我的观察：“现在有很多强大的小模型冒出来了。”更准确地说，专用模型值得关注，但**专用不一定小，快也不能证明参数少**；Jev 的参数规模本轮未核验。
- 同等任务范围和质量要求下，全能模型通常难在训练时兼顾各项能力；多个专用模型单项更容易优化，但部署、路由和版本维护更繁琐。
- **总参数量、每次参与计算的参数量、训练成本、运行成本要分开看**。多个小模型参数相加不一定少，但一次请求可以只调用其中一个；统一模型则可能共享基础知识。
- 从零训练和基于现成模型微调的成本不能混为一谈。使用现成模型，是复用了别人已经投入的预训练成本。
- 例子：[Falconsai 摘要模型](https://huggingface.co/Falconsai/text_summarization)是约 6050 万参数的英语 T5-small 微调模型；“专做摘要”不代表擅长中文长文或一定超过通用模型。

## Workflow＋决策模型，不一定需要 Agent

我的理解：“以前有些勉强使用 Agent 的场景，替换成 Workflow＋一个决策小模型，完全 OK。”

🟢 已验证理解（常见场景）：**流程稳定、只有部分节点需要语义判断时，这个思路成立**；具体模型是否够准、够省仍需验证。

- Workflow（工作流，应用控制层）：程序预先定义步骤和分支，模型负责分类、评分等局部判断。
- Agent（智能体，应用控制层）：模型根据目标和反馈动态决定下一步，适合需要探索、路径不确定的任务。
- 先问：**缺的是语义判断，还是动态规划？**调用模型理解或生成文本，并不意味着必须让模型掌控整个流程。
- 典型流程：工单 → 判断类别/紧急度 → 程序分流 → 查询、回复草稿或审批。判断不确定时留出追问或人工处理出口。

## 意图识别怎么做

Intent Classification（意图分类，应用理解模块）负责识别“用户想做什么”，例如查询物流、申请退货。

- 不只有便宜 LLM：规则/关键词、专用分类模型、向量相似度、通用 LLM、Jev/Laya 类决策模型都可以实现。
- 便宜 LLM 的价值是启动快：给类别说明和例子就能建立基线；固定、高频任务也可以评估专用分类器。
- **意图识别 ≠ 信息提取 ≠ 执行**：“查订单 123 的物流”中，意图是查询物流；槽位填充（Slot Filling）提取订单号 123；工作流负责校验身份并查询。
- 多轮对话要带必要上下文。类别需要边界清楚，并允许未知、多个意图和追问，不能强迫所有输入选一个类别。

## 全量微调、LoRA、Adapter

这些是模型训练层面的参数更新方式；后训练是阶段，SFT（监督微调）是利用输入—目标答案样本进行训练的方法，可以结合全量微调或 LoRA。

| 方式 | 关键区别 |
| --- | --- |
| 全量微调 | 更新原模型全部可训练参数 |
| LoRA（Low-Rank Adaptation，低秩适配） | 冻结原矩阵 W，在选定线性变换旁训练两个小矩阵 A、B；输出为 Wx＋BAx（省略缩放），增量可合并进 W |
| 传统瓶颈 Adapter（适配器） | 在层内插入降维→非线性→升维的小网络，通常带残差连接，主要训练新增参数 |

LoRA 不是统一放在所有 Transformer 层后面：它作用于选定层内部的注意力/前馈矩阵，不要求每层都加。框架也把 LoRA 增量叫 adapter，别与传统插入式 Adapter 混淆。

参考：[工作流与 Agent](https://www.anthropic.com/engineering/building-effective-agents)、[传统意图识别](https://rasa.com/blog/intents-entities-understanding-the-rasa-nlu-pipeline)、[LoRA 论文](https://arxiv.org/abs/2106.09685)、[Adapter 论文](https://proceedings.mlr.press/v97/houlsby19a.html)。
