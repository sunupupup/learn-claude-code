# 第三阶段：生产实践进阶

> 调研日期：2026-10-28。下面是公开工程实践与针对 Pir 的学习设计，不是所有大厂共同执行的统一标准，也不是 Pir 已上线能力清单。

## 学习顺序与练习

先完成 Workshop 与 Pir 的一个闭环，再逐项扩展；预计 6–9 次专题学习，不按天承诺。

| 顺序 | 学什么 / 为什么 | 针对 Pir 的练习与完成证据 | 依据 |
|---|---|---|---|
| C1 业务成功定义 | 分清回复质量、执行轨迹、最终业务状态；模型说完成不代表业务完成 | 给一个工具场景定义三类检查：答案有依据、动作合法、下游状态正确；取消、失败、结果未知单列 | S1 |
| C2 跨层观测契约 | BFF→Runtime→模型→工具→异步任务的关联；重试次数与业务操作身份分开 | 写最小字段表，关联 session/turn/trace/tool call/operation；画一条重试或子任务链，说明父子与因果关系 | S2 |
| C3 数据治理与观测可靠性 | 原文/摘要/引用的取舍；脱敏、访问范围、保留与删除；采样和导出失败 | 设计“结构记录＋受控内容证据”方案；用合成敏感字段检查脱敏；模拟导出不可用，检查丢弃计数、队列和 flush | S3、S4 |
| C4 评测集与评委可信度 | 版本化案例、环境和 grader；人工参考、失败分类、数据污染与分布覆盖 | 从一组人工确认样本检查评委的误报/漏报；业务规则用代码，语义问题用模型，分歧回人工 | S1、S5 |
| C5 非确定性与安全回归 | 重复 trial、按场景分组而非只看平均分；隔离副作用、超时重试、权限与幂等 | 同配置重复执行小样本，保留波动与逐条差异；mock 做确定性回归，受控真实依赖做集成核验；关键越权不被平均分抵消 | S1；门禁策略为本路线设计 |
| C6 质量与运行告警 | 区分质量下降、服务故障、评委故障；服务指标、目标和错误预算 | 设计一张最小看板：任务结果、p95 延迟、错误、成本、评测覆盖、导出/评委失败；定义负责人和排查步骤 | S6、S7 |
| C7 发布与持续迭代 | 回归门禁→候选版本→有限灰度→扩大或回滚→复盘回流 | 为一次改动写发布演练：固定数据/评委/代码/提示词/模型版本；定义阻断、灰度观察和回滚条件；把新问题补进测试集 | S8 |

以上练习是后续学习任务，不在准备路线时自动部署、运行真实写入或修改产品。

## 三项必须深入的设计问题

### 1. 评的是谁，证据来自哪里？

答案评测看文本；轨迹评测看调用与边界；结果评测查真实业务状态。工具返回成功也不总等于外部状态已提交，测试要按实际提交语义取证。
需要分别保存 task 输入、trial 执行证据、grader 判断和 outcome 业务结果。不要给正常运行错误套一个“模型质量差”的标签。

### 2. 改善是真改善，还是测试/评委变化？

先固定案例版本、评委标准、运行环境和应用配置，再比较候选与基线。保留未用于调提示词的测试切片，防止只针对已知题目优化。
同一案例重复尝试；记录样本量和不确定性。`pass@k` 关注多次尝试中至少成功一次，`pass^k` 关注多次都成功；按业务需要选择，不把两者混用。
先看逐例结果与关键场景，再看总体分数；语义评委本身也要用人工标签校准。

### 3. 平台有图表，是否就能可靠运行？

采样率变化会影响可见案例分布，缺失记录不能直接计为成功。还要监控采集、传输和评委本身。
SLI（服务水平指标）是测量口径，SLO（服务水平目标）是预先承诺的目标；错误预算表示允许偏离的空间。
技术成功率、业务成功率和评委分数分别统计。阈值从基线与业务风险确定，不套一个通用“95 分”标准。
灰度需要同时间对照、足够样本和业务护栏；离线评测过关是进入发布流程的证据之一。

## 最终综合验收

拿一个 Pir 合成失败场景，完整演示：发现信号 → 找到可读证据 → 定位原因 → 建立回归案例 → 固定基线 → 定向修改 → 重复评测与人工复核 → 模拟门禁/灰度/回滚 → 案例回流。

最后交付一个能复述的数据流、一份基线对比和一份发布判定。没有真实线上证据时标为演练；不把此路线扩展成全公司平台建设。
