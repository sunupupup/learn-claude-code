## 按顺序学习

每小步采用：一个问题 → 一段源码 → 一次执行或一份证据 → 两道自测。预计 7–10 次小课，仅作节奏参考。

| 步骤 / 官方章节 | 本次要回答的问题 | 阅读入口 | 最小验收 |
|---|---|---|---|
| A1 / 00、01 | 用户消息怎样变成工具调用和回复？ | Setup、Base App；从请求入口追到 `src/server/support-agent.ts` 的 `runSupportConversation` | 画出一次模型→工具→模型链，不急着接监控 |
| A2 / 02 | 谁创建 Trace，谁记录内部步骤？ | Tracing；对照初始化和模型/工具埋点 | 一次请求的输入输出、父子关系、失败终态可以对应到源码 |
| A3 / 03 | 怎么知道这条记录用了哪个提示词版本？ | Prompt Management；提示词发布和解析逻辑 | Trace 可以关联提示词版本；区分版本与标签 |
| A4 / 04 | 怎么从大量对话中筛出可疑案例？ | Monitoring；平台评测器和变量映射 | 触发一次用户反对信号，人工检查误报；知道评委运行在平台侧 |
| A5 / 05 | 什么记录能成为稳定测试案例？ | Dataset；`data/`、数据集辅助脚本 | 准备成功、边界、失败场景，写清预期；不把整条日志直接当标准答案 |
| A6 / 06 | 谁重新跑 Agent，谁评分？ | Experiments；`scripts/run-dataset.ts` | 跑一轮小数据集，看到逐条输出、两个评分和执行记录 |
| A7 / 07、08 | 一次修改是否改善了行为？ | Evaluation、Wrap-up | 固定数据和评委，对比两个版本，解释一个改善和一个未改善/回归案例 |

## 两条评测链必须分清

1. 平台在线监控：应用产生记录 → Langfuse 规则选中记录 → 平台调用评委/执行检查 → 保存 Score。
2. 本地离线实验：脚本取数据集 → 执行同一个 Agent 函数 → 本地评测回调打分 → 关联实验和 Trace。

[04 Monitoring](https://github.com/langfuse/langfuse-workshop/blob/8114728f41f47bb208e1c555fd40c01be7e29d0e/docs/learner/04-monitoring.md) 使用平台评测器；[06 Experiments](https://github.com/langfuse/langfuse-workshop/blob/8114728f41f47bb208e1c555fd40c01be7e29d0e/docs/learner/06-experiments.md) 使用 `keyword_overlap` 与 `correctness` 回调，后者调用模型。关键词匹配与语义评判可能不一致，必须阅读原始回答。

## 教学案例的边界

- 用户反对/大写情绪是排查线索，不是真实成功率，更不能直接当事故告警。
- 两个答案分数不能证明工具权限、外部写入和整个多轮任务都正确；这些留给 Pir 和第三阶段补齐。
- 官方 07 有切换 `production` 提示词标签的练习；学习只用独立实验项目/标签。真实发布需先离线验证，第三阶段再学习灰度。
- 本阶段不阅读 Langfuse 全部后端源码，不先搭 Kubernetes 或完整指标集群。

## 阶段出口

能拿一组证据讲清：请求如何执行 → 数据如何采集 → 平台如何筛选问题 → 数据集如何复测 → 如何比较版本。
产物是一个可解释的改进前后实验；不要求分数必涨，失败实验也要保留。

## 术语速查

- Instrumentation：埋点，在应用关键位置生成运行记录。
- Trace / Span：一次执行链路 / 其中一个操作区间；Session 关联多次交互。
- Evaluator / Score：评测器 / 判断结果；Experiment 是对固定案例运行某个版本的实验。
- Baseline：作为对照的基线；Regression：修改后原有行为变差。
