# 生产级 Agent 的评测与持续优化 扩展

# 1. 明确设计业务指标

明确“什么叫 Agent 做得好”，以及怎么判断。

业务指标和 Agent 的具体业务强相关。

比如你们的媒体创作 Agent，重点是：模型与工具选得对不对、资源引用是否真实、生成结果是否符合要求。

一般可以分为三层

| 层次 | 关注什么 | 例子 |
|---|---|---|
| **运行指标** | 跑得稳不稳、快不快、贵不贵 | 错误率、耗时、token、成本 |
| **Agent 行为指标** | 决策与执行是否正确 | 工具选择、参数合法性、重复调用、失败后虚报成功、资源引用真实性 |
| **业务结果指标** | 是否真正满足用户需求 | 图片是否符合要求、视频主体是否一致、用户任务是否完成 |


时间开销（以下数字仅为量级估算示例，不是 Pir 实测、固定值或上限）：
准备上下文、获取外部数据，并行获取数据，每个200ms
    ↓
请求模型供应商
    ├─ 网络传输  200ms以内
    ├─ 排队调度 0-200ms
    ├─ 处理输入上下文（Prefill）
    └─ 推理思考、生成首个可见 Token ， 非推理 100ms ，推理 1-10s
    ↓
后端转发、前端渲染

前两层可以在不同 Agent 之间复用；第三层最依赖具体业务。

# 2. 多session内存爆炸

100 万 token 的上下文文本暂按约 10 MB 粗估；这不是最大值，也不是整个 Session／Turn 的实际内存占用，副本、对象和缓冲还会增加开销。

1. 采用 LRU 机制
2. 不活跃的，用本地文件先存起来

这两个可以组合成“内存热缓存＋本地磁盘冷存储”。
- LRU：内存设总字节上限，优先淘汰最久未使用的 Session 数据。
- 落盘：不活跃的上下文写到本地文件，再释放内存；下次使用时加载回来。


还有其他办法，**排队策略**，这个也比较常见 （但要注意保活、或者适时显示繁忙）

补充办法：
| 方法 | 具体做法 |
|---|---|
| **减少单 Turn 加载量** | 读取“摘要＋游标后的增量消息”；大文件、工具结果只加载必要片段 |
| **减少重复副本** | 避免 messages 反复完整复制、序列化；可共享的数据使用引用或共享对象 |
| **限制执行期间的增长** | 工具结果、累计事件、输出队列都设大小上限；及时消费或落盘 |

# 4. 采样——成本优化

哪些执行记录需要保留

| 记录类型 | 策略 |
|---|---|
| **基础信息**：关联 ID、耗时、状态、token 等 | 全量保留 |
| **正常请求的完整输入输出** | 按比例抽样，比如 10% |
| **错误、异常慢、用户反馈有问题的请求** | 优先保留完整证据 |

开销主要是，存储量

以及对应的写入、查询成本。冷热分层是合理方向。

不过冷数据更适合放 S3／OSS／MinIO 这类对象存储。ES 更偏向搜索和索引，通常不是最低成本的冷存储选择。

# 5. 脱敏

观测数据上传前，把不该记录的内容处理掉

上传数据的时候，脱敏

要么按结构化数据处理、要么正则

```json
{
  "user_id": "user-123",
  "email": "[REDACTED]",
  "api_key": "[REDACTED]"
}
```

# 6. Langfuse 上传失败

有限重试＋退避，比如失败后等 1 秒、2 秒、4 秒再试，别无限重试把内存和请求堆满。

仍失败的话，重要记录可以先落盘，后续补传。认证失败、数据格式错误则要修配置或数据，原样重试没用。

# 7. 建立可靠 Eval

先看“数据集版本”。

比较 v1、v2 时，两次必须使用同一版测试集和验收标准，否则分数变化可能来自题目变了。

例如：
dataset-v1：100 个案例＋固定评分规则
    ├─ Agent v1：通过 80 个
    └─ Agent v2：通过 90 个
这样才能分析哪些案例改善、哪些退化。

每份实验报告至少关联：
- Agent 版本：代码、Prompt、模型及配置。
- 数据集版本：案例和快照的固定版本。
- 评分器版本：断言代码或模型评委的 Prompt、模型配置。
数据可以存在仓库外，但引用必须固定，不能每次都取“最新数据”。

# 8. 人工标注

明确每个案例“应该怎样才算对”

Langfuse 评估器先筛出疑似失败，再由人工审核确认，补齐正确预期，加入正式回归集。

人工主要确认两件事：
- 是否真的失败：排除评委误判。
- 应该怎样才算通过：补上预期行为、结果和验收标准。

感觉挺重要的

数据闭环的关键：失败记录要经过确认、补齐正确预期，才能变成可靠的优化数据。
线上记录 → 评估器筛选 → 人工确认与标注
→ 固定回归案例 → 修改 Agent → 验证改善
这样积累的不是单纯的日志，而是带有判断依据和验收标准的数据资产。

RSI 递归自我改进（Recursive Self-Improvement），这就是其中重要的反馈基础；自动筛选负责扩大覆盖，人工审核负责校准数据质量。

# 9. 重复实验

一次通过，不代表稳定通过。

同一个案例、相同版本运行多次：
Agent v1：跑 10 次，通过 6 次
Agent v2：跑 10 次，通过 9 次

# 10. 分组分析
别只看整体平均分

比如 v2 的总成功率提高了，但拆开可能是

| 场景 | v1 | v2 |
|---|---:|---:|
| 文生图 | 80% | 95% |
| 图生视频 | 85% | 70% |

整体提升，可能掩盖某个关键场景退化。

需要对比多维度、多标签的 指标提升

# 11. 监控与告警

SLI（服务指标）：实际测量的数字。
SLO（服务目标）：这个数字需要达到的标准。

比如：
| SLI：测什么 | SLO：达到什么要求 |
|---|---|
| 普通对话首字延迟 | 95% 请求在 2 秒内开始吐字 |
| 媒体任务提交成功率 | 一周内达到 99% |
| 无依据的产物引用率 | 不超过 0.1% |

langfuse可以配置告警

指标：首 Token 延迟（TTFT）
统计：过去 5 分钟的 P95
阈值：> 5 秒
动作：发送通知

这表示过去 5 分钟的 P95 超过 5 秒才告警，不是单个请求超过就立刻通知。

# 12. 发布闭环

| 阶段 | 做什么 | 决策 |
|---|---|---|
| **固定基线** | 保存当前稳定版本、测试集和评分器版本，以及实验结果 | 新版本和谁比 |
| **CI 回归门禁** | 改代码、Prompt 或工具后，自动跑测试并比较 | 是否允许进入发布 |
| **小流量灰度** | 先让少量真实用户使用新版本 | 真实环境是否正常 |
| **观察／回滚** | 对比质量、错误、延迟、成本，异常就切回旧版 | 是否扩大流量 |
| **新案例回流** | 审核灰度中发现的问题，加入固定测试集 | 下次怎样提前发现 |

CI 先保证：每次修改后，已收集的测试用例仍然通过，覆盖的 Agent 行为没有退化。

关于 小流量灰度 ，白名单或流量染色，白名单的方式简单点

灰度之后观察
| 类型 | 重点看什么 |
|---|---|
| **质量指标** | 线上评估器通过率、任务成功率、虚假成功／资源引用错误、用户负反馈 |
| **硬指标** | 错误率、首字延迟、总耗时、单任务成本 |


意识到一个问题 “完成一个任务，花多少token” 这个测试
要评估“完成一个完整任务花多少 Token”，多 Turn／Session 级别更有意义。

# 补：coding agent的测试指标

| 维度 | 指标 | 回答什么问题 |
|---|---|---|
| **完成效果** | 任务成功率、回归失败率 | 做成了多少，有没有改坏其他功能？ |
| **稳定性** | 同任务重复运行的成功比例 | 是偶尔做对，还是稳定做对？ |
| **时间** | 整个任务耗时、P50／P95、超时率 | 用户到底等了多久？ |
| **Token** | 累计输入、输出、缓存用量 | 完成任务消耗了多少模型资源？ |
| **费用** | 每次任务费用、每个成功任务成本 | 做成一件事到底花多少钱？ |
| **执行效率** | 模型调用数、工具调用数、重试与返工次数 | 有没有绕路、重复搜索、反复修坏？ |
| **改动质量** | 测试、静态检查、代码审查、无关改动 | 结果是否可维护、符合要求？ |
| **运行可靠性** | 工具错误、环境错误、OOM、异常退出 | 失败来自 Agent，还是基础设施？ |
