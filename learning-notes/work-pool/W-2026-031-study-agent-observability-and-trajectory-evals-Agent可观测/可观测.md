# PIR 项目中的 Agent 可观测与评测

> 本文是 W-2026-031 的项目案例笔记，用来把学习主题对应到 Popipo/PIR 项目。当前依据是项目文档与启动脚本的静态阅读；没有检查 PIR Rust 源码，也没有运行真实模型 Eval。文中“文档写明”不等于“当前运行已验证”。

## 先记住这条边界

- **Langfuse 是观测数据的查看平台 / 后端。** 数据进了 Langfuse，不能单凭这一点断定项目一定直接使用了 OpenTelemetry SDK。
- 项目文档提到 Langfuse sink、OTLP attributes、`trace` / `observation` 等设计，但这只能证明文档规划了相应的数据模型和出口边界。要确认代码是否用了 OpenTelemetry SDK，还要查看 PIR/BFF 的依赖、初始化代码和 exporter 配置。
- 常见链路是 `Agent 代码 → OpenTelemetry API/SDK 生成 Trace/Span → OTLP exporter 发送 → Langfuse 接收与展示`。另一种情况是 Langfuse SDK 帮忙创建或发送观测数据；它也可能在内部采用 OpenTelemetry。
- **OTel SDK、OTLP、Langfuse 不在同一层：** SDK 负责生成/处理遥测；OTLP 是传输协议；Langfuse 是接收和分析观测数据的平台。OTLP 本身不做授权，也不规定 Eval 的通过标准。

## 建议按四个问题学习

### 1. 怎样把一次 Agent 执行串成可读的轨迹？

研究模型调用、工具执行、工作区变化和子 Agent 如何关联到一次 `Run` / `turn`：哪些步骤成为 Span，哪些情况只是 Span Event；如何设置稳定 ID、父子 Span，并在流式调用、异步工作和子 Agent 边界传播上下文。并行步骤的时间顺序不一定代表因果顺序。

**检查目标：** 给定一条执行记录，能回答“模型做了什么、调用了哪个工具、发生了什么真实变化、子 Agent 如何返回结果”。

### 2. 为排障保留哪些数据，如何保护它们？

排障可能需要模型输入输出、工具参数/结果、文件变化摘要、错误和耗时；其中也可能含用户隐私、凭据、源代码或大文件。需要确定脱敏和截断规则、哪些人可查看、保存多久，以及 trace 是否只留摘要或改用受控引用。

**检查目标：** 对每个字段解释它解决什么排障问题、敏感性是什么、为何可以记录或必须删改。可观测数据并非天然安全。

### 3. 怎样用轨迹回归验证 Agent 没有“做错事但答对了”？

固定代表性任务，把预期行为写成可检查断言：工具是否被允许、是否先审批再执行、是否按要求排序、拒绝时有无副作用、是否重复创建任务或重复扣费。对工具调用次数、授权结果、文件/数据库状态等硬事实，优先用确定性 grader；开放语义判断才考虑带 rubric 版本的模型 grader，并用人工标注样本校准。

**检查目标：** 评测最终回答之外的执行轨迹和外部状态。Agent 自己说“已完成”不是副作用已经发生或未发生的证据。

### 4. 观测导出失败时会发生什么？

检查 Langfuse/OTLP 超时、429/5xx、缓冲队列满、进程退出时的行为：是否排队、重试、丢弃、限流和退出前 flush；观测系统异常是否会拖垮 Agent 请求。还要区分一般诊断 Trace 与安全审计记录：若安全审计要求不可丢，不能默认把普通遥测队列当作可靠审计账本。

**检查目标：** 画出数据从进程到后端的失败路径，并说明每类数据丢失的后果与恢复手段。

## PIR 项目中的评测体系

### 1. `popipo-quality`：共享的质量门禁基础

`quality/README.md` 将 `popipo-quality` 描述为各仓共用的确定性质量控制层：它校验 Quality Spec、扫描 Q key、选择业务仓库自己的原生 runner、统一运行结果并计算结论；测试仍由 Vitest、Playwright、Go test、Cargo test、pytest 或 `pir-eval` 执行。

典型流程是：

```text
Quality Spec / Q key
    → validate（校验契约）
    → compile（编译出执行计划）
    → run（调用原生 runner）
    → decide（按门禁策略判定）
    → aggregate（需要时聚合多仓证据）
```

PIR Eval 的用例通过 `quality_keys` 绑定 Q key，配置的 binding rule 使用 `pir_eval_quality_keys`。已批准且属于 hard 的断言必须有 programmatic 绑定。runner 被跳过或没有生成本次运行要求的证据，结果应是 `skipped` / `missing_evidence`，不能当成 pass。

需要特别读懂 `enforcement: observation`：失败、跳过和证据缺失会被记录，但暂时不阻断质量结论。项目质量文档写明，Loop E2E 和 PIR 真实模型 Eval 走 nightly / 手动 release 入口；达到最少观察天数、运行次数与 flake 阈值后，还要由 QE/Harness owner 确认，才能单独升级为 `required`。因此，不能把“有共享门禁框架”误说成“真实模型轨迹 Eval 已经阻断每个 PR”。

### 2. PIR Eval：Agent 行为评测要看什么

从现有文档的目标契约看，Eval 目标不是单独一个模型，而是 **模型 + Prompt + Harness + 工具 + 执行环境** 的组合。测试集可按能力、回归、安全和真实事故组织；断言要检查有证据支持的结果，尤其要在隔离的测试身份/工作区确认真实文件、数据库或任务状态。

硬事实优先确定性判定；开放式语义可用模型 grader，但要固定 rubric 和版本，并以人工 golden 样本校准。Trace 可以提供回归用例的线索，真正重放应走受控的 `pir-eval` 身份与隔离环境，而不是让 Langfuse 直接执行轨迹。

### 3. Langfuse 观测计划记录的差距

`langfuse-observability-ux-plan.md` 区分了 root `turn` trace、模型 generation observation、tool observation 和事件；目标是把模型输入/输出、工具参数/结果、错误、耗时、token/cost 等按用途放到对应层级，并对敏感字段脱敏、对大内容截断或引用。

同一计划的“Current State and Target”明确列出若干待补能力：Langfuse trace 尚无 `trace_id` resolver 和 source snapshot/provenance；replay 隔离不完整；当前每个 case 一次运行，缺少 repeated trials 及 flaky、latency、token、cost 聚合。计划还要求未知 YAML 字段 fail-fast；这是目标契约，不应当据此宣称当前实现已经如此。

所以目前应分开描述：

- **共享质量控制基础：** 项目质量文档记载了 Spec、Q key、runner、证据和聚合门禁机制。
- **Agent 真实模型轨迹回归：** 以 observation 方式记录并逐步完善；从计划文档看，trace 转回归用例、隔离重放和多次运行统计仍有缺口。

## 下一步怎么学

1. 先拿项目一条真实 trace 样例，标出 root turn、model generation、tool observation、event 和它们的关联 ID。
2. 选一个“应拒绝”的工具调用，设计轨迹断言，并确认要检查的真实状态，而不是只检查助手回复。
3. 查看 PIR/BFF 依赖与初始化代码，核实前面悬而未决的 OpenTelemetry SDK / Langfuse SDK / OTLP exporter 关系。
4. 再看 `run-pir-eval-real.sh` 对应的 runner 和报告，记录一次成功、一次拒绝或失败轨迹；当前本笔记不声称这些实验已经完成。
