# 我的笔记 - 基础知识了解

先是看到了 Pi 里面自己实现了一套 pi-telemetry

其实就是一种数据的采集，Agent的数据埋点、记录运行数据，方便后续统计和分析

项目初期，可以搜集大量业务tool的各种校验失败的error，来提前观测可能的任何错误，来优化

Telemetry 的含义是 遥感
作用是：自动记录系统运行时发生了什么，让你能定位问题、衡量性能和成本。

常见记录的数据有
| 能力 | 记录什么 | 能回答什么 |
| --- | --- | --- |
| **链路追踪（Trace）** | 一次任务中的模型请求、工具调用及父子关系 | 哪一步出问题？由哪次调用触发？ |
| **耗时与状态** | 操作开始、结束、耗时、成功或失败 | 是模型慢，还是工具慢？ |
| **事件记录（Event）** | 重试、拦截、参数修复、输出截断等 | 系统采取了哪些处理？ |
| **指标统计（Metric）** | 调用次数、失败率、延迟分布 | 最近整体运行是否变差？ |
| **用量与成本** | token、缓存命中量、费用 | 钱花在哪里？缓存有没有效果？ |
| **错误诊断** | 错误类型、工具名、关联 ID、必要上下文 | 怎样找到并复现失败原因？ |

几个概念的区别：
- Span：一项操作的记录，有持续时间，例如一次 bash 执行。
- Trace：把相关 Span 串起来，形成一次任务的执行链路。
- Event：某个时间点发生的事，例如“输出被截断”。
- Metric：聚合后的数字，例如“今天工具失败率 3%”。

搜集到的数据有很多用途

| 用途 | 具体例子 |
| --- | --- |
| **统计** | 工具调用次数、失败率、平均耗时、token 和费用 |
| **排查问题** | 这次任务卡在哪一步？哪个工具失败？失败前发生了什么？ |
| **发现异常** | 某工具失败率突然升高、同一个错误反复出现时告警 |
| **评估改进** | 加了参数修复后，成功率是否提高？加了输出截断后，token 是否减少？ |
| **操作审查** | 哪次调用被拦截、因为什么、用户是否批准过 |

## OpenTelemetry，简称
| 名称 | 是什么 |
| --- | --- |
| **Telemetry** | 收集运行数据这件事，包括日志、指标、链路追踪 |
| **OpenTelemetry，简称 OTel** | 一套通用的可观测标准、接口和 SDK，帮助统一采集方式 |
| **OTLP** | OpenTelemetry 的数据传输协议，用于把遥测数据发送到接收端 |
| **Pi 的 `pi-telemetry`** | Pi 自己提供的接口抽象，可以通过适配器连接其他系统 |

有这些概念

Telemetry其实是个很通用的名字，代表着整个系统的感知、记录等

OpenTelemetry 是一套可观测数据的标准，防止大家重复造轮子

OTLP 是一种数据传输协议

Collector 最后就是一些数据的接收端，比如 LangSmith， 就能分析完整的 遥感数据

## Telemetry 数据的重要性

采集的数据种类（证据） -> 送到哪 -> 根据数据优化 -> 验证改动有无效果

这是完整的一个链路 

参数错误多 → 改工具描述或参数设计 → 看错误率是否下降。
无效调用多 → 改工具选择策略 → 看任务成功率和调用次数。
成本高 → 减少冗余上下文 → 确认省钱的同时，效果没变差。

## 集中常见的 Telemetry 数据

重要字段
1. name 操作或事件名称，例如 tool.execute
2. traceId 这一次用户请求的最外层的 trace id 用于还原用户一次query触发的完整agent调用链路
3. parentSpanId, 父 Span 的 ID，可以理解为是那一次 run()
4. spanId， 细粒度的 span ， 可以是一次tool call、llm call
5. timestamp
6. status 失败、成功
7. attributes 更加具体的信息，比如错误码、错误信息等

> 参数校验失败 
```json
{
  "name": "tool.validate",
  "status": "ERROR",
  "attributes": {
    "tool.name": "read",
    "error.code": "MISSING_REQUIRED_FIELD",
    "error.field": "path"
  }
}
```
> 模型调用成本和用量
```json
{
  "name": "model.request",
  "attributes": {
    "usage.input_tokens": 2000,
    "usage.output_tokens": 300,
    "cost.amount": 0.0012,
    "cost.currency": "USD"
  }
}
```
> 一次工具执行的时间
```json
{
  "name": "tool.execute",
  "startTime": "2026-10-13T10:00:00.000+08:00",
  "endTime": "2026-10-13T10:00:00.350+08:00",
  "status": "OK",
  "attributes": {
    "tool.name": "read"
  }
}
```

## Collector 的作用

Collector（采集器）是遥测数据的中转处理站：接收数据、加工、转发到观测平台。 你说的“聚合”，这里要分清集中接收、批量发送和统计汇总。

典型的流程：

多个应用的 OTel SDK
       ↓ 通过 OTLP 上报
Collector 接收 → 处理 → 转发
       ↓
观测平台存储、查询、统计

| 部分 | 做什么 |
| --- | --- |
| **Receiver（接收器）** | 例如监听 OTLP HTTP/gRPC 接口，接收应用主动发送的数据 |
| **Processor（处理器）** | 批量整理、过滤、脱敏、补充属性、采样等 |
| **Exporter（导出器）** | 把处理后的数据发送到一个或多个后端 |

几个重要的基本作用 
“聚合”有两种常见含义：
- 把多个应用的数据汇到一起、攒成一批发送：Collector 可以做，减少发送开销。
- 按 name 计算失败率、平均耗时，按 traceId 展示调用树：通常由后面的观测平台完成。

所以基本上 我们的业务代码，把name自己弄清楚、然后一定要带上traceid、spanid等数据
就能够进行最基本的数据分析、聚合、链路追踪了


## 我的笔记 - 观测和改进

学习目标：从观测数据中发现问题、定位原因、提出改进，并验证改动是否有效。

### 学习顺序

| 顺序 | 学习内容 | 要能回答的问题 |
| --- | --- | --- |
| 1 | **成功标准与指标口径** | 工具执行没报错，是否代表用户任务完成？成功率的分子、分母分别是什么？ |
| 2 | 分析异常与定位根因 | 问题集中在哪类任务、哪个版本？如何结合 Trace 和实际结果，找到真正出错的环节？ |
| 3 | **轨迹评测（Trajectory Evals）** | 最终回答看起来正确，但过程中漏步骤、重复操作或越权，该怎样判断？ |
| 4 | **将失败案例转为回归用例** | 如何保留典型失败案例，并定义检查条件，防止问题再次出现？ |
| 5 | **验证优化效果** | 修改 Prompt、工具或执行逻辑后，如何确认改进有效，而不是任务难度或样本发生了变化？ |
| 6 | **观测自身的可靠性** | 埋点遗漏、采样或导出失败会怎样影响判断？如何发现数据缺失？ |
