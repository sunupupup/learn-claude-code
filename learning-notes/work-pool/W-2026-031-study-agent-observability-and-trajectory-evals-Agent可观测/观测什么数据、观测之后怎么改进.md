# 观测什么数据、观测之后怎么改进

> W-2026-031 专题笔记。目标是回答一个真实工程问题：Agent 上线后通常观察什么，看到异常后如何判断改哪里，以及如何证明改动有效。
>
> 难度：D2→D3（要把产品结果、Agent 执行链、运行质量、安全和评测连起来）；学习从 D1 术语开始。资料核对日期：2026-09-26。

## 先用一句话回答面试官

我会先从业务目标和风险确定观测项，再在 Agent 的模型、检索、工具、权限、状态变更等边界接入埋点，把 Trace、结构化事件和聚合指标送到 Langfuse 或相应观测后端。先按功能、版本、任务类型等切片找出异常，再查看代表性 Trace 和真实业务状态定位根因；把真实失败沉淀成反馈/评测用例，针对性修改数据检索、Prompt、工具契约、权限、编排或产品交互，最后用固定回归集和灰度结果验证改动有效且没有伤害安全、质量、延迟和成本。

关键点：**观测数据是定位线索，不会自动告诉你正确改法；改法要由根因假设和可重复验证共同支撑。**

## 1. 先把几个相邻概念分开

| 名词 | 它回答的问题 | 例子 |
|---|---|---|
| 业务指标（Product / Outcome Metrics） | 用户的任务有没有真正完成？ | 工单是否正确解决、文件是否生成且内容正确、是否需要人工接管 |
| 质量评测（Eval） | 对固定或采样任务，行为是否符合预先定义的标准？ | 答案有无依据、工具是否选对、拒绝用例是否真的没有副作用 |
| Trace / Span | 某次任务经过了哪些步骤，哪里耗时或出错？ | 一次 Trace 关联模型调用、检索、工具和子 Agent 的 Span |
| Metrics（聚合指标） | 一段时间或一批请求的趋势如何？ | 成功率、P95 延迟、工具失败率、每个成功任务的成本 |
| Logs / Events（日志 / 事件） | 某个时间点记录了什么结构化事实？ | `approval_denied`、`tool_retry`、`workspace_file_changed` |
| Audit（审计记录） | 谁在什么授权下做了哪项重要操作，能否追责？ | 用户身份、策略版本、批准人、业务对象 ID、实际变更结果 |

Trace 是一次运行的诊断轨迹；Metrics 是大量运行的汇总；Eval 是用标准判断质量；Audit 是对重要动作留有治理/追责证据。它们可以关联，但不能互相替代。**有 Trace 不等于通过安全检查，有成功率也不等于知道失败根因。**

### 本文里的几个专业词

- **P95（第 95 百分位）**：把请求按耗时排序后，95% 的请求不超过此耗时，剩下 5% 更慢。它用于观察尾部体验，不代表最慢的那几个请求；同时要看样本量和分组。
- **RAG（Retrieval-Augmented Generation，检索增强生成）**：先从业务知识源检索相关资料，再把资料给模型回答。知识库问答例子会分别查“没检索到资料”与“检索对了但模型仍答错”。
- **Grader（评判器）**：按照规则给答案、轨迹或任务结果打分的程序、模型或人工评审。工具权限和文件状态等硬事实优先用确定性检查；主观质量才考虑校准过的模型评判。
- **基数（Cardinality）**：某字段可能取到的不同值数量。`environment=prod/dev` 基数低；`trace_id` 几乎每次都不同，基数高。高基数字段用于单条 Trace 排查通常有用，但不适合作为大规模 Metrics 的分组标签。
- **SLO（Service Level Objective，服务等级目标）**：一段时间内服务希望达到的可靠性/时延目标，例如满足业务约束的请求比例；它是告警和发布判断的依据之一，不等于随便设一个“越高越好”的数字。
- **A/B（对照实验）**：把符合条件的流量分到不同方案，对照其业务结果。它可帮助评估线上改动，但要控制用户/任务分布等混杂因素；不能用它替代安全回归。
- **CI（Continuous Integration，持续集成）**：代码变更时自动运行检查的流程。Eval 接入 CI 后可在已知回归时阻止合并/发布，但门槛要按风险与 Eval 稳定性设计。

## 2. 先看端到端全链路

```text
业务目标 / 风险定义
        ↓ 决定“什么叫成功、什么绝不能发生”
Agent 项目接入观测
        ↓ 在模型、检索、工具、权限、状态变化等边界生成信号
Trace / Span / Event / Metric / Eval score / 用户反馈
        ↓ 通过 SDK 或 instrumentation 产生，OTLP / exporter / Collector 传送
Langfuse / Metrics 后端 / 日志平台 / 业务库 / 审计存储 / Eval 数据集
        ↓ 按时间、功能、版本等聚合切片；从异常指标跳到 Trace
发现异常 → 分析执行轨迹 + 核实真实结果 → 判断根因
        ↓
修数据 / Prompt / 工具 / Policy / 编排 / Runtime / 产品交互
        ↓ 固定数据集回归 + 灰度 / A-B + 线上指标观察
成功则保留并沉淀用例；变差则回滚或继续调查
```

这条链中，观测平台帮我们看数据，不会自动替团队诊断和改代码；Eval/人工审核帮助判断改动是否符合标准；业务服务和授权策略仍负责真正的状态和安全边界。

### 这部分怎么学：项目优先，开源资料补机制

建议不要一上来克隆一个大型 Agent 框架。用自己的 PIR/Poppipo 任务作主线，因为面试问题问的是实际场景；开源项目和官方 Demo 用来补你项目里看不清的机制：

1. **本地概念样例：** 先拿本仓库已有 `TraceCollector` 和 Eval 说明，识别一次模型→工具→结果的事件。它是简单教学样例，不是完整 OTLP 平台。
2. **自己项目的观测视图：** 在 Langfuse 找一条无敏感信息的成功 Run 和失败 Run，先只读 trace tree，画出根 Trace、模型/工具 observations 和结果关联。
3. **开源平台示例：** Langfuse 官方 Datasets/Experiments 示例展示如何把生产 trace 的问题转成固定用例并比较改动；重点学评测闭环，不要求先重写项目去适配它。[Langfuse Datasets](https://langfuse.com/docs/evaluation/experiments/datasets) [Langfuse Evaluation](https://langfuse.com/docs/evaluation/overview)
4. **传输层实验：** 等知道要采哪些字段后，再用 OpenTelemetry Collector Quick Start 看“接收→处理→转发”这段管线。官方 Demo 明确是本地入门，不是生产配置。[OTel Collector Quick Start](https://opentelemetry.io/docs/collector/quick-start/)
5. **回到项目验证：** 阅读 PIR/BFF 文档、配置和源码，核实实际使用的 SDK/exporter、Trace 字段、Eval runner 与数据去向；对比设计契约和运行证据。

## 3. 怎么接入一个 Agent 项目？

“接入观测”不是只安装一个 SDK。先画出现有 Agent 的执行边界，再决定在哪里自动 instrumentation、在哪里加少量业务埋点。

| 接入位置 | 记录什么 | 为什么放这里 |
|---|---|---|
| API / Agent Run 入口 | Run/trace ID、任务类别、环境、版本、开始与终止状态 | 为一次请求建立根，能从结果回溯整次运行 |
| 模型客户端 | 每次模型调用、模型名/版本、输入/输出 Token、耗时、错误；必要且合规时记录受控输入输出 | 分清模型调用耗时、用量、截断和供应商故障；Agent loop 有多次模型调用时应分别看 |
| 检索 / RAG | query 摘要、检索器/索引版本、过滤条件、命中文档 ID/分数、耗时 | 判断是知识源缺失、权限过滤、召回还是生成环节出错 |
| Tool 调度与执行 | 模型请求了什么工具、参数校验、Policy 决策、审批、真实执行结果、重试和副作用 ID | 把“模型提议调用”与“系统授权并执行”区分开 |
| 工作区 / 业务状态 | 写操作摘要、变更前后状态或变更 ID、提交/事务结果 | 核实副作用是否真的发生，以及拒绝后是否保持未变 |
| 子 Agent / handoff | 父子 Run 关联、任务摘要、输入输出、完成/失败/超时状态 | 找到并行或委派链路中的断点及错误归属 |
| 业务完成边界 | 下游对象状态、用户反馈、人工接管、任务重开 | 以权威业务状态定义完成，避免把模型自述当成功 |

接入方式有三类，常能组合使用：

- **框架自动集成：** 复用已有 callback / middleware / instrumentation，快速得到模型和工具调用轨迹；需要检查它是否漏掉项目自己的权限、状态和业务结果。
- **手工业务埋点：** 在自有 Tool dispatcher、授权判断、状态转换和副作用边界记录结构化事件；它补上通用框架看不到的业务语义。
- **SDK / 协议导出：** OpenTelemetry API/SDK 可以创建与处理信号，Exporter 发送 OTLP；可以直达后端，也可以经 Collector 做批处理、过滤或转发。Langfuse 也支持其 tracing SDK 和 OpenTelemetry 接入路径。实际采用哪条必须检查该项目依赖和初始化配置，不能从“数据出现在 Langfuse”反推。

所有跨组件操作要约定关联关系（例如 trace/run/session/request ID）、稳定的操作名和版本元数据；不要把高基数动态 ID 用作 Metrics 标签。先选一个低风险垂直切片，确认从 API 到结果能串起来，再扩大覆盖面。

## 4. 数据采集后送到哪里？

先区分**产生地点、传输节点、最终存储/使用地点**：

```text
PIR/BFF/Agent 进程中的 instrumentation
  ├─ Trace / Span / Event ─ Exporter ─ OTLP ─（可选）OTel Collector ─ Langfuse / Trace 后端
  ├─ 运行指标（延迟、错误、调用量）─────────────── Metrics 后端 / Dashboard / 告警
  ├─ 诊断日志 ─────────────────────────────── 日志检索系统
  ├─ 授权与关键副作用审计 ─────────────────── 权威审计/业务存储
  └─ Eval 结果 / 用户评分 ─────────────────── Langfuse Scores / Eval 数据集 / 质量报告
```

| 数据类型 | 适合的去向 | 原因与注意点 |
|---|---|---|
| Agent Trace / 模型和工具 observations | Langfuse 或 Trace 后端 | 用于按 Run 展开执行树、看输入输出/耗时/错误、关联 score；正文需要脱敏与访问控制 |
| 聚合延迟、错误率、调用数、Token 指标 | Metrics 存储与 Dashboard/告警 | 适合看趋势、分位数和服务目标；维度保持有限，避免 `trace_id` 等高基数标签 |
| 运行诊断日志 | 日志平台 | 适合检索错误堆栈/服务日志，使用 Trace ID 与 Trace 关联；避免把敏感请求全文重复写入 |
| 任务完成状态、订单/工单/文件等真实结果 | 业务数据库或系统 of record | 这是判断副作用成功与否的事实源，Langfuse Trace 不能取代它 |
| 高风险授权与副作用审计 | 具备访问控制、完整性和保留策略的审计存储 | 安全审计不能只依赖可能采样、延迟导出或丢失的普通 Trace |
| Eval 用例、期望结果、grader 与实验结果 | 版本化数据集/质量仓库，必要时同步到 Langfuse | 保证同一基线可重复比较，能追踪来源和版本 |

**Langfuse 是数据接收/分析产品之一；OTLP 是传输协议；Collector 是可选的数据管道组件。**它们不要求所有数据都必须存进 Langfuse，也不替代业务数据库、授权判断或不可丢的审计账本。数据怎么分流取决于查询用途、敏感级别、成本和保留政策。

## 5. 观测哪些数据？

不要先从“能打哪些埋点”开始，而是先问：这个 Agent 要完成什么任务，用户和业务如何定义完成，哪些错误代价最高？指标应由场景目标和风险决定，不存在所有 Agent 共用的一张万能指标表。

| 数据块 | 常见观测项 | 能回答什么问题 | 典型改进方向 |
|---|---|---|---|
| **业务结果** | 任务完成率、正确解决率、人工接管率、重开/撤销率、用户等待后放弃率、下游状态核实 | Agent 是否解决了用户的问题，而非只产出看起来像答案的文字？ | 重新定义成功条件、补必要工具能力、改变交互/审批流程，或缩小 Agent 的职责 |
| **回答质量** | 正确性、相关性、完整性、事实依据/引用、格式正确率、合适拒答率；用户评分和人工抽检 | 哪类输入或用户拿到不可靠/不合用的结果？ | 修复数据/检索、Prompt、输出 Schema、模型选择或产品需求；按坏例子扩充 Eval |
| **执行轨迹** | 每轮模型调用与版本、Agent 步数、工具名和参数摘要、工具结果、重试、路由、handoff、审批和状态转移、结束原因 | 它为什么这样回答？调用了哪个工具？有没有循环、漏步骤、重复执行或错误委派？ | 调整工具描述/Schema、路由与状态机、停止条件、重试/幂等策略、子 Agent 边界 |
| **安全与权限** | 工具 allow/deny、策略和审批结果、越权尝试、拒答/拦截、被拒绝后的副作用数、工作区/数据库最终状态 | 高风险行为有没有在代码执行边界前被挡住？拒绝之后是否仍发生变更？ | 修复服务端授权、最小权限、审批、隔离、事务/幂等、撤销机制；增加轨迹安全断言 |
| **运行健康** | 端到端及各 Span 延迟、错误率、超时、取消、429/5xx、工具可用率、队列等待、服务资源 | 慢或失败发生在模型、检索、工具、网络、队列，还是 Runtime？ | 超时预算、并发、缓存、降级、重试策略、依赖治理、容量或供应商切换 |
| **资源与成本** | 输入/输出 Token、模型调用数、工具调用数、每任务成本、模型/工具分布、上下文长度 | 成本为何升高？是否长上下文、重复调用或低价值步骤造成？ | 缩短/重组上下文、限制循环、复用缓存、模型路由、减少不必要工具调用；随后跑质量 Eval 防止省钱省坏了 |
| **反馈与失败样本** | 👍/👎、用户纠正、重试、人工修改、投诉/工单、抽样标注 | 用户在哪里感到失败？新出现了哪些真实边缘案例？ | 分类失败、澄清成功标准、把代表性坏例子变成回归用例，验证修复是否解决同类问题 |

### 一条运行的 Trace 里通常放什么

以一次 Agent `Run` 为根，把有诊断价值的操作按因果关系组织起来：

```text
Agent Run / Trace
├─ 输入校验 / Context 装配
├─ 检索 Span（索引版本、过滤条件、命中数量/引用 ID、耗时）
├─ Model Span（模型与 Prompt 版本、用量、延迟、错误、受控输入输出）
├─ Tool Span（工具名、脱敏参数、权限判定、调用结果/错误、重试）
├─ Workspace / 外部状态事件（变更摘要、目标对象、状态前后值或变更 ID）
├─ 子 Agent / handoff（父子关联、输入输出、完成/失败状态）
└─ 最终业务结果与 Eval / 用户评分的关联 ID
```

Trace 中应能定位 `run_id/trace_id`、模型/Prompt/工具/索引版本、环境和任务类型；不要为了可搜索性把每个 `user_id`、`trace_id` 都塞进 Metrics label。高基数的请求身份通常放在 Trace/日志上下文，聚合指标选有限维度（例如模型、功能、环境、主要工具、语言类别）。

记录可检查的输入输出、调用、工具结果和状态变化即可；不要把模型私有推理文本当作必须采集的观测数据。完整 Prompt、用户原文、工具 payload、文件内容可能含隐私、凭据、客户数据或机密代码，必须按用途做最小化、脱敏、访问控制和保留周期设计。没必要为了“可观测”把所有数据无界地写入后端。

## 6. 怎么分析这些数据？

分析不是盯着一张 Dashboard 看数字，而是逐层缩小范围，最后用一次任务的证据解释变化。

1. **先看用户/业务结果：** 哪个目标变坏了？例如“正确完成率”下降还是 P95 延迟升高？先确认分子、分母、时间窗和当前基线，避免数据口径变了却误当系统退化。
2. **按有意义的维度切片：** 功能、任务类型、模型/Prompt/工具/索引版本、语言、环境、租户/用户群、发布批次。切片用来发现问题集中在哪里；隐私和低样本量需要额外保护。
3. **选代表性 Trace：** 从失败组、慢请求、拒绝请求中抽样，也看少量正常样本作对照。比较同一任务下成功与失败的上下文、检索结果、模型调用、权限决策、Tool 结果和状态变化。
4. **核对权威结果：** 对文件、工单、扣费等副作用查真实业务状态/审计记录；不要只以 Trace 写了 `success=true` 或 Agent 回复“我完成了”作为事实。
5. **归类根因：** 产品需求定义、知识数据、检索/context、模型/Prompt、工具契约、授权策略、状态/并发、外部依赖、Runtime、Eval/grader 自身都有可能。先判断所在层，再判断要改什么。
6. **提出并检验假设：** 例如“失败集中在新政策问题，是因为知识索引落后两天”。查看索引更新时间和缺失文档能支持或推翻假设；不要先动 Prompt 再寻找理由。

### 分析时实际要回答的问题

- 哪个**用户任务**受影响，影响多大，集中在哪一类用户/版本/条件？
- 失败发生在流程哪一步：输入、检索、模型、工具、权限、状态提交、返回，还是外部系统？
- 是一次个例、稳定可复现的产品问题、供应商/网络瞬时错误、任务/评测定义问题，还是埋点丢失？
- Trace 中观察到的行为与数据库/文件等最终状态是否一致？有没有重复、漏掉或未授权副作用？
- 修哪个控制杠杆最可能改变目标结果？是否会伤及另一个任务群或安全边界？
- 改完后用什么独立证据确认有效：Eval、人工复核、下游状态，还是灰度对照？

建议让聚合图表能 drill down 到 Trace，Trace 再能跳到 Eval item / 用户反馈 / 业务对象引用。**聚合看趋势，Trace 看单次过程，业务库看真实结果，Eval 看候选版本是否回归。**

## 7. 分析后能带来什么“正反馈”？

这里的“正反馈”不是指标自动变好，而是观测数据帮助团队做出有效决策，并让后续迭代更快、更有依据。

| 获得的反馈/收益 | 例子 | 最终带来的改善 |
|---|---|---|
| 更快发现和定位事故 | 失败率告警关联到版本；Trace 显示某工具超时集中出现 | 降低排障时间和故障影响面，少靠猜测和人工复现 |
| 质量/产品需求反馈 | 某类用户反复纠正回答，评审发现缺少“提供来源”标准 | 更新产品成功条件、回答呈现和功能设计，而不只是改模型 |
| 数据/知识维护反馈 | Trace 显示目标文档从未进入索引，用户反复问新政策 | 修摄取、索引新鲜度和 owner 告警，让内容负责人知道要更新什么 |
| Agent 行为反馈 | 错选工具、重复调用、误拒绝集中出现在某版本 | 精准改工具说明、授权映射、状态机或重试逻辑 |
| 成本/容量反馈 | 某任务平均需要很多次模型调用，且成功率没有更高 | 限制无效循环、收窄上下文、改模型路由/并发预算，用单位成功任务成本判断收益 |
| 组织知识反馈 | 同一失败类型反复被不同工程师修复 | 将失败分类、Trace 链接、期望行为和验证用例形成共享回归资产 |

### 把线上反馈沉淀成回归用例

```text
用户差评 / 人工改正 / 业务事故 / 异常 Trace
        ↓ 关联原始 Run、版本、任务与实际状态
人工确认问题和“正确结果/正确轨迹”
        ↓ 去隐私、去重复、分类别，确认数据有权留用
形成 Eval item（输入、期望结果、轨迹/状态断言、来源）
        ↓
对当前基线跑一次，确认用例能发现问题且不会误杀合法解法
        ↓
修系统后重跑同一数据集，与原版本对照
        ↓
通过门槛后灰度；线上继续看新信号，回流新的失败样本
```

Langfuse 官方资料展示了从生产 Trace 挑选样本、补充 expected output、形成 dataset，再用 Experiments 对比 Prompt/模型/代码改动的路径；在线评估和用户反馈可继续发现新问题。[Dataset from production traces](https://langfuse.com/docs/evaluation/experiments/datasets) [Evaluation loop](https://langfuse.com/docs/evaluation/core-concepts)

但是，用户评分不是绝对真值：用户可能误点，差评可能由网络或等待体验导致，线上样本也有分布偏差。**反馈先成为待核验线索，经过分类、人工确认和隐私处理后再入数据集。**不要把原始反馈自动用于 Prompt 更新、训练或放权；否则会引入错误标签、数据投毒和回归风险。

## 8. 怎样把分析结论变成系统改进？

```text
定义业务成功与高风险失败
        ↓
采集分层信号：结果指标 + Eval 分数 + Trace/事件 + 资源指标
        ↓
发现异常，并按功能/模型/版本/语言/工具/环境分组
        ↓
挑选代表性 Trace 和真实下游状态，分类根因
        ↓
提出一个可证伪的修复假设；把失败例冻结成回归用例
        ↓
修改对应层（产品定义 / 数据检索 / Prompt / 工具 / Policy / Runtime）
        ↓
在同一 Eval 集与基线比较：质量 + 安全 + 延迟 + 成本
        ↓
灰度或 A/B 上线，观察线上结果；不满足门槛则回滚
        ↓
新故障进入 Eval 集，形成下一轮反馈
```

OpenAI 的 Agent 评测指南建议：行为还在排查时，先用 Trace grader 找工作流问题；知道“好”是什么后，再把样本固定成数据集，重复比较不同 Prompt、路由或实现。Langfuse 的评测资料也描述了“生产 Trace → 数据集 → 实验比较 → CI/发布门槛 → 回到线上观察”的闭环。[OpenAI Agent Evals](https://developers.openai.com/api/docs/guides/agent-evals) [Langfuse Evaluation Overview](https://langfuse.com/docs/evaluation/overview)

建议每次改动写成这个格式：

> **信号：** 哪项指标/哪组任务变差？分母和观察时间段是什么？  
> **证据：** 哪些 Trace、运行状态或人工样本支持这个判断？  
> **根因假设：** 当前证据排除了哪些解释，最可能是哪层出错？  
> **改动：** 只调整哪个主要杠杆？为什么是它？  
> **验证：** 哪些固定用例要通过，线上哪些业务/安全/成本指标必须不退化？  
> **回退：** 灰度期间触发什么条件要撤回？

## 9. 常见信号怎么映射到改进动作？

| 观测信号 | 先查什么 | 可能改什么 | 怎样确认改对了 |
|---|---|---|---|
| 任务完成率下降 | 按任务类型和版本切片；抽 Trace；检查下游真实状态，区分答错、工具失败、流程未结束、需求定义不清 | 修产品流程/数据/工具/Prompt 中被证据指向的部分；不可只为抬高分数放松成功定义 | 在固定任务集上检查结果与过程；灰度看真实成功率及人工接管，不只看模型自评 |
| 👎 增多，但自动质量分数没变 | 看反馈是否集中于语言、功能或用户群；人工阅读评分理由；检查 Eval grader 是否漏掉了用户在意的维度 | 补任务成功标准或 Eval 维度；调整输出表达、引用或产品交互 | 用新反馈案例和人工校准集重测，再看线上反馈分布 |
| 答案错且检索为空/召回错 | Trace 中查看 query、过滤、索引版本、命中文档及权限过滤 | 修数据覆盖、切分、索引/过滤/查询改写或检索排序 | 用检索命中与权限用例测 Recall/Precision，再验最终答案正确性 |
| 证据正确，但模型仍答错/遗漏 | 对照真实发送给模型的上下文、输出 Schema、模型版本、Token 截断与 finish reason | 修 Context 选择/排序、Prompt、Schema、模型路由或上下文预算 | 以同一组输入比较候选版本；检查准确性/完整性且拒答、安全边界不退化 |
| 选错工具、参数无效或工具没被调 | 看每个模型调用和工具 Schema、验证错误、路由规则与任务类别 | 明确工具职责/参数 Schema，改工具可见范围、路由或前置数据校验 | 覆盖“应该调用”和“不应该调用”的正反例，验证参数和结果状态 |
| 工具被拒绝率上升 | 区分正常拒绝（策略生效）与误拒绝；看策略版本、用户权限、工具、租户和申请参数 | 若误拒绝，修真实授权规则/身份映射；若本应拒绝，则保留阻断并改进用户解释 | 正例应允许、越权反例应拒绝；检查拒绝后副作用为零。不能通过放开权限“优化拒绝率” |
| 有重复创建/扣费/写文件，或工具重试上升 | 看调用 ID、超时与实际下游结果、重试时是否得到前次成功确认、状态前后快照 | 优先修幂等键、去重、事务、结果查询、重试边界与恢复流程；必要时增加人工批准/撤销 | 故障注入“下游成功但响应超时”，重复运行用例，核实只发生一次副作用 |
| 端到端 P95 延迟升高 | 用 Span breakdown 检查模型、检索、工具、队列和重试哪个阶段拉长；按 provider、model、tool 分组 | 优化慢阶段、并行无依赖步骤、缓存、超时/降级或供应商策略 | 对同一负载比较端到端 P95 与子阶段分布，同时检查成功率和质量 |
| Token / 每任务成本增加 | 查看每次 generation 的输入/输出 Token、步数、重复检索与工具循环、任务难度分布 | Context 裁剪/摘要、减少重复调用、模型分级、缓存、明确终止条件 | 在固定任务集比较 cost per successful task，检查答案质量、工具成功和安全不下降 |
| 子 Agent / 工具链出现循环或失联 | 检查父子 Trace Context、handoff 次数、等待/超时、重复任务 ID、结束状态 | 加预算和终止条件、委派输入/输出契约、取消传播与失败归属 | 构造正常完成、子 Agent 超时、重复 handoff 和部分成功用例验证 |
| 观测缺失或 Langfuse 中 Trace 不完整 | 检查 exporter 错误/队列、采样、异步上下文传播和各服务 ID 关联；对照请求侧独立计数 | 修传播或导出链路、flush/重试策略、采样规则；安全审计用可靠业务审计存储而非只靠 Trace | 故障注入 exporter 限流/断连/进程退出，并验证 Agent 请求行为与安全审计记录符合预期 |

### 重要例子：安全指标不等于“越低越好”

“权限拒绝率”高可能说明系统在挡住越权，也可能说明授权误配让合法用户不断失败；“工具调用率”高也可能表示能力充分，或 Agent 多走了无用步骤。指标必须与任务类型、授权期望和实际结果一起读。安全目标往往是**越权副作用为零**，不是简单把拒绝率降到某个数字。

## 10. 一个完整小案例：知识库问答 Agent

### 用户症状

用户反馈“有时回答没有来源、而且找不到新发布的政策”。不能直接得出“Prompt 写差了”。

### 先观测和切片

1. 业务结果：政策问题一次解决率、人工升级率、用户差评/纠正率；明确“一次解决”的下游定义。
2. 质量 Eval：答案是否被检索证据支持、引用是否指向正确文档、当前政策问题是否覆盖；不能只用文本相似度。
3. Trace：按坏例查看模型版本和 Prompt、检索 query、索引/数据版本、过滤条件、命中文档/引用 ID、模型实际上下文、最终回答。
4. 切片：按问题类型、语言、知识库版本、时间范围和应用版本分组，确认问题是否集中于近期发布的政策。

### 找到根因再改

假设 Trace 证据显示索引里根本没有新政策文档，答案缺引用不是 Prompt 造成的。改进应落在**文档摄取/索引新鲜度及失败提示**，不是换一个更贵的模型。将这个问题和几个相似旧政策案例组成 Eval：确认新文档可检索、答案引用正确，权限过滤没有放开；再对候选索引管线做回归和灰度。

如果文档正确命中并进入模型上下文，但模型仍错误引用，则这是另一种根因，需要检查上下文组织、Prompt 或答案判定，不能拿同一修复假定覆盖所有坏例。

## 11. 指标设计中的常见坑

- **只看最终答案或点赞率：** 找不到失败发生在检索、模型、工具、授权还是 Runtime；点赞样本也可能很少且有偏差。
- **只看平均值：** 平均延迟掩盖尾部慢请求；同时看 P50/P95/P99、错误率及分群。百分位需要足够样本量。
- **没有分母和任务定义：** “成功率 90%”要说清楚分母是请求、Agent Run、还是有明确目标的业务任务；部分成功/人工接管怎么算。
- **所有失败都归模型：** 数据缺失、错误权限、工具协议、外部 API、状态竞态、Eval bug 都会让 Agent 表现像“模型变笨”。
- **只优化一个指标：** 压 Token 可能损害正确性；降拒绝率可能带来越权；追求调用少可能漏掉必要验证。质量、安全、延迟、成本一起设 guardrail。
- **线上相关性被当作因果：** 某版本成本高可能只是该版本处理更多复杂任务。对照同一 Eval 集、同任务分层，必要时做灰度/A-B，再作因果结论。
- **Eval 被优化到满分：** 任务覆盖偏、用例过时或 grader 有漏洞时，高分不能证明能力可靠。读失败和通过样本，监控饱和与分布变化。
- **只收集成功 Trace：** 会造成幸存者偏差。对错误、超时、拒绝、接管和随机正常样本都要有覆盖，并说明采样率。
- **把观测数据当安全控制：** Trace 通常在运行时写出或稍后送达，不应承担授权、事务保护或不可丢审计的职责。

## 12. 最小可用观测面板

早期可以从以下几张图开始，不必先做巨型 Dashboard：

1. **业务与质量：** 任务完成率、人工接管/重开率、用户反馈、Eval pass rate；显示时间范围、任务类别、分母和置信/样本数。
2. **可靠性：** 端到端 P50/P95、Run 错误/超时率、模型/工具失败率、重试和取消。
3. **执行安全：** 工具选用与参数验证、allow/deny/approval、拒绝后副作用、工作区/外部状态核实、循环/超预算次数。
4. **成本：** 每个成功任务的模型与工具成本、Token、调用数，并按功能/模型/任务类型切片。
5. **Trace 排查入口：** 从异常指标跳到代表性 Trace，展开每个模型调用和工具调用，能看到版本、阶段耗时、受控输入输出、状态结果和错误。

**告警应针对用户/业务风险或 SLO，不要只因模型调用数波动就报警。** 对危险写操作、重复扣费等高严重度风险，可以设置零容忍的安全门槛；对质量和体验则根据基线、样本量及业务风险制定目标。

## 14. 面试时展开成 1 分钟

> 我会先从业务成功和高风险失败出发，在模型、检索、工具、权限、工作区变更等边界接入 instrumentation，建立一次 Run 的 Trace/Span/Event 和聚合指标。数据通过 SDK/exporter/OTLP（必要时经 Collector）分流到 Langfuse、指标/日志后端、业务状态库和审计存储；各自用途不同。分析时先看业务结果和趋势，按版本、任务类型等切片，再下钻代表性 Trace，并核实业务数据库等权威状态。找到根因后把真实失败整理成带来源和期望行为的 Eval 用例，再修数据/检索、Prompt、工具契约、Policy、编排、Runtime 或产品交互；用固定回归集、灰度和线上结果验证质量、安全、延迟、成本的变化。用户反馈和线上坏例能让 Eval 集持续覆盖真实问题，但要审核和隐私处理后再回流。Trace 帮助诊断，Eval 帮助重复验证，授权和审计仍由运行时/业务系统负责。

## 15. 下次继续时的学习检查

看见“Agent 完成率下降”，先尝试按顺序回答：

1. 这个完成率的分子、分母和业务完成定义是什么？
2. 问题集中在哪些任务、版本、工具、模型、用户群或环境？
3. 从一条失败 Trace 里，能排除哪些根因，证据是什么？
4. 如果要改，改哪一层？安全、质量、延迟、成本会有什么副作用？
5. 哪些 Eval 用例和线上指标可以证伪“改好了”的假设？
