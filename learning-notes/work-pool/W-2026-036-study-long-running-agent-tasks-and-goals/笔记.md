# 长任务

长任务的难点，是工作越往后，越难保持“目标、记忆、实际进度和执行结果”一致。

长任务的几个维度：时间长、步骤多、需要跨轮或跨进程接续。

长任务可能导致的问题

| 问题 | 为什么长任务容易遇到 | 具体表现 |
|---|---|---|
| **1. 重要信息逐渐被淹没** | 工具结果、历史讨论不断累积，模型当前能处理的信息有限 | 前面要求“只用一手资料”，后面却引用了转载 |
| **2. 压缩、换会话后丢信息** | 历史摘要未必保留后来才显得重要的细节 | 忘了某条结论已经被否定，又重新采用 |
| **3. 忘记做过什么，重复或漏做** | 聊天、计划、产物之间没有可靠对应关系 | 同一篇文章看了三遍，另一篇始终没处理 |


| 问题 | 为什么长任务容易遇到 | 具体表现 |
|---|---|---|
| **4. 逐渐偏离最初目标** | 每一步都围绕眼前发现展开，局部探索不断扩大 | 本来研究技术可行性，最后写成行业新闻汇总 |
| **5. 计划失效，仍按旧路线推进** | 执行中会发现新限制、缺失依赖和错误假设 | 核心数据拿不到，仍继续撰写依赖该数据的结论 |
| **6. 前面的错误污染后面的工作** | 后续步骤把先前输出当作可靠输入 | 错认一个概念，后面的筛选、比较和结论全部跟着错 |
| **7. 做到一半留下难以接续的现场** | 中间状态不完整，操作与进度没有清楚记录 | 只有半份报告，不知道哪些段落已核验、哪些只是草稿 |

| 问题 | 为什么长任务容易遇到 | 具体表现 |
|---|---|---|
| **8. 中断后不知道从哪里继续** | 运行时间越长，越可能遭遇网络故障、进程退出或服务重启 | 已阅读几十份资料，恢复后却从头再做 |
| **9. 操作结果未知，重试造成重复** | 外部操作成功与本地收到确认，可能发生在两个时刻 | 报告已上传，但确认响应丢失，恢复后再次上传 |
| **10. 等待之后没人继续推进** | 等待工具、用户或外部系统，与重新启动执行是不同环节 | 数据已经生成，整个任务却一直停在“等待中” |
| **11. 运行期间外部条件发生变化** | 原计划依据的文件、数据、权限或服务状态可能过时 | 报告前半段和后半段使用了不同版本的数据 |

最后还有两个直接影响交付的问题：
- **12. 忙了很久，却没有有效进展。** 不断搜索、反复改计划、重复尝试同一路径，时间和费用持续增长，但关键问题没有解决。生产研究系统也需要处理长链路中的错误累积和昂贵重启。Anthropic 生产经验
- **13. 过早宣布完成，或者不知道何时结束。** 看到报告文件就认为任务完成，却没有检查覆盖范围、引用和结论；另一头则可能无限润色、持续补充。Anthropic 实验明确观察到了提前宣告成功和未经充分测试就标记完成。完成判断的实验观察

这些问题还会相互影响。例如：

早期判断错误 → 写入进度记录 → 压缩时保留为“已确认结论” → 后续继续引用 → 最终交付一份内部一致、但依据错误的报告。


我们先把这块知识归成四个容易记的学习问题：
1. 方向对不对？ ——目标、计划、错误传播。
2. 之前做了什么？ ——上下文、进度、记录与真实结果。
3. 还能接着做吗？ ——等待、中断、恢复、环境变化。
4. 什么时候算结束？ ——有效进展、预算、完成证据。

# 长任务验收什么

结果有没有完成：功能做全？用户问题是否得到解决？
质量是否ok：结论是否有来源？引用是否有依据？有没有遗漏或者编造？
执行约束：是否遵守了权限、费用、时间的限制？
长任务可靠性：中断是否能继续？ 有无重复操作？是否如实报告未完成部分？

# 长任务常用验收方法

| 做法 | 怎么理解 | 主要解决什么问题 |
|---|---|---|
| **1. 拆阶段，逐项验收** | 把大目标拆成可检查的小目标，每完成一项就验证，再推进下一项 | 一口气做太多、漏项、过早宣布全部完成 |
| **2. 保存结构化进度，做好交接** | 明确记录已完成、待做、失败、证据位置和下一步；换上下文后先读这些记录 | 忘记进度、重复劳动、恢复后重新猜现场 |
| **3. 检查点与持久执行** | 在关键位置保存执行状态；进程退出、等待审批后，能够从已保存位置接续 | 中断后从头再来、长时间等待后无法继续 |
| **4. 执行与验收分开** | 执行者交付结果，由测试程序、评判模型或人按标准检查；未通过就返工 | 自己做、自己说成功，缺少真实检查 |
| **5. 设置预算与停止条件** | 约定最多运行多久、花多少、重试几次，以及何时算无进展、需要人工介入 | 无限循环、反复尝试、一直消耗却没有结果 |

中：
- 前两类是 Anthropic 长任务实验的重要做法：维护明确的功能清单，逐项推进，并留下进度与工作现场。长任务实验
- 第三类更偏执行基础设施。检查点可以支持恢复，但涉及外部写入时，还要防止恢复或重试导致重复操作。持久化与恢复文档
- 第四类也出现在长时间开发实验中：生成结果后，再经过评估与反馈循环。验收者可以是程序，不必另设一个 Agent。执行与评估实验


核心办法是：拆小目标 → 做一点 → 检查一点 → 保存进度 → 接着做 → 最终总验收。

# 长任务知识点

## 1， 重要信息埋没



学到一半有感！长任务的本质！

**任务清单 → 子 agent 逐项执行 → 汇报结果 → 协调器更新进度，继续下一项。**

## 从 Pi 插件理解长任务（2026-10-20）

当前从具体的 `pi-long-task` 插件入手，已串通 `pi_long_task` 执行主线；整个长任务专题尚未系统学完。
以下是固定版本源码阅读的理解，不代表已实际运行插件，也不代表所有长任务系统都这样实现。
具体源码学习笔记见：[Pi 长任务处理](../../../开源项目学习/Pi%20Coding%20Agent/长任务处理.md)。

### 计划与调度
- 主 agent 调用工具，通过 `inputText`、`goal` 传递任务信息；规划 session 不自动继承主会话 messages。
- 请求先生成 TODO Markdown，再解析成 `Task[]`，方便程序找出下一个未完成任务。
- TODO Markdown 保存计划和完成进度；更新后再解析、刷新任务数组。
- 协调器默认逐项执行，每次给 worker 分配一个 TODO。

### 子 agent 如何干活
- worker 是通过 Pi SDK 创建的独立 session，不是额外启动一个 Pi CLI 进程。
- 新 session 不继承主会话消息；工作目录仍是同一个项目，健康的 worker session 也可能被复用。
- 任务提示词包含当前 TODO 的完整 section、整体目标、全局要求、历史尝试和结果格式。
- Goal、Status、Verify、Done when 都随 section 发送；Verify 本身是给模型的验证要求。
- worker 使用工具完成工作，最后在 assistant 回复末尾输出固定格式的 `TASK_RESULT` 文本。

### 结果与完成状态
- 插件解析 `status`、`summary` 等文本字段，不是依赖模型 API 的 JSON Schema 强制输出。
- 模型报告 done，还要检查结果完整、没有异常、超时或取消，才得到 `outcome.done = true`。
- 协调器先把执行结果追加到 `TASK_RESULT.md`，成功后再更新 TODO 的 Progress 和 Status 勾选。
- Markdown 的 `[x]` 对应 `done: true`，`[ ]` 对应未完成；执行记录不等于业务正确性的独立证明。
- 未完成任务会再次被选中；达到尝试上限后停止整个长任务，保留未完成勾选、执行记录和已有现场。
- `commit: true` 时，由协调器尝试提交符合条件的子任务改动，worker 本身被要求不要提交。
- 最终 `runCoordinator` 汇总返回 `CoordinatorResult`，工具将 `result.message` 交回主 agent。
- `pi_goal_task` 下一步再学：重点是清单执行后审查整体目标，未达成时安排下一轮，而不只是多传一个 goal。
