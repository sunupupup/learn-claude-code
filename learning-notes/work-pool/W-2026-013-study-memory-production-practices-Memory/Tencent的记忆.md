# TencentDB-Agent-Memory

https://github.com/TencentCloud/TencentDB-Agent-Memory

用户对话 -> L0 -> L1 -> L2 -> L3

| 层 | 这两句话会怎样保存 |
|---|---|
| **L0 会话记录** | 保留两句原话及其上下文，必要时能查到用户确切说了什么。 |
| **L1 原子记忆** | 分成两条。一条是「默认用 pnpm」，一条是「项目甲那次排查临时用 npm」。每条都有自己的类型、优先级和来源消息 ID。 |
| **L2 场景** | 把临时用 npm 的经历和其他相关发现整理到「项目甲依赖排查」。以后回到这个项目，可以先恢复整块背景。 |
| **L3 画像** | 归纳稳定的偏好和工作方式。「默认用 pnpm」可以纳入画像，单次排查用 npm 则继续留在事件和场景里。 |

# 四层记忆

## L0 会话记录

就当成是 jsonl 数据

## L1 原子记忆

从一批L0数据中，提取和记忆相关的内容，抽出来的数据也是jsonl数据，类似于
也在sqlite里面

```json
{
  "id": "mem_001",
  "content": "用户要求安装依赖时默认使用 pnpm。如果项目另有约定，按项目约定执行。",
  "type": "instruction",
  "scene_name": "依赖管理",
  "priority": 90,
  "source_message_ids": ["msg_101", "msg_102"]
}
```

| 层 | JSONL | SQLite |
|---|---|---|
| **L0 会话消息** | `conversations/YYYY-MM-DD.jsonl`，一行一条采集到的消息 | `l0_conversations` |
| **L1 原子记忆** | `records/YYYY-MM-DD.jsonl`，一行一条提炼后的记忆 | `l1_records` |

## L2 场景

L2 就是把多条 L1 记忆整理成一份可持续更新的「场景 Markdown」。这边有 Markdown 了

L1更多的是保存一份事实
L2把用户或团队过去积累的几条记忆，整理成「遇到这个场景，可以怎么做」的一份指南。

其实L2的宗旨还是，汇总散落的记忆，合并成一个更加综合的记忆

一个实际的例子

加入数据库有三条L1数据
然后整理成了L2的Markdown数据

- 用户默认用 pnpm，项目另有约定时按项目来。
- 项目甲的 CI 用 Node 22。
- 上次排查发现，本地 Node 版本与 CI 不一致，切到 Node 22 后安装成功。

```yaml
-----META-START-----
created: 2026-11-12T10:00:00+08:00
updated: 2026-11-12T10:00:00+08:00
summary: 项目甲的依赖安装约定，以及遇到环境不一致时的排查步骤。
heat: 1
-----META-END-----

## 适用条件
在项目甲安装依赖，或者排查本地安装与 CI 表现不一致。

## 核心 SOP
1. 先检查项目声明的包管理器。项目没有约定时用 pnpm。
2. 安装失败时，先对比本地和 CI 的 Node 版本。
3. 发现版本不一致时，先切到 CI 使用的版本，再重试。

## 关键事实依据
上次项目甲的安装问题在切到 Node 22 后消失。
```

如何写出呢？ 上次游标 + 场景去重 + 更新场景文件

用上次处理进度（游标）从数据库读出新增或更新的 L1，再把这批记忆和已有场景的文件名、摘要交给 LLM。LLM 找到相关场景后，可以打开原文更新。确实是新主题时才创建文件，重叠的场景也可以合并。最后由程序同步场景索引。

## L3 画像

L3 是从多份 L2 场景里提炼出来的稳定画像或工作原则

只把能跨场景复用的原则、流程和判断方法写进 L3

比如，有项目A和项目B的两个L2记忆
| 层 | 记录 |
|---|---|
| **L2：项目甲依赖排查** | 本地安装失败时，先比对本地与 CI 的 Node 版本。这个项目的 CI 用 Node 22。 |
| **L2：项目乙构建排查** | 构建结果不一致时，先比对本地与 CI 的构建工具版本。 |
| **L3：可跨项目使用的原则** | 遇到本地和 CI 表现不一致，先核对运行环境和工具版本，再修改项目配置。 |

# 写记忆

腾讯的写记忆分两步：每轮结束先存 L0 对话，后台再决定要不要写 L1

每轮对话结束之后，会通知一下记忆管理器

写L1，后台的记忆管理器，刷一遍最新的L0数据

把 L1 提取放到后台后，前端可以先收到回答，无需等记忆提取完成

后台记忆管理器异步调度 L1 → L2 → L3。主流程每轮结束后保存 L0、通知管理器，就可以继续服务用户。后台再从 L0 提取原子记忆，用变化的 L1 更新场景，最后用变化的 L2 更新画像。

腾讯这套接入可以不给主 Agent 提供 write_memory 工具 ！！！

不过确实有个边界问题

用户说「把前面那个也记下来」，如果原话已经落在游标之前，后台提取器可能只看到保存请求，看不到要保存的内容。结果可能是漏记，也可能是猜错对象。

这是个真实的边界问题。「记住前面那个」只表达了保存意图。如果被指代的内容没进入提取器的上下文，而提取器也不能回查历史，它就可能漏记或记错。
