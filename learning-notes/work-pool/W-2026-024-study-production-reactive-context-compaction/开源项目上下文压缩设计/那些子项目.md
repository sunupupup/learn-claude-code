## 统一观察框架

每个项目沿同一条链路找证据；没有相关实现时明确记为“未发现/无法核验”，不推断其不存在或存在：

1. 上下文预算如何估算，哪些错误被识别为真实超限？
2. Proactive、阈值自动、手动和 API 错误后 Reactive 分别在哪里触发？
3. 压缩怎样处理 System Prompt、用户消息、assistant 消息及一条或多条 Tool Call/Result？
4. 切点或消息重建如何维持调用 ID、顺序和协议合法性？
5. 任务目标、进度、证据、权限版本与副作用凭证保存在哪里？
6. Transcript、Checkpoint 和原始 Artifact 有什么区别，如何取回？
7. 摘要失败、再次超限、进程中断、取消或权限改变时怎样停止/恢复？
8. 哪些 Trace、指标和测试能证明恢复正确？

## 调研顺序

- 先做六个项目的文档入口初筛；Pi 必须进入正式学习。
- 主样本先选 OpenClaw，深读对照先选 Pi 与 OpenHands SDK；固定版本后追完整调用链。Codex CLI、Hermes Agent 与 CodeWhale 按发现的独特机制做目标明确的补充，不要求全量通读。
- 若固定版本源码显示预设样本不覆盖真实 API 超限恢复，记录选择理由后再从候选中替换；不把普通摘要压缩写成 Reactive Compact。
- 不默认克隆、安装或运行第三方项目；源码需读时浅克隆到仓库外的 source-reading/，本仓库只保留笔记与必要证据。
- 每份项目页区分 documented、source-verified、observed-runtime 与 production-proven；产品主张和推论单独标记。

## 与相邻主题的边界

- s08 解释教学版压缩流水线；本任务聚焦 API 真正超限后的生产级恢复契约。
- C-2026-012 维护单个 Tool Result 的压缩、外置、幂等和业务副作用安全；本组只记录整个消息上下文恢复所需的交界。
- W-2026-032 研究 Context 组装与 Provider Prompt Cache；前缀缓存行为不能代替消息压缩或恢复证据。
