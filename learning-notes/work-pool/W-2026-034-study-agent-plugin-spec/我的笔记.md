# Codex Plugin

https://learn.chatgpt.com/docs/plugins?surface=app

一个插件可以包含一个或多个这样的组成部分：

1. Skills 技能
针对特定类型工作的可重复使用的指令。ChatGPT 和 Codex 可以在需要时加载这些指令，从而确保它们能够按照正确的步骤来执行任务，并使用合适的参考资料或辅助脚本来完成工作。

2. MCP servers MCP 服务器
这类服务将 ChatGPT 和 Codex 与 GitHub、Slack、Google Drive 等系统中的各种工具和信息连接起来。它们负责定义各种工具、处理身份验证、返回结构化数据，以及与外部系统进行交互。此外，这些服务器还可以根据需要包含自定义的用户界面。

3. Browser extensions 浏览器扩展
插件在其正常运行过程中所必需的、由浏览器提供的功能。

4. Hooks 钩子
这些是在 Codex 运行时中，在预先设定的生命周期节点上执行的命令。在由云平台管理的 ChatGPT Work 环境中，不支持插件钩子功能。而 Synced Work 则仅支持在 Agent Security 中配置的、由管理员定义的 MCP 钩子。请参阅“工作线程同步兼容性”相关内容。钩子脚本必须存在于执行环境中；仅在网页上安装插件并不能使这些脚本生效。企业管理员可以通过移动设备管理功能来部署所需的脚本。在运行之前，请务必仔细审查并确认这些插件钩子的可靠性。有关设置和管理钩子的详细信息，请参阅相关文档。

# 上下文工程相关的 Plugin

上下文工程（Context Engineering）：组织模型每次处理任务时能看到的信息，包括指令、工具说明、历史消息、检索资料和工具结果。

## Agent Skills for Context Engineering：上下文工程技能合集

这个项目把上下文工程的方法整理成多个 Skill（可按需加载的工作指令），涵盖上下文基础、退化、压缩、优化、记忆系统和工具设计等主题。适合学习这些方法，也可以让 Agent 在相关任务中参考对应流程。

按项目 README 的设计，先提供 Skill 名称和简介，遇到相关任务再加载详细内容；安装整套合集不等于每次都把全部正文放进上下文。可以先看 `context-fundamentals`、`context-degradation`、`context-compression`。

## Context Mode：减少工具输出占用上下文

这个项目通过 MCP（Model Context Protocol，模型上下文协议）工具和 Hooks（Agent 运行过程中的事件钩子），在工具结果进入模型上下文前进行处理：让程序先筛选、统计大量原始数据，只返回需要的结果；也提供内容索引、检索、会话状态记录和诊断能力。

它偏向实际运行中的上下文管理，可以观察“原始工具输出 → 外部处理或存储 → 按需取回相关信息”这条链路。具体功能取决于客户端支持的工具和钩子；项目宣传的节省比例属于作者报告，尚未在本地验证。

## Context Mode 这个库，我自己的理解

首先，Context Mode 是一种 MCP 服务器，提供了很多优质的tool，来代替某些效率低的tool

比如：**Everything else → `ctx_execute` or `ctx_execute_file`.** Any command that reads, queries, fetches, lists, logs, tests, builds, diffs, inspects, or calls an external service. This includes ALL CLIs (gh, aws, kubectl, docker, terraform, wrangler, fly, heroku, gcloud, etc.) — there are thousands and we cannot list them all.

ctx_execute_file 代替某些 bash 操作

比如： “统计这个日志文件里面所有错误的日志 + 最后三条error”
普通bash：读取全文给模型，然后给出结果，取决于文件大小
ctx_execute_file：写一个 js 函数fn， fn(文件名)，只会有fn和fn的计数结果进入到上下文，只有几B大小

他的核心能力在于：“教 Agent 少读全文、多用代码筛选”这一部分。

**但其实看来，这种外置能力，迟早不需要了**
**模型的强化 + harness本身的优化**
一个bash就本身过滤能力就很强了

对，你这个判断有道理，尤其是它“教 Agent 少读全文、多用代码筛选”这一部分。
模型越擅长使用现成工具，就越可能自己完成：
大日志 → 用 Shell 统计、筛选 → 只看关键结果
大文件 → 先搜索定位 → 按需读片段
多个独立操作 → 批量或并行执行


# 面试题：为什么使用plugin、真实项目有啥提高、怎么量化啊

对于某些 context7 plugin来说，其实是有很明显的提升的，因为确确实实提供了外部的工具能力，进行了能力的横向扩展

到那时对于context plugin来说，确实比较玄乎，因为我们没有完整经历过提升效能的测评，也不知道去测试哪些指标

在 Context Mode   的官方文档中倒是提到：https://github.com/mksglu/context-mode/blob/main/BENCHMARK.md

他有个专门的benchmark文档
他对于大量场景下的工具的输出，进行了对比，确实有优化

然后回到我们的问题 

其实我也是看了这个Gemini CLI 而发起的疑惑，她这边定义了很多context的规定，其实已经内置了一些context规则了
https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/prompts/snippets.ts#L198

那么现在 skill 的来源就分成的三层
1. 模型训练：有些skill已经被训到模型内部
2. Harness内置提示词：产品内嵌的预制提示词
3. 额外安装的skill

然后，要不要引入 Context Plugin 的核心问题：它给现有系统带来了多少可验证的增量收益？

至少需要验证这些：减少无关内容 → 降低上下文占用 → 可能降低成本、改善任务表现。

**！！！！**
实际上影响这个插件的原因有很多
- 模型能力
- harness能力
- 已有其他插件、hook的能力
- 任务类型：大量日志、长会话可能更需要这类机制；读几个小文件的任务，可能收益很小。
**！！！！**

所以评估也变得复杂：
在当前模型 + Harness + 已有插件配置下，加入 Context Mode 后，同一批任务的质量、成本和耗时有什么变化？

面试中怎么回答才扎实？
可以沿着 问题 → 机制 → 对照 → 结果 → 边界 讲。
如果还没有实测，可以诚实地这样回答：
我关注这个插件，是因为我们的任务可能存在大量工具输出挤占上下文的问题。它通过外部存储和按需检索减少直接进入模型的内容。作者提供了输出体积缩减的基准，但我们还没有验证真实任务收益，所以目前只能把它作为候选方案。下一步会对比原生 Agent、简单优化规则和插件方案，在任务质量达标的前提下，测总成本、耗时及长任务约束保留情况，再决定是否引入。
