# browser use 提供的能力

| 能力 | Playwright MCP | Chrome DevTools MCP |
|---|---|---|
| 打开或跳转网页 | `browser_navigate` | `navigate_page` |
| 读取页面结构 | `browser_snapshot` | `take_snapshot` |
| 点击元素 | `browser_click` | `click` |
| 输入内容 | `browser_type` | `fill` |
| 截图 | `browser_take_screenshot` | `take_screenshot` |

其实各种Browser Use的能力，本质上都是对CDP的各种能力进行封装

# 两种机制控制浏览器

两种控制机制：

外部程序控制 Chrome：
程序 → WebSocket 等通道 → CDP → Chrome

浏览器扩展控制 Chrome：
扩展 → chrome.debugger API → CDP → Chrome

外部程序的表现形式一般是 MCP 居多，会对某些内容进行封装

# Codex的浏览器插件

| 能力 | 看到的调用 |
|---|---|
| 连接某个标签页或调试目标 | `chrome.debugger.attach(...)` |
| 向浏览器发送 CDP 命令 | `chrome.debugger.sendCommand(...)` |
| 在网页中执行 JavaScript、读取信息 | `Runtime.evaluate` |
| 截取页面画面 | `Page.captureScreenshot` |
| 输入文字、发送按键 | `Input.insertText`、`Input.dispatchKeyEvent` |
| 与本地程序建立通信 | `chrome.runtime.connectNative(...)` |

浏览器扩展可以使用 CDP

Chrome 专门提供了 chrome.debugger API，让扩展发送 CDP 命令。

它需要在 manifest.json 中声明： `"permissions": ["debugger"]`


```js
// 连接目标标签页的调试接口。
const target = { tabId };
await chrome.debugger.attach(target, "1.3");

// 发送 CDP 命令，让网页执行 JavaScript 并返回标题。
const result = await chrome.debugger.sendCommand(
  target,
  "Runtime.evaluate",
  { expression: "document.title", returnByValue: true }
);
```



# Browser Use MCP

就单纯快照这块的作用，agent想找到可操作的元素 （一份好的页面表示，不仅要让模型“看懂”，还要让模型选中的对象能被执行器准确找到。）
1. 去噪
2. 补充语义
3. 保留关键元素引用

他们不仅仅是封装了一下 CDP， 加个工具名

更重要的是，网页加工成“模型能理解、能据此操作”

就比如一个页面，
```
商品搜索
[请输入关键词        ] [搜索]
共找到 20 件商品
```

但是他可以有很多种表现形式：

| 表示方式 | 可能返回什么 | 主要用途 |
|---|---|---|
| **DOM 结构** | 标签、属性、文本、父子节点 | 检查网页实现、精确查询元素 |
| **可访问性结构** | 标题、输入框、按钮，以及名称和状态 | 理解“这是什么控件、有什么含义” |
| **交互元素列表** | 可点击、可输入、可选择的候选元素 | 缩小下一步动作的选择范围 |
| **文本提取结果** | “商品搜索；共找到20件商品” | 阅读、总结、抽取内容 |
| **布局信息** | 元素坐标、大小、是否在视口内 | 定位、滚动、结合截图操作 |
| **截图** | 实际显示的像素画面 | 理解视觉布局、图片和自绘界面 |

**取什么**：DOM / 语义 / 文本 / 布局 / 图像

**保留谁**：所有节点 / 有意义的节点 / 交互候选
**怎样返回**：树 / 列表 / 简短文本 / 图片


# 浏览器沙箱

其实就是指定一个空的 用户数据目录 
进行数据隔离

然后使用 remote debug 服务来进行控制

使用 这个 remote debug服务的 ws接口，来进行控制

感觉理解为 DSL 、 RPC 都合适
这两个类比可以同时成立，因为它们关注的角度不同：
- 像 DSL：它有一套浏览器领域的专用词汇，例如 Page.reload、Runtime.evaluate，以及对应的参数和语义。
- 像 RPC（Remote Procedure Call，远程过程调用）：外部程序发送“方法名 + 参数”，让 Chrome 执行，再拿回结果。

请求体格式
```json
{
  "id": "递增的id",
  "method": "方法名",
  "params": {
     //方法的参数
  }
}
```

# 远程浏览器

两阶段
1. 准备浏览器：连接远程环境，启动 Chrome、指定数据目录、开启调试入口；拿到外部可达的连接地址。
2. 控制浏览器：连接该入口的 WebSocket，发送 CDP 命令、接收响应和事件。


控制浏览器，还是得看沙箱给提供了什么能力
1. 提供命令行， 在沙箱内运行 Playwright 、ws连接等脚本，控制 Chrome
2. CDP连接地址，只是使用 ws 发送 CDP 命令


主要有两种方式

| | E2B／E2B Desktop | Browserless |
|---|---|---|
| 核心对象 | 一个可执行程序的沙箱环境 | 一个远程浏览器会话 |
| 主要能力 | 执行命令、管理文件、安装和运行程序；Desktop 增加桌面交互 | 连接浏览器、网页自动化、截图、会话与登录状态管理 |
| 浏览器的位置 | 沙箱里运行的一个应用 | 服务主要管理的对象 |
| 适合观察的问题 | 浏览器、文件、脚本怎样协同完成任务 | 浏览器怎样启动、连接、重连和回收 |

# Browserless

https://github.com/browserless/browserless

对，就是把浏览器的创建、启动、连接、保留、销毁这些管理流程封装了一遍

之前本地的流程
创建数据目录 → 启动 Chrome → 开启调试端口 → 找到 WebSocket 地址 → 发送 CDP 命令

Browserless的流程
你的程序连接 Browserless，携带认证 Token
  → 服务提供一个远程浏览器
  → 你通过 CDP／Playwright／Puppeteer 操作
  → 服务按会话规则管理保留和回收

Browserless 其实就是把 Chrome 的启动、CDP 连接、会话保留和回收这些，统一封装成一个服务

## CDP如何多账号隔离

```bash
# 创建全新的数据目录，并转换为 Chrome 使用的 Windows 路径。
experiment_profile="$(mktemp -d -t cdp-learning-XXXXXXXX)"
experiment_profile_win="$(cygpath -w "$experiment_profile")"

# 启动独立 Chrome，在本机开放 CDP 调试端口。
"/c/Program Files/Google/Chrome/Application/chrome.exe" \
  "--user-data-dir=$experiment_profile_win" \
  --remote-debugging-address=127.0.0.1 \
  --remote-debugging-port=9223 \
  --no-first-run \
  --no-default-browser-check \
  about:blank &

printf '实验目录：%s\n' "$experiment_profile_win"
```

这个就是在创建一个独立的浏览器环境了
分这么几步骤
1. chrome.exe 启动
2. 定义临时的用户数据目录：ser-data-dir
3. 定义远程控制的服务，这边是在  127.0.0.1:9223  启动了一个进程来控制

上面执行完之后，就能弹出来一个全新的chrome页面


这个 9223 进程，既能 http 接口暴露某些方法，又能 ws 的方式发送 CDP 命令
| 部分 | 作用 | 你已经用过的例子 |
|---|---|---|
| **HTTP 接口** | 查询浏览器信息、发现可调试的页面和连接地址 | `/json/version`、`/json/list` |
| **WebSocket 连接** | 持续发送 CDP 命令、接收响应及事件 | `/devtools/page/某个ID` |

`http://127.0.0.1:9222/json/version`
可以查看这个进程的一些基本信息，版本号、webSocketDebuggerUrl 等
webSocketDebuggerUrl 很重要 ，ws://127.0.0.1:9222/devtools/browser/fd83784e-e79a-47bc-953b-133997c441d1
能Call这个接口发送Json数据来控制浏览器

## 反扒、风控、安全沙箱经验

反爬：识别验证码、限流、访问拒绝；合理降低频率，优先使用网站允许的 API，遇到验证时交给用户处理。
风控：保持账号与会话对应，避免重复提交；执行前确认当前账号，触发验证时暂停。
安全沙箱：不让网页内容随意指挥 Agent；限制下载文件、账号权限和高影响操作的执行范围。

这边可能涉及到
1. 限定访问特定的页面
2. 对页面只读，不能进行任何删除、付款、发布等操作，必要时需要用户确认
3. 文件和系统隔离：限制下载目录
4. 生命周期管理：结束后释放浏览器、清理数据

可能需要CDP和Harness多方控制

| 控制位置 | 可以做什么 | 主要边界 |
|---|---|---|
| **Chrome 启动配置** | 指定独立数据目录、调试入口等 | 不能完整表达业务授权 |
| **工具／CDP 网关** | 检查调用者、目标页面、命令和参数，允许或拒绝操作 | 只检查命令名通常不够 |
| **Harness** | 判断任务是否授权删除、付款、发布等动作 | 需要理解业务含义 |
| **操作系统／网络层** | 限制文件访问、网络出口、进程权限 | 提供更强制的执行边界 |
