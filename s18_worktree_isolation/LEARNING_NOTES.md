## 1. 术语速查

| branch / feature branch | Git 分支 / 功能分支：记录开发历史的分支 | 分支与磁盘目录是不同对象；本章创建工作区时也创建分支 |

## 2. 学习动机与前置理解校准

s17 已引入任务看板和队友自动认领，但不同任务仍可能修改同一个 config.py。s18 在执行层增加独立目录，并通过任务字段关联目录。

我的原始疑问：“同一个任务怎么还开多个 worktree？只有不相干的功能才有意义吧？”

🟡 已纠正：判断依据是执行是否需要独立，以及结果如何接收，不是功能是否完全无关。同一大目标可以拆成独立子任务，也可以在不同目录尝试不同实现后择优。同文件强耦合时可以顺序执行或指定单写者，但不能据此断言同文件永远不能并行。

当前教学 Task 只有一个 owner 字段，是归属模型；claim 的读、检查、写没有锁，因此仍有并发认领竞态。目录隔离不能修复这一竞态。

| 机制 | 负责什么 | 不自动保证什么 |
|---|---|---|
| s06 上下文隔离 | 减少子任务中间消息对主对话的干扰 | 文件系统隔离 |
| s17 看板与认领 | 目标、依赖、归属与状态 | 文件写入互不覆盖、完成证据 |
| s18 工作区与 cwd | 将工具执行导向独立目录 | 合并无冲突、业务正确、权限隔离 |

## 3. 创建、绑定与认领：谁写状态，谁读取

我的原话：“原来 worktree 在创建的时候就能绑定 task id，我以为是 claim 后发现别人改这个文件才切。”

🟢 代码与注释理解已确认：Lead 可以提前调用 create_worktree(name, task_id)。当前没有“发现文件冲突后自动隔离”的检测流程。

实际创建顺序：名称校验 → Git 创建目录与 wt/{name} 分支（基于 HEAD）→ 可选任务绑定 → 记录 create 事件 → 返回工具结果。

bind_task_to_worktree 只写 task.worktree 并保存。对于原本 pending 的任务，绑定后仍为 pending；函数没有把其他状态强行改为 pending。一个字段记录一个目录标识，但代码未实施全局一对一唯一性检查。

显式认领的关键调用链：

```text
模型调用队友的 claim_task 工具
→ sub_handlers 分发到 _run_claim_task
→ 全局 claim_task 检查状态、owner、依赖
→ 保存 owner 与 in_progress
→ 包装函数读取 task.worktree，更新 wt_ctx
→ 后续 bash/read/write 包装函数读取 _wt_cwd()
→ 实际工具使用指定目录
```

我的原话：“难怪看不到 cd，run_bash 会默认使用这个 cwd。”

🟢 对显式认领路径成立。wt_ctx 是每个队友在线程内保存的上下文；程序传入执行目录，无需模型另发 cd，也不修改全局进程 cwd。模型在 Bash 中主动切目录不会自动更新这个字典或其他文件工具的默认目录。

### 自动认领路径的实际缺口

| 入口 | 更新 Task | 更新 wt_ctx | 向模型提供的信息 |
|---|---|---|---|
| _run_claim_task 显式工具调用 | 成功后更新 | 成功后更新或清空 | 返回认领结果；list_tasks 可显示绑定名称 |
| idle_poll 自动认领 | 成功后更新 | 没有更新 | 消息包含 Work directory |

🟢 静态代码确认：idle_poll 直接调用全局 claim_task，绕过包装函数；外层调用它之后也未同步 wt_ctx。README 的自动切目录描述不能无条件覆盖这条路径。

🔴 待运行验收：模型会如何使用提示中的路径，最终写入落在哪里。本轮未执行 Demo，也未修复此缺口。

记录当前行为的伪代码（用于复习，尚不是我独立完成的验收答案）：

```text
显式认领：
  result ← 认领任务
  如果成功：
    wt_ctx ← 任务绑定目录；没有绑定则为 None
  返回 result

自动认领：
  扫描可认领任务，调用全局认领函数
  如果成功：将任务与目录描述加入 messages
  返回 work；当前没有更新 wt_ctx

文件工具：
  base ← wt_ctx 指定目录，否则 WORKDIR
  按 base 解析相对路径或启动命令
```

_run_complete_task 在 complete_task 返回后清空 wt_ctx；它没有先判定返回内容是否代表成功。完成状态、执行目录和工作区保留是分别变化的状态。

## 4. keep、remove 与真正的运行时约束

我的原始问题：“不调用 remove 不就行了？keep 是不是往 Lead 里面加个 message？最终是不是只留一个？”

🟢 代码确认：keep 做名称校验、写 keep 事件、打印并返回结果。它不设置防删标记，不限制保留数量，也不检查对应目录是否真实存在。返回值由 Agent Loop 包成 Tool Result 后进入模型上下文。

专业表述：keep 记录并反馈本次保留供审查的决定；它不是防删除锁，也没有保证模型之后不会请求删除。

### 已完成的小题

题设：工作区名称合法且存在，先 keep，再 remove(discard_changes=False)，改动检查返回 (0, 0)。是否因先前 keep 而拒绝？

我的回答：“不会拒绝。keep 没有防删标记，remove 也没有检查，主要是 model 层弱防护。”

🟢 答案与关键代码依据正确。措辞已纠正并确认理解：模型收到的是保留决定的反馈，不宜称为弱防护；Harness 有删除前的改动检查，只是没有基于 keep 状态的防删约束。通过检查后程序尝试删除，最终成功仍取决于 Git 结果。

### discard_changes 的准确含义

我的原话：“discard_changes 使这边多个 --force。”

🟡 已纠正：实际删除语句始终包含 --force；参数只控制是否跳过应用层检查。

| 参数 | 改动检查 | 到达删除语句时 |
|---|---|---|
| False | 检查；负值或发现改动时返回 | 仍带 --force |
| True | 跳过计数检查 | 带 --force |

名称与目录存在性检查不因 True 而跳过。remove 成功删除目录后还会尝试删除分支；它不自动完成任务，也没有消费 keep 日志。

我的原话：“files < 0 表示内部报错。”专业表述：它表示计数函数捕获了 Python 异常；函数未检查 Git 退出码，不能覆盖所有命令失败。

## 6. 隔离之后怎样集成

保留我的设计思路：队友各自完成 → Lead 检查结果 → 执行合并。这是合理的集成职责划分；check_temp_worktree_task 与 merge_worktree 是个人设计草图，不是本章已有 API。

我最初把合并想成“两次 read_file 加一次 write_file”。已校准：读两份最终内容再生成一份文件属于内容合成；Git 三方合并会结合共同祖先与两边版本。LLM 可辅助理解和处理冲突，但其输出仍需审查、差异检查和测试，不能因改动位置不重叠就认定可靠。

合并是正常集成流程，不能统称为兜底；冲突处理是额外步骤。同文件不必然有文本冲突，不同文件也可能有语义冲突：例如一边改函数签名，另一边仍按旧签名调用。文本合并成功不证明业务正确。

讨论过的集成顺序：保留可审查产物与提交 → 检查各任务结果 → 合并或择优 → 验证组合后的行为 → 决定保留或清理。任务 completed、分支已提交、合并成功、测试通过是不同证据。

要将产物接回主线，应明确由谁负责集成；可以是 Lead、父 Agent、人工或流程，不强制要求一个名叫 merge task 的任务。临时实验若最终丢弃，可以不合并。worktree 数量也不能简单限定为 teammate 数量：已完成任务的工作区可能继续保留。

## 8. 已讨论的实现边界与失败场景

以下为已讨论的源码观察，未在本轮修复，也未进行完整运行复现。

- 自动认领没有更新 wt_ctx：任务消息中写了目录，不等于文件工具使用该目录。

- keep 仅记录决定；多个工作区都可保留，之后仍可请求删除。
- 任务认领没有原子读改写；complete_task 不检查测试与真实产物。
- 工具 cwd 与 safe_path 提供目录选择及文件路径检查，但通用 Bash 不受同样的文件路径函数约束。不能把本章称为完整安全沙箱。

### 例子 1：目录提示不等于执行目录

题设：Task A 已绑定 auth，Alice 的 wt_ctx 初始为 None。比较显式工具认领与 idle_poll 自动认领成功后，write_file("config.py", ...) 的默认写入位置。

我的初答（保留原意）：

```text
显式：Alice → claim task A → write("config.py", wt/auth)
自动：Alice → idle_poll → claim task A
      → add context "work dir is wt/auth"
      → 默认 write("wt/auth/config.py")
```

初答判断：显式路径的核心理解正确；自动路径把“模型收到目录文字”误当成“工具参数或默认目录自动改变”。另一个术语纠正：wt/auth 是分支名，目录是 WORKDIR/.worktrees/auth。

校准后的实际调用链见第 3 节。固定题设中，显式认领包装函数更新 wt_ctx，最终默认写入 WORKDIR/.worktrees/auth/config.py；自动认领只更新任务状态和 messages，wt_ctx 仍为 None，最终默认写入 WORKDIR/config.py。模型可能自行补路径，但题设固定传入 config.py，不能假设这一步发生。

专业表述：messages 影响模型选择，工具参数表达模型选择，wt_ctx 影响工具执行；三者需要程序显式连接，文字提示不会自动变为运行时配置。

我的进一步判断：“那这个自动领取任务，不是废了么，在当下这个 demo？”

校准：认领状态仍有效，但“自动认领后自动使用绑定目录”未接完整。再次调用 claim_task 也不能补救：任务已为 in_progress，再次认领被拒绝，包装函数不会进入成功后的目录更新分支。

我的修复思路：“idle_poll 捞取任务，设置 poll_task_wt；下次 loop 先设置 wt_ctx。”

🟢 方向可行：自动认领成功后返回任务与目录信息，由当前队友的外层循环在下一轮执行工具前更新 wt_ctx["path"]。这是讨论中的设计草图，未修改代码、未测试。

已补充的边界：

- 只有 claim 成功后才同步目录，扫描到候选任务还不够。
- 新领任务无绑定目录时，将 path 设为 None，避免沿用旧任务目录。
- 若仅收到普通消息、没有领取新任务，应保留原执行目录。
- 返回结果应区分“没有新任务”与“新任务没有绑定目录”；只给一个 None 不足以表达两者。
- 目录状态属于当前队友，不使用所有队友共用的全局 poll_task_wt。

验收记录：初答部分正确，经讨论识别到实现缺口并提出修复方案；“仅收到普通消息时如何处理目录”的追问由教练补充了规则，用户未单独作答，不能记为独立验收通过。

### 例子 2：无冲突合并不等于功能完成

题设：Alice/Bob 各自任务都为 completed，独立工作区的修改合并时没有文本冲突。能直接宣布总任务完成并清理吗？

我的回答：“不能。两者可能在同一个文件里面加了同一个名字的方法。”

我提出的流程：

```text
Lead → check task status → merge worktree
     → run bash: npm run build、npm run test
       → failed: create task，loop
       → success: done
```

🟢 独立回答通过：能区分文本合并和功能正确，并提出“合并 → 验证 → 修复 → 再验证”的闭环。同名方法若加在不同位置，可能没有文本冲突，却出现重复定义、覆盖或编译错误；结果取决于语言和作用域。

专业表述：子任务状态和无冲突合并是进入集成验收的依据。总任务完成需要对合并后的版本执行构建、测试，并核对需求验收条件；失败则进入有边界的修复与重新验证流程。

教练补充的条件（已讨论，不冒充用户独立回答）：

- 构建和测试必须针对合并后的目录与版本；各分支分别通过不能代替组合验证。
- 测试通过还要检查是否覆盖实际需求。例如只测正常登录，不能证明“未登录用户不能访问订单”。这属于语义正确性：组合后的业务行为是否满足要求。
- 失败后先区分代码、环境或依赖问题；不能无限创建修复任务循环，持续失败应反馈阻塞。
- 完成与清理分开：所需提交、产物和验证证据已有去处，且没有遗漏的未提交改动，再清理工作区。
- npm run build / npm run test 是我举的项目命令示例，本次没有运行，也没有确认本仓库提供这些脚本。
