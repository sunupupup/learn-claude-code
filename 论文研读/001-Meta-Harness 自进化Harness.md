# Meta-Harness: End-to-End Optimization of Model Harnesses

## 论文地址

[论文原文（arXiv:2603.28052）](https://arxiv.org/abs/2603.28052)

## 核心论点

固定模型的表现也取决于 Harness（模型外围的提示词、工具和上下文管理等运行程序），其设计可以自动优化。Meta-Harness 让编码 Agent 按需读取文件系统中历次候选的源码、成绩和执行轨迹，提出并实现新的 Harness，再由外部评测记录结果、继续迭代，寻找更好的实现。

## 我的笔记

它的基本思路是：固定任务模型，让一个提出者 Agent 阅读 Harness 源码、历史成绩和执行轨迹，再生成新版本。
Harness 版本
    ↓
运行任务，保存成绩和轨迹
    ↓
提出者查看源码与历史实验
    ↓
修改 Harness 程序
    ↓
评测新版本，继续搜索

它特别强调：过去的实验信息保存在文件系统中，提出者可以访问，而不是仅收到一句“成绩不好，再改改”。官方项目包含文本分类和终端任务的参考实验，示例使用 Claude Code 作为提出者。原论文、官方代码
**你能从它学到：**一个“自动改 Harness”的系统，怎样把源码、实验记录、提出者和评测器接起来。

### “搜索 Harness”到底是什么意思？

他这边提到的**搜索** 其实就是 反复生成不同的Harness实现，运行比较，寻找表现更好的方案

假设你在手动优化一个 Agent：
方案 A：工具结果全部保留
方案 B：长结果截断，但允许重新读取
方案 C：长结果保存为文件，上下文只放摘要和路径

你不知道哪个最好，于是实现、测试、比较，再根据失败继续修改。这就在搜索不同的设计方案。
Meta-Harness 将其中“读日志、诊断、提出并实现新方案”的工作交给编码 Agent。

因此，这样一个过程，可以称之为搜索：

已有实现和实验结果
    ↓
提出一个值得尝试的新实现
    ↓
运行并测量
    ↓
把新证据加入历史
    ↓
继续寻找

这种搜索，不会保证找到全局最优的方案，通常会运行到预设的迭代预算就停止

### 执行任务、改代码、验证者，分别是谁

在终端任务参考实现中，可以拆成四个角色：

| 角色 | 工程对象 | 职责 |
|---|---|---|
| 任务 Agent | 固定模型 + 候选 `AgentHarness` | 在任务环境中调用工具、完成任务 |
| 修改提出者 | Claude Code 编码 Agent | 查看历史、分析轨迹、写新的 Harness |
| 评测运行器 | Harbor，由评测脚本调用 | 加载候选、启动环境、组织任务运行 |
| 任务验证器 | Benchmark 的验证程序 | 检查任务结果，产生 reward |

### 一轮实际的运行

① 先跑基线。
系统运行已有 Harness，得到初始成绩和轨迹。没有基线，就不知道后面的修改有没有改善。

② 启动提出者。
外层脚本把历史结果和日志位置交给 Claude Code。它读取候选代码、成功与失败轨迹，决定要验证什么假设。

③ 写一个新的候选。
当前示例要求生成新的 agents/<name>.py，类名为 AgentHarness，保持与评测运行器兼容。已有候选文件不应被覆盖；可复用的代码复制到新文件中。

④ 提交待评测清单。
提出者写出 pending_eval.json，告诉外层程序：

{
  "candidates": [{
    "name": "candidate_a",
    "import_path": "agents.candidate_a:AgentHarness",
    "hypothesis": "这次修改想验证的假设",
    "changes": "具体改了什么"
  }]
}

这个文件是提出者与评测程序之间的交接接口。完整 Benchmark 由外层运行，提出者不负责给自己评分。当前 Skill 还组织了分析与实现两个子 Agent 阶段。

⑤ 检查、评测、记录。

外层程序先做导入和类型检查，再做单任务冒烟检查，通过后才运行完整评测。随后解析 reward，更新成绩记录，进入下一轮。外层循环源码

冒烟检查只能说明候选能基本运行，不能证明它比旧版本更好。

### 历史和版本怎么保存

论文的关键设计是：把历史作为可查询的文件系统保存。 每个已评测候选都有源码、成绩和执行轨迹，提出者按需读取，而不是把所有历史一次塞进上下文

| 位置 | 保存什么 |
|---|---|
| `agents/<name>.py` | 有名字的候选 Harness 实现 |
| `logs/<run_name>/evolution_summary.jsonl` | 每个候选的假设、改动、成绩及运行指标 |
| `logs/<run_name>/frontier_val.json` | 当前记录中的各任务最佳候选、总体最佳候选 |
| `logs/<run_name>/claude_sessions/` | 提出者交互日志 |
| `jobs/<run_name>/` | Benchmark 运行产物与逐次结果 |

这些路径属于 Meta-Harness 官方项目内部。源码中的存储与更新逻辑

版本主要通过不同候选文件名、导入路径和对应实验记录关联。不能把 RRSI 的“候选 worktree + 接受后推进 Git commit”机制套过来：这个参考循环没有采用同样的 Git 版本流转。

失败候选仍有学习价值。下一轮可以查看它为什么失败，也可以结合多个历史实现生成新候选。

### “最好版本”怎样决定？

这里有一个值得区分的实现差异：
- **论文一般设计：**多目标时维护 Pareto frontier，即保留“在效果、成本之间各有优势，未被另一方案全面超过”的候选。
- 当前终端参考实现：frontier_val.json 主要按通过率记录各任务最佳和总体最佳，运行指标另外保存。论文 §3、参考代码
例如，一个方案更准但更贵，另一个稍低但便宜很多，多目标搜索可能同时保留它们。并不是任何场景都只剩一个冠军。
对你理解“自进化”最关键的是：变化持久化在 Harness 程序和实验历史里；模型参数保持固定，下一轮修改会受到已有证据影响。 这就是它自动搜索和持续改进的工程基础。

# 重点内容

搜集了什么数据 +  cc去迭代harness的一套机制 + 如何评测

Meta-Harness 的工程主线：

运行候选 Harness，保存数据
    ↓
Claude Code 按需查看历史、诊断问题
    ↓
编写新的 Harness 候选
    ↓
外部评测程序运行候选、产生分数
    ↓
保存新证据，进入下一轮

| 重点 | 具体需要看什么 |
|---|---|
| **收集了什么数据** | 候选源码、总体和逐任务成绩、执行轨迹；参考实现还记录 Token、成本、轮数等 |
| **CC 怎样迭代 Harness** | 查看历史代码与成功/失败轨迹，提出修改假设，写新候选，提交给评测程序 |
| **如何评测** | 加载候选、检查能否运行、执行任务，由任务验证器评分，再比较结果 |
