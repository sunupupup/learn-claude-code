# Meta-Harness: End-to-End Optimization of Model Harnesses

## 论文地址

[论文原文（arXiv:2603.28052）](https://arxiv.org/abs/2603.28052)

## 核心论点

固定模型的表现也取决于 Harness（模型外围的提示词、工具和上下文管理等运行程序），其设计可以自动优化。Meta-Harness 让编码 Agent 按需读取文件系统中历次候选的源码、成绩和执行轨迹，提出并实现新的 Harness，再由外部评测记录结果、继续迭代，寻找更好的实现。

## 我的笔记

它的基本思路是：固定任务模型，让一个提出者 Agent 阅读 Harness 源码、历史成绩和执行轨迹，再生成新版本。
Harness 版本
    ↓
运行任务，保存成绩和轨迹
    ↓
提出者查看源码与历史实验
    ↓
修改 Harness 程序
    ↓
评测新版本，继续搜索

它特别强调：过去的实验信息保存在文件系统中，提出者可以访问，而不是仅收到一句“成绩不好，再改改”。官方项目包含文本分类和终端任务的参考实验，示例使用 Claude Code 作为提出者。原论文、官方代码
**你能从它学到：**一个“自动改 Harness”的系统，怎样把源码、实验记录、提出者和评测器接起来。

### “搜索 Harness”到底是什么意思？

他这边提到的**搜索** 其实就是 反复生成不同的Harness实现，运行比较，寻找表现更好的方案

假设你在手动优化一个 Agent：
方案 A：工具结果全部保留
方案 B：长结果截断，但允许重新读取
方案 C：长结果保存为文件，上下文只放摘要和路径

你不知道哪个最好，于是实现、测试、比较，再根据失败继续修改。这就在搜索不同的设计方案。
Meta-Harness 将其中“读日志、诊断、提出并实现新方案”的工作交给编码 Agent。

因此，这样一个过程，可以称之为搜索：

已有实现和实验结果
    ↓
提出一个值得尝试的新实现
    ↓
运行并测量
    ↓
把新证据加入历史
    ↓
继续寻找

这种搜索，不会保证找到全局最优的方案，通常会运行到预设的迭代预算就停止

### 执行任务、改代码、验证者，分别是谁

在终端任务参考实现中，可以拆成四个角色：

| 角色 | 工程对象 | 职责 |
|---|---|---|
| 任务 Agent | 固定模型 + 候选 `AgentHarness` | 在任务环境中调用工具、完成任务 |
| 修改提出者 | Claude Code 编码 Agent | 查看历史、分析轨迹、写新的 Harness |
| 评测运行器 | Harbor，由评测脚本调用 | 加载候选、启动环境、组织任务运行 |
| 任务验证器 | Benchmark 的验证程序 | 检查任务结果，产生 reward |

### 一轮实际的运行

① 先跑基线。
系统运行已有 Harness，得到初始成绩和轨迹。没有基线，就不知道后面的修改有没有改善。

② 启动提出者。
外层脚本把历史结果和日志位置交给 Claude Code。它读取候选代码、成功与失败轨迹，决定要验证什么假设。

③ 写一个新的候选。
当前示例要求生成新的 agents/<name>.py，类名为 AgentHarness，保持与评测运行器兼容。已有候选文件不应被覆盖；可复用的代码复制到新文件中。

④ 提交待评测清单。
提出者写出 pending_eval.json，告诉外层程序：

{
  "candidates": [{
    "name": "candidate_a",
    "import_path": "agents.candidate_a:AgentHarness",
    "hypothesis": "这次修改想验证的假设",
    "changes": "具体改了什么"
  }]
}

这个文件是提出者与评测程序之间的交接接口。完整 Benchmark 由外层运行，提出者不负责给自己评分。当前 Skill 还组织了分析与实现两个子 Agent 阶段。

⑤ 检查、评测、记录。

外层程序先做导入和类型检查，再做单任务冒烟检查，通过后才运行完整评测。随后解析 reward，更新成绩记录，进入下一轮。外层循环源码

冒烟检查只能说明候选能基本运行，不能证明它比旧版本更好。

### 历史和版本怎么保存

论文的关键设计是：把历史作为可查询的文件系统保存。 每个已评测候选都有源码、成绩和执行轨迹，提出者按需读取，而不是把所有历史一次塞进上下文

| 位置 | 保存什么 |
|---|---|
| `agents/<name>.py` | 有名字的候选 Harness 实现 |
| `logs/<run_name>/evolution_summary.jsonl` | 每个候选的假设、改动、成绩及运行指标 |
| `logs/<run_name>/frontier_val.json` | 当前记录中的各任务最佳候选、总体最佳候选 |
| `logs/<run_name>/claude_sessions/` | 提出者交互日志 |
| `jobs/<run_name>/` | Benchmark 运行产物与逐次结果 |

这些路径属于 Meta-Harness 官方项目内部。源码中的存储与更新逻辑

版本主要通过不同候选文件名、导入路径和对应实验记录关联。不能把 RRSI 的“候选 worktree + 接受后推进 Git commit”机制套过来：这个参考循环没有采用同样的 Git 版本流转。

失败候选仍有学习价值。下一轮可以查看它为什么失败，也可以结合多个历史实现生成新候选。

### “最好版本”怎样决定？

这里有一个值得区分的实现差异：
- **论文一般设计：**多目标时维护 Pareto frontier，即保留“在效果、成本之间各有优势，未被另一方案全面超过”的候选。
- 当前终端参考实现：frontier_val.json 主要按通过率记录各任务最佳和总体最佳，运行指标另外保存。论文 §3、参考代码
例如，一个方案更准但更贵，另一个稍低但便宜很多，多目标搜索可能同时保留它们。并不是任何场景都只剩一个冠军。
对你理解“自进化”最关键的是：变化持久化在 Harness 程序和实验历史里；模型参数保持固定，下一轮修改会受到已有证据影响。 这就是它自动搜索和持续改进的工程基础。

# 重点内容

搜集了什么数据 +  cc去迭代harness的一套机制 + 如何评测

Meta-Harness 的工程主线：

运行候选 Harness，保存数据
    ↓
Claude Code 按需查看历史、诊断问题
    ↓
编写新的 Harness 候选
    ↓
外部评测程序运行候选、产生分数
    ↓
保存新证据，进入下一轮

| 重点 | 具体需要看什么 |
|---|---|
| **收集了什么数据** | 候选源码、总体和逐任务成绩、执行轨迹；参考实现还记录 Token、成本、轮数等 |
| **CC 怎样迭代 Harness** | 查看历史代码与成功/失败轨迹，提出修改假设，写新候选，提交给评测程序 |
| **如何评测** | 加载候选、检查能否运行、执行任务，由任务验证器评分，再比较结果 |

## 搜集的数据部分

在已有Harness中，会有这些数据的搜集

然后会有个外部的verifier检查任务是否完成，给出reward， 0 或 1
https://github.com/harbor-framework/terminal-bench-2
会有专门的测试集，来进行评估

1. 模型显式输出的分析与计划：保存为 message；内容取决于配置
把llm response里面的所有的content都记录下来

2. 执行动作与参数：命令、等待时长、声明任务完成

记录所有工具的执行命令、参数、运行时长

3. 动作后的反馈：终端输出、警告或完成确认提示

observation_results， 简单可以累计为，tool call的返回值内容
比如 ：
查看文件：{"port": 8080}
执行测试：3 passed, 1 failed
执行失败：cat: config.json: No such file or directory

4. 步骤信息：步骤编号、时间、来源、模型名称

其他的一些基本的原信息：timestamp时间戳、source来源是user还是agent、model_name当前模型

5. 每步资源消耗：输入、输出、缓存 token 和成本

输入的所有prompt、输出的token、命中缓存多少、花费多少

输入的所有prompt，可能会好几万字，但是为了还原现场，肯定要记下来的

6. 模型调用耗时

```py
start_time = time.time()
tool_response = await self._call_llm_with_tools(messages)
end_time = time.time()
```

后续可以分析：改了 Harness 后，模型调用是否变慢，以及调用次数是否增加。

7. 任务执行轮数
用于记录一个任务，到底执行了多少轮次的llm call

用处：比较两个 Harness 完成同一任务时，是否需要更少的轮次：
- 旧版通过任务，用了 30 轮。
- 新版也通过，用了 15 轮。
- 可以进一步检查新版是否减少了重复查文件、反复验证等操作。
如果任务失败且轮数特别多，CC 也可以沿轨迹查是否陷入循环。

8. 异常记录：解析失败的模型输出、纠错反馈及消耗

一些比较少见的错误搜集， 比如：llm输出的tool call name不存在、inputs参数json解析失败、缺少必要参数

9. 上下文摘要与交接：摘要事件、子轨迹引用、交接文本

这部分记录两件事：“发生过摘要”，以及“摘要后带着什么信息继续任务”。
历史对话太长，压缩成一份说明，让主 Agent 带着这份说明继续执行。

记录 context 压缩的声明、压缩结果

```py
self._trajectory_steps.append(
    Step(
```

## CC 如何利用这些数据、并且修改Harness

得到了 上面的trace数据 、 reward结果

1. evolution_summary.jsonl， 一行对应一个版本完成整批任务的记录， 记录任务的通过率、平均成本、平均轮数
2. frontier_val.json, 保留最好的 版本名称和通过率 

但此时只有 baseline_kira 的基线标准，因为一开始只有一个基础的agent，此时frontier_val.json就只有初始版本

然后启动 CC，让它分析基线的表现，并生成一些新候选。

agents/
├─ baseline_kira.py
├─ candidate_v2.py
└─ candidate_v3.py

然后接下来，让新候选跑同一套测试任务，看看有没有比基线更好。
然后得到 基准版本 + cc生成新版本的 evolution_summary
然后得到 frontier_val.json 最好的新版本


然后不断迭代，cc的外部数据参考包括之前能搜集到的所有数据，包括evolution_summary、Step数据

然后还会利用一个Skill
https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/terminal_bench_2/.claude/skills/meta-harness-terminal-bench-2/SKILL.md

有些关键的方法论
1. 先读数据，找到值得改的问题

读 frontier_val.json：当前谁最好。
读 evolution_summary.jsonl：试过哪些修改、成绩和消耗怎样。
深读成功和失败的轨迹。
读对应候选源码。

2. 必须提出具体、可检验的假设

不能只说“优化一下”，要说明改什么、为什么改、预计观察到什么变化。

比如一个例子：
```
发现：轨迹中多次出现重复检查。
假设：完成确认流程导致重复检查。
修改：调整完成确认逻辑。
预测：平均轮数下降，通过率保持或提高。
```

3. 一个候选，只验证一个假设

把一些假设，原子化
一次别同时改提示词、摘要和工具执行。否则成绩变化后，很难判断是哪项修改起了作用。

4. 改通用机制，避免记住具体题目  **这边感觉和RRSI有交集了**

禁止硬编码某个任务的知识。
禁止在代码、提示词、注释中提及任务名称。

其实就是口头说明，不要和测试集的任务太关联

```
不合适：遇到某道题，直接写入预先知道的答案。
合适：修改前备份文件；改进长输出处理。
```

告诉AI：从具体失败中提炼通用改进，而不是给测试题写专用答案。

5. 生成独立候选，保留旧版本

保留可比较的旧版本，让修改范围集中在新候选上。

- 复制一个已有实现到 agents/<新名字>.py。
- 按分析阶段的具体方案修改。
- 检查新文件能否导入。
- 返回文件路径和检查结果。

6. 提交修改说明，评分交给外层程序

记录一些修改说明,保留修改原因、证据
```json
{
  "iteration": 1,
  "candidates": [{
    "name": "candidate_a",
    "import_path": "agents.candidate_a:AgentHarness",
    "hypothesis": "这次要检验的假设",
    "changes": "实际修改",
    "expected_efficiency": "预计对 token 和轮数的影响"
  }]
}
```
