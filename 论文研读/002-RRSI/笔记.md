# 谷歌RRSI论文学习笔记

RRSI: Regularized Recursive Self-Improvement of Agent Harnesses

https://arxiv.org/abs/2609.24972

它确实专门研究 Harness 层面的递归自我改进。 底层模型参数保持固定，改进对象包括提示词、控制流程、工具、Memory、上下文管理和子 Agent。论文将这种循环称为 Agent 系统层面的 RSI。

它的流程可以直观理解为：
当前 Harness 做任务 → 分析执行记录 → 提出 Harness 修改 → 评测并筛选 → 新 Harness 进入下一轮。

这篇的重点是：怎么避免越改越会“背测试题”，换一批任务就失效。 因此加入了正则化（Regularization，也就是约束改进过程，减少过拟合）：
- 每轮控制改动数量，方便判断哪个修改有效。
- 保留历史证据，避免反复尝试已经失败的修改思路。
- 筛查针对测试题写死的规则，并结合评分波动、成本和组件贡献决定是否保留修改。方法章节

## 正则化的作用

模型训练里的正则化（Regularization），通常就是为了减少过拟合，提高对新数据的泛化能力

正则化的核心：给模型的学习加一些约束，让它不要为了迎合训练数据，学出过于复杂、敏感的规律。

先考虑过拟合的情况
如果，对于训练样本预测非常准确，整个预测曲线是弯弯绕绕的，连偶然误差也一并记住了
结果就是：训练数据的预测特别准，但是遇到新数据反而不准
这就是过拟合，训练太认真了，把所有细节都学习进去了

防止过拟合，就是希望模型的训练，学习的不是特殊规律，而是一般规律

将训练数据 = 一般规律 + 偶然因素

正则化，是给“追求准确”加了一个条件

一般的训练目标：尽量减少 预测误差
假如正则的目标：尽量减少 预测误差 + λ × 惩罚项

可以把它理解成：
“既要预测准确，也别为了追上每个样本，把模型调整得太极端。”

其中：
- **惩罚项：**规定哪些变化要付出代价，例如参数变得很大。
- **λ：**控制约束力度，读作 lambda。越大，约束越强。

以 L2 正则化为例，它惩罚参数的平方和，倾向于让参数小一些。你暂时不用记公式，只需要理解：模型不能毫无代价地放大参数，去迎合训练样本里的细小变化。

## 正则为啥能防止过拟合

因为“追着偶然误差跑”往往需要更极端的参数，或者更复杂的拟合方式。加上约束后，这种做法的收益可能抵不过代价，模型就更倾向于保留较稳定的规律。
学习方式	对训练数据	对新数据
拼命贴合每个细节	可能非常准确	容易受偶然因素误导
加入合适约束	可能稍微不准	可能更稳定、更准确


关键是：我们愿意牺牲一点训练成绩，换取对新数据更可靠的表现。
但这不是保证。约束太强，模型连真正的规律也学不到，就是欠拟合。所以正则化的力度，需要用没有参与训练的验证数据来选择。
回到 RRSI，你可以做一个对应：模型训练约束参数；RRSI 约束 Harness 的改进过程。 都是为了减少对已有样本的过度迎合。

假设要拟合一个方程：y=wx+b

目的是得到这个 预测的 w b 参数
在考虑拟合测试集，去调整 w b 的时候

假设增大w ，原预测误差，也就是基础的均方误差（MSE）会变小

如果要去拟合 w

增大 w，虽然MSE变小了，但是惩罚项会增大
减小 w，虽然MSE变大了，但也伴随着惩罚项的减小

## RRSI 中提出的 正则化

谷歌的 这个 RRSI ，其实就是把 机器学习，模型训练的里面的 
正则化，引入了 harness RSI 这种 偏向于工程领域
目标是，工程的这边的进化，也需要遵循这种 正则化的方式

对，这就是 RRSI 的核心思路，你这个理解很到位。
它把机器学习中正则化的思想，迁移到 Harness 自动演进这个工程过程：
模型训练	Harness 演进
不只追求训练误差更小	不只追求当前评测分数更高
约束参数，减少过拟合	约束修改和筛选，减少对评测任务的过度迎合
希望新数据上也有效	希望换一批任务仍然有效


RRSI 关心的是：这次修改虽然涨分了，但是否夹带题目专用规则、增加过多成本，或者只是碰巧涨分？

Harness 的自动进化也需要约束；RRSI 借鉴正则化思想，设计了一套约束方式。

“需要约束”是核心；具体是否采用 RRSI 这套方式，可以根据工程目标选择。

# 论文研读

论文的出发点是：同一个固定模型，配上不同的 Harness，完成任务的表现会不同。Harness 决定它如何读取文件、调用工具、处理失败和管理上下文。因此，改进 Agent 可以从修改 Harness 入手

基本流程：
运行当前 Harness → 收集执行反馈 → 让 LLM 提出修改 → 评测候选 → 保留更好的版本。

RRSI 重点研究的是：这个过程为什么可能在原来的任务上涨分，换一批任务却没效果，甚至退步。

论文指出的三个风险：
| 风险 | 工程上的含义 |
|---|---|
| 针对评测题做特殊处理 | 加入只适合某些题目或环境的规则 |
| 追逐评分噪声 | 一次碰巧表现更好，就把修改永久留下 |
| 不断积累复杂度 | 增加步骤、组件和计算成本，却没有获得可迁移的能力 |

## 把“自动改进 Agent”拆成几个能运行、记录和比较的工程对象

### Agent：模型和 Harness 的组合

Agent = Model + Harness H

RRSI 固定模型，改变 Harness，所以实验比较的是：
同一个模型 + H0
同一个模型 + H1
同一个模型 + H2

### 执行轨迹：一次任务从开始到结束的运行记录

作者把任务记作 x，执行轨迹记作 τ，Agent 在任务对应的环境里运行，产生轨迹和最终交付物。
下面是教学例子：
任务：修复某个接口的分页错误

轨迹：
1. 读取接口代码
2. 读取相关测试
3. 修改分页计算
4. 执行测试
5. 根据失败信息再次修改
6. 测试通过，结束

交付物：代码补丁
区别在于：
- 交付物回答“最终做出了什么”。
- 轨迹帮助解释“怎么得到结果、哪里失败、花了多少成本”。
一次轨迹只代表一次运行。同样的任务和 Harness，多次运行仍可能走不同路径，所以论文不会把一次结果直接等同于稳定能力。

## AHE：让自进化过程变得可观察、可解释

AHE 全称 Agentic Harness Engineering。它认为自动演进需要解决三个工程问题：
| 问题 | 它的做法 |
|---|---|
| Agent 不清楚能改什么 | 把可修改组件显式表示为文件 |
| 原始轨迹太多，读不完 | 整理成分层证据，允许继续查看细节 |
| 修改原因和结果对不上 | 每次修改先声明预测，再用后续任务结果检查 |


你可以理解为：
给“改自己代码的 Agent”准备一套清楚的项目结构、可查询的日志和实验记录。

这些是原论文提出的三类可观测性：组件、经验和决策可观测性。原论文、官方代码
**你能从它学到：**怎样把海量 Agent 日志转成能指导修改的证据。这与你日常的 Trace、故障分析、回归验证最接近。

## TTHE：运行新任务的过程中，也持续修改 Harness

TTHE 全称 Test-Time Harness Evolution，测试时 Harness 演进。
它与预先调好 Harness 再固定运行的方式不同：系统在执行任务序列时，维护多个候选，利用执行轨迹提出修改，再由 Judge 根据执行产生的代理信号选择版本。选中的 Harness 持续影响后续任务，模型参数保持固定。原论文
这里的 代理信号，是没有标准答案时，用来间接判断运行是否更可靠的依据。
**你能从它学到：**怎样让改进持续发生，而不只是部署前优化一次。
它的原论文也直接指出一个挑战：执行轨迹中的间接信号，是否真的能可靠判断改进？ 例如程序成功退出，并不自动代表业务结果正确。

## HarnessX：先把 Harness 做成可组合的模块

HarnessX 关注 Harness 的结构：把运行过程中的机制做成有明确接口、可以组合、审查和演进的部件，再利用执行反馈调整它们。
https://darwin-agent.github.io/HarnessX/

工程上可以类比为：为上下文处理、工具调用和执行控制建立明确的扩展接口，方便修改局部机制。
**你能从它学到：**怎样设计一个“容易被改进”的 Harness，减少修改整套运行逻辑的困难。

# 论文中如何解决Harness过拟合问题

所谓的 自进化，其实说白了，和学习、拟合、训练，很多时候都是差不多的意思 

那其实就和算法的某些思想进行的挂钩

就比如说拟合，那自然就会有过拟合的处理

首先，明确下这个论文的观点 

**自动改进 Harness，不能只看当前评测是否涨分，还要看改进能否迁移到新任务。**

文章的目的就是在找： 减少Harness进化的过拟合问题

有这几种解决办法

**少量修改：**逐渐收紧每轮改动数量。
**参考历史：**利用过去修改的结果，减少无依据的重复尝试。
**扩大探索：**停滞时探索尚未尝试的组件。
**审查与筛选：**拦截题目专用规则，结合评分波动和成本决定是否接受。
**删除冗余：**让缺乏收益的组件退出 Harness
