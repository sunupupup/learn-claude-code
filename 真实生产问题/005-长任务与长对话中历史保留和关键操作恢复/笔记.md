# 长任务与长对话中历史保留和关键操作恢复

## 真实问题描述

- 状态：已登记，待专门学习；本次只建立入口并保留 Context Mode 的方法线索。
- 假设场景：Agent 修复支付问题，已经修改文件、运行测试，用户又限定“先只修验签”。多轮工作或对话压缩后，模型可能忘记操作、错误和要求，重复执行或偏离目标。
- 两个目标分别是：历史保存到上下文之外、以后仍可查询；后续决策需要时，将关键历史重新提供给模型。存下来了不等于模型会想起来。
- 最简单的 loop 依赖当前消息，缺少独立记录、历史选择与重新注入机制；所在环节是“执行工具／接收要求 → 记录 → 压缩／续聊 → 组装下一次模型输入”。
- 本章关注模型工作上下文恢复；[004](../004-Agent流式展示与会话恢复的状态一致性/笔记.md) 关注执行、持久化和界面展示的一致性，分别学习。

## 解决办法

以下仅登记已讨论的方法，尚未完成生产方案设计与效果验证。

### 解决办法1：将关键操作和要求持久化为事件

Context Mode 通过宿主 Hook／扩展事件接收工具调用、结果和用户输入，按规则提取文件操作、错误、决策等，写入 SQLite。原生文件工具可提取“动作＋对象”，MCP 工具也有工具名与参数的通用记录，但不等于完整业务语义或无损保存全部历史。

### 解决办法2：压缩前生成恢复快照

以固定版本的 Pi 适配为例，`session_before_compact` 读取会话事件，通过 `buildResumeSnapshot` 生成并保存快照；后续任务开始时，将存在且尚未使用的快照加入待注入内容。

### 解决办法3：在任务开始前自动补充工作状态

Pi 适配在 `before_agent_start` 按优先级、类别、条数和篇幅预算选取事件，再通过 `context` 回调追加消息。该处理在普通任务轮次也会尝试执行，并非仅 session 重启或压缩后触发；筛选不是根据当前问题做语义相关性判断，可能产生重复、过期或无关提示。

### 解决办法4：需要历史细节时按需检索

通过 `ctx_search` 搜索已记录的历史，再结合当前文件与业务状态继续处理，避免一次注入所有记录。恢复指“让模型重新获得信息”，不代表重放工具动作，也不保证模型每次都会主动搜索。

后续专门讨论：记录范围和遗漏风险、事件中的尝试／成功／结果未知如何区分、何时自动注入或按需检索、记录过期与覆盖规则、如何测量恢复效果和额外上下文成本。关键边界：调用过工具不能直接当作操作已成功，恢复记录不能作为盲目重试的依据。
