# 问题描述

Skill 更新时如何避免版本混用？

你使用一个 Agent 平台，平台预置了 review Skill；你开启 Session 后，Agent 在执行代码审查时加载了这个 Skill；执行过程中，平台发布了新版 Skill。

你的代码审查 Agent 正在执行一个持续 20 分钟的 Run：
1. Run 启动时加载了 code-review Skill v1.8。
2. 执行期间，平台发布 v1.9 并刷新共享缓存。
3. Agent 发生 Context Compact，随后 Worker 崩溃并恢复。
4. 恢复后，Skill 正文来自 v1.8，但某个 reference 资源却从缓存读到了 v1.9。
5. 最终 Agent 按两套互相冲突的规范修改了代码。

系统还要求：
- 支持不同租户分批升级；
- 支持灰度发布和快速回滚；
- 恢复后不得悄悄更换 Skill；
- Skill 仅包含说明和只读资源，暂不执行脚本。

请设计一套 D2 方案，至少回答：

1. 一次 Run 应固定哪些信息？版本号、内容哈希分别有什么作用？
2. Skill 正文和 reference 的缓存键应包含什么？
3. Compact、进程重启后，怎样恢复到同一套 Skill 内容？
4. 发现版本缺失、哈希不一致或缓存陈旧时，应重试、降级、失败还是等待人工？
5. Trace 应记录哪些字段，才能还原这次版本混用？
6. 请设计至少 4 条故障注入 Eval，并给出确定性的通过条件。
7. 新版本如何灰度、回滚？已经运行中的 Run 是否切换版本？

# 解决办法

需要解决的问题：如何防止同一个 run 混用两个版本

## 一致性保证

首先思考：
Run A 已经使用 v1.8 开始审查，此时平台发布了 v1.9。你认为 Run A 应继续使用 v1.8，还是立即切换到 v1.9？为什么？

这边肯定用用 1.8 的，为了一致性

## 内容hash

skill的变更需要考虑两种标识
1. 版本号
2. 内容hash 

防止，直接改了skill内容，但是忘记更新版本

```
原来的文件：
version = v1.8
hash = abc123

文件被修改后：
version = v1.8
hash = def456
```

所以在run开始的时候，就需要 记录这俩字段
skill_version = v1.8
skill_hash = abc123

## 数据留存

为了让 Run A 重启后还能取得 abc123，平台发布 v1.9 时，不能直接覆盖或删除旧版 Skill 文件

## 如何读取到匹配的skill呢

每个run，需要保存相关的 skill 元信息快照

Run Checkpoint
└── skill_snapshot
    ├── skill: review
    ├── version: 1.8
    ├── manifest_hash: M123
    └── references
        ├── rules.md: H001
        └── examples.md: H002


Agent 请求 rules.md
  ↓
Tool 从 Checkpoint 找到预期哈希 H001
  ↓
读取固定版本中的 rules.md
  ↓
计算实际哈希
  ↓
一致：返回文件
不一致：返回 SKILL_HASH_MISMATCH

## 

不建议直接在 read_file 的通用工具里面加判断
```js
if path.startswith("skills/"):
    check_skill_hash()
```

可以给skill读取资源文件，一个专门的tool
```js
read_file(path)
    → 读取普通工作区文件

read_skill_resource(skill, resource)
    → 根据 Run Checkpoint 定位固定版本
    → 检查资源 allowlist
    → 校验 hash
    → 返回 reference 内容
```


完整的读取流程：

Agent 请求读取 rules.md
  ↓
read_skill_resource("review", "references/rules.md")
  ↓
Runtime 从 Checkpoint 找到 review@1.8
  ↓
定位固定资源并校验 H001
  ↓
返回内容或者明确错误

## Skill 作者应该怎样组织文件

最基本的skill文件组织形式

```
code-review/
├── SKILL.md
└── references/
    ├── react-rules.md
    ├── sql-rules.md
    └── examples.md
```

带有版本号的skill组织方式

```
skill-artifacts/
└── review-skill/
    ├── 1.8.0/
    │   ├── SKILL.md
    │   └── references/
    └── 1.9.0/
        ├── SKILL.md
        └── references/
```

其实就是静默有个 第二层级的目录是吧

但是对于 agent  其实是感知不到的

只会在 runtime 层面静默处理

## 如何判断哪个skill是最新的

肯定不能用版本号谁大，这就是最新的

需要设计一套 Skill 发布指针策略

针对每个独特的skill，搞个版本指针文件
```yaml
review-skill:
  versions:
    - 1.8.0
    - 1.9.0

  channels:
    stable: 1.8.0
    canary: 1.9.0
```

# Skill指针系统设计

上面提到了 skill 指针策略

针对于外部的skill，我们可以这么设计

假如有个 Agent 系统

用户从外部的 比如 一个 github 仓库，安装了skill

这时候，这个Agent系统就可以根据这个 仓库的 uri 标志，初始化这个skill的指针文件

后期，用户每次要求更新这个skill文件，其实同步也会更新指针文件

这个skill不一定有版本号，所以这个 agent 系统可以根据 skill 的hash 来自行迭代 hash 和 version 号

这样来处理外部的skill内容

比如 用户需要安装 https://github.com/acme/agent-skills
初始化 一个 pointer.json，后期迭代这个 json 就行
```json
{
  "skillId": "github:acme/agent-skills#skills/code-review",
  "sourceUri": "https://github.com/acme/agent-skills",
  "sourcePath": "skills/code-review",
  "activeRevision": 1,
  "releases": {
    "1": {
      "sourceCommit": "abc123",
      "contentHash": "H001",
      "artifactPath": "artifacts/code-review/1/"
    }
  }
}
```
