# MCP 工具的发现方式

## 问题要点

- **三件事**：程序知道服务入口、客户端取得工具列表、模型看见工具定义；三者不必同时发生。
- **职责分工**：宿主程序（Host）管理连接与加载策略，MCP 客户端连接服务、获取工具；模型可提出需求，由程序执行。

## 解决办法

- **服务入口目录**：宿主从配置、内置集成或服务注册目录取得连接线索；有目录不等于已连接，模型也不会自动知道目录。
- **启动预加载**：宿主启动时连接已配置服务、获取工具定义，再筛选并提供给模型。
- **按需连接**：先提供服务简介或搜索入口，由模型需求或程序规则触发，再连接目标服务、获取工具定义。
- **延迟提供定义**：可先连接并取得工具列表，模型需要时再提供完整定义；延迟加载不等于延迟连接。
- **必要边界**：连接与加载时机属于宿主策略，不能当作 MCP 统一默认行为；具体 Pi 桥接与其他产品实现待验证。
- **关联问题**：工具如何裁剪、搜索并减少选错，见 [002](../002-工具太多如何告诉模型并减少选错/笔记.md)。

## 我的笔记

## 关于发现MCP工具

其实主要流程是固定的：

找到服务 → 获取工具定义 → 提供给模型

主要就是分时机

### 标准版

1. connect_mcp 通过 tool 来链接
2. agent启动的时候默认链接 + 工具注册， pi是这样的

connect_mcp 按需连接：模型需要知道有哪些 MCP 可连接、何时连接、怎么调用。可以通过系统提示词说明，也可以由工具描述或服务目录提供。
程序自动加载 MCP：Harness 自己完成连接，再把业务工具提供给模型，不需要先提示模型去连接 MCP。

connect_mcp 一般需要提供 list_mcp_servers 或者 某些系统提示词

### 自制版

若不考虑mcp协议，其实有很多种方式 

| 方式 | 怎么做 | 最小场景 |
|---|---|---|
| **1. 启动全量加载** | 启动时连接已配置服务，取得工具定义，直接提供给模型 | 启动就加载订单、物流的全部工具 |
| **2. 启动获取，按需提供** | 启动时取得定义并保存在 Harness，模型需要时才加载选中的定义 | 程序已经有 200 个工具，模型查物流时才看到物流工具 |
| **3. 已知服务，按需连接** | 先保存服务配置与简介，需要时才连接、取得定义并提供 | 模型先知道“有订单服务”，查询订单时再接入 |
| **4. 先搜索服务，再连接加载** | 起初只有服务搜索入口，找到服务后再取得连接信息、连接并获取定义 | 先搜索“哪个服务能查物流”，再接入对应服务 |
| **5. 使用缓存，必要时刷新** | 读取以前保存的服务目录或工具定义，按有效期、版本或变化信号更新 | 本次启动先使用缓存，必要时重新向服务获取定义 |

### connect_mcp VS 静默链接


| 场景 | 合适的处理方式 |
|---|---|
| 少量 MCP、少量工具 | 程序自动连接，直接向模型提供工具 |
| 大量 MCP、大量工具 | 程序自动连接并登记工具，模型通过搜索按需加载定义；也可以先按需连接目标服务，再搜索工具 |
| 对话中途接入新 MCP | `connect_mcp` 这类管理工具很有价值：模型根据新提供的配置，请求 Harness 接入服务 |

但确实，说实话，connect_mcp还是很少见

对固定配置的 coding agent 来说，你这条路线很自然：

修改 MCP 配置 → 重新加载会话 → Harness 自动连接。
