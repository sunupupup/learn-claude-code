# MCP 工具过多时，除了动态加载还能怎么办

## 真实问题描述

- **当前疑问**：已经理解 Harness（模型外围执行程序）可搜索工具并按需提供定义，继续研究服务端、工具接口和调用方式还能怎样减少工具过多的影响。
- **假设场景一**：Coding Agent 同时接入代码平台、浏览器和业务系统，用户只要求修复一个接口；如果全部工具定义都提供给模型，无关描述和参数会占上下文，相似工具也可能增加选择困难。
- **正常预期与后果**：应只使用完成任务所需的能力；工具选择混乱可能导致调用无关服务、走错操作路径或增加纠错轮次。这里是问题推演，尚未测量具体正确率和成本。
- **假设场景二**：即使已经按需加载，某个 MCP Server 仍包含大量细碎、重叠的接口；搜索可能返回多个相似候选，模型仍需辨别用途、参数及组合顺序，延迟提供定义不能独自解决接口设计问题。
- **讨论边界**：[006](../006-MCP工具的发现方式/笔记.md) 讨论服务发现和连接时机，[002](../002-工具太多如何告诉模型并减少选错/笔记.md) 讨论模型侧工具选择；本栏集中研究动态加载之外的治理办法。

## 解决办法

以下先列通用研究方向，具体项目实现、适用条件与效果待逐项核验。

- **服务端工具集裁剪（Toolsets／Allowlist）**：按项目和业务用途关闭不需要的工具，从来源减少候选数量。
- **工具接口收敛**：合并重复能力、提供任务级操作、澄清描述与参数边界，减少模型在细碎接口间选择和组合的负担。
- **代码或命令行入口（Code Mode／CLI）**：通过代码调用或命令执行承接部分能力，减少直接暴露的工具定义；仍需提供可发现的接口说明。
- **按职责分流（专用 Agent／子 Agent）**：让不同执行者只获得对应领域的工具，主 Agent 通过任务委派使用能力。
- **结果控制与本地处理**：过滤、分页或在执行端汇总大结果，处理工具调用后继续挤占上下文的问题。

### MCP Server服务端解决办法

| 办法 | 核心做法 |
|---|---|
| **工具集／白黑名单裁剪** | 按配置只开放指定类别或具体工具 |
| **按身份和权限过滤** | 根据当前用户、角色或授权范围，只提供其可用工具 |
| **合并相似工具** | 将多个相近操作收敛为一个参数化接口 |
| **提供任务级工具** | 一个工具完成一项常见任务，内部组合多个底层操作 |
| **搜索＋描述＋统一调用入口** | 服务端保存完整目录，对外只提供少量发现和执行入口 |
| **代码模式（Code Mode）** | 提供代码执行入口，让模型通过代码调用、组合服务能力 |
| **按领域拆分服务** | 将大而全的 Server 拆成职责集中的服务，使用者按需接入 |
| **优化工具定义** | 精简名称、描述和参数，明确用途边界，降低体积和混淆 |

#### 1. 黑、白工具集

这种方式，偏向于 mcp server提供了能力
但是个人很少用，团队一般会用到

MCP Server 提供裁剪能力，团队通过统一配置决定开放哪些工具。

所以它更偏向团队治理和范围控制

github本身提供了一些命令行的参数设定

```json
// 本地服务，命令行
{
  "mcpServers": {
    "github": {
      "command": "github-mcp-server",
      "args": [
        "stdio",
        "--toolsets=issues,pull_requests",
        "--read-only"
      ]
    }
  }
}

// 如果是远程服务的话
"headers": {
  "X-MCP-Toolsets": "issues,pull_requests",
  "X-MCP-Readonly": "true"
}
```

#### 2. 按身份和权限过滤

验证访问令牌、登录凭证，匹配权限

假设一个数据库mcp能力有：查看表结构、查询数据、修改数据、删除表

对，主要还是团队权限治理，内部 MCP 是很典型的使用场景。 企业 SaaS 的 MCP 也可以按账号、角色或套餐做同样的过滤。

使用场景
- 内部团队按角色分权限、
- ToB 服务按客户授权范围开放能力
- 付费 MCP 按套餐等级开放工具。 （Moltline Studio 的 MCP 服务、 分析用户的股票列表的当日行情）


#### 3. 合并相似工具

针对于很多查询选项，合并成 search 方法 + type 参数

对，这就属于 MCP Server 的工具接口设计最佳实践了。
核心是：面向 Agent 的任务设计工具，而不是把底层 API 原样逐个搬出来。 哪些操作适合合并、参数怎样清晰表达差异，都是服务端设计

查询股票行情
查询指数行情
查询ETF行情

这就看设计者的抽象能力了
需要权衡 职责边界 + 工具数量

#### 4. 提供任务级工具

把一个常见任务所需的多个操作，封装成一次工具调用。

这个就是按照任务列表来抽象
而不是按照底层API的能力抽象


#### 5. 服务端搜索＋描述＋统一调用入口

服务端只保留几个最通用的接口

搜索能力：search_tools(query)  重要的检索模块
查看接口：describe_tool(name)
执行操作：call_tool(name, arguments)

例如模型要查行情：
搜索“股票当日行情” → 获取目标接口的参数说明 → 通过统一入口执行。


搜索能力这里，简单处理的话就是，一个向量检索
接收搜索词 → 在工具目录里做关键词或向量检索 → 返回工具及参数说明。


这里既要“找得准”，也要“返回准确、可调用的接口定义”。向量检索很适合根据自然语言需求找候选工具。

很适合向量检索
向量检索找候选 → 按工具 ID 从注册表读取原始定义。

### Agent客户端Harness解决办法

| 客户端机制 | 怎么做 | 作用 |
|---|---|---|
| **工具白名单／黑名单** | 已经获取工具列表，但只允许其中一部分进入 Agent 的工具池 | 直接排除不需要、重复或危险的工具 |
| **按任务切换工具集** | 写代码、查数据库、处理工单，各使用一组工具 | 避免所有任务都面对同一套大目录 |
| **专用子 Agent** | 数据库工具交给数据库 Agent，主 Agent 只负责委派任务、接收结果 | 减少主 Agent 需要理解和选择的工具 |
| **统一调用入口／代码模式** | 模型通过少量入口查看接口、调用或编排工具 | 避免把每个 MCP 工具都作为独立工具暴露 |

#### 3. 专用子agent：按照职责拆分工具集，减少主Agent工具集

https://code.claude.com/docs/en/sub-agents#scope-mcp-servers-to-a-subagent

竟然真的能把一个MCP当成是sub agent去调用！！！

不过需要注意的是，这个不是默认行为，只是一种方式

这个是 claude code的sub agent定义

里面有个 mcpServers，可以专门把一个mcp 交给 sub agent
此时这个mcp对主agent不可见

```yaml
---
name: browser-tester
description: Tests features in a real browser using Playwright
mcpServers:
  # Inline definition: scoped to this subagent only
  - playwright:
      type: stdio
      command: npx
      args: ["-y", "@playwright/mcp@latest"]
  # Reference by name: reuses an already-configured server
  - github
---

Use the Playwright tools to navigate, screenshot, and interact with pages.
```

### 其他补充：session id 作用

记录是哪一次对话


| 用途 | 例子 |
|---|---|
| **保存操作环境** | 浏览器 MCP 保存当前会话对应的浏览器实例、已打开页面 |
| **保存临时资源** | 文件处理 MCP 保存本次上传文件、临时目录，后续调用继续使用 |
| **管理订阅** | 记录这个客户端订阅了哪些资源变化，变化时向它发送通知 |
| **关联日志** | 把初始化、查询、调用等记录串起来，排查一个会话里发生了什么 |
| **清理资源** | 会话关闭或过期后，释放浏览器、临时文件和其他占用 |


比如我想初始化一个 沙箱，里面配置一个东西
那么，就可以用session id来对应，持久化这，暂时不销毁
