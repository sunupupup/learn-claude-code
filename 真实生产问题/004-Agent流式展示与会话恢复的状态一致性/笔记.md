# Agent 流式展示与会话恢复的状态一致性

## 真实问题描述

从 [工具事件流与恢复 Demo](../../practice/tool-stream-demo/README.md) 引出：前端已经流式显示正文、工具运行过程和结果；断线或重启后，恢复的对话应该尽量与之前的最终显示一致。但后端实际执行状态、前端显示状态和持久化记录，可能暂时对不上。

当前用“状态一致性”概括这条学习主线；它不能涵盖此前提到的全部生产考量，例如大输出的资源控制与结果的安全渲染。这些暂不展开，不把本章扩展成完整框架课程。

- 假设场景：SSE 连接断开，前端没有收到工具结束；后端可能仍在运行，也可能已经完成。连接断开本身不能证明任务结束或取消。
- Demo 已验证：执行中途退出，恢复显示“中断／结果未知”；工具结束已落盘但发送前退出，实时前端不知道结果，恢复却能读到工具成功，整体任务仍未完成。
- 正常期望：完整消息顺序、工具 ID、名称、参数、最终输出和成功／失败状态可正确恢复；没有最终记录时，不伪装成功，不盲目重新执行。
- 所在环节：执行工具 → 生成进度／结果 → 持久化与发送 → 前端展示 → 断线／重启后恢复。
- 最简单的 loop 只考虑调用模型、执行工具和回传结果，没有定义断线后的任务生命周期、恢复依据与重复执行边界，因此不足以处理这些故障。
- 学习进度：已初始化。下一个小问题是“流式连接断开以后，后端任务是否仍在执行”；真实项目的生产实现待核验。

## 解决办法

### 解决办法1：用持久化记录和统一状态更新规则恢复最终界面

由外围执行程序（Harness，负责运行与状态管理的支撑程序）保存恢复需要的数据，前端按稳定 ID 展示消息与工具块。模型提供内容和工具调用，不能代替程序保证落盘与恢复。

教学实现中的数据流：

```text
工具执行 → 生成事件 → 最终记录落盘 → 发送事件 → 前端按 ID 更新状态
                           ↓
重启 → 读取 JSONL → 同一状态归约器 → 恢复快照 → 前端重新展示
```

状态归约器（reducer）是“把事件依次应用到当前状态的函数”，属于应用程序层。实时路径与恢复路径使用同一规则，减少两套逻辑产生不同结果的风险。

- JSONL（JSON Lines，每行一个 JSON 对象）是 demo 的存储格式；SSE（Server-Sent Events，服务端持续向客户端推送事件）是传输方式，两者职责不同。Demo 前后端实际使用管道 JSONL，真实模型响应使用 SSE。
- 完整消息与工具开始／结束记录持久化；模型文字分片和工具进度仅实时发送。恢复应重建相同的最终内容，不要求重新播放全部中间过程。
- 工具开始后缺少结束记录，失联或恢复时显示“中断／结果未知”；不推断业务实际失败，不自动重试。
- 前后对照：只保存正文时，重启可能丢掉工具块和结果；保存完整消息与工具开始／结束后，可以恢复工具身份、参数和最终状态，识别无结束记录的执行。
- Demo 已验证成功、工具失败与执行中断的稳定字段比较；稳定字段不包括临时进度。
- 必要边界：落盘和发送不是一个原子操作。结果落盘但发送前退出时，两端状态可存在预期差异；恢复以持久化记录为依据。对于外部业务副作用，记录不足时仍需业务核对，当前尚未展开。

后续待讨论：连接状态与任务状态的区别、重连后获取最新状态、工具已产生业务效果但未记录结果时如何处理。一次只展开一个问题。

### 解决办法2：刷新后按原任务 ID 重新订阅，并补齐已发生的状态

通用设计讲解，尚未在本 demo 或真实产品中做 HTTP/SSE 运行验证。假设任务需要 30 秒，用户在第 10 秒刷新页面，后端任务仍然运行：新页面应该接回原任务的流，而不是重新执行一次任务。

需要区分两种情况：页面未刷新时，浏览器原生 EventSource 的可重连断线会触发自动重连；刷新后旧页面与 EventSource 实例被销毁，新页面需要应用代码重新创建连接，不能依赖旧实例自动恢复。用 fetch 读取 SSE 时也不能直接套用 EventSource 的自动重连行为。

处理位置：启动任务并得到 taskId → 后端独立执行并保存状态 → 前端订阅 → 页面刷新 → 从 URL 或服务端会话找到原任务 → 重新订阅并恢复界面。

sessionId 标识对话，taskId/runId 标识这次执行；同一对话可能有多次执行，后端需要能找到该对话当前的运行任务。若仍运行，应重新订阅；若已结束，恢复最终状态即可，不持续重连。

必须同时处理两件事：恢复刷新前及断线期间已产生的内容，以及继续接收后续内容。只重新连接后续事件，会丢掉此前正文、工具开始和部分结果。一个办法是后端提供当前状态快照与对应事件序号，再接续该序号之后的事件；另一个办法是保留可回放事件日志并按游标补发。两者是尚待源码核验的设计选项，不等于 SSE 自动提供存储和补发。

前后对照：只连新事件时，前端可能突然收到“工具结束”，但没有对应工具块；恢复此前状态再接续后，工具块、已有正文和后续进度可以对应起来。快照与订阅之间也可能产生新事件，需要游标和补发衔接以避免漏事件或重复拼接，后续再展开。

#### 本次展开：状态快照＋事件序号接续

一个常用设计是后端把当前界面需要的状态和对应事件序号作为一个快照发送，再发送该序号之后的事件。快照是“截至某一时刻已经形成的完整状态”，包含完整历史、正在生成的部分正文与工具当前状态，不一定只来自磁盘 JSONL。

例如快照覆盖到事件 100，页面渲染完快照后，继续处理 101、102……；所有增量按 messageId/toolCallId 更新原有块，最终 message_end 用完整内容替换对应消息，不再新增一份或把全文追加到分片末尾。

本 demo 的 JSONL 只保存完整消息，不保存所有文字分片：如果模型已经输出“正在检查”，但 message_end 尚未产生，仅读 JSONL 会漏掉这段正文。因此页面刷新且后端仍存活时，后端需要维护正在生成的消息状态并纳入快照。工具最新进度同理；这不是说所有中间事件都必须永久保存。若要求后端崩溃后也精确恢复半段正文，则需要额外持久化支持，目前未实现。

最关键的衔接窗口：读取快照时为 100，前端发起 SSE 订阅时已到 103；若只发新事件会漏掉 101～103。一种实现是后端在同一个受控顺序内注册订阅并取得状态与序号，把随后事件先排入该订阅队列，然后沿同一 SSE 响应先发快照，再发排队事件。状态与序号必须来自同一一致位置；更复杂的多进程实现需要另行核验，当前只讲设计机制。

“先渲染 JSONL，再接收流”是直观目标；网络接收可以提前建立并暂存，界面应用顺序仍是快照在前、对应序号之后的增量在后。不能简单地等页面渲染完再只订阅新事件。

必要边界：独立任务是否在断线后继续由后端决定；重新订阅不能重新触发工具执行。当前终端 demo 没有网页刷新、SSE 重连或中间事件回放，不能把已有重启测试当成此场景已经验证。

## 我的笔记

### 页面刷新后还能继续接收吗？

前端 SSE 连接断开了，后端的任务是不是还会继续执行？
前端不小心刷新页面了，刷新完之后 SSE 还能重连吗？还应该重连吗？

| 情况 | 怎么恢复连接 |
|---|---|
| 页面还在，只是网络暂时断了 | 浏览器原生 `EventSource` 对可重连的断线会自动重连 |
| 页面刷新了 | 新页面需要重新创建连接，订阅原任务；旧连接不会跨刷新自动恢复 |

```text
刷新页面
   ↓
找到这个对话原来正在运行的任务
   ↓
恢复已经产生的正文、工具块和结果
   ↓
接收这个任务后续的流式事件
```

**关键不只是“重新连上”，还要补齐之前的内容。** 否则新页面可能直接收到“工具执行成功”，却连对应的工具块都没有。

### 我的方案

我记得，前后端交互的时候，后端会不断地 `emit` 事件，让前端动态刷新。
当 SSE 断开的时候，这些 `emit` 事件是不是会积存，因为没发送成功？

我的方案实现：

```text
后端主动保存 emit 事件
   ↓
页面刷新，恢复 JSONL 中的已有内容
   ↓
找到原来还在运行的任务，重新连接 SSE
   ↓
补发尚未包含在恢复内容里的事件
   ↓
继续发送新产生的事件
```

成立需要三个条件：

1. **后端任务继续运行**，不会因为 SSE 断开就退出。
2. **事件主动缓存**，不能指望发送失败后自动积存。
3. **恢复内容有对应事件序号**：恢复到 100，就补发 101 之后的事件；补发期间新产生的事件也要接着排进去。

前端向后端查询当前 session 有没有正在运行的 loop；有的话，重新订阅它，恢复 JSONL 内容，再补上缓存事件，继续实时展示。

合并策略最关键的是：**同一消息／工具按 ID 更新，已经恢复的事件不再重复消费。** 比如 JSONL 恢复到事件 100，缓存就从 101 接上。

### 难点：合并与去重

难点其实集中在合并策略，因为 SSE 推送的内容和 JSONL 的数据差别很大。

**SSE 是“发生了什么变化”，JSONL 通常是“最终保存了什么”。**

很有可能，JSONL 里面的一个 `content`，已经是一些 SSE 分片拼装而成的。

此时一个重要的处理就是：**需要跳过某些已包含的 SSE 数据。**

我理解，大部分时候就是考虑这个跳过重复 SSE 消息的场景。

1. 超时结束：用户一直不批准，就结束本次等待。之后回来，通过新的请求重新处理。
