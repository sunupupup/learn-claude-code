# 问题

常见问题就是
1. 回答了不知道的事实
2. 假装调用工具

真正困难的部分其实是：
系统怎么判断“这个问题必须依赖外部事实”？

# 解决办法1：给出外部证据

研究表明，检索增强能够显著减少知识型对话中的幻觉。Retrieval Augmentation Reduces Hallucination in Conversation
https://aclanthology.org/2021.findings-emnlp.320/


外部证据不能只在“第一次回答”时临时出现，它要成为本次 Agent 运行中的一等状态，贯穿生成、验证、纠错和最终回答

这种确实依赖于外部的数据源，但是种类很多，

RAG、联网搜索、数据库、工具API结果、用户文件、人工确认的信息

**Harness需要把关键外部证据当成一等运行状态，不能像普通聊天消息一样随意裁剪或丢弃。**

# 解决办法2: 意图识别

看业务场景

如果某个场景，强行要求调用一个tool

API 层强制调用工具
OpenAI API 当前确实支持：
```json
{ "tool_choice": "required" }
```

或者在 loop 结束的时候，检查一遍有没有相关的 tool 调用


或者 加个 意图识别 
```py
if this_request_requires_project_data:
    response = call_llm(
        tools=[get_project_info],
        tool_choice={
            "type": "function",
            "name": "get_project_info",
        },
    )
else:
    response = call_llm(
        tools=[get_project_info],
        tool_choice="auto",
    )
```

## 拒绝回答

必须要是： 开源模型+能力后训练（强化学习、监督学习）

准备两类训练样本
```
模型已知的问题
用户：法国首都是什么？
助手：巴黎。

模型未知或无法确认的问题
用户：某个不存在项目的最新版本是什么？
助手：我没有足够信息确认。
```

但是这边有个问题， “过度拒绝”

惩罚不能太重，否则模型遇到不会的只会回答 “我不知道”

因此不能只评价“幻觉率降低了多少”，还要同时评价：
- 错误风险：回答中有多少是错误的；
- 回答覆盖率：多少问题真正给出了答案；
- 正确拒答率：确实无法回答时是否拒答；
- 错误拒答率：明明能回答却拒绝了多少。

感觉只能适用于 那些 怼着一个模型狠狠做应用的场景
模型的后训练，其实和基座模型是绑定的

训练时间开销：
Qwen3.8-27B
10,000 条左右数据
QLoRA
1×H100/H200
预计 12～30 小时

7B → 14B：约 1.5～2 倍时间
14B → 32B：约 2～3 倍时间
32B → 70B：约 2 倍左右


## 基于证据

目的“回答的内容，每个事实，都能在输入证据中得到支持”


比如一个工具返回了一个结果

```json
{
  "project": "AgentX",
  "latest_version": "3.2.1",
  "release_date": "2026-10-20"
}
```

符合证据的回答：
AgentX 最新版本是 3.2.1，发布日期是 2026-10-20。

不符合证据的回答：
AgentX 最新版本是 3.2.1，修复了工具调用失败问题，建议所有用户立即升级。


也是能通过后训练的方式来减缓这个问题
这个样本同时训练了两个行为：
1. 使用已有证据回答；
2. 对证据没有覆盖的部分局部拒答。

# 其他产品的解决办法

| 实际系统 | Harness做了什么 | 值得借鉴的点 |
|---|---|---|
| Google Vertex AI Grounding | 把答案片段绑定到具体证据块 | 保存“哪句话用了哪条证据” |
| Anthropic Citations/Web Search | 保存文档位置、引用片段和多轮加密搜索内容 | 证据是协议状态，不能随意丢弃或修改 |
| AWS Bedrock Guardrails | 比较来源、问题和回答，返回grounding/relevance分数 | 不符合阈值的答案可以直接拦截 |

| LangGraph Checkpointer | 每个执行阶段保存完整状态和节点结果 | 出错恢复时不重复执行已成功工具 |
| Stanford STORM | 先联网研究并收集来源，再根据来源写报告 | 把“找证据”和“写答案”拆成两个阶段 |

# Harness设计原则

## 1. 证据不能只存在历史消息里

容易被压缩掉
必须有更可靠的保存

专门一个 Evidence Store：保存原始证据

## 2. 证据应该是一个不可变快照

就算是相同的查询有不同的结果
也不能覆盖之前的

## 3. 保存原始结果，而不是摘要


## 4. 模型内容给用户看之前，必须有门禁

获取外部证据
  ↓
assistant message
  ↓
保存、绑定外部证据
  ↓
给用户看


# Evidence Store

只有研究型Agent、企业RAG、审计要求较高的Agent，才更可能将它单独设计成

Evidence Store
Artifact Store
Source Store
Research State
Grounding Context

Evidence Store本质上就是：把查到的数据存下来，分配一个ID，需要时再取出来。

为了保证证据的可靠性
需要存 时间错、内容、id、内容hash、信息来源等 

“证据别丢、以后能追溯”


要想真正利用这些证据来减少错误回答、llm的幻觉，必须有个
额外的事实校验器、门禁机制、打分系统
