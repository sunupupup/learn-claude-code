# 问题1：子 Agent 说完成了，真的完成了吗？

不一定，需要有三层判断

| 判断 | 能证明什么 |
|---|---|
| 子 Agent 回答“完成了” | 模型认为自己完成了 |
| 插件把状态设为 `done` | 子 Pi 正常结束了这次运行 |
| 检查改动、测试和验收结果 | 才能判断任务是否满足要求 |

`done` 的主动标记，其实这个完成状态是最弱的
因为这个是hook直接触发，只要是 turn_end 直接就能标记
哪怕是模型说 “我没法完成”


| 子 Agent 回答“完成了” | 模型认为自己完成了 |
这个可以通过final text 来进行记录

最后给主agent的一个清单内容是

完成状态意思的final text + +修改历史 + 测试成功清单

其实绝大部分时候，可以认为是 已经完成任务了

如果除了这种，主动声明自己成功，还是不满足验收需求的话。。。

可以让agent留存 测试记录 + e2e测试截图 + 关键步骤截图

关键就是，找到更多完成任务的依据，而不是llm口头说明

# 问题2：子agent运行达到上限，中间断了，此时task状态？主Agent此时会怎么办？

subagent一般有这些状态

| 中断情况 | 插件中的任务状态 |
|---|---|
| 子 Pi 异常退出，退出码非零 | `error` |
| 前台任务收到取消信号后结束 | `cancelled` |
| 子 Pi 输出部分结果，但正常退出 | 可能是 `done` |
| 子 Pi 卡住，没有退出 | 仍然是 `running` |

所以 基本上是 done   和 running 是吧
然后 依赖于final text来判断，事做到哪一步了

一般主Agent能获取到的信息有这些：

- 最近工具活动
- 轮数
- final text
- task status

## 问题3：如何防止子Agent卡死、运行时间太长

最常见的就是“最长运行时间 + 无进展检测 + 超时取消”。

最常运行时间，其实最简单的方法，bash设置超时时间
`timeout --kill-after=3s 15m pi --mode json "检查登录逻辑"`

有个这个 pi 的插件
LukasParke/pi-subagent

| 配置 | 默认值 | 意义 |
|---|---:|---|
| `defaultTimeoutMs` | 15 分钟 | 整个任务的时限，包含排队时间 |
| `stallAfterMs` | 90 秒 | 没有协议活动后，标记疑似停滞并探测 |
| `stallKillAfterMs` | 再等 90 秒 | 继续无响应，则停止任务 |
| `killGraceMs` | 3 秒 | 请求终止后，等待多久再强制终止 |

defaultTimeoutMs 整个子agent声明周期
stallAfterMs 多久没收到能被解析器识别的协议更新；随后先探测，不是立即杀掉。

如果主Agent发现子Agent一直在running
还有个 get_status 机制
这个会让子Agent获取当前内存的状态，保证子Agent不是主进程卡死
（比如harness里面有个while死循环了、某个同步等待网络接口卡住了）
而是某个子进程，比如bash一直在跑

# 问题3：最后汇总各个子agent干的活，是主agent来进行合并么 ？

对，通常由主 Agent 负责最后汇总、检查和整合。 但“合并”有两种

| 子 Agent 做的工作 | 主 Agent 如何整合 |
|---|---|
| 调研、分析、审查 | 阅读各份报告，整理结论、处理矛盾和遗漏 |
| 在独立 worktree 中修改代码 | 检查各分支改动，再执行 Git 合并、处理冲突 |
| 在同一工作目录中修改代码 | 改动已经在一起，主要检查是否相互覆盖、整体是否正常 |


这边其实就比较简单了是吧 
agent自己本身肯定能理解这种行为

开出 worktree 干活 

要么是俩不同的功能，分支就直接push了
要么是一个功能俩模块，那就在这边自己合并然后push

这个其实模型能力足够理解

这种工作方式，模型通常足够理解，不需要专门设计一套复杂的合并机制。
- 两个独立功能：各自在 worktree 中完成，提交到对应分支，再分别推送、提 PR。
- 一个功能的两个模块：主 Agent 收集成果，在一个集成分支里合并，解决冲突、跑整体测试，再推送。


不放心的话就加点简单的提示词

```markdown
委派并行开发任务时，为每个子 Agent 指定负责范围和独立 worktree，
记录其任务、工作目录和分支。

要求子 Agent 完成后汇报：
- 完成了什么，修改了哪些文件
- 提交记录和分支
- 验证结果，以及遗留问题

收到结果后：
- 独立功能保留各自分支，分别交付。
- 同一功能的不同模块，合并到集成分支，检查接口衔接，
  解决冲突并运行整体测试。
- 子任务中断时，先检查已有改动，再决定续做或撤销。

只有用户已授权推送时，才推送对应分支。
```
