# 工具太多，如何告诉模型并减少选错

## 问题要点

- 全量提供工具定义 → 占用上下文，相似工具容易选错。
- **工具定义**：名称、用途、参数 Schema（字段结构）；提供给模型的是接口说明，执行函数留在程序端。
- **三个集合**：全部注册工具、授权可用工具、本轮模型可见工具；注册不等于全部提供给模型，可见范围不代替执行权限。

## 解决办法

- **按职责与权限裁剪**：OpenClaw 使用工具策略过滤链，按 Agent、沙箱等范围筛选工具，减少无关候选（原笔记固定源码已核验）。
- **工具搜索 + 延迟加载**：langgraph-bigtool 使用 `retrieve_tools` 检索工具 ID，再通过 `bind_tools` 提供选中工具的完整定义，缩小本轮工具集合（原笔记固定源码已核验）。
- **搜索／描述／通用调用**：OpenClaw 所引文档介绍 `tool_search`、`tool_describe`、`tool_call`，按需发现、读取接口并分发调用（实验功能，当前版本待验证）。
- **代码模式（Code Mode）**：通过代码执行入口发现、编排工具，并筛选中间结果，减少逐个暴露工具与中间数据回传（实现方式依产品而异）。
- **提示缓存（Prompt Cache）**：复用稳定的工具与提示前缀，降低重复处理成本；不缩小工具集合、不释放上下文，也不直接解决选错。
- **必要边界**：搜索需取得完整参数定义；限制搜索次数与活动工具数量；执行时仍须校验参数和权限。
- **效果判断**：同时看工具定义 token、选错率与任务成功率，不只看 token 降幅；以上机制未在本仓库运行验证。

## 我的笔记

Agent可以接入很多工具，但不一定一开始就把所有工具的完整定义交给模型。

### Codex 的行为

通过工具执行入口可以访问的目录有 574 个工具条目，包含文件操作、Codex 应用功能，以及 GitHub、Notion、Figma 等集成。这不是 Codex 固定自带的数量，也不代表 574 份完整定义都已放进模型上下文。

这些工具通过各种方式进入codex

1. 内置工具，codex自己实现的工具
2. MCP 工具，获取了工具清单，直接接入宿主
3. 插件、扩展，通过SDK或宿主的接口，注册额外的tools

### 按需加载

按需加载的核心是：先给模型一个“找工具”的入口，等它找到需要的工具，再把这些工具的完整定义提供给它。

先从入口搜索工具

search_tools(query)
用途：查找订单、物流、日历、文件等相关工具。

agent发起调用
search_tools("查询订单发货状态") 

然后返回相关的tool


search_tools 内部一般会有个 专门的检索
```js
results = store.search(
    namespace_prefix,  # 限定在哪个目录范围内查
    query=query,
    limit=limit,       # 最多返回几个候选，默认是 2
    filter=filter,     # 可选的条件过滤
)
```
还是一个向量检索

会返回一个个完整的对象

```json
[
  {
    "namespace": ["tools"],
    "key": "tool-17",
    "value": {
      "description": "get_order：查询订单及发货状态"
    },
    "score": 0.86
  },
  {
    "namespace": ["tools"],
    "key": "tool-42",
    "value": {
      "description": "get_shipment：查询包裹物流轨迹"
    },
    "score": 0.79
  }

```

搜索返回 key，例如 "tool-17"
    ↓
外围程序用 key 查工具注册表
tool_registry["tool-17"]
    ↓
取得完整工具对象：名称、描述、参数定义、执行入口
    ↓
把工具定义加入下一轮模型请求
    ↓
模型选择调用，外围程序再执行

### 各家Agent的工具搜索方式

基本上是分为两种

1. BM25
2. 向量语义化搜索


BM25：将工具名称、描述等文本分词，建立倒排索引；查询时找出匹配词的候选，再根据词频、词的稀有程度和文本长度算分、排序。


向量语义检索：提前把工具描述等文本转换成向量，并关联工具 ID；查询时把搜索词也转换成向量，比较相似度，返回候选工具 ID。


#### BM25检索

BM25 是 “Best Matching 25” 的缩写，可以理解为“最佳匹配算法的第 25 个版本”。

本次核验的 Codex 使用现成的 bm25 2.3.2 库，没有看到它自行修改评分公式。你说的“词权重”，本来就是 BM25 的核心机制。

几个核心机制

1. 将所有工具的名称、介绍等文本分词，建立“词 → 工具 ID”的倒排索引。分词器负责切词，BM25 负责后续评分。
2. 一个词出现在越少的工具介绍中，区分能力通常越强，匹配时贡献越大。同时还考虑它在当前介绍里的出现次数，以及介绍的长度。
3. search_tool 的 query 也经过相同的分词处理，通过倒排索引找到候选工具 ID。
4. 用 BM25 给候选工具算分、排序，取前几个，再按 ID 找回完整工具定义。


#### 向量化检索


可以让同一个工具对应多条检索记录，再按工具 ID 去重
| 检索文本 | 关联工具 ID |
|---|---|
| 根据订单编号查询订单状态 | `tool-17` |
| 查询订单是否发货以及物流单号 | `tool-17` |
| 查询订单支付状态 | `tool-17` |

到那时对于用途单一、描述清楚的工具，名称 + 描述 通常足够作为初始检索文本。 先这样做很合理，不必一开始就拆成多条。
关键在描述质量。例如：

> get_order：根据订单编号查询订单状态、发货状态和物流单号；仅查询，不修改订单。

这是 LangGraph InMemoryStore 的实际代码

```python
from langchain.embeddings import init_embeddings
from langgraph.store.memory import InMemoryStore

# 模型
embeddings = init_embeddings("openai:text-embedding-3-small")

store = InMemoryStore(
    index={
        "embed": embeddings,          # 生成入库向量和查询向量
        "dims": 1536,                # 必须与模型实际输出维度一致
        "fields": ["description"],   # 只对这个字段生成向量
    }
)

store.put(
    ("tools",),
    "tool-17",
    {
        "description": "get_order：根据订单编号查询订单及发货状态",
        "service": "orders",         # 保存用于过滤，不参与此次向量化
    },
)


# 查询
results = store.search(
    ("tools",),                    # 在哪个目录里查
    query="查询订单是否已经发货",   # 搜索文本
    filter={"service": "orders"},  # 可选：只查订单服务
    limit=5,                      # 最多返回 5 条
    offset=0,                     # 从第几条开始，通常保持 0
)

# 阈值仅为演示，需要根据实际问题评估。
# 然后再按照相似度score过滤一遍
selected = [
    item for item in results
    if item.score is not None and item.score >= 0.6
]
```

有个比较关键的是这个 0.6 阈值

https://docs.weaviate.io/weaviate/concepts/search/vector-search#notes-and-best-practices

其实并没有强制要求这个阈值的筛选

上面的博客说的也是，优先设置limit，后面再调整阈值
通常，先设定用户可提供结果的最大数量限制，并调整阈值，使得无关结果不太可能返回。

所以对于项目初期， limit+日志记录，够用了
