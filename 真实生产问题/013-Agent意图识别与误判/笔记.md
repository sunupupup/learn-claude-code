# Agent 如何识别用户意图，识别错了怎么办

## 真实问题描述

- **学习状态**：已初始化，待逐条学习；以下是假设场景，不代表已复现的事故或已核验的产品行为。
- **本题范围**：意图识别（Intent Recognition）是判断用户想达成什么目标、提出了什么限制；属于 Agent 的理解与决策环节，可以由大模型结合上下文完成，也可以由 Harness（模型外围执行程序）增加专门的分类或澄清步骤，并非一定有独立分类器。工具路由则进一步决定调用什么能力。
- **假设场景一：讨论被当成执行授权**。用户说“这个文件是不是可以删了”，本意是讨论是否有用，Agent 却直接删除；正常应结合上下文判断是在询问还是要求执行，信息不足时先澄清，误判可能导致数据丢失。
- **假设场景二：一句话有多个需求，却只做了一个**。用户要求“查一下订单，没发货就取消，已经发货就告诉我物流”；Agent 只识别到“取消订单”，跳过状态条件直接操作，造成错误取消；正常应保留查询、条件和后续动作之间的关系。
- **假设场景三：后续消息被误判为新任务**。Agent 正在整理报告，用户补充“只看国内市场”，Agent 却放弃原报告、改成泛泛介绍国内市场；正常应把它理解为原任务的范围调整，保留既有目标与进度。
- **假设场景四：对象不明确却自行猜测**。用户说“把刚才那个改一下”，上下文里有两份文档；Agent 选错对象并修改，导致返工；正常应利用明确的上下文线索，仍有歧义时询问具体对象。

# 解决办法

以下为通用研究方向，具体项目实现与实际效果待验证；一次只展开一条。

- **上下文联合理解**：结合当前消息、正在执行的任务及已确认约束，区分新任务、补充、纠正、取消与询问。
- **结构化意图提取**：提取目标、对象、限制、条件和所需信息，减少只识别一个标签而遗漏执行条件的问题。
- **歧义澄清与拒绝猜测**：目标、对象或关键条件无法确定时提出最小必要问题，研究何时能合理推断、何时必须询问。
- **任务分解与条件路由**：把复合需求拆成有依赖和分支的步骤，再选择工具或子任务，避免把意图分类直接等同于执行流程。
- **意图与授权分离**：识别“用户可能想做什么”后，仍根据已确认授权和操作影响判断能否执行，理解正确也不自动获得权限。
- **误判评测与回放**：用带上下文的表达及预期处理方式构建测试样例，检查误执行、漏需求和不必要澄清，避免只评估分类准确率。

## 我的笔记

意图识别的作用

| 作用 | 识别什么 | 识别后怎么处理 |
|---|---|---|
| **业务分流** | 查订单、开发票、申请售后 | 进入对应业务流程 |
| **Agent 分工** | 编程任务、资料研究、数据分析 | 交给具备相应工具和知识的 Agent |
| **模型成本与能力匹配** | 简单问题、复杂推理、图片理解 | 选择合适的模型，兼顾成本、速度和效果 |
| **选择知识来源或工具** | 问的是产品用法，还是实时订单状态 | 查询说明书知识库，或调用订单接口 |
| **理解对话控制** | 新任务、补充条件、纠正、暂停、取消 | 更新当前任务，或调整执行状态 |
| **识别歧义与缺失信息** | “取消那个订单”具体指哪个 | 先询问对象，再继续处理 |

3. 模型成本与能力匹配

- 翻译，或者单纯对话：用成本低、响应快的模型
- 复杂故障、工具调用：推理能力更强、需要工具调用的模型

# 小结

在我们讨论的通用 Agent Loop 中，意图理解通常包含在主 LLM 的正常推理里，包括选择工具、安排子 Agent、理解补充和纠正，不一定有独立分类步骤。

**需要明确分流时，可以单独增加识别／路由模块。**它可以使用规则、小型分类模型或额外的 LLM 调用，输出业务类别、目标 Agent、模型名称，也可能输出分数或置信度，不一定都有置信度。

模型路由选择用哪个模型，兼顾质量、成本和延迟。RouteLLM 就属于这一类；它预测的胜率也不能直接等同于一般分类置信度。

业务／Agent 路由选择进入哪个流程、交给哪个专业 Agent，主要服务于职责分工。
