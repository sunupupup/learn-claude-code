# 云端 Agent 并发会话导致内存膨胀

## 真实问题描述

本次从 Pi 会话管理学习引出：如果云端服务把多个会话的完整历史加载并长期保留在内存中，单会话历史增长与同时驻留会话增多会叠加，可能超过进程或容器预算，导致 OOM 或任务中断。

这是待研究的通用生产风险与假设场景，不是已核验的厂商事故。不能据此断言各厂商都全量加载 JSONL。

- 当前问题：完整历史是否有必要全部驻留内存？如何同时控制单会话占用和驻留会话数量？
- 所在环节：恢复会话 → 组装上下文 → 运行与等待 → 完成后的状态驻留与释放。
- 范围：后端自身内存，不展开前端渲染或网络请求体积。
- 状态：已初始化，独立聊天中一次探究一个小问题；没有负载测试或实际内存测量。

## 解决办法

尚未展开具体办法。先核对“长期存储的完整历史”和“一次执行需要驻留的数据”的区别，再选择一个真实服务端实现逐步阅读。后续机制与有效性以源码和可重复证据为准，不提前写成已验证结论。

## 我的笔记

你写了一个后端 Agent，用一个数组保存对话：

```text
messages = [
    用户的问题,
    模型的回答,
    用户的新问题,
    模型的新回答,
    # 聊得越久，这个数组越大
]
```

**这个数组在后端进程的内存里。** 一个用户聊天时可能没问题；如果后端同时保留了很多用户的这种数组，**总占用就会变大**。这就是我们要研究的起点。

现在先不想怎么优化，只看用户聊完、离开后的两种状态：

| 状态 | 后果 |
|---|---|
| 历史已经写到数据库，后端仍保留 `messages` 数组 | 数据保存了，数组也继续占内存 |
| 历史已经写到数据库，后端不再保留这个数组 | 数据仍在，数组可以被运行时回收 |

所以，**“历史不能丢”不等于“历史必须一直放在内存里”。**

### 首先明确一个观点：

若**内存无限**，所有对话的 `messages` 全都可以在内存，永远

此时首 `token` 的延迟非常小，全都取决于模型供应商的延迟

但实际，不可能，**必须要有取舍**

**必须要合理利用内存**

### 问题描述

**历史长期保存在数据库里，有新消息时才加载到内存，这次处理结束后释放。**

比如用户 A 发来一句话：

1. **加载**：按会话 ID，从数据库读取历史，组装内存中的 `messages`。
2. **执行**：运行 Agent；新增的模型回复、工具结果继续进入 `messages`。
3. **保存**：把新增记录保存到数据库。
4. **释放**：处理结束，后端不再持有这次执行的消息数组，让运行时可以回收它。

**问题在于**

> 那每次都要把完整历史加载到内存吗？如果单个会话的历史已经很大，还是会占很多内存吧？

假设这么一个场景

```text
数据库：
  完整历史：第 1～10,000 条
  已保存摘要：较早对话的重要信息
  摘要覆盖到：第 9,800 条
```

### 解决办法

假设这么一个场景， **5次 + summary 1-3条 + 继续对话1次**， 的所有 `JSONL` 数据

```json
{"type":"message","seq":1,"role":"user","content":"我想去杭州旅游。"}
{"type":"message","seq":2,"role":"assistant","content":"打算去几天？"}
{"type":"message","seq":3,"role":"user","content":"三天。"}
{"type":"message","seq":4,"role":"assistant","content":"几个人，预算多少？"}
{"type":"message","seq":5,"role":"user","content":"两个人，总预算3000元。"}
{"type":"message","seq":6,"role":"assistant","content":"好的，按两人三天、3000元安排。"}
{"type":"message","seq":7,"role":"user","content":"我想去西湖。"}
{"type":"message","seq":8,"role":"assistant","content":"可以把西湖作为主要游览地点。"}
{"type":"message","seq":9,"role":"user","content":"行程轻松一点。"}
{"type":"message","seq":10,"role":"assistant","content":"那就少安排几个地点，减少赶路。"}

{"type":"summary","id":"S1","covered_seq":6,"content":"用户计划两人去杭州旅游三天，总预算3000元。"}

{"type":"message","seq":11,"role":"user","content":"住哪里合适？"}
{"type":"message","seq":12,"role":"assistant","content":"可以考虑西湖附近、交通方便且符合预算的住宿。"}
```

恢复成 `messages`， **summary 的数据被提前到了最前面**

```json
[
  { "role": "user", "content": "此前对话摘要：用户计划两人去杭州旅游三天，总预算3000元。" },
  { "role": "user", "content": "我想去西湖。" },
  { "role": "assistant", "content": "可以把西湖作为主要游览地点。" },
  { "role": "user", "content": "行程轻松一点。" },
  { "role": "assistant", "content": "那就少安排几个地点，减少赶路。" },
  { "role": "user", "content": "住哪里合适？" },
  { "role": "assistant", "content": "可以考虑西湖附近、交通方便且符合预算的住宿。"  }
]
```

**Pi 的压缩策略，天生是压缩前面的**

它的压缩策略是，**从后往前**，算 `reverse_token`

保留后面一段的 `message`

然后**前面所有的内容，全量压缩！**

所以这么看来，**Pi 的压缩机制，天生能够支持很好的内存优化！**

Pi 这种“**前缀累计摘要 + 明确保留边界**”的机制，很适合作为内存优化的基础。

因为下一次执行需要的数据，可以明确缩小为：

```text
最新 summary + 保留边界之后的消息
```

把这个机制用到我们的数据库方案里，后端就能**直接查询这部分数据**，让已经总结过的旧原文继续留在数据库里。历史越来越长，**也不必让内存占用跟着完整历史一起增长。**

数据库到后端来的数据，这边的**数据量可以大大减小**是吧

不过 整体的 `messages` 对象，还是有着最大 **1M token** ， 简单估算如果纯文本 还是占用 **4MB 的内存**
是吧
