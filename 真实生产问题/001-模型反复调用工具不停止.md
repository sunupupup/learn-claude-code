# 模型反复调用工具不停止

## 真实问题描述

会出现。更准确地说，是 LLM（大语言模型）反复生成工具调用请求，外围执行程序 Harness（负责调用模型、执行工具和推进循环）不断接受请求，导致 Agent Loop（智能体循环）不能主动收敛。模型不直接执行工具；是否继续执行由程序控制。

以下是用于讲解的假设场景，不是已复现的事故：用户要求读取 `config.json`，工具返回“文件不存在”；模型没有检查目录或说明缺少文件，而是再次请求读取同一路径；程序执行后仍返回同一个错误，如此反复。

其他常见触发方式包括：权限拒绝后仍重复原操作；工具反馈含糊，模型不知道已成功；检索无结果后持续搜索却没有新增信息；轮询任务状态一直得到“处理中”；在两个工具之间来回尝试。同一工具执行多次本身不是故障，例如分页查询、读取不同文件都可能正常。

🟢 教学源码已核验：[s01 的 agent_loop](../agents/s01_agent_loop.py#L81) 使用 `while True`，在 `stop_reason != "tool_use"` 时返回，没有总轮数限制或重复检测。只要模型持续请求工具且调用没有抛出中断循环的异常，程序就会继续。实际可能先遇到上下文超限、服务错误或人为中断，因此“无限”准确地指**程序没有主动设定循环上界**。

后果包括等待时间、调用费用和上下文不断增长；若工具会创建订单、发送消息等，还可能重复产生外部效果。s01 的单次命令 `timeout=120` 不能阻止下一轮再次执行相同命令。

## 解决办法

### 解决办法1：设置循环轮数上限

先掌握一个常用办法：**由 Harness 为一次任务设置总轮数上限，到达上限后主动停止。** 提示词可以要求模型避免重复，但不能代替程序中的上限判断。

处理位置：用户输入 → 初始化本次任务计数 → **检查轮数预算** → 调用模型 → 解析工具请求 → 执行工具 → 回传结果并更新计数 → 回到预算检查；模型正常回答可提前结束，预算耗尽则走明确的中止分支。

例如教学策略设为最多 10 轮（仅作示例，不是行业标准）：开始计数为 0，每完成一轮工具交互加 1；到 10 后不再开启下一轮，保留已有结果并说明“达到执行上限，任务尚未完成”，由用户补充信息或决定后续。不要自动从零重新启动同一任务，否则上限又被绕过。如果需要额外调用模型总结，也必须计入独立、有限的预算。

前后对照（逻辑推演，未做运行实验）：同一路径一直不存在时，原循环会继续接受模型请求；加入上限后，最多完成指定数量的交互轮次，再报告中止。这样能限制损失，不能保证模型已经找到文件或解决根因。

| 容易混淆的限制 | 约束对象 | 主要边界 |
|---|---|---|
| 总轮数上限 | 本次任务的循环次数 | 一轮可能包含多个工具调用，不等于工具执行次数 |
| 单次工具超时 | 某一次执行的等待时间 | 超时返回后，模型仍可能再请求 |
| 重复／无进展检测 | 多轮之间的工具、参数、结果与状态变化 | 同样参数的正常轮询可能被误判，不能只看工具名 |

轮数检查本身不能打断卡住的模型请求或工具执行，需要它们各自的超时与取消机制。对写入工具，还要在工具／服务层处理幂等性（Idempotency：同一业务操作重试不重复产生效果），停止循环不会撤销已经发生的效果。本章先不展开这些独立机制。

### 解决办法2：设置循环总时间上限

🟢 对下文固定版本的 AgentExecutor，`max_iterations` 默认 15，`max_execution_time` 默认 `None`。后者表示执行器不设置总时长上限，不代表模型请求、工具或外部服务没有自己的超时。任一启用的上限达到，就不再进入下一轮；15 指循环迭代次数，不保证最多执行 15 个工具。

这两个参数是 `_should_continue` 中的预算检查，不能据此推断“大多数产品只有这两种机制”。正常完成、工具直接返回、异常等也可能结束执行；`early_stopping_method` 描述达到限制后如何收尾，并不是第三个循环额度。

由 Harness 记录任务开始时间，在循环检查处比较已用时间与上限；超限后停止开启下一轮，保留已有结果并报告中止。同步版本是在轮次之间检查：假设上限为 60 秒，第 50 秒进入耗时 40 秒的工具，可能到第 90 秒才检查并停止。这是逻辑推演，说明总时间检查不能替代单次请求和工具超时。

时间上限难以统一设置，因为模型、网络和工具耗时都会波动。应结合用户可接受的等待时间、任务类型和正常任务的耗时记录设置，并留出余量。它表达“最多愿意等多久”，不能直接证明任务是否空转。没有耗时数据时，具体数值只是初始假设；不能从默认 `None` 推导出生产环境“一般不设置”。

### 解决办法3：限制相同工具和参数的重复调用

用户提出的 `toolname + input` 相同调用计数，是 Harness 层可增加的重复检测策略，本次没有把它核验为上述 AgentExecutor 的内置功能。若使用它，应明确计数范围（本次任务累计，或最近若干轮），并对参数进行规范化，例如忽略 JSON 对象键顺序，但不随意改变字符串含义。

处理位置在工具执行前：根据工具名和规范化参数查询计数，达到上限则阻止本次执行并报告重复；未达到则记录本次尝试并执行。对始终失败的同一路径读取，这可以在总轮数耗尽前停止重复；具体阈值需结合工具用途确定。此处是设计推演，尚未实现或运行验证。

🟢 新增源码证据：下文固定 Commit 的 Gemini CLI 在 `getToolCallKey` 中拼接工具名与 `JSON.stringify(args)`，再生成哈希（Hash，用于比较的摘要值）。这是精确匹配，不是语义理解；该函数没有先排序对象键，不能把前述参数规范化建议说成它已实现的行为。

以下是其余可考虑的方向；重复序列与无进展检测见办法4、5，错误分类与资源预算暂不展开：

- 重复调用检测：相同工具和参数反复出现时提前干预。连续计数可能漏掉 A → B → A → B，窗口内累计可覆盖这种情况，但参数一直变化仍会绕过精确匹配。
- 无进展检测：结合结果或业务状态判断，例如不同搜索词始终没有新增证据。比精确匹配更难定义，不能把“输出文字变了”当成取得进展。
- 错误分类：对明确不可重试的权限拒绝，条件未变化时停止重试或请求用户处理；暂时性错误才允许有限重试。
- 资源预算：按需要限制实际工具执行次数、累计 token 或费用，弥补“一轮多个工具”和“每轮成本不同”的差异。

同样的状态查询参数可能是在正常轮询；同样的文件读取参数也可能因为文件刚被修改而合理。因此不能将相同调用计数一律当成死循环证明。触发后可以中止，或提供一次有预算的纠偏机会；不要无限重复“请换一种办法”。本章的最小理解仍是：总轮数／时间负责兜底，重复检测负责更早发现可疑空转。

### 解决办法4：检测重复的调用序列

Harness 不只比较连续相同调用，也比较历史尾部是否反复出现同一段序列，例如 A → B → A → B。Gemini CLI 的 `checkToolCallLoop` 覆盖长度 1–5 的周期，每个周期重复 5 次触发；长度 1 对应办法3。这里只比较请求，不比较工具结果，因此是可疑模式检测，不是无进展的证明。

处理位置：工具请求事件 → 更新有限历史 → 检查周期 → 返回检测结果给主循环。相比只检测连续 A，该机制能发现交替重复；正常轮询仍可能误报。数字是该版本的实现选择，不是通用标准。

逐步读 `checkToolCallLoop`（基于源码手工推演）：

1. 用 `getToolCallKey` 得到本次请求指纹，追加进历史；因此判断包含本次请求，不代表本次工具已经执行。
2. 最长周期为 5，重复阈值 `R` 也是 5，最多需要最近 `5 × 5 = 25` 条指纹；`slice(-25)` 留下最新部分。这是滑动窗口，不是任务最多只能调用 25 次。
3. 依次尝试周期长度 `k = 1…5`，各需 `k × R` 条记录：5、10、15、20、25 条。记录不足就跳过当前长度。
4. `slice(-k)` 取最后一组作为候选周期；检查最近 `k × R` 条能否完整匹配这组连续重复 5 遍。
5. `n - indexFromEnd` 等价于 `n - requiredLength + i`，从待检查尾部片段的起点向右逐项访问。`i % k` 是取余，让候选周期的下标反复从 0 走到 `k-1`。
6. 一项不同就放弃当前 `k`，继续试下一种长度；全部相同则返回 `true`，所有长度均未命中才返回 `false`。本函数只报告检测结果，不负责停工具或停止任务。

例如历史为 `X Y A B A B A B A B A B`：在 `k=2` 时，`n=12`、`requiredLength=10`、候选周期为 `A B`；实际比较下标 2–11，对应预期 `A B` 重复 5 遍，因此命中。前面的 X、Y 不影响。这里 A、B 表示完整调用指纹，可以是同一工具的不同参数，不一定是两个不同工具。

关键边界：只检查以当前请求结尾的连续周期，不是统计某个调用在历史里累计出现了几次；此函数内的 `for` 是检测算法自身的遍历，不是 Agent 调用模型／工具的工作循环。长度大于 5 且不能归约为更短周期的重复、变化的参数、工具结果有无进展，都不由这段精确匹配直接判断。

### 解决办法5：用额外的模型调用判断是否没有进展

Gemini CLI 的 `turnStarted` 按轮次触发 `checkForLoopWithLLM`，把近期历史与原始任务交给模型评估；提示词要求同时考虑重复行为和没有进展。达到判断条件后，结果交还主循环处理。

例如“反复改回同一段代码，再遇到同样的测试错误”可能需要结合历史判断；仅看工具名不足以区分正常调试。这个例子是讲解推演。额外模型调用也会消耗时间、费用，并可能误判；模型给出的置信度不是经过验证的准确率，不能代替两个 max 的兜底。

### 解决办法6：检测后给予有限纠偏机会，再次触发则停止
消息角色与内容已核验：Gemini CLI 的 `_recoverFromLoop` 把反馈文本传给 `sendMessageStream`，经 `Turn.run` 进入 `GeminiChat.sendMessageStream`，后者调用 `createUserContent(message)`，最终为 `role: user`，内容放在 `parts[].text`。反馈虽然以 `System:` 开头，但那只是文本，不会把消息角色变为 system。其大意是：检测到可能的循环，附检测详情，请回顾是否取得进展，必要时重新考虑做法，避免重复没有新结果的工具调用或回复。

需与前面 LangChain 两个 max 区分：其已讨论的默认 force 路径直接返回停止说明给调用方，不追加给模型的反馈消息，因此不存在这条消息的 role。不要把 LangChain 的预算停止与 Gemini CLI 的纠偏注入当成同一个实现。

源码定位：[反馈构造 client.ts](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/core/client.ts#L1270)、[user 消息封装 geminiChat.ts](https://github.com/google-gemini/gemini-cli/blob/acae7124bdd849e554eaa5e090199a0cf08cd782/packages/core/src/core/geminiChat.ts#L392)。这里只核验源码，没有运行 API 实验。

这是检测后的处置，和办法3–5配合使用。该版本 `client.ts` 首次检测到循环且还有轮数余量时，调用 `_recoverFromLoop` 注入反馈，让模型重新考虑做法；清除检测标志但保留检测次数，继续时递减轮数预算，再次触发则结束。

它给误入重复的任务一次恢复机会，而不是立即放弃；也避免无限重复提醒。恢复不保证成功，不会撤销已执行工具产生的效果。

关联学习：这直接补足 s01“由模型决定何时停”的教学循环；[工程学习路线](../specs/work-pool/W-2026-001-agent-engineering-master-learning-roadmap.md)中的“有限补查循环”也使用预算约束。这里只做问题笔记，不启动该 Work Pool。

```ts
    const argsString = JSON.stringify(toolCall.args);
    const keyString = `${toolCall.name}:${argsString}`;
    return createHash('sha256').update(keyString).digest('hex');

```

checkToolCallLoop
从名字就能看出，检查 tool call 的循环

```ts
  private checkToolCallLoop(toolCall: { name: string; args: object }): boolean {
    const key = this.getToolCallKey(toolCall);
    this.toolCallHistory.push(key);

    const maxRequiredLength = 5 * TOOL_CALL_LOOP_THRESHOLD;
    if (this.toolCallHistory.length > maxRequiredLength) {
      this.toolCallHistory = this.toolCallHistory.slice(-maxRequiredLength);
    }

    const n = this.toolCallHistory.length;
    const R = TOOL_CALL_LOOP_THRESHOLD; // 5

    // Check for repeating patterns of cycle length k from 1 to 5
    for (let k = 1; k <= 5; k++) {
      const requiredLength = k * R;
      if (n >= requiredLength) {
        const cycle = this.toolCallHistory.slice(-k);
        let isPatternMatch = true;

        for (let i = 0; i < requiredLength; i++) {
          const indexFromEnd = requiredLength - i;
          const actualKey = this.toolCallHistory[n - indexFromEnd];
          const expectedKey = cycle[i % k];
          if (actualKey !== expectedKey) {
            isPatternMatch = false;
            break;
          }
        }

        if (isPatternMatch) {
          return true;
        }
      }
    }

    return false;
  }
```

其实这边是检查可疑的相同工具链调用

k = 1、2、3、4、5
k=1的时候，检查最近的 5个工具调用
k=2 检查最近10个

for (let i = 0; i < requiredLength; i++) 
这边其实就是检查末尾和模版是否对应
加入 k=2，那这个 requiredLength 就是 10，然后一个个，和 cycle 来进行映射
预期 如果是 命中了 相同工具链 调用
那么， 假设 m = toolCallHistory.length - 1
toolCallHistory[m] = toolCallHistory[m-2] = toolCallHistory[m-4] = toolCallHistory[m-6] = toolCallHistory[m-8] = cycle[1]
toolCallHistory[m-1] = toolCallHistory[m-3] = toolCallHistory[m-5] = toolCallHistory[m-7] = toolCallHistory[m-9] = cycle[0]

**检测到重复不会中断loop，会额外添加一个user message，提示llm出现了循环，进行纠偏，继续loop**

  ↓

  └─ 大于等于 0.9

                    ├─ 置信度 ≥ 0.9 → 确认检测到循环
                    └─ 分数不足或没拿到有效结果 → 本次不确认循环

_recoverFromLoop
```ts

  /**
   * Handles loop recovery by providing feedback to the model and initiating a new turn.
   */
  private _recoverFromLoop(
    loopResult: { detail?: string },
    signal: AbortSignal,
    prompt_id: string,
    boundedTurns: number,
    displayContent?: PartListUnion,
  ): AsyncGenerator<ServerGeminiStreamEvent, Turn> {
    // Clear the detection flag so the recursive turn can proceed, but the count remains 1.
    this.loopDetector.clearDetection();

    const feedbackText = `System: Potential loop detected. Details: ${loopResult.detail || 'Repetitive patterns identified'}. Please take a step back and confirm you're making forward progress. If not, take a step back, analyze your previous actions and rethink how you're approaching the problem. Avoid repeating the same tool calls or responses without new results.`;

    if (this.config.getDebugMode()) {
      debugLogger.warn(
        'Iterative Loop Recovery: Injecting feedback message to model.',
      );
    }

    const feedback = [{ text: feedbackText }];

    // Recursive call with feedback
    return this.sendMessageStream(
      feedback,
      signal,
      prompt_id,
      boundedTurns - 1,
      displayContent,
    );
  }
```
