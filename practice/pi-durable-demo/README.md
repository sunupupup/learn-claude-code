# 映语：流式对话助手与视频确认恢复

通用对话助手网页 + Node 后端 + 真实 DeepSeek Agent + Mock 视频工具。
普通聊天、问答和写作直接流式回答；只有明确要求制作视频时才调用工具。
用户确认前，工具调用保持等待；刷新页面或重启后端后，继续使用同一份任务状态。

## 直接使用

Windows 下双击本目录的 **[start.cmd](start.cmd)**：首次自动安装依赖，服务就绪后打开浏览器。
保持启动窗口运行；关闭窗口会停止后端，再次启动可以恢复已有对话和任务。
也可按下方命令启动，然后访问 [http://127.0.0.1:8787/](http://127.0.0.1:8787/)。

**不要直接双击 `public/index.html` 当作运行入口**：它只是前端文件，不能自行启动 Agent。
直接打开 HTML 时，页面会自动跳转到默认本地服务；样式使用相对路径。
服务未连接时，点击发送会说明原因；输入框为空或助手正在处理时，按钮提示禁用原因。
输入消息后点击发送或按 Enter；Shift + Enter 换行。回复来自真实模型流式更新。
同一用户请求下，工具执行前后的助手内容放在同一个回复区；中间显示等待确认、生成或完成进度，
标记为“同一次任务”。刷新后也按相同规则重建。底层仍保留独立模型消息和工具结果，不改写历史。
参数确认表单直接嵌在这次助手回复里；批准后原地显示参数摘要与进度，后续正文接在下方。
“视频任务”按钮只定位到对话中的相应块，不再打开独立工作台。

## 入口与数据流

| 文件 | 职责 |
|---|---|
| [demo.ts](demo.ts) | 加载后端配置、启动 Harness、HTTP 接口、SSE 快照与更新 |
| [video.ts](video.ts) | 视频工具、业务文档、两阶段 Task、参数校验与批准 |
| [public/app.js](public/app.js) | 展示聊天和确认卡片，刷新或重连后根据后端状态重绘 |
| [video.test.ts](video.test.ts) | 不访问网络的模拟模型 + SQLite 恢复检查 |

```text
网页发送消息（requestId）
    ↓
DeepSeek 返回 generate_video 工具调用
    ↓
工具原子创建 VideoTask + app.videos 中的待确认参数
    ↓
VideoTask.awaiting_confirmation 等待网页批准；不向模型提前返回工具结果
    ↓ 用户确认 / 修改后确认
保存最终参数和批准决定
    ↓
VideoTask.generating：保存模拟完成截止时间，等待约 4 秒
    ↓
保存 Mock 结果与任务完成状态 → 工具返回结果 → DeepSeek 回复
```

等待阶段每 500ms 读取一次持久化决定，是这个小 Demo 的唤醒实现，不额外请求模型。
拒绝则结束子任务，返回拒绝结果，不进入生成阶段。

## 配置和启动

需要 Node.js **22.19+**，依赖固定为 Pi 1.0.0。
后端自动读取仓库根目录 `.env` 中的 `DEEPSEEK_API_KEY` 和 `DEEPSEEK_MODEL`。
当前已找到这两个变量；密钥不复制、不进入前端、不写入源码。
优先级：已有环境变量 → Demo 自己的 `.env`（如果有）→ 仓库根 `.env`。
默认模型 `deepseek-flash`；端口可通过 `VIDEO_DEMO_PORT` 设置，默认 8787。

```powershell
cd D:\code\third-party-labs\agent\learn-claude-code\practice\pi-durable-demo
npm install --ignore-scripts
npm run check
npm test
npm start
```

打开 [本地页面](http://127.0.0.1:8787)。发送消息会调用真实 DeepSeek 并产生模型费用；
视频侧只做 Mock，不调用视频供应商、不产生真实视频文件或虚构的播放地址。

## 怎么观察恢复

1. 发送“生成一段 5 秒的雨夜城市视频，720p”。
2. 等助手回复内部出现待确认参数。此时不应有生成结果，模型正在等工具返回。
3. 刷新网页：同一个任务和后端已保存的参数应重新出现，仍需确认。
4. 可以修改参数，再点“确认并模拟生成”；或者点“拒绝”。
5. 生成期间刷新：应显示正在生成或最新完成状态，不应重新要求批准。
6. 在等待确认期间停止后端，再 `npm start`：同一数据库中的原任务会恢复。
7. 在生成期间重启：按原来的截止时间继续，不重新创建一个生成任务。

已实际验证普通对话、流式回复、明确视频请求、刷新恢复、后端强杀重启恢复和修改后批准生成。
验收数据使用独立的 `.state/acceptance.sqlite`，默认页面使用 `.state/video.sqlite`。
详细证据和边界见 [实现记录](../../specs/implementation/I-2026-029-pi-durable-demo.md)。

## 具体保存了什么

数据库在 `.state/video.sqlite`，与原来的 CLI 实验 `agent.sqlite` 分开。
服务只监听 `127.0.0.1`；当前是本机单用户、一个共享会话，不含账号系统和多租户隔离。
同一份数据库只启动一个后端。要重新开始，先停止后端，再将整个 `.state` 目录改名留存。

- 对话 entries：用户输入、模型提出的工具调用、最终工具结果和回复。
- `app.videos`：最终待确认/已确认参数、用户决定、生成状态、Mock 结果、子任务 ID。
- TaskRecord：工具任务及视频子任务的 checkpoint、归属和执行状态。
- `pi.live`：模型部分输出、运行中的工具输出等已提交状态。

前端不把自己的内存当作业务真相；SSE 首次连接和重连都收到当前快照，再接收后续更新。
确认表单**尚未提交的编辑不会保存**；刷新恢复的是后端已保存的参数。
重复提交同一 requestId 接回原提交；重复确认同一份参数是幂等操作，不能覆盖已批准参数。

## 阅读关键点与边界

1. `generate_video.execute()`：用工具任务 ID 定位原视频子任务；恢复时复用，避免重复创建。
2. `runtime.commit()`：主动提交阶段变化；不是自动捕获函数执行位置。
3. `decideVideo()`：用户决定是独立 HTTP 操作；用户在聊天里说“继续”不会直接绕过批准。
4. SSE：输出来源是已提交的对话视图和业务文档；页面断开不会取消后端任务。

工具声明 `replay: safe` 的依据是业务去重和无外部副作用的 Mock。
接入真实视频服务后，还要保存供应商任务 ID、查询结果，并处理请求已发出但结果未知的窗口；
不能直接沿用本例就宣称真实扣费操作恰好执行一次。

主要参考 `test/examples/12-tasks.ts`、`19-json.ts`、`27-plan-mode.ts`，
