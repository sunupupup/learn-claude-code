# 阶段 2 设计

## 已确认范围

用户授权在阶段 1 基础上继续阶段 2，并要求用户确认、tool call 效果展示、流式输出和前后端一键启动。固定后端 user ID，不做登录页。

## 交互故事

沿用 [S2 用户故事](../user-stories.md)，补充：

- S2-07：输入问题后，真实 DeepSeek 正文增量显示；收到完整工具参数后，工具卡显示执行中与结果。中途断线提示输出中断，不假装完成。
- S2-08：退款卡展示后端确定的订单、全额金额、原因和申请含义；取消不执行，确认后展示申请编号，不声称到账。
- S2-09：刷新页面可读取同一运行进程内的会话；后端重启后明确提示会话失效。等待确认期间禁用新消息，先完成或取消当前操作。
- S2-10：双击 start.cmd 或运行 python start.py，首次安装前端依赖并构建，启动本地服务并打开网页；退出终端停止服务。

## 最小架构与取舍

采用 Python 标准库 HTTP 服务同时提供 API 与 React 构建产物，比两个常驻开发服务更容易一键启动，也不增加 Python 框架依赖。Vite 负责构建 React + TypeScript；无需独立 mock server。

复用 run_turn，增加可注入的工具集合、执行器和流式事件回调。DeepSeek SSE 分片先拼成完整工具调用，校验结束状态后才执行。浏览器通过 fetch 读取 SSE，不靠定时逐字播放假流式。

业务工具包括订单查询、物流查询、规则查询和创建待确认操作。确认接口执行模拟业务，模型本身没有绕过确认的执行接口。多订单候选由后端锁定，选择接口只接受当前候选。所有操作由服务端读取固定用户、订单和金额，忽略模型的授权声明。

每个新会话有独立模拟订单副本，便于重复实验；这不是共享真实订单系统。进程内互斥防重复请求，已处理确认返回原状态；不宣称已经解决阶段 4 的分布式幂等。规则文档含来源和版本，含糊资格转人工入口。

## 实施顺序

1. 扩展流式模型协议与循环，保留阶段 1 CLI 回归。
2. 模拟业务、选择与确认状态，HTTP 与 SSE 接口。
3. React 聊天、订单卡、确认卡、工具卡、流式错误状态。
4. 一键启动与前端锁文件。
5. 离线故障/授权测试、真实模型故事、浏览器验证，记录限制。

服务仅监听 127.0.0.1，前端不接收密钥；静态文件仅来自 frontend/dist。重启恢复和跨进程幂等留到后续阶段。
