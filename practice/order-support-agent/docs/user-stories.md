# 用户故事：从对话到可验证的行为

这份文档用来回答：用户在什么场景下说了什么，我们期待 Agent 怎样回应、什么时候查数据、什么时候等待用户，以及如何证明做对了。

这是预期行为，不是运行结果。实际证据记录在对应阶段的验收记录中。

## 怎么写一个有用的故事

每个故事包含：起始会话和业务数据、用户原话、预期交互、工具与程序行为、禁止发生的行为、验收证据。对回复检查含义和事实，不要求模型逐字复读示例；仅约束必要的工具依赖，不把所有对话写成固定脚本。

例如，“用户查询订单，Agent 正常回复”太模糊；“查询昨天的耳机，必须查当前用户订单，回复未发货和 399 元，且结果确实来自工具”才有明确的通过条件。

## 阶段 1：订单查询

阶段 1 的 session（会话）就是一次交互式 CLI 进程中的内存历史。重新启动进程是新会话；每次 --query 调用也都是新会话。下面的“昨天”相对程序启动时的上海业务日期计算。

### S1-01 新会话查询自己的订单

- 起始条件：固定用户 demo-user-001 昨天购买了一副白色无线耳机，订单 ORD-1001，399 元，未发货；历史为空。
- 用户：**“查一下我昨天买的耳机，多少钱，发货了吗？”**
- 预期交互：Agent 查询后回答白色无线耳机、399 元、未发货；可展示订单号，不承诺送达时间。
- 必要工具：query_orders，product_name 使用“耳机”等有效关键词，purchased_on 为昨天的 YYYY-MM-DD 日期。
- 程序行为：固定用户身份从程序注入；保存 assistant 工具调用，执行工具，再将对应 tool_call_id 的结果发送给模型。
- 禁止：未查工具就编造订单；直接相信用户描述等于数据库事实；声称已催单或退款。
- 验收证据：工具入参、返回订单、下一次模型请求中的 tool result、最终回答一致。最小正常路径通常两次模型请求，不以次数恰好为二作为普遍规则。

### S1-02 新会话查询不存在的商品

- 起始条件：与 S1-01 相同，模拟数据中没有手机订单。
- 用户：**“查一下我昨天买的手机发货了吗？”**
- 预期交互：查询后明确说明未找到匹配订单，可建议核对商品或日期。
- 必要工具：query_orders，商品关键词为手机，日期为昨天。
- 程序行为：工具返回 status=not_found 和空 orders；模型可以结束，无需为了“找到结果”不断重复相同查询。
- 禁止：把耳机当作手机返回；把未找到解释为接口故障；编造订单或状态。
- 验收证据：空工具结果和不含虚构订单的回答。

### S1-03 信息不足，先询问再查询

- 起始条件：新会话，没有任何候选订单或商品信息。
- 用户第一句：**“帮我查一下订单。”**
- 预期交互：询问商品信息，可同时询问购买日期；此时不凭空生成商品参数。
- 用户第二句：**“昨天买的耳机。”**
- 预期交互：调用 query_orders，取得订单后回答状态。
- 必要工具：澄清后才出现可执行的 query_orders 调用。
- 程序行为：两条用户消息处于同一份 Context；第二轮请求可看到上一轮澄清。
- 禁止：在没有商品信息时猜“耳机”；把程序里的模拟数据直接暴露给模型以跳过工具查询。
- 验收证据：第一轮澄清、第二轮工具参数与结果、整个消息序列。

### S1-04 同一会话追问，正确理解指代

- 起始条件：已经完成 S1-01，本进程历史仍在。
- 用户：**“那这一单的订单号是什么？”**
- 预期交互：回答 ORD-1001，能够从历史工具结果中找到来源。
- 工具要求：已有订单号可直接复用；合理地再次查询也允许，不强制每句都调用工具。
- 禁止：遗忘刚查过的订单而无故要求重说商品；输出另一用户订单号。
- 验收证据：本次模型输入包含前次订单证据，最终订单号正确。

### S1-05 新会话没有旧会话的记忆

- 起始条件：结束上一个 CLI 进程，重新启动；没有持久化或跨会话记忆。
- 用户：**“刚才那一单发货了吗？”**
- 预期交互：说明当前缺少订单信息，询问商品或购买时间。
- 工具要求：不能凭空猜测商品后查询；收到补充信息才能继续。
- 禁止：声称记得上一进程查询过的订单。
- 验收证据：新 Context 只有系统消息与本次用户输入；回答请求补充信息。

### S1-06 当前还不能执行退款

- 起始条件：新会话，或已经查询出耳机订单。
- 用户：**“直接帮我把耳机退了。”**
- 预期交互：明确当前版本仅支持查询，不能办理退款。可以提供查询帮助。
- 工具要求：只暴露 query_orders；不存在可执行的退款工具。
- 禁止：声称“退款申请已提交”。若模型捏造退款调用，分发层必须返回 UNKNOWN_TOOL。
- 验收证据：用户可见能力边界、暴露的工具列表、无退款副作用。

## 阶段 1 的工程异常验收

以下是系统故障/攻击场景，不要求通过自然语言稳定诱导模型产生，使用预设模型响应或直接调用工具测试。

| 编号 | 条件 | 预期与证据 |
|---|---|---|
| E1-01 | 模型调用未知工具或输出非法参数 | 返回结构化错误，不执行业务查询；下一次模型请求能看到错误 |
| E1-02 | 模型参数夹带 user_id | 参数被拒绝；固定用户查询结果不包含其他用户订单 |
| E1-03 | 模型连续请求同一工具 | 最多请求模型 6 次，所有已接受调用都有对应结果，程序提示达到上限 |
| E1-04 | 密钥缺失、API 超时或模型响应截断 | 明确说明无法完成，不编造订单结果，不执行截断的工具调用，不输出密钥 |

## 阶段 2 的交互故事

| 编号 | 新会话输入与前置条件 | 预期交互与工具行为 |
|---|---|---|
| S2-01 | “昨天买的耳机发货了吗？”；匹配两笔订单 | query_orders 返回候选，页面展示列表；用户选中后再围绕该单处理 |
| S2-02 | “周五出差，耳机能赶上就催一下”；截止时间不明确 | 先查订单并澄清最晚收货时间，再查物流；预计赶得上时展示催单确认，确认后创建工单 |
| S2-03 | “赶不上就退款”；预计送达晚于明确截止时间 | 查询规则并结合订单判断，后端准备具体订单和金额；展示确认卡片，确认后提交模拟退款申请 |
| S2-04 | “能不能赶上？”；没有可靠预计送达时间 | 查询后承认无法判断，让用户选择下一步，不自动把未知判成赶不上 |
| S2-05 | 页面已经展示退款确认，用户点击取消 | 取消待执行操作，退款工具不执行；前端展示已取消 |
| S2-06 | 规则缺失、冲突或无法确认资格 | 说明不确定性并提供人工处理入口，不继续自动提交退款 |

### 当前模拟样本

固定用户的昨天订单：白色耳机 ORD-1001，399 元，预计明日 18:00；黑色耳机 ORD-1002，299 元，预计三日后 18:00；充电线 ORD-1003，59 元，无预计；定制键帽 ORD-1004，129 元，缺适用退款规则。全部初始未发货。每个新会话有独立副本。

S2-01 的 query_orders 返回两个候选后，后端暂停执行其他订单工具，选择接口只接受当前候选 ID。S2-02/S2-03 选单后调用 get_logistics，退款前再调用 query_rules，最后 request_action_confirmation 创建卡片；真实模拟申请由确认接口产生，模型没有直接执行退款的工具。

### S2-07：能看到正在发生的过程

- 用户发送问题后：输入区显示处理中，正文随真实模型增量出现，工具卡显示名称与运行状态。
- 工具完成后：显示结果与耗时，可展开查看参数；未完整接收的工具调用不执行。
- 断线或模型错误：显示未完成/错误提示，不能把半段输出当成完整成功。
- 证据：SSE 的多条 delta 事件先于 done，浏览器展示增量与工具卡。

### S2-08：确认、取消与重复点击

- 退款卡显示具体订单、后端计算金额、范围、原因，以及“申请不等于到账”。
- 点击取消：卡片显示已取消，订单不进入退款申请中；可继续聊天。
- 点击确认：卡片显示申请已提交和编号；同进程内再次提交相同操作 ID 返回原结果。
- 订单金额或状态已经变化：旧卡片失效，重新查询与确认。
- 证据：操作记录和订单状态断言；前端不提交金额，后端不采信模型授权声明。

### S2-09：刷新与重启边界

- 同一个后端进程中刷新：读取原会话快照，待确认卡片仍在。
- 后端重启：旧会话 ID 失效，页面提示新建；不宣称已支持持久化恢复。

### S2-10：一键启动

- 双击 start.cmd 或运行 python start.py：检查配置，安装并构建前端，启动本地 HTTP 服务并打开网页。
- 下次源码和锁文件未变：复用构建，避免每次安装。
- 缺密钥、缺 npm 或端口占用：明确报错，不泄露凭证，不结束其他服务。
