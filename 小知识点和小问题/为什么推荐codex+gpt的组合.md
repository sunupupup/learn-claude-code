# codex + gpt 的优势

## apply_patch

codex官方提到 

“我们强烈建议使用我们 apply_patch 的实现，因为模型已经经过训练，能够在这种不同格式中表现出色。对于终端命令，我们推荐使用 shell 工具，对于计划/待办事项，我们的 update_plan 工具应性能最佳。”


apply_patch 是 codex 的修改文件的一个工具

比如模型调用 apply_patch 传入了 下面的内容 

```diff
*** Begin Patch
*** Update File: hello.py
@@
-print("你好")
+print("你好，世界")
*** End Patch
```

他把 修改文件的操作，训了一个可能更好的方法进入模型，并且再harness中实现了

所以可以理解成：模型练习如何写修改单，Harness 实现如何执行修改单。


普通的 edit_file 
```json
{
  "path": "hello.py",
  "old_text": "print('你好')",
  "new_text": "print('你好，世界')"
}
```

## 提示词优化

提示词优化，就是观察“这个模型在这个 Harness 里容易怎么做偏”，再调整传给它的指令，让它更稳定地完成任务。

模型在进化，提示词也在进化

| 问题 | 这个案例中的答案 |
|---|---|
| **针对什么？** | GPT-5 在该环境里过度调查的行为倾向 |
| **怎么优化？** | 修改 Harness 注入的指令，弱化重复强调的“彻底调查” |
| **优化什么？** | 减少无效搜索、耗时和 token，同时保持任务完成质量 |

优化提示词不一定是“加更多要求”，也可能是删掉原来有用、现在反而拖后腿的要求。


## phase 字段

消息阶段 phase	GPT-5.3-Codex 输出 commentary／final_answer，区分中途说明与最终答复	保留并正确处理这个字段；官方明确警告，丢失它可能导致提前停止和性能下降

对，就是标识这条 assistant 消息在一个 turn（轮次）里的角色：
- commentary：中途说明，例如“找到原因了，接下来修改”。
- final_answer：本轮最终答复，例如“修改完成，验证结果如下”。


一个中途的回答和一个结束语
```json
{
  "type": "message",
  "role": "assistant",
  "phase": "commentary",
  "content": [
    {
      "type": "output_text",
      "text": "我先检查登录逻辑和错误日志。"
    }
  ]
}

{
  "type": "message",
  "role": "assistant",
  "phase": "final_answer",
  "content": [
    {
      "type": "output_text",
      "text": "已修复登录失败问题，相关测试通过。"
    }
  ]
}
```

# 其他认知

其实，这就涉及到了一些面试题

“你觉得使用codex、cursor或其他agent使用起来有啥区别么”

## GPT 和 Codex 的特色

Codex 较慢，却更经常主动重新检查假设、整理代码，作者觉得可以少盯一些。

这是因为 模型倾向多调查、多验证 → 执行时间可能增加 → 遗漏可能减少 → 用户感觉更放心。

## Opus 和 CC 的特色

Claude Code 推进较快、互动更多，但需要更频繁地检查与纠正。

修 bug、快速修改，希望尽快看到结果并继续调整

这是网上的评价

| 模型 | 用户喜欢的地方 | 主要分歧或抱怨 |
|---|---|---|
| **Opus** | 需求不清楚时更能理解意图；复杂 bug、边界条件和审查更让人放心 | 简单任务可能用不着；高推理力度、多个子 Agent 容易增加消耗 |
| **Sonnet** | 日常实现够用；任务说明清楚时，结果可能接近 Opus | 碰到隐含要求、复杂判断和细微错误时，差距更明显 |
| **Haiku** | 搜索代码、明确的小修改、批量任务成本低 | 自主判断、验证和事实核查的评价差异很大 |
