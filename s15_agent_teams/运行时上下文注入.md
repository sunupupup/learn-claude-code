# Agent 状态访问：Tool Pull 与 Runtime Context Injection

## 这个知识点通常怎么称呼

这个问题没有一个唯一、严格统一的行业术语，可以按层次理解：

- **Context Engineering / Context Management**：更大的上位概念，讨论如何组织、筛选和提供 Agent 所需的上下文；
- **Runtime Context Injection / Dynamic Context Injection**：Runtime 在每次模型调用前，把当前状态动态注入上下文；
- **Tool-mediated State Access / Tool-based Retrieval**：Agent 通过 `list`、`get`、`search` 等 Tool 按需读取状态；
- **Pull vs Push Context**：对“主动查询”和“运行时预先注入”这两种方式的直观分类，更适合用来解释差异，不算严格的标准术语。

本笔记采用 **Runtime Context Injection** 作为文件名和核心术语，同时把 Tool 查询作为它的互补方式记录下来。

## 核心模型

Agent 并不会直接读取数据库、内存或文件。通常由 Runtime/Harness 负责读取外部状态，再把结果暴露给 Agent Loop：

```text
外部状态 / Memory / Team Registry / Database
                    ↓
                 Runtime
                ↙       ↘
       Pull：Tool 查询   Push：动态上下文注入
       list/get/search    Runtime Context
                ↘       ↙
                 Agent Loop
```

因此，问题的核心不是“状态是否在外部”，而是：

> Runtime 选择让 Agent 主动 Pull 状态，还是提前 Push 一份状态快照给 Agent。

## 两种状态访问方式

| 方式 | 触发者 | 优点 | 代价与风险 | 适合的状态 |
| --- | --- | --- | --- | --- |
| Tool Pull | Agent 决定何时调用 `list/get/search` | 按需读取，数据可以更接近实时，避免每轮都塞入大量内容 | 多一次 Tool 调用；Agent 必须知道何时查询；结果仍可能在下一刻过期 | 大量、变化快、条件式或需要精确详情的数据 |
| Runtime Context Injection | Runtime 在模型调用前注入 | Agent 不必先调用查询 Tool；适合每轮都需要的少量状态 | 消耗上下文 Token；可能是快照；注入过多会造成上下文膨胀 | 当前用户、当前任务、队友摘要、权限摘要、短期运行状态 |
| 混合模式 | Runtime 注入摘要，Agent 按需调用 Tool | 兼顾可发现性和详细查询成本 | 需要定义摘要与详情的边界，并处理快照过期 | 生产系统中最常见的方式 |

## `list/get` 和动态注入的区别

以 Durable Teammate 为例：

```text
Team Registry（权威状态）
          ↓
      Context Builder
       ↙            ↘
注入队友摘要       list/get_teammate
                    ↓
              查询详细状态
```

- Registry 是权威来源，保存 Agent ID、角色、状态、能力、权限和心跳等信息；
- 动态上下文可以注入“当前有哪些队友、各自负责什么、是否在线”的摘要；
- Agent 需要详细任务、最近错误或完整能力列表时，再调用 `list` / `get`；
- `send_message` 仍然是执行动作的 Tool，不会因为上下文里出现了队友信息就自动获得发送权限；
- Runtime 在真正发送消息前仍应重新校验目标是否存在、是否在线以及当前 Agent 是否有权限发送。

所以，Durable Teammate 需要的是 Runtime 层的 Team Registry，不一定需要一个模型可见的 `list_teammates` Tool。列表可以被 Runtime 自动注入，也可以由 Agent 主动查询。

## 几个重要边界

### 动态注入不等于修改了事实来源

动态 System Prompt 或 Runtime Context 只是 Registry 的一个视图或快照，不是 Registry 本身。不能把注入到 Prompt 里的内容当成最终权威状态。

### 动态注入不等于增加了工具能力

Prompt 可以告诉 Agent “有哪些队友”，但不会因此创建 `send_message`、`shutdown_teammate` 等能力。能力仍由 Tool Schema、Runtime 路由和权限层共同决定。

### 注入状态必须考虑过期和不可信内容

状态快照可能在模型读取后立刻变化；外部文本也可能包含不应被当作指令的内容。因此应使用清晰的上下文边界，并在执行写操作前重新读取或校验关键字段。

### 不要把所有外部状态都注入每一轮

大型日志、完整消息历史、数据库记录和高频变化的指标，通常更适合通过 Tool 按需查询。动态注入应优先保留 Agent 当前决策真正需要的摘要。

## 放回当前 s15 教学代码

当前 s15 已经有 Tool Pull 的雏形：

- Lead 通过 `check_inbox` 读取自己的消息；
- Lead 通过 `send_message` 向 Teammate 写入消息；
- `active_teammates` 保存的是进程内的简单名称表。

但当前实现还没有：

- 独立的 Team Registry；
- `list_teammates` / `get_teammate` Tool；
- 每次模型调用前的动态队友摘要注入；
- 跨进程、跨 Session 的持久状态和权限校验。

因此，本章代码帮助理解的是通信和生命周期的基础；生产实现还需要把“状态来源、上下文视图、动作权限”拆成不同层次。

## 一句话总结

> Agent 获取外部状态有两条主要路径：让 Agent 通过 Tool 主动 Pull，或由 Runtime 通过 Context Injection 预先 Push；实际系统通常注入小而常用的摘要，再用 `list/get/search` 按需获取细节。
